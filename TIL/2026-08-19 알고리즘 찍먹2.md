

## 파이썬 기본 자료구조와 알고리즘 (리스트, 링크드 리스트, 큐, 스택, 데크)

> 
> 🏷️ 키워드: list, linked list, queue, stack, deque
> 
>   

### 리스트와 링크드 리스트의 개념 및 비교

- **리스트 (List)**
    
      
    - 파이썬의 `list`는 내부적으로 배열(Array)로 구현되어 있다.
        
          
        
    - 메모리상에 연속적으로 배치되어 있어 인덱스(위치 번호)를 통한 데이터 조회가 매우 빠르다 ($O(1)$).
        
          
        
- **링크드 리스트 (Linked List)**
    
      
    - 각 데이터(노드)가 값과 함께 다음 데이터의 메모리 주소(포인터)를 저장하며 화살표처럼 연결된 구조이다.
        
          
        
    - **시작과 끝 처리:** 시작 위치는 `head` 변수가 첫 노드의 주소를 가리키고, 마지막 노드는 다음 주소로 `None`을 가리킨다.
        
          
        
    - **메모리 단점:** 값 외에 포인터(주소) 공간이 추가로 필요해 **메모리 오버헤드**가 발생하며, 메모리에 흩어져 있어 CPU 캐시 효율이 떨어진다.
        
          
        
    - **장점:** 중간 데이터의 삽입/삭제 시 주소 연결만 변경하면 되므로 전체 데이터를 밀어낼 필요가 없다.
        
          
        
    - **변형:** 마지막 노드가 첫 노드를 가리키면 **원형 링크드 리스트**, 앞뒤 양방향 주소를 가리키면 **이중 링크드 리스트**가 된다.
        
          
        

### 선형 자료구조: 큐, 스택, 데크

- **큐 (Queue)**
    
      
    - **선입선출 (FIFO: First-In, First-Out):** 가장 먼저 들어간 데이터가 가장 먼저 나온다.
        
          
        
    - 데이터 삽입은 맨 뒤(Tail/Rear), 삭제는 맨 앞(Head/Front)에서 일어난다. 입구와 출구가 서로 다르다.
        
          
        
    - **활용:** 웹 서버 접속 대기열, 메시지 큐, 작업 버퍼링 등 순차적 처리가 필요할 때 사용한다.
        
          
        
- **스택 (Stack)**
    
      
    - **후입선출 (LIFO: Last-In, First-Out):** 가장 나중에 들어간 데이터가 가장 먼저 나온다.
        
          
        
    - 삽입과 삭제가 같은 곳(맨 위)에서만 일어난다.
        
          
        
    - **활용:** 뒤로가기, 실행 취소(Undo), 알고리즘의 DFS 탐색 등에 사용된다.
        
          
        
- **데크 (Deque, Double-Ended Queue)**
    
      
    - 양쪽 끝(앞, 뒤) 모두에서 데이터의 삽입과 삭제가 가능한 양방향 자료구조이다.
        
          
        
    - 스택과 큐의 역할을 모두 수행할 수 있다.
        
          
        

### 파이썬에서의 자료구조 선택과 활용

- **`list` vs `collections.deque`**
    
      
    - 파이썬 기본 `list`로 `pop(0)`을 써서 큐를 구현하면, 맨 앞 데이터 제거 후 모든 요소가 앞으로 당겨져 $O(N)$의 시간 복잡도를 가져 속도가 느리다.
        
          
        
    - 파이썬의 `collections.deque`는 내부적으로 이중 링크드 리스트로 구현되어 있어 맨 앞과 맨 뒤 데이터 추가/삭제 시 $O(1)$로 매우 빠르다.
        
          
        
- **상황별 사용 기준:**
    
      
    - **`list` 사용:** 인덱스를 지정하여 특정 위치의 데이터를 자주 조회하거나(`arr[i]`), 맨 뒤에서만 추가/삭제가 일어날 때.
        
          
        
    - **`deque` 사용:** 맨 앞과 맨 뒤 양쪽에서 데이터의 추가/삭제가 빈번하게 일어날 때 (큐, 스택, BFS 알고리즘 구현 등).
        
          
        

### ⚠️ 헷갈리기 쉬운 점

- **링크드 리스트 예외 처리:** 마지막 노드의 다음 주소(`None`)를 제대로 처리하지 않으면 `AttributeError`나 Null Pointer 예외가 발생하기 쉽다.
    
      
    
- **무조건적인 데크(deque) 선호:** `deque`가 맨 앞 데이터 처리에 빠르다고 해서 무조건 쓰면 안 된다. 내부 구조가 링크드 리스트 형태이므로, 중간에 위치한 데이터에 인덱스로 접근할 때는 $O(N)$의 시간이 걸려 일반 `list`보다 훨씬 느리다.

## 파이썬 deque의 특징과 list 변환 및 메서드 활용

> 📍 정리 #2
> 
> 🏷️ 키워드: deque, list, popleft, appendleft, insert
> 
> 🔗 이어짐: 정리 #1 파이썬 기본 자료구조와 알고리즘 (리스트, 링크드 리스트, 큐, 스택, 데크)
> 
>   

### list와 deque 간의 타입 변환

- **`list` $\rightarrow$ `deque` 변환:**
    
      
    - `deque(my_list)` 형태로 변환한다.
        
          
        
    - 기존 리스트 원본을 변경하는 것이 아니라, 데이터를 복사하여 `deque` 타입의 새로운 객체를 생성한다.
        
          
        
    - 리스트 기반의 입력 데이터를 받아서 $O(1)$의 빠른 맨 앞/뒤 연산(`popleft`, `appendleft`)이 필요한 큐/스택 문제로 풀고자 할 때 주로 사용한다.
        
          
        
- **`deque` $\rightarrow$ `list` 변환:**
    
      
    - `list(my_deque)` 형태로 변환한다.
        
          
        
    - `deque` 안의 데이터들을 복사하여 `list` 타입의 새로운 객체를 생성한다.
        
          
        
    - `deque` 기반의 연산을 다 끝낸 후, 결과 데이터를 리스트의 인덱스 접근(`[i]`)이나 슬라이싱(`[1:5]`) 기능으로 활용해야 할 때 변환하여 사용한다.
        
          
        

### deque 전용 메서드와 list 메서드의 차이

- **`popleft()` 및 `appendleft()`:**
    
      
    - **`deque` 전용 메서드**로, 파이썬 기본 `list`에는 존재하지 않는다.
        
          
        
    - `deque`에서 `popleft()`를 호출하면 맨 앞 노드의 주소(포인터)만 변경하므로 $O(1)$(즉시 처리)로 매우 빠르다.
        
          
        
    - 파이썬 `list`로 변환된 상태에서 `popleft()`를 호출하면 `AttributeError`가 발생한다.
        
          
        
    - `list`에서 맨 앞 요소를 빼려면 `list.pop(0)`을 써야 하지만, 이는 모든 요소를 앞으로 한 칸씩 당겨오므로 $O(N)$으로 느리다.
        
          
        
- **`insert(index, element)` 메서드:**
    
      
    - **`list`와 `deque` 둘 다에서 공통으로 사용 가능하다.**
        
          
        
    - 첫 번째 인자로 **위치(인덱스 번호)**, 두 번째 인자로 **넣을 데이터 값**을 전달한다 (예: `insert(0, 100)`).
        
          
        
    - 하지만 `deque`에서 `insert()`를 이용해 중간에 데이터를 삽입하면, 내부 노드의 주소를 처음부터 타고 찾아가야 하므로 **$O(N)$으로 느려진다.**
        
          
        
    - 따라서 맨 앞에 데이터를 추가할 때는 `insert(0, 값)` 대신 `deque.appendleft(값)`를 사용하는 것이 $O(1)$로 성능상 훨씬 유리하다.
        
          
        

### deque의 내부 작동 원리 및 표기

- **표기 형태와 내부 구조:**
    
      
    - `deque`를 `print()`로 출력하면 `deque([1, 2, 3])`과 같이 리스트 형태로 보이지만, 이는 직관적인 확인을 위한 출력 포맷일 뿐이다.
        
          
        
    - 실제 내부 동작 방식과 메모리 구조는 리스트(배열)가 아닌 **이중 링크드 리스트(Double-Linked List)** 형태로 구동된다.
        
          
        

### ⚠️ 헷갈리기 쉬운 점

- **타입 변환 시 메서드 사용 불가 실수:** `deque` 상태에서 쓰던 `popleft()`나 `appendleft()`를 `list`로 변환한 이후에도 계속 쓸 수 있다고 착각하기 쉽다. 변환 후 호출 시 `AttributeError`가 발생하므로, 맨 앞 데이터의 빈번한 처리 작업이 남아있다면 `list`로 바꾸지 말고 `deque` 상태를 유지해야 한다.
    
      
    
- **deque에서의 insert() 남용:** `deque`가 모든 연산에서 빠른 자료구조라고 오해하여 중간 데이터 삽입 시 `insert()`를 남발하는 경우. `deque`는 **양쪽 끝(맨 앞, 맨 뒤)** 추가/삭제 시에만 $O(1)$로 동작하며, 중간 위치에 `insert()`를 수행할 경우 `list`와 똑같이 $O(N)$으로 느려진다.

### 1. 4대 그래프 알고리즘 핵심 비교

- **DFS (깊이 우선 탐색, Depth-First Search):**
    
      
    - **개념:** 막힐 때까지 한 방향으로 깊게 들어가고, 막히면 이전 갈림길로 돌아와(백트래킹) 다른 경로를 탐색하는 방식.
        
          
        
    - **핵심 자료구조:** 재귀함수, 스택(`stack`)
        
          
        
    - **주요 활용:** 모든 가능성을 탐색해야 하는 경우 (순열, 조합), 백트래킹 기반 문제, 미로 탈출 가능 여부 확인.
        
          
        
- **BFS (너비 우선 탐색, Breadth-First Search):**
    
      
    - **개념:** 시작점에서 가까운 노드부터 동심원 형태로 한 단계씩 퍼져나가며 탐색하는 방식.
        
          
        
    - **핵심 자료구조:** **`deque` (큐)**
        
          
        
    - **주요 활용:** **간선 이동 거리가 동일(가중치 1)할 때의 최단 거리/최소 이동 횟수 구하기**.
        
          
        
- **다익스트라 (Dijkstra) 알고리즘:**
    
      
    - **개념:** 간선마다 가중치(거리, 시간, 비용)가 다를 때, 특정 출발지에서 다른 노드까지의 최단 경로를 찾는 방식.
        
          
        
    - **핵심 자료구조:** 우선순위 큐 (`heapq`)
        
          
        
    - **주요 활용:** 네비게이션 최단 경로 탐색, 가중치가 양수인 그래프에서의 최단 시간/최소 비용 문제.
        
          
        
- **MST (최소 신장 트리, Minimum Spanning Tree):**
    
      
    - **개념:** 그래프의 모든 노드를 연결하되, **간선들의 비용 합을 최소**로 만드는 트리 구조를 찾는 알고리즘 (크루스칼, 프림 알고리즘 활용).
        
          
        
    - **핵심 자료구조/기법:** Union-Find (서로소 집합), 우선순위 큐
        
          
        
    - **주요 활용:** 모든 지점을 최소 비용으로 연결하는 통신망/전력망/도로 건설 문제.
        
          
        

### 2. 알고리즘선택 및 적용 기준 (코딩테스트 활용 기준)

|**구분**|**DFS**|**BFS**|**다익스트라**|**MST**|
|---|---|---|---|---|
|**목적**|모든 경로 탐색 / 백트래킹|가중치 없는 최단 경로|가중치 있는 최단 경로|전체 최소 비용 연결|
|**탐색 방식**|끝까지 깊게 탐색|가까운 곳부터 넓게 탐색|비용이 가장 적은 곳부터 탐색|간선 비용이 가장 적은 순 연결|
|**핵심 도구**|재귀 / `list.pop()`|**`deque.popleft()`**|`heapq` (우선순위 큐)|`Union-Find` / `heapq`|
|**비유**|미로에서 한쪽 벽 잡고 끝까지 가기|호수에 돌을 던져 물결이 퍼지는 모습|T맵/카카오내비 최단시간 경로|최소 케이블로 건물 전체 인터넷 연결|

### ⚠️ SSAFY 수강생이 자주 오해하는 포인트

- **BFS와 `deque`의 관계:** BFS 구현 시 리스트의 `pop(0)`을 사용하면 $O(N)$으로 시간 초과가 난다. 앞에서 배운 `deque.popleft()` ($O(1)$)를 반드시 사용해야 정상적인 시간 복잡도를 달성할 수 있다.
    
      
    
- **BFS vs 다익스트라 구분:** 간선의 이동 비용이 모두 같다면 **BFS**, 도로마다 통행시간/비용이 제각각이라면 **다익스트라**를 선택해야 한다.
    
      
    
- **최단 경로(다익스트라) vs 전체 연결(MST) 구분:** A에서 B로 가는 "특정 지점 간 최단 경로"는 **다익스트라**, 모든 도시를 "최소 비용으로 하나로 잇는 문제"는 **MST**로 접근해야 한다.

### 1. HTTP 메서드 주요 4대장 (CRUD 매핑)

|**HTTP 메서드**|**CRUD 매핑**|**데이터 전달 위치**|**핵심 역할 및 특징**|
|---|---|---|---|
|**GET**|Read (조회)|URL (Query String)|서버의 **데이터를 조회**할 때 사용. 서버 상태를 변경하지 않음.|
|**POST**|Create (생성)|HTTP Request Body|서버에 **새 데이터를 등록**할 때 사용. 서버 상태가 변경됨.|
|**PUT / PATCH**|Update (수정)|HTTP Request Body|서버의 **기존 데이터를 수정**. (`PUT`: 전체 덮어쓰기, `PATCH`: 일부 수정)|
|**DELETE**|Delete (삭제)|Path Variable 또는 Body|서버의 **데이터를 삭제**할 때 사용.|

### 2. HTTP 상태 코드 (1~5번대)

- **2xx (성공):**
    
      
    - `200 OK`: 요청 성공 (가장 일반적인 조회/처리 성공).
        
          
        
    - `201 Created`: POST 요청 등을 통해 **새로운 데이터 생성 완료**.
        
          
        
    - `204 No Content`: 성공했으나 응답 본문(Body)에 반환할 데이터가 없음.
        
          
        
- **3xx (리다이렉션):**
    
      
    - `301 Moved Permanently`: 요청한 리소스의 URL이 영구적으로 이동됨.
        
          
        
    - `304 Not Modified`: 데이터가 변경되지 않았으므로 **브라우저 캐시**를 그대로 사용함.
        
          
        
- **4xx (클라이언트 오류 - 요청 문제):**
    
      
    - `400 Bad Request`: 요청 파라미터나 형식 문법 오류.
        
          
        
    - `401 Unauthorized`: **인증되지 않음** (로그인 필요).
        
          
        
    - `403 Forbidden`: 인증은 되었으나 해당 리소스에 대한 **접근 권한 없음**.
        
          
        
    - `404 Not Found`: 요청한 URL이나 리소스가 존재하지 않음.
        
          
        
    - `429 Too Many Requests`: **요청 횟수 제한 초과** (Rate Limit 초과, 디도스 방지).
        
          
        
- **5xx (서버 오류 - 서버 내부 문제):**
    
      
    - `500 Internal Server Error`: 서버 내부 코드 버그 또는 예외 발생.
        
          
        
    - `502 Bad Gateway` / `503 Service Unavailable`: 게이트웨이 응답 오류 또는 서버 과부하/점검 중.
        
          
        

### 3. HTTP vs HTTPS 핵심 비교

|**구분**|**HTTP**|**HTTPS**|
|---|---|---|
|**개념**|기본 웹 프로토콜 (평문 전송)|HTTP + **SSL/TLS 보안 암호화** 적용|
|**기본 포트**|**80번**|**443번**|
|**보안성**|암호화 없음 (중간 도청/탈취에 취약)|**데이터 암호화 및 디지털 인증서 검증**|
|**SEO 영향**|검색 노출 시 감점 요인|구글 등 검색엔진에서 우대 (SEO 가산점)|

### ⚠️ 백엔드/웹 개발 시 실수하기 쉬운 포인트

- **보안 오해 (GET vs POST):** POST는 데이터가 URL에 드러나지 않지만, HTTPS를 사용하지 않으면 HTTP 패킷을 캡처할 때 Body 내용이 평문으로 다 노출된다. 보안은 메서드 선택이 아니라 **HTTPS 적용**으로 해결해야 한다.
    
      
    
- **401 vs 403 구별:** `401`은 인증 부족(로그인 안 됨), `403`은 권한 부족(로그인은 했으나 해당 기능 사용 불가)을 의미한다.
    
      
    
- **오류 주체 구별:** `4xx` 에러 발생 시 프론트엔드/클라이언트의 요청 데이터와 URL을 체크하고, `5xx` 에러 발생 시 백엔드 서버의 로그 및 코드를 점검해야 한다.

  

### 1. API vs RESTful API

|**구분**|**API**|**RESTful API**|
|---|---|---|
|**개념**|프로그램끼리 소통하기 위한 **모든 인터페이스(창구)**|HTTP 표준을 활용해 만든 **웹 API 설계 규칙(스타일)**|
|**본질**|**함수 호출과 동일** (입력값을 주고 결과를 받아옴)|상식적이고 표준화된 **웹 함수 호출 방식**|
|**범위**|탈것 (가장 큰 개념)|전기차 (API의 한 종류)|
|**예시**|`len()`, OS 기능 호출, DB 접속 도구 등|`GET /users`, `POST /users`|

### 2. RESTful API의 핵심 설계 규칙

상식적으로 "요청하는 기능에 맞춰 메서드와 URL을 직관적으로 쓰자"는 약속이야.

  

- **URL에는 자원(명사)만 사용한다.** (동사 사용 금지)
    
      
    
- **행동(CRUD)은 HTTP 메서드로 표현한다.**
    
      
    

|**행동 (CRUD)**|**HTTP 메서드**|**올바른 RESTful 표현 (Good)**|**잘못된 표현 (Bad)**|
|---|---|---|---|
|**조회 (Read)**|`GET`|`GET /users`|`POST /getUser`|
|**생성 (Create)**|`POST`|`POST /users`|`GET /createUser`|
|**수정 (Update)**|`PUT` / `PATCH`|`PUT /users/1`|`POST /updateUser?id=1`|
|**삭제 (Delete)**|`DELETE`|`DELETE /users/1`|`GET /deleteUser?id=1`|

### 3. 결론

- **API**는 "인터넷 너머 다른 서버에 있는 **함수를 부르는 것**"
    
      
    
- **RESTful API**는 "그 함수를 부를 때 **명사형 URL + 역할에 맞는 GET/POST/PUT/DELETE 메서드**로 깔끔하게 규격을 맞춰 부르는 것"
