## 2. 예외 처리 (`try` / `except` / `raise`)

  

### `raise`부터 — 원래 에러는 저절로 나지만, `raise`는 내가 강제로 발생시키는 것

  

```python

raise Exception

```

이 줄을 만나면 `10/0`에서 에러 났을 때와 똑같이 프로그램이 멈춘다. 아래 코드는 실행 안 됨. **"여기서부터는 진행하면 안 된다"는 신호**.

  

### `try`/`except`로 감싸면 멈추는 대신 넘어감

  

```python

try:

    raise Exception

except Exception:

    print("처리함")

print("프로그램 계속 실행됨")

```

  

`try` 안에서 문제가 나면 그 즉시 `except`로 점프. 프로그램은 안 죽고 계속 진행.

  

**`try/except`는 오직 오류 상황을 위한 문법**이며 C의 `switch/case`와는 다름 — `switch`는 정상적인 값을 미리 분기하는 것, `try/except`는 **일단 실행해보고 문제가 터지면** 반응하는 것.

  

### 특정 종류만 잡기, 여러 종류 나누기

  

```python

except IndexError:            # 이 종류만

    ...

except ValueError:

except ZeroDivisionError:     # 여러 종류를 각각 다르게

```

  

### `as e` — 오류 메시지를 변수로 받기

  

```python

except ZeroDivisionError as e:

    print(e)     # 시스템이 준 메시지 출력

```

  

**`e`를 안 쓸 거면 `as e`는 안 써도 됨.** (`except NotFoundException:` 만으로 충분)

  

### `else` / `finally`

  

- `else`: `try`가 성공했을 때만

- `finally`: 성공/실패 상관없이 무조건

  

### 사용자 정의 예외

  

```python

class MyCustomError(Exception):

    pass

```

  

`Exception`을 상속만 하면 됨 — 메시지 저장/출력 기능은 부모(`Exception`)한테 전부 물려받으므로 `pass`만 있어도 충분.

## 3. 자판기 코드에 실제로 적용된 커스텀 예외 (오늘 강사님이 추가함)

  

**새 파일 `exceptions.py`:**

```python

class NotFoundException(Exception):

    pass

  

class OutOfStockException(Exception):

    pass

```

  

**`vending_machine.py` 변경**: `raise Exception` → `raise NotFoundException('없는 상품입니다.')` / `raise OutOfStockException('재고가 없습니다.')` 로 종류를 나눔. `except`도 종류별로 나눠서 서로 다르게 반응하게 됨.

  

### 왜 이렇게 나눴나 — "종류"와 "메시지"는 다른 일

  

- **종류(클래스)**: `except`가 **뭘 잡을지 구분**하는 기준. 메시지 내용이 뭐든 상관없이, 클래스만 같으면 그 블록으로 감.

- **메시지(글자)**: 사람이 읽는 설명일 뿐. `except`의 동작에는 영향 없음.

  

만약 종류를 안 나누고 메시지 문자열을 직접 비교(`if str(e) == '없는 상품입니다.':`)했다면, 메시지에 오타 하나만 나도 조용히 안 걸림. **종류로 구분하면 메시지가 뭐든 안정적으로 분기됨** — 이게 예외를 종류별 클래스로 나누는 진짜 이유.

  

### 남아있는 약점

  

`exceptions.py`는 여전히 `pass`뿐이라, `raise NotFoundException("아무 말")`처럼 **메시지는 매번 자유롭게 씀 → 실수로 앞뒤 안 맞는 메시지를 넣어도 파이썬이 못 잡아줌.** 고치려면 `__init__`을 직접 만들어 메시지를 클래스 안에 고정하면 됨:

```python

class StockError(Exception):

    def __init__(self, product_name):

        super().__init__(f"{product_name}의 재고가 없습니다")

```

  

### 만약 애초에 상황별로 다르게 반응할 필요가 없었다면

  

`exceptions.py` 자체가 필요 없었을 것. 커스텀 예외를 만드는 이유는 "다르게 반응하고 싶다"는 목적이 있어야 성립함. 목적 → 여러 except 필요 → 종류 구분 필요 → 커스텀 클래스 필요 → 파일 분리, 순서의 인과관계.

## 4. 파이썬 추가 문법 (`python_additional.ipynb`) — 9종 요약

  

**`*args`, `**kwargs`**: 매개변수 개수를 미리 안 정해도 되게 함. 이름 없이 넘긴 값 → 튜플(`args`)로, `이름=값` 형태로 넘긴 값 → 딕셔너리(`kwargs`)로 자동 정리. 이름 자체는 관례고, 진짜 핵심은 `*`/`**` 별표.

  

**패킹/언패킹**: `def`에서 `*args`로 모으는 것(패킹)과 반대로, 함수를 **부를 때** `*리스트`/`**딕셔너리`로 펼쳐서 넘기는 것(언패킹)은 서로 짝.

  

**`is` vs `==`**: `==`는 내용(값)이 같은지, `is`는 진짜 같은 객체(메모리상 동일한 것)인지. `a = [1,2,3]; b = [1,2,3]` → `a==b`는 True, `a is b`는 False. `None`은 `is None`으로 비교하는 게 관례.

  

**얕은 복사 / 깊은 복사**: `b = a`는 복사가 아니라 같은 걸 가리키는 이름표 하나 더. `.copy()`(얕은 복사)는 바깥만 새로 만들고 내부 리스트는 공유 → 원본 내부를 바꾸면 얕은 복사본도 같이 바뀜. `copy.deepcopy()`는 내부까지 전부 새로 복제.

  

**`__str__` / `__repr__`**: 복습. `__str__`은 사람이 읽기 좋게(`print()`), `__repr__`은 개발자 디버깅용(리스트 안에 있을 때, 변수만 찍었을 때). `!r`은 `repr()`을 문자열 안에서 짧게 쓰는 문법.

  

**제네릭 (`TypeVar`)**: "들어온 것과 같은 타입을 돌려준다"를 타입힌트로 표현. 실행에는 영향 없음(타입힌트는 원래 강제 아님).

  

**덕 타이핑 + `Protocol`**: `ABC`의 대안. `Protocol`은 상속 안 해도 되고, 그냥 "이런 메서드가 있어야 한다"는 걸 타입힌트로만 표시. 실행 중 강제(ABC)가 필요 없고 상속 관계 없이 유연하게 쓰고 싶을 때 사용.

## 5. 제너레이터 — 처음부터 정리

  

`return`은 값 하나 주고 함수를 완전히 끝냄. `yield`는 값 하나 주고 **그 자리에 멈춤**, 나중에 이어서 실행 가능.

  

```python

def simple_generator():

    print("첫 번째 값을 생성합니다.")

    yield "A"

    print("두 번째 값을 생성합니다.")

    yield "B"

```

  

- `gen = simple_generator()` → **아무것도 실행 안 됨.** "generator object"라는 대기 상태만 만들어짐.

- `next(gen)` → 그제서야 실행 시작 → 첫 `yield`까지 실행하고 멈춤 → 그 값을 반환

- `next(gen)` 또 호출 → 멈췄던 자리부터 이어서 실행 → 다음 `yield`까지

- `for text in gen:` → 내부적으로 `next()`를 자동 반복 호출, 값이 바닥나면 알아서 멈춤

  

**어떤 함수가 제너레이터 함수인지 구분법**: 함수 안에 `yield`가 하나라도 있으면 제너레이터 함수. 이 판단은 **함수를 부를 때가 아니라 `def`로 정의할 때 이미 정해짐.**

  

**왜 쓰나**: 값을 전부 미리 만들어서 메모리에 쌓아두는 리스트 방식과 달리, **필요할 때 하나씩만** 만들어서 메모리를 아낌. 데이터가 아주 크거나 끝을 모를 때 유리.

  

**정의 위치 규칙**: 제너레이터만의 특별 규칙이 아니라 파이썬 함수 전체의 규칙 — `def`(이름+본문 한 덩어리)는 **쓰기 전에 위에서 완전한 형태로 정의**돼 있어야 함. C처럼 "선언 따로, 구현 따로"는 불가능. 데코레이터 배울 때 `trace_log`가 클래스보다 위에 있어야 했던 것과 같은 이유.

## 6. 오늘 다시 짚은 헷갈림 — 다형성/for-in

  

### `for animal in [Dog(), Cat()]:` 은 "확인"이 아니라 "꺼내기"

  

`in`은 두 가지로 쓰임 (전에 배운 것 재확인):

| 쓰임 | 하는 일 |

|---|---|

| `for x in 리스트:` | 하나씩 **꺼내기** |

| `if x in 리스트:` | 들어있는지 **확인** (True/False) |

  

`for animal in [Dog(), Cat()]:` 은 "animal이 Dog나 Cat에 속하는지 검사"하는 게 아니라, **그냥 상자(리스트)에서 순서대로 하나씩 꺼내서 `animal.speak()`를 실행하는 것뿐.** 종류 확인 과정 자체가 없음.

  

### `Dog()`, `Cat()` — 클래스가 아니라 그 클래스로 만든 객체

  

`Dog`(괄호 없음) = 클래스 자체, `Dog()`(괄호 있음) = 그 클래스로 만든 객체 하나. `allow_weapon_list = {Sword}` 때 봤던 구분과 동일한 규칙.

  

### 종류(클래스) 개수와 리스트 길이는 무관

  

`Dog`, `Cat` 같은 클래스가 늘어나는 것과, 리스트 `[Dog(), Cat()]`에 객체가 몇 개 들어있는지는 서로 다른 문제. 다형성으로 절약되는 건 **"리스트 길이"가 아니라 "종류별로 분기하는 if/elif 코드"** — `for animal in animals: animal.speak()` 이 두 줄은 클래스가 몇 개든 그대로 유지됨.

  

### 다형성 자체엔 전용 선언 문법이 없음

  

다형성은 "같은 이름의 메서드 호출이 객체에 따라 다르게 동작하는 현상"이지, `class Child(Parent)`처럼 선언하는 문법이 아님. 상속+오버라이딩으로 만들 수도, 덕 타이핑(상속 없이 이름만 맞춰서)으로 만들 수도 있음.

  

### ABC 상속 vs `@abstractmethod`는 역할이 다름

  

- `class Weapon(ABC):` → **상속** (ABC라는 클래스를 물려받음)

- `@abstractmethod` → **데코레이터** ("자식이 반드시 구현해야 한다"는 표시만 붙임)

  

둘이 같이 있어야 강제력이 생김. `ABC` 상속 없이 `@abstractmethod`만 쓰면 효과 없음 (자판기 `Payment` 클래스가 실제로 이 상태).

## 오늘의 핵심 정리

  

1. **`raise`**: 강제로 문제 상황을 발생시키는 명령. `try` 안에서 쓰여야 프로그램이 안 죽고 `except`로 넘어감.

2. **커스텀 예외 클래스**: "상황별로 다르게 반응하고 싶다"는 목적이 있을 때만 필요. 메시지가 아니라 **종류(클래스)** 로 분기해야 오타/불일치에 안전함.

3. **덕 타이핑**: 클래스 내용이 같아야 하는 게 아니라, **메서드 이름만 같으면** 상속 없이도 다형성이 성립.

4. **제너레이터**: `yield`가 있으면 부르는 즉시 실행되지 않고 대기 상태만 만들어짐. `next()`/`for`가 실행을 한 단계씩 진행시킴.

5. **`for x in 리스트:`는 확인이 아니라 꺼내기.** 종류 검사와는 무관.

### LLM의 개념과 핵심 메커니즘

LLM(Large Language Model)은 다음 문장에 올 내용을 예측하고 생성하는 대형 언어 모델이다.

  

- **트랜스포머(Transformer) 구조:** LLM은 트랜스포머라는 아키텍처를 기반으로 만들어졌다.
    
      
    
- **문맥 파악:** 트랜스포머 내부의 **어텐션(Attention)** 메커니즘이 문장 내 여러 요소(단어)들이 서로 어떤 관계를 가지는지 계산하며 전체 문맥을 파악한다.
    
      
    
- **트랜스포머의 특성:** 문맥을 매우 정교하게 파악하지만, 한 번에 처리할 수 있는 텍스트 길이(컨텍스트 윈도우)에 제한이 있으며 입력 길이가 길어질수록 계산량이 제곱으로 증가하는 한계가 있다.
    
      
    

### 트랜스포머의 역사 및 실무적 위치

- **탄생:** 2017년 구글 연구진이 발표한 논문 "Attention Is All You Need"에서 처음 제안되었다.
    
      
    
- **생태계 영향:** 구글이 기술을 제시했으나 이를 대규모 상용화하여 LLM 시대를 연 것은 OpenAI(ChatGPT)였다.
    
      
    
- **현재 위상:** GPT, Claude, Gemini 등 현존하는 대부분의 최신 AI 모델이 트랜스포머 아키텍처를 기반으로 확장·변형되어 사용된다.
    
      
    

### LLM과 AI 에이전트의 차이

- **LLM:** 입력받은 질문에 대해 텍스트를 생성하여 답을 주는 **'뇌'** 역할에 집중한다.
    
      
    
- **AI 에이전트:** LLM이라는 뇌에 '손과 발(외부 도구 호출, 웹 검색, 코드 실행, 데이터베이스 연동 등)'을 부여한 시스템이다. 단순히 답변을 생성하는 데 그치지 않고, 주어진 목표를 달성하기 위해 스스로 계획을 수립하고 절차를 수행한다.

### AI 에이전트와 LLM의 구조적 차이

AI 에이전트는 기본적으로 LLM을 기반 엔진으로 사용하지만, 단순히 텍스트 응답을 출력하는 데 그치지 않고 **'ReAct(Reason + Act) 루프'** 구조를 통해 목표를 완수할 때까지 행동을 반복하는 시스템이다.

- **ReAct 루프 (Thought-Action-Observation):**
    
    1. **추론(Reason):** LLM이 들어온 요청과 현 상황을 분석하여 다음에 필요한 행동(예: 외부 API 호출, DB 검색, 코드 실행)을 텍스트로 결정한다.
        
    2. **행동(Act):** 프레임워크 실행기가 LLM이 선택한 외부 도구를 실제로 실행한다.
        
    3. **관찰(Observation):** 도구 실행 결과 값을 다시 LLM의 입력으로 전달한다.
        
    4. **반복:** 최종 목표가 달성될 때까지 이 과정을 스스로 반복하고 최종 결과를 출력한다.
        
- **에이전트 개발 시 필수 고려사항:**
    
    - **무한 루프 방지:** 도구 실행 실패나 판단 오류로 인해 에이전트가 동일 행동을 무한히 반복할 수 있으므로, 최대 반복 횟수(Max Iterations) 설정을 통한 예외 처리가 필수적이다.
        
    - **상태 관리(State Management):** 루프가 돌 때마다 이전 단계의 결과와 맥락을 잊지 않고 전달할 수 있는 메모리/상태 관리 파이프라인이 필요하다.
        

### 컨텍스트(Context)와 토큰(Token)의 개념

LLM은 이전 대화를 자체적으로 저장하지 않는 **무상태(Stateless)** 구조다. 따라서 이전 대화를 기억하는 것처럼 동작하게 하려면 매 요청마다 지난 대화 내역을 함께 넘겨주어야 한다.

- **컨텍스트(Context):** 모델이 답변을 생성할 때 참조할 수 있도록 함께 전달되는 정보 데이터로, LLM의 **단기 기억** 역할을 담당한다.
    
- **토큰(Token):** LLM이 텍스트를 인식하고 처리하는 최소 단위이다. (OpenAI Tokenizer 등을 통해 확인 가능)
    
    - **언어별 특성:** 영어는 단어/공백 단위로 비교적 효율적으로 토큰화되는 반면, 한국어는 자음·모음 분리 등으로 인해 동일 내용 대비 토큰 소비가 2~3배 많아 컨텍스트 한도를 더 빠르게 소모한다.
        
- **실무에서의 컨텍스트 관리 기법:** 대화가 길어질수록 비용 증가 및 컨텍스트 길이 초과(Context Window Exceeded) 문제가 발생하므로, 이전 대화를 요약(Summary Memory)하거나 최근 N개 대화만 유지하는 슬라이딩 윈도우(Sliding Window) 방식을 적용한다.
