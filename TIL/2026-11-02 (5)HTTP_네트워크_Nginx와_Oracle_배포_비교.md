## 주제 1: HTTP·REST API·내부 주소를 구분하기

EC2에서 FastAPI를 실행하고 다음 HTTP 요청으로 정상 응답을 받았다.

```text
http://127.0.0.1:8000/health
http://127.0.0.1:8000/search
```

HTTP는 클라이언트와 서버가 요청·응답을 주고받는 통신 프로토콜이다. REST API는 자원과 작업을 HTTP 메서드·주소 등으로 표현하는 API 설계 방식이다. Nginx는 요청을 처리·전달하는 프로그램이다. 셋은 같은 분류의 대체재가 아니다.

> ➕ **더 알아두기 — 지금 누구의 localhost인가**
> 127.0.0.1은 명령이나 브라우저가 실행되는 컴퓨터 자신이다. EC2 터미널의 curl이라면 EC2 자신을 가리킨다. 같은 주소를 로컬 PC 브라우저에 넣으면 로컬 PC를 가리키므로 EC2에 접속하는 주소가 아니다.
>
> HTTP 요청에 200이 나왔다는 것은 그 요청 경로가 동작했다는 뜻이다. EC2 내부에서만 검증했다면 인터넷 외부 접속까지 성공했다고 해석하지 않는다. HTTP 자체는 내용을 암호화하지 않는다. 하지만 FastAPI → RDS 구간은 별도로 TLS를 설정했으므로 브라우저 → 서버 구간과 DB 구간의 보호 여부를 나누어 본다.

Nginx 추가 전 Compose는 EC2의 127.0.0.1:8000을 컨테이너의 8000으로 연결했다. 따라서 퍼블릭 IP만 브라우저에 입력한다고 자동으로 이 내부 주소로 전달되지 않았다.

## 주제 2: VPC·퍼블릭 액세스·보안 그룹과 내 IP

VPC(Virtual Private Cloud)는 AWS에서 구성하는 가상 네트워크다. EC2와 RDS를 같은 VPC에 두고 사설 주소로 통신하도록 구성할 수 있다. 라우팅과 보안 그룹 등 조건이 맞아야 하므로 같은 VPC라는 사실만으로 모든 접속이 허용되는 것은 아니다.

| 설정 | 무엇을 정하는가 |
|---|---|
| RDS 퍼블릭 액세스 | 인터넷에서 직접 접속할 수 있는 구성인지 |
| 라우팅 등 네트워크 경로 | 통신이 목적지까지 도달할 수 있는지 |
| 보안 그룹 | 어떤 출발지·프로토콜·포트의 연결을 허용할지 |
| DB 계정·암호 | 접속 사용자를 인증할 수 있는지 |

> ➕ **더 알아두기 — 퍼블릭 액세스 아니오**
> RDS의 퍼블릭 액세스가 아니오라면 인터넷에서 DB로 직접 접속하는 경로를 사용하지 않는다. VPC 내부 자원이나 별도 사설 연결을 통해 접근한다. EC2는 조건이 맞으면 사설 주소로 DB에 접속할 수 있다. 이번 실습은 로컬 PC에서도 RDS에 직접 접속하므로 예로 설정했다. 예라고 누구나 인증 없이 들어갈 수 있는 것은 아니다.

### RDS 규칙과 EC2 웹 규칙은 다르다

| 목적지 | 소스 | 포트·목적 |
|---|---|---|
| RDS | 로컬 PC의 공인 IP /32 | PostgreSQL 5432, VS Code·로컬 적재 |
| RDS | EC2 보안 그룹 | PostgreSQL 5432, EC2의 앱·적재 |
| EC2 | Instance Connect 접두사 목록 | SSH 22, 브라우저 터미널 접속 |
| EC2 | Anywhere-IPv4 | HTTP 80·HTTPS 443, 외부 웹 접속 |

RDS 규칙 편집 화면에서 기존 EC2 그룹 규칙과 기존 IP /32 규칙이 보였고 사용자가 “내 IP를 또 넣을 필요가 없다고 한다”고 물었다. 로컬 VS Code 접속이 이미 성공했고 해당 허용 규칙도 존재하므로 같은 IP를 중복 추가할 필요가 없었다. 당시 EC2 적재에는 EC2 보안 그룹 규칙이 사용됐다. 불필요하게 추가된 빈 셋째 행은 저장하지 않도록 안내했다.

> ♻️ 처음엔 EC2 메뉴의 보안 그룹 화면이므로 EC2만 관리한다고 생각했으나, 보안 그룹이 실제로 연결된 자원이 기준이다. RDS에 붙은 그룹을 편집하면 RDS로 들어오는 통신을 제어한다. 그 안에서 EC2 그룹을 소스로 선택하면 EC2에서 오는 DB 연결을 허용한다.

## 주제 3: 0.0.0.0/0은 브로드캐스트가 아니다

교안은 EC2 보안 그룹에 HTTP·HTTPS 인바운드 규칙을 추가한다. 사용자 화면에서도 기존 SSH 규칙과 새 HTTP 80·HTTPS 443, Anywhere-IPv4 소스가 확인됐다.

```text
HTTP   TCP 80    source 0.0.0.0/0
HTTPS  TCP 443   source 0.0.0.0/0
```

> ➕ **더 알아두기 — CIDR 읽기**
> CIDR(Classless Inter-Domain Routing)은 IP 주소 범위를 접두사 길이로 표현하는 방식이다. IPv4는 32비트이고 /숫자는 앞에서 몇 비트를 고정할지 뜻한다.
>
> | 예시 | 주소 범위의 뜻 |
> |---|---|
> | 192.168.1.10/32 | 전체 32비트를 고정하므로 주소 하나 |
> | 192.168.1.0/24 | 앞 24비트 고정, 마지막 8비트가 바뀌는 256개 주소 범위 |
> | 0.0.0.0/0 | 고정하는 비트가 없으므로 모든 IPv4 주소 범위 |
>
> 보안 그룹의 0.0.0.0/0은 모든 IPv4 출발지에서 해당 서비스 포트로 접속을 시도할 수 있게 허용한다는 뜻이다. 전 세계 컴퓨터에 패킷을 방송한다는 뜻이 아니다. 공개 웹서비스이므로 사용자 IP를 미리 한정하지 않고 웹 포트를 허용한 것이다.

> ♻️ 처음엔 모든 대상에 관련된 표현이므로 브로드캐스트 주소와 같은 개념인지 의문이 있었으나, 인바운드 소스의 CIDR 범위와 브로드캐스트 목적지는 다르다. 일반적인 IPv4 서브넷에서 호스트 비트를 모두 1로 둔 마지막 주소가 브로드캐스트다. 192.168.1.0/24의 예에서는 192.168.1.255다. /31·/32 등 특수한 사용까지 “항상 마지막 주소는 브로드캐스트”로 일반화하지 않는다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> IPv4 서브넷 계산에서 네트워크 부분·호스트 부분·접두사 길이를 구분한다. 주소 범위의 크기와 실제 사용 가능한 호스트 수는 같은 질문이 아니다. 접근 통제 정책의 출발지 범위와 통신 방식인 브로드캐스트도 구분한다. 0.0.0.0 단독 주소와 /0이 붙은 범위 표현은 문맥이 다르다.

## 주제 4: FastAPI가 되는데 왜 Nginx를 추가하는가

Nginx(엔진엑스)는 웹 서버이며 리버스 프록시(Reverse Proxy)로 사용할 수 있다. 클라이언트 요청을 먼저 받아 뒤쪽 애플리케이션으로 전달하고, 애플리케이션 응답을 다시 클라이언트에게 돌려준다. 교안에서는 EC2 안에 Nginx와 FastAPI를 각각 컨테이너로 실행한다.

> ➕ **더 알아두기 — 이미 되던 기능과 새 역할**
> FastAPI는 Nginx가 없어도 HTTP 요청을 받아 REST API를 제공할 수 있다. 실제로 앞서 EC2 안에서 검색까지 성공했다. Nginx를 넣어서 FastAPI의 API가 다른 방식으로 대체되는 것이 아니다. 외부 접속·HTTPS·요청 전달을 별도의 프로그램에 맡기는 운영 구조를 택한 것이다.
>
> 식당에서 Nginx는 주문을 받고 음식을 전달하는 직원, FastAPI는 실제 조리하는 주방에 비유할 수 있다. 요청을 두 번 검색하는 것이 아니라 앞쪽은 전달·연결을 관리하고 뒤쪽은 앱 기능을 처리한다.

| Nginx가 맡을 수 있는 일 | 얻는 이점 | 이번 실습 상태 |
|---|---|---|
| 외부 HTTP 요청을 FastAPI로 전달 | 접근 창구와 내부 앱 역할 분리 | 설정·실행 확인 |
| HTTPS 인증서 사용 | 웹 암호화 연결을 한곳에서 관리 | 이후 단계 |
| HTTP → HTTPS 리다이렉트 | 암호화 주소로 이동 안내 | 이후 단계 |
| URL별 다른 앱으로 전달 | 하나의 주소에서 여러 백엔드 관리 | 개념 설명만 |
| 업로드 크기·요청 빈도 제한 | 앱 앞단에서 요청 정책 적용 | 설정하지 않음 |

> ➕ **더 알아두기 — 자동으로 생기는 장점은 아니다**
> Nginx를 추가했다고 HTTPS·속도 제한·여러 서버 분산이 저절로 적용되는 것은 아니다. 필요한 기능을 설정해야 한다. 작은 서비스는 다른 방식으로 공개할 수도 있고 다른 프록시나 관리형 서비스를 쓸 수도 있다. 이번 교안의 당장 목적은 HTTP 입구를 만들고 이후 HTTPS를 설정하는 것이다.

## 주제 5: nginx.conf 작성과 Compose의 Nginx 서비스

### 파일을 만드는 것과 실행하는 것

사용자는 로컬 실습 복사본 backend 폴더에 빈 nginx.conf를 만들었다. nginx.conf는 Python으로 실행하는 파일이 아니라 Nginx가 읽는 설정 파일이다. 교안 코드를 붙여넣고 EC2_PUBLIC_IP를 실제 EC2 퍼블릭 IPv4 주소로 바꿔 저장한다. RDS 엔드포인트와는 다른 주소다.

사용자가 요청해 AI가 실습 복사본의 nginx.conf를 작성했다. 원본 강의 폴더는 수정하지 않았다. 아래는 실제 퍼블릭 IP를 제거한 공개용 설정 예시다.

```nginx
server {
    listen 80;
    server_name <EC2_PUBLIC_IP>;

    location ^~ /.well-known/acme-challenge/ {
        root /var/www/certbot;
        default_type text/plain;
        try_files $uri =404;
    }

    location / {
        proxy_pass http://backend:8000;

        proxy_set_header Host $host;
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
```

| 설정 | 하는 일 |
|---|---|
| listen 80 | HTTP 80번 포트에서 요청 수신 |
| server_name | 요청의 호스트 이름 등에 맞춰 서버 블록을 선택할 때 사용하는 값 |
| acme-challenge 경로 | 이후 인증서 발급·갱신 검증 파일을 HTTP로 제공 |
| try_files $uri =404 | 요청한 파일이 없으면 404 응답 |
| proxy_pass http://backend:8000 | 일반 요청을 Docker 네트워크의 backend 서비스로 전달 |
| Host 헤더 | 원래 요청의 호스트 정보 전달 |
| X-Forwarded-For | Nginx에서 본 클라이언트 주소 전달 |
| X-Forwarded-Proto | 원래 요청이 HTTP·HTTPS 중 무엇이었는지 전달 |

> ➕ **더 알아두기 — server_name은 방화벽이 아니다**
> listen은 어느 포트에서 받을지, server_name은 서버 블록 선택에 쓰는 호스트 정보를 다룬다. server_name에 IP를 적는다고 그 IP에서 출발한 사용자만 허용한다는 뜻은 아니다. 접속 소스 제한은 보안 그룹 등 별도 정책과 구분한다.

### Compose에 실행 지시 추가

nginx.conf가 처리 방법을 적은 설명서라면 Compose 서비스는 그 설명서를 읽을 Nginx 프로그램을 실제 실행하는 지시다. 기존 backend 환경변수에는 FORWARDED_ALLOW_IPS를 추가했다.

```yaml
      FORWARDED_ALLOW_IPS: "*"
```

다음 nginx 서비스를 추가했다.

```yaml
  nginx:
    image: nginx:1.30.6-alpine
    ports:
      - "80:80"
    volumes:
      - ./nginx.conf:/etc/nginx/conf.d/default.conf:ro
      - /var/lib/letsencrypt:/var/www/certbot:ro
      - /etc/letsencrypt:/etc/letsencrypt:ro
    depends_on:
      - backend
    restart: unless-stopped
```

| 항목 | 의미 |
|---|---|
| image | 교안의 Nginx 이미지를 사용해 컨테이너 생성 |
| 80:80 | EC2의 80번 포트를 Nginx 컨테이너 80번 포트에 연결 |
| nginx.conf 마운트 | 로컬 파일을 컨테이너의 기본 서버 설정 위치에 읽기 전용 연결 |
| 인증서 관련 두 마운트 | 나중에 검증 파일·인증서를 제공하기 위한 경로 연결 |
| depends_on | backend 컨테이너를 먼저 시작하는 순서 지정 |
| restart | 명시적으로 중지하지 않은 경우의 재시작 정책 |

> ➕ **더 알아두기 — 순서와 신뢰 범위**
> depends_on의 이 짧은 형식은 backend가 요청을 받을 준비까지 끝났음을 보장하는 상태 검사가 아니다. 시작 순서를 정하는 것이다. 실제 정상 여부는 로그와 HTTP 응답으로 확인한다.
>
> FORWARDED_ALLOW_IPS는 앱 서버가 프록시 전달 정보를 신뢰할 출발지를 정한다. *는 모든 연결 출발지의 전달 정보를 신뢰하므로 앱에 임의 클라이언트가 직접 접근할 수 있는 구성에서는 신중해야 한다. 교안은 Nginx를 앞에 두고 백엔드 포트 공개를 제한한 구성을 전제로 한다.

Compose 설정 검사를 통과했다. 로컬에서 Nginx를 실행해 EC2 인증서 경로를 사용하는 구성을 검증한 것은 아니며, 실제 기동은 EC2에서 진행했다.

## 주제 6: GitHub 반영·EC2 적용·HTTP 성공 검증

수정 파일은 처음에는 로컬 aws_practice/backend에만 있었다. 승인 후 기존 업로드용 Git 저장소에 compose.yaml과 nginx.conf를 복사해 두 파일만 커밋·push했다. 실제 .env·CA 파일은 포함하지 않았다.

```text
db00f21 feat: Nginx HTTP 프록시 설정 추가
```

원격 main 커밋 일치를 확인했다. 사용자 요청에 따라 EC2에서 교안과 같은 작업 네 줄을 실행하도록 안내했다. 실행 위치는 /home/ubuntu/aws-agent-backend다.

```bash
GIT_SSH_COMMAND="ssh -i /home/ubuntu/.ssh/github_backend -o IdentitiesOnly=yes" git pull --ff-only
sudo mkdir -p /etc/letsencrypt /var/lib/letsencrypt/.well-known/acme-challenge
sudo docker compose up -d backend
sudo docker compose up -d nginx
```

> ➕ **더 알아두기 — 교안보다 긴 첫 줄**
> 교안의 git pull --ff-only와 같은 Git 작업이다. private 저장소에서 우리가 만든 키 이름을 명시해야 하므로 SSH 명령 지정이 앞에 붙었다. 작업 폴더를 맞추기 위한 cd는 네 줄과 별도로 설명했다. 기존에 작성한 .env를 예제 파일로 다시 복사하지 않았다.

실제 캡처에서 Nginx 이미지가 Pulled, backend가 Running, nginx 컨테이너가 Started로 표시됐다. 이후 EC2에서 다음 요청을 실행했다.

```bash
curl -i http://127.0.0.1/health
```

```text
HTTP/1.1 200 OK
Server: nginx/1.30.6
```

```json
{"status":"ok"}
```

포트를 생략한 HTTP URL은 기본 80번을 사용한다. 기존 8000번 직접 요청과 달리 이번에는 Nginx를 거쳐 FastAPI의 health에 도달했다. nginx 응답 헤더와 status=ok를 함께 확인했다.

```text
EC2의 curl → Nginx:80 → FastAPI:8000 → RDS
```

사용자 PC 브라우저에서 http://<EC2_PUBLIC_IP>/health를 열어 외부 경로도 확인하도록 안내했다. 사용자가 다음 질문으로 넘어갔지만 브라우저 응답 화면은 별도로 공유하지 않았다. 따라서 외부 브라우저 성공을 캡처로 확인했다고 기록하지 않는다.

### 지금까지의 완료 범위

| 작업 | 상태 |
|---|---|
| FastAPI 직접 health·검색 | EC2 내부에서 실제 성공 |
| Nginx 파일·Compose 작성 | 복사본에 저장, 구성 검사 통과 |
| GitHub 반영 | db00f21 push 확인 |
| EC2 Nginx 컨테이너 | 실행 화면 확인 |
| Nginx 경유 health | EC2 내부에서 200·nginx 헤더·status=ok 확인 |
| 외부 브라우저 health | 테스트 안내, 별도 결과 화면 미확인 |
| HTTPS 서버 인증서 발급·설정 | 아직 진행하지 않음 |
| HTTPS 자동 갱신·Vercel | 이후 단계 |

보안 그룹에서 HTTPS 443을 허용해도 HTTPS가 자동으로 켜지는 것은 아니다. 현재 Compose에는 80번 포트만 공개돼 있고 Nginx 설정도 listen 80이다. 이후 인증서·443 포트 매핑·TLS 설정을 추가해야 한다.

## 주제 7: EC2 퍼블릭 IP는 언제 바뀌는가

사용자가 주소로 접속하면서 AWS는 고정 IP인지 물었다. AWS 전체를 하나의 IP 정책으로 말하지 않고 EC2의 자동 할당 퍼블릭 IPv4 기준으로 설명했다.

| 동작 | 자동 할당 퍼블릭 IPv4 |
|---|---|
| 계속 실행 | 유지 |
| 재부팅 Reboot | 유지 |
| 중지 Stop 후 시작 Start | 기존 주소 반환, 새 주소 할당 |

Elastic IP(탄력적 IP)는 사용자가 할당받아 보유하는 고정 퍼블릭 IPv4 주소이며 연결할 EC2를 바꿀 수 있다. 직접 해제하기 전까지 보유하는 자원이다. 별도 사용 비용과 정책은 실제 사용 시 확인해야 한다.

> ♻️ 현재 주소가 계속 보인다고 고정 IP라고 가정하면 안 된다. 이번 대화에서 탄력적 IP를 할당하거나 연결한 작업은 없었다. 중지 후 다시 시작해 주소가 바뀌면 접속 URL과 Nginx 설정, 추후 IP 기반 인증서 등 주소에 의존하는 구성을 다시 확인해야 한다.

## 주제 8: 왜 배포 설정이 많고, 이전 Oracle은 빨리 끝났는가

### 프로그램 실행과 공개 서비스 운영의 차이

사용자는 결국 로컬에서 실행하던 프로그램을 클라우드에 올린 것인데 왜 설정이 많은지 물었다. 핵심은 컴퓨터 위치 변경에 더해 인터넷 접속 경로·접근 통제·비밀 설정·통신 보호·프로세스 운영을 준비했다는 것이다.

| 해결한 문제 | 이번 실습의 수단 |
|---|---|
| 계속 실행할 컴퓨터 | EC2·Ubuntu |
| 같은 패키지·실행 환경 | Docker·잠금 파일 |
| 코드 전달 | GitHub·SSH Deploy key |
| DB 저장과 접속 | RDS·엔드포인트·계정·암호 |
| 누가 어디에 접속할지 | VPC·보안 그룹·포트 |
| DB 통신 보호 | TLS·CA 인증서 |
| 외부 HTTP 요청 창구 | Nginx·80번 포트 |
| 웹 HTTPS 제공 | 이후 인증서·443 설정 |

> ➕ **더 알아두기 — 이번 흐름이 길어진 이유**
> 강의는 설정을 하나씩 직접 경험하도록 구성돼 있다. 대화에서는 여기에 로컬 SSH 인증 확인, private 저장소 Deploy key 준비, 처음 전달된 로컬 실습 폴더와 실제 배포 폴더 비교·교정, EC2 적재 후 강의대로 로컬 실습 재준비가 추가됐다. 이 부분은 모든 배포에서 반드시 같은 횟수로 반복하는 표준 단계가 아니다. 실습 방식과 경로 혼선 때문에 추가된 작업도 구분한다.
>
> 기반 설정 후 코드 수정은 보통 수정 → push → EC2 pull → 재빌드·실행 → 확인의 반복이다. 서버·네트워크·키를 매번 새로 만들지 않는다. 더 많은 운영을 대신해주는 서비스를 선택하면 직접 설정할 항목도 줄일 수 있다.

### 이전 Oracle 서버 기록에서 실제 확인한 것

사용자는 Claude Code가 만든 Oracle 무료 서버와 금융 RAG 프로젝트도 같은 구조인지 질문했다. 로컬 financial-rag-agent 저장소를 찾아 읽었지만 그 폴더에서는 배포 설정을 확인하지 못했다. 이어 로컬 Oracle 서버 README와 작업일지를 읽었다. 접속정보.local.md나 개인 키 내용은 읽지 않았고 서버에 SSH로 접속하지 않았다.

기록에서 배포 완료로 적힌 프로젝트 이름은 langgraph-financial-agent였다. 사용자가 떠올린 financial-rag-agent와는 이름이 다르므로 같은 저장소라고 단정하지 않는다.

| 이번 AWS 실습 | Oracle 로컬 기록 |
|---|---|
| EC2 Ubuntu | Oracle Ubuntu 가상 머신 |
| SSH 접속 | SSH 키 접속 |
| 보안 그룹의 80·443 | Oracle Security List와 서버 iptables의 두 겹 방화벽 |
| Docker로 앱 관리 | systemd의 bank-agent 서비스로 실행·재시작 관리 |
| Nginx | Nginx 사용 기록 |
| HTTPS는 다음 단계 | Certbot 인증서·HTTPS·자동 갱신 테스트 완료 기록 |

README에는 처음 Caddy를 계획한 내용과 Nginx로 바꾼 내용이 함께 남아 있었다. 작업일지의 이후 변경 기록에 따라 최종 설명은 Nginx + Certbot 기준으로 했다. 기록에는 한 대의 작은 서버에 여러 프로젝트를 운영하려는 목적, 스왑 준비, Reserved 공인 IP, 로컬에서 코드를 묶어 SSH로 전달한 방식도 있었다. 무료 자원 한도나 현재 요금을 검증한 것은 아니므로 과거 기록의 수치를 최신 정책처럼 재인용하지 않는다.

> ➕ **더 알아두기 — AI가 빨리 했다는 뜻**
> 이전에 AI가 짧은 시간에 준비했다면 패키지 설치·방화벽·실행 서비스·Nginx·인증서 설정을 묶어서 대신 수행했을 수 있다. 필요한 운영 조건이 사라진 것이 아니라 사용자가 각 단계를 따로 입력하고 확인하지 않았던 것이다. 이번에는 학습을 위해 과정을 나눠 설명하고 결과를 직접 확인했다. 다만 당시 Claude의 실제 실행 내역 전체를 본 것은 아니므로 정확한 소요 시간이나 모든 자동화 방식을 단정하지 않는다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> 클라이언트·서버 구조, 방화벽 접근 통제, TLS 서버 인증, 서비스 가용성과 프로세스 운영을 연결한다. 프록시는 앱 로직 자체와 다르며, HTTPS는 HTTP 통신을 TLS로 보호하는 방식이다. 제품 이름을 외우는 것보다 어떤 요구를 어떤 계층에서 해결하는지 설명하는 것이 중요하다.

## 정리

- HTTP는 통신 방식, REST는 API 설계 방식, Nginx는 요청을 처리·전달하는 프로그램이다.
- 퍼블릭 액세스·네트워크 경로·보안 그룹·DB 인증은 서로 다른 조건이다.
- 0.0.0.0/0은 모든 IPv4 소스 범위이고 브로드캐스트 전송을 뜻하지 않는다.
- FastAPI만으로 HTTP API는 동작한다. 교안은 외부 창구와 이후 HTTPS를 Nginx에 맡기는 구조다.
- nginx.conf는 처리 규칙이고 Compose는 Nginx 컨테이너와 파일·포트 연결을 실행하는 설정이다.
- EC2 내부 Nginx 경유 /health 성공까지 확인했다. HTTPS와 외부 브라우저 결과는 구분한다.
- 자동 할당 EC2 퍼블릭 IP를 고정이라고 가정하지 않는다.
- Oracle에도 비슷한 네트워크·Nginx·인증서·실행 관리 기록이 있었다. AI가 대신 처리한 것과 사람이 단계별로 배우는 것의 차이를 구분한다.
