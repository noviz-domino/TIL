## 주제 1: View란

- 뷰는 **저장된 SELECT 쿼리를 테이블처럼 조회할 수 있게 만든 DB 객체**이다.
- **조회 결과 데이터를 따로 저장하지 않으며**, 뷰를 조회할 때 **원본 테이블의 데이터를 바탕으로** 결과를 반환한다.
- **복잡한 쿼리를 단순화**하고, **필요한 행과 컬럼만 제공**하는 데 사용한다.

### 주요 특징 및 장단점

| | 내용 |
|---|---|
| **보안성** | 특정 컬럼이나 행만을 공개하여 사용자에게 **민감한 정보 노출을 방지**한다 |
| **편의성** | 반복되는 복잡한 조인이나 서브쿼리문을 **미리 정의**해 두어 사용 효율을 높인다 |
| **제한사항** | **인덱스를 직접 가질 수 없다.** 단순한 뷰는 삽입·수정·삭제가 가능하지만, **조인이나 집계 등을 포함한 뷰는 기본적으로 읽기 전용**이다 |

> ➕ **더 알아두기 — 뷰를 쉽게 이해하기**
> (수업에서 나온 설명이 아니라 대화 중 정리한 설명이다.) **자주 쓰는 SELECT에 이름을 붙여 DB에 저장해 둔 것**이다. 저장되는 것은 **쿼리(정의)** 이고, **결과 데이터는 저장되지 않으며** 조회할 때마다 원본에서 새로 계산한다. 그래서 원본 테이블이 바뀌면 뷰의 결과도 자동으로 바뀐다. (JOIN이나 `GROUP BY` 결과가 저장되지 않는 임시 결과인 것과 같은 성질이다.)

> 📝 **기사 시험 포인트** (정보처리기사, 확실도는 항목마다 표시)
> - **뷰의 특징** (확실도: 높음): **논리적 데이터 독립성**(테이블 구조가 바뀌어도 응용 프로그램에 미치는 영향을 줄임), **보안 강화**(일부만 공개), **복잡한 질의 단순화**, 물리적으로 존재하지 않는 **가상 테이블**(정의만 저장)
> - **뷰의 제약** (확실도: 높음): 독립적인 **인덱스를 가질 수 없고**, 조인·집계·`DISTINCT` 등이 포함되면 **갱신이 제한**되는 경우가 있다. 정의를 `ALTER`로 바꾸는 것이 가능한지는 DBMS마다 다를 수 있다. (확실도: 중간)
> - `CREATE VIEW`, `DROP VIEW`는 **DDL**이다. `DROP VIEW`에 `CASCADE`(의존하는 것도 함께 삭제)/`RESTRICT`(의존하는 것이 있으면 거부) 옵션이 있는 것으로 알고 있다. (확실도: 중간, 수업에는 없다.)

> 📝 **기사 시험 포인트** (정보보안기사, 확실도: 중간)
> 원본 테이블의 조회 권한은 막고 **뷰에만 조회 권한**을 주어 민감한 정보를 숨기는 것은 DB **접근 통제**의 대표 기법으로 알고 있다. 수업의 보안성 항목과 같다. 정보보안기사에서 어떤 형태로 출제되는지는 확인하지 못했다.

## 주제 2: 뷰의 생성 및 관리

### 뷰 생성 (CREATE VIEW)

```sql
CREATE VIEW view_name AS
SELECT column1, column2
FROM table_name
WHERE condition;
```

### 뷰 삭제 (DROP VIEW)

- **테이블 데이터는 영향을 받지 않는다.**

```sql
DROP VIEW view_name;
```

## 주제 3: 보안 및 접근 제어

원본 테이블의 **직접 조회 권한을 제한**하고 **뷰에 조회 권한을 부여**하면, 필요한 정보만 공개할 수 있다.

**고객의 이름과 이메일은 제외하고, 고객 ID와 활성화 여부만 조회하는 뷰**

```sql
CREATE VIEW customer_status AS
SELECT customer_id, activebool
FROM customer;
```

```sql
SELECT * FROM customer_status;
```

## 주제 4: 복잡한 조인 쿼리 단순화

**영화 제목과 카테고리명을 결합한 뷰**: 매번 3개의 테이블을 조인할 필요 없이 생성된 뷰를 통해 영화별 카테고리를 조회할 수 있다.

```sql
CREATE VIEW film_with_category AS
SELECT film.title, category.name AS category_name
FROM film
JOIN film_category ON film.film_id = film_category.film_id
JOIN category ON category.category_id = film_category.category_id;
```

```sql
SELECT title
FROM film_with_category
WHERE category_name = 'Action';
```

## 주제 5: 예제

**영화 제목과 출연 배우 이름을 조회하는 뷰**

```sql
CREATE VIEW film_actor_info AS
SELECT f.title, a.first_name, a.last_name
FROM film f
JOIN film_actor fa ON f.film_id = fa.film_id
JOIN actor a ON fa.actor_id = a.actor_id;
```

`film_actor_info` 뷰로 `first_name`이 'PENELOPE'인 배우의 출연 영화 제목 조회

```sql
SELECT title
FROM film_actor_info
WHERE first_name = 'PENELOPE';
```

**뷰를 사용하지 않고 같은 결과를 조회하는 SQL**

```sql
SELECT f.title
FROM film f
JOIN film_actor fa ON f.film_id = fa.film_id
JOIN actor a ON fa.actor_id = a.actor_id
WHERE a.first_name = 'PENELOPE';
```

**2005년 5월에 발생한 대여 기록만 조회하는 뷰**

```sql
CREATE VIEW rental_may_2005 AS
SELECT *
FROM rental
WHERE rental_date >= '2005-05-01' AND rental_date < '2005-06-01';
```

`rental_may_2005` 뷰와 `customer` 테이블을 조인하여 고객 이름과 대여 일시 조회

```sql
SELECT c.first_name, c.last_name, r.rental_date
FROM rental_may_2005 r
JOIN customer c ON r.customer_id = c.customer_id;
```

> ➕ **더 알아두기 — 예제 읽기**
> 뷰를 쓰면 `WHERE first_name = 'PENELOPE'`만 쓰면 되지만, 뷰 없이는 JOIN 두 번을 다 써야 한다. **뷰는 반복되는 쿼리의 단축 도구**이다. 마지막 예제는 **뷰를 테이블처럼 `JOIN`에 쓸 수 있다**는 것을 보여 준다. `rental_date >= '2005-05-01' AND rental_date < '2005-06-01'`처럼 **시작은 이상, 끝은 미만**으로 월을 자르는 방식은 날짜 범위를 빠짐없이 나누는 일반적인 방법이다. (`BETWEEN`은 양 끝을 포함한다.)

## 주제 6: 뷰가 레퍼런스에 가까운 이유와 수정 (수업 외 · 대화 중 보충)

> ♻️ 처음엔 **뷰를 값을 복사해 따로 저장하는 call by value 방식**으로 알았으나, **뷰는 데이터를 복사해 저장하지 않고 원본 테이블을 참조(레퍼런스)** 한다. 그래서 단순한 뷰를 통한 삽입·수정·삭제가 원본에 반영되고, 원본이 바뀌면 뷰의 결과도 바로 바뀐다. (수업의 "단순한 뷰는 삽입·수정·삭제가 가능"이 이 뜻이다.)

> ➕ **더 알아두기 — 레퍼런스 비유와 한계**
>
> | 방식 | 프로그래밍 비유 | 뷰 |
> |---|---|---|
> | 값 복사 (call by value) | 데이터를 복사해 따로 가짐 | ❌ 복사해 저장하지 않음 |
> | 참조 (reference) | 원본을 가리킴 | ✅ 원본 테이블을 가리킴 |
>
> ```sql
> UPDATE customer_status SET activebool = false WHERE customer_id = 1;
> -- 실제로 바뀌는 것은 뷰가 아니라 원본 customer 테이블
> ```
>
> (위 `UPDATE` 예시는 대화 중 만든 것이며 직접 실행해서 확인한다.)
>
> - 비유가 완벽하지는 않다. 뷰의 정체는 데이터에 대한 포인터가 아니라 **저장된 SELECT 쿼리(정의)** 이고, 조회할 때 그 쿼리를 **매번 다시 실행**해서 결과를 만든다. 수정은 **단순한 뷰만** 가능하다.
> - **조인·집계가 들어간 뷰가 읽기 전용인 이유**: 결과의 한 줄이 **여러 원본 행(또는 계산값)** 에서 왔기 때문에, 그 줄을 고쳐도 원본의 어느 행을 어떻게 고칠지 정할 수 없다. (`GROUP BY` 결과의 `125`가 어느 나라의 값인지 알 수 없는 것과 같은 이유이다.) 그래서 뷰는 수정보다 **조회용**이 주 용도이다.
> - PostgreSQL에서 단순한 뷰(단일 테이블, 집계 없음)는 자동으로 갱신 가능한 것으로 알고 있다. (확실도: 높음~중간)

> ➕ **더 알아두기 — 구체화 뷰 (MATERIALIZED VIEW)**
> 값을 **복사해서 저장하는 뷰**도 있다. **구체화 뷰**는 쿼리 결과를 실제로 저장해 두고 필요할 때 **새로 고침(`REFRESH`)** 하는 방식이다. call by value에 가까운 쪽이다.
>
> | | 일반 뷰 (이번 레슨) | 구체화 뷰 |
> |---|---|---|
> | 데이터 저장 | ❌ | ✅ (결과를 복사해 저장) |
> | 원본 변경 반영 | **즉시** (조회할 때마다 계산) | **새로 고침해야** 반영 |
> | 속도 | 조회마다 계산 | 저장된 결과를 읽어 빠름 |
>
> (PostgreSQL 일반 지식이며 수업에서 나오면 보완한다. 확실도: 높음~중간)

## 주제 7: 왜 SQL 파일 대신 뷰로 저장하는가 (수업 외 · 대화 중 보충)

> ➕ **더 알아두기 — SQL 파일 vs 뷰**
>
> | | SQL 파일에 저장 | 뷰(View)로 저장 |
> |---|---|---|
> | 쓰는 방법 | 파일을 열어 **복사해서 실행** | `SELECT * FROM 뷰이름`으로 **바로 조회** |
> | 위에 조건 더 붙이기 | 쿼리 본문을 직접 고쳐야 함 | `WHERE category_name = 'Action'`처럼 **뒤에 덧붙이면 끝** |
> | 다른 쿼리와 JOIN | 서브쿼리로 통째로 붙여 넣어야 함 | 뷰를 **테이블처럼 JOIN** |
> | **보안(권한)** | 파일을 가진 사람은 원본 쿼리 전체를 봄 | 원본 테이블 권한은 막고 **뷰만 공개** 가능 |
> | 정의를 바꿀 때 | 파일을 쓰는 모든 사람이 새로 받아 써야 함 | **DB의 뷰 하나만** 고치면 모두에게 반영 |
> | 사용 범위 | 파일을 아는 사람 | **DB에 접속한 모든 사용자·프로그램·도구** |
>
> - 가장 큰 차이는 **DB 안의 객체가 되느냐**이다. SQL 파일은 DB가 모르는 텍스트이고, 뷰는 DB가 관리하는 이름 붙은 객체라서 권한 관리, 조회, JOIN이 모두 가능하다.
> - 보안 예제에서 `customer_status` 뷰만 공개하고 `customer` 테이블 권한을 주지 않으면 이름·이메일을 볼 방법이 없다. SQL 파일은 받은 사람이 쿼리를 고쳐 원본을 조회하면 막을 수 없다. (앞에서 배운 `GRANT`(DCL)와 이어진다.)
> - 정의를 한 곳만 고치면 된다는 점은 정규화의 "같은 정보를 두 군데 이상 적지 않는다"와 같은 정신이다.
> - 한 번만 쓰고 말 쿼리는 뷰를 만들 필요가 없다. 버전 관리(git)는 SQL 파일이 편해서, 뷰의 `CREATE VIEW` 문을 SQL 파일로 관리하는 경우가 많고 둘을 같이 쓰는 것이 흔하다.
> - 서브쿼리와 `WITH`는 **한 문장 안에서만** 이름이 살아 있고, 뷰는 **DB에 계속 남는다.** 뷰는 그 저장판으로 볼 수 있다.

## 정리

- **뷰**는 저장된 SELECT 쿼리를 테이블처럼 조회하게 하는 DB 객체이다. **결과 데이터는 저장하지 않고** 조회할 때 원본을 바탕으로 결과를 만든다.
- **장점**: 보안성(일부 컬럼·행만 공개), 편의성(반복되는 복잡한 JOIN·서브쿼리를 미리 정의). **제한**: 인덱스를 직접 가질 수 없고, 조인·집계가 있는 뷰는 기본적으로 읽기 전용(단순한 뷰는 삽입·수정·삭제 가능).
- **생성/삭제**: `CREATE VIEW 이름 AS SELECT …;`, `DROP VIEW 이름;` (테이블 데이터는 영향 없음)
- **보안**: 원본 테이블의 직접 조회 권한을 제한하고 뷰에 조회 권한을 부여한다. (예: 이름·이메일을 뺀 `customer_status`)
- **단순화**: 3개 테이블 조인을 `film_with_category` 뷰로 저장해 `WHERE category_name = 'Action'`만 쓰면 된다. 뷰는 테이블처럼 `JOIN`에도 쓴다.
- (수업 외) 뷰는 데이터를 복사하지 않고 원본을 **참조(레퍼런스)** 하므로 수정이 원본에 반영되고 원본 변경이 뷰에 즉시 반영된다. 값을 저장하는 것은 구체화 뷰이다. SQL 파일과 달리 DB 객체라 권한 제어와 한 곳 수정이 가능하다.
