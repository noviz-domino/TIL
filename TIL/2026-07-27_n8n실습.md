## 1. LLM과 컨텍스트 엔지니어링 복습

> 09:00–10:00 저번 시간 수업 복습 — 컨텍스트엔지니어링에 대한 기본개념 복습

LLM은 다음 토큰의 확률을 예측하는 시스템이다.

과거에는 프롬프트 엔지니어를 1억씩 주고 뽑았으나 지금은 없다. 지금은 **하네스 엔지니어링**과 **컨텍스트 엔지니어링**으로 표현이 바뀌었다.

둘은 조금 다른데, 그 차이는 단기 기억을 담당하는 컨텍스트 메모리를 어떻게 활용하느냐에 있는 것 같다.

다만 웹에서 사용하면 컨텍스트 메모리를 40% 정도밖에 사용하지 못한다고 한다. 오픈AI나 구글에서 웹으로 접속할 때 자신들이 미리 가이드해둔 기본 컨텍스트가 입력되기 때문이다. 컨텍스트 메모리가 1M(100만 토큰)라고 하면 소설책 6~7권 분량인데, 여기에 개인정보나 기존 대화가 자동으로 들어가게 되는 듯하다.

PC로 사용한다고 해도 기본적으로 로드하는 컨텍스트가 있기 때문에 100% 사용할 수는 없다. 오로지 100% 사용하는 방법은 API뿐인데, API는 한 번 사용할 때마다 사용량에 대해 요금을 부과하기 때문에 그것대로 부담이다.

> ➕ **더 알아두기**
> **하네스(harness)**는 원래 말에 씌우는 마구(馬具)를 뜻한다. AI에서는 모델 자체가 아니라, 모델을 **감싸서 일하게 만드는 바깥 장치 전체**(어떤 도구를 쥐여줄지, 어떤 순서로 부를지, 무엇을 읽히고 무엇을 기억시킬지)를 가리킨다.
> 그래서 셋의 관계는 이렇게 정리된다.
> - **프롬프트 엔지니어링** — 한 번의 질문을 잘 쓰는 기술
> - **컨텍스트 엔지니어링** — 무엇을 얼마나 넣어줄지 설계하는 기술
> - **하네스 엔지니어링** — 모델이 도구를 쓰고 여러 단계를 스스로 돌게끔 시스템을 짜는 기술
>
> 웹 채팅에서 컨텍스트를 다 못 쓰는 이유가 되는 그 "미리 들어가는 기본 컨텍스트"를 **시스템 프롬프트**라고 한다.

## 2. 프롬프트 엔지니어링

> 10:00–11:00 프롬프트엔지니어링의 개념

### 2.1 지금도 배워야 하는 이유

지금은 프롬프트 엔지니어링을 쓰지 않아도 되지만, 그동안 그 방식으로 개발이 진행돼 왔기 때문에 랭체인(LangChain)과 랭그래프(LangGraph)를 학습하려면 배워야 한다.

랭체인과 랭그래프는 AI에 구조를 덧씌우는 것이다.

### 2.2 프롬프트 엔지니어링의 기초

**좋은 프롬프트의 4요소: 역할, 맥락, 작업, 형식**

* **역할** — "너는 ○○야" (안 하면 일반인 수준의 밋밋한 답변이 나온다)
* **맥락** — "이건 신입 교육용 자료야. 대상은 비전공자 5명이야." (대상과 수준이 맞아야 한다)
* **작업** — "아래 약관에서 불리한 고객 조항 3개를 찾아줘" (어떤 일을 해야 하는가)
* **형식** — "표로 만들어서 각 항목이 2줄씩, 근거 조항 번호를 표시해서 만들어줘" (안 하면 매번 다른 형태로 나와서 후처리가 불가능하다)

### 2.3 프롬프트 기법

* **zero-shot** — 예시 없이 지시만 시키는 것
* **few-shot** — 예시를 몇 개 주고 기준을 보여주는 것
* **Tree-of-Thought** — 갈래를 펼쳐서 탐색하게 하는 것 (서로 다른 접근 3가지를 제안하고, 각각의 장단점을 평가한 뒤, 최선안을 골라 상세화해)

**시스템 프롬프트는 규칙을 적는 자리이고, 사용자 프롬프트는 데이터를 적는 자리다.**

> ➕ **더 알아두기**
> few-shot의 "shot"은 **예시 하나**를 뜻한다. 예시 1개면 one-shot, 2~5개면 few-shot이다. 예시를 주면 말로 설명하기 힘든 기준(어디까지가 '긍정'인지 같은 것)을 한 번에 전달할 수 있어서, 분류·형식 맞추기 작업에서 특히 효과가 크다.
>
> 시스템 프롬프트와 사용자 프롬프트를 나누는 이유도 여기에 있다. **규칙은 한 번만 넣고 계속 재사용**하고, 데이터만 바꿔 가며 여러 번 호출하는 구조가 되기 때문이다. 아래 2.4 실습이 정확히 그 구조다.

### 2.4 실습 — 배달 후기 분류 시스템 프롬프트

> 11:00–12:00 실습

상황 설정은 이렇다. 나는 배달잇츠의 엔지니어이고, 쌓여 있는 후기 데이터를 시스템에 넣으려고 한다. 이 후기 데이터를 AI를 이용해 분류하는 시스템 프롬프트를 만들어야 한다.

결과는 다음과 같이 분류되어야 한다.

- 카테고리
- 긍정/부정
- 배달 별점 (5점 만점)
- 한 줄 요약 (30자 이내)

내가 한 것 주소: https://app.notion.com/p/codecohort/3aa32b3ccea8801282adca7e0aa4ba60?source=copy_link

**사용한 프롬프트**

```text
시스템 프롬프트 작성 할꺼야. 너는 후기를 분류해서 정리하는 CX 전문가야. 아래 후기를 분석해서 데이터를 분류해줘.

#임무
입력된 고객 리뷰를 확인하고 분석해서 지정된 JSON 형식으로 응답한다.

#분류기준
- category: (일반적인 음식 분류 기준)
- sentiment : 긍정 / 부정
- star_rating : (0~5로 숫자가 높을수록 만족도가 높음, 만족도를 예상하여 입력 )
- summary: (30자 이내)

#규칙 
- json 외의 텍스트를 절대 출력하지 않는다.
-별점의 판단기준이 애매하면 별점은 0.5점을 뺀다.
-작성되지 않은 내용은 추측하거나 추가해선 안된다.

#출력 예시
{"category": "중식", "sentiment" : "긍정", "star_rating" :  "4.5", "summary" : "짜장면에 들어간 투플러스 소고기가 만족스럽다는 내용"}
```

> ➕ **더 알아두기**
> 이 프롬프트가 잘 짜인 이유는 2.2의 4요소가 전부 들어 있기 때문이다. **역할**(CX 전문가) → **작업**(#임무) → **형식**(#분류기준, #출력 예시) → **규칙**(#규칙) 순서다.
> 특히 `#출력 예시`가 있는 것이 중요하다. 이게 바로 2.3의 **one-shot**이다. 원하는 JSON 모양을 말로 설명하는 것보다 예시 한 줄을 보여주는 쪽이 훨씬 정확하게 전달된다.
> `json 외의 텍스트를 절대 출력하지 않는다`도 실무에서 꼭 필요한 규칙이다. AI는 습관적으로 ```` ```json ```` 같은 코드블록 표시나 "알겠습니다"를 붙이는데, 그러면 프로그램이 JSON으로 읽지 못하고 파싱 에러가 난다.

## 3. 노코드 자동화 툴과 n8n

> 13:00–14:00 n6n , make 등의 노코드 자동화 툴 설명, 클로드 코드 결제 설명.

### 3.1 노코드 툴이란

디자인 쪽에 미리캔버스나 캔바가 있다면, n8n은 코드 없이 자동화를 할 수 있게 만들어주는 도구다.

둘 다 전공자가 아니거나 전문 지식이 없어도 사용할 수 있다.

### 3.2 바이브코딩 vs n8n

클로드로 하는 바이브코딩은 블랙박스라서 안의 로직을 한 번에 확인하거나 문제를 찾기 어렵다.

반면 n8n은 자동화 시스템을 구축하면서도 코드를 직접 수정할 수 있는 기능을 함께 제공한다.

> ➕ **더 알아두기**
> n8n이 블랙박스가 아닌 이유는 **각 노드마다 들어온 데이터와 나간 데이터를 눈으로 볼 수 있기 때문**이다. 6개 노드 중 어디서 값이 틀어졌는지 클릭 한 번으로 확인된다.
> 그래서 다음 날 배우는 "한 노드씩 붙이고 테스트하기"가 가능해진다. 바이브코딩은 이게 안 되니 오류가 나면 전체를 뒤져야 한다.

### 3.3 무료(셀프호스팅) vs 유료(n8n cloud)

n8n은 유료이기도 하고 무료이기도 하다. 로컬로 자기 컴퓨터에 깔아서 실행하겠다면 무료로 쓸 수 있다. 다만 컴퓨터를 24시간 계속 켜둘 수 없다는 문제가 있고, 설정과 서버 유지보수 등이 필요하다.

설치하기 어려운 환경이거나 365일 돌아가는 자동화가 필요하다면, 유료 버전인 n8n cloud를 결제해서 쓰면 된다.

**셀프호스팅**: 내가 직접 서버를 구축해서 사용하고, 유지보수 등도 알아서 해야 하는 방식.

n8n 2주 무료 체험 버전에 가입했다. 7월 27일 가입 후 2주 동안 사용 가능하다.

로그인하고 왼쪽 메뉴바에서 '퍼스널(Personal)'을 누르면 들어갈 수 있다.

> ➕ **더 알아두기**
> "24시간 켜둘 수 없다"가 셀프호스팅의 진짜 약점이다. n8n의 자동화는 **정해진 시간에 스스로 실행**되는 것이 핵심인데, 내 컴퓨터가 꺼져 있으면 그 시각의 실행은 그냥 건너뛴다.
> 그래서 실무에서는 셀프호스팅을 하더라도 내 노트북이 아니라 **항상 켜져 있는 서버**(클라우드 VPS 등)에 올린다. 즉 무료의 대가는 돈이 아니라 **서버를 직접 관리하는 수고**다.

## 4. n8n 실습 — 구글 폼 설문 응답 자동화

> 14:00–15:00 n8n실습
> 15:00–18:00 실습 과제 day02 — 구글폼을 이용한 스프래드시트용 메일 자동화 만들기.

기본 노드를 생성하고, 지메일로 스프레드시트가 갱신될 때 메일을 전송해보는 실습을 했다.

n8n 기본 사용법을 익히고, 노드 생성과 구글 폼을 이용한 스프레드시트 연동 메일 자동화를 만들었다.

### 4.1 🚀 전체 프로세스 개요

3개의 개별 구글 폼(1번: 회원 정보, 2번: 취미/음식, 3번: 영화) 응답을 **구글 시트(통합 시트) 하나로 수집 및 업데이트**하고, 조건에 따라 안내 메일을 발송하는 자동화 워크플로우.

```text
[폼 1/2/3 트리거]
       ↓
[Skip empty rows] (빈 행 제거 / 예외 처리)
       ↓
[Append or Update row] (통합 시트 업데이트)
       ↓
[Get row(s) in sheet] ➔ [If 노드] ➔ [Gmail 발송]
```

### 4.2 🛠️ 핵심 구현 및 노드별 설정

**① 트리거 예외 처리 (Skip empty rows 노드)**

  * 목적: 구글 시트에서 발생할 수 있는, 데이터 없는 빈 행(Blank Row)을 미리 걸러낸다.
  * 설정 (Filter 노드):
    * Left Value: {{ $json['이메일 주소'] }}
    * Condition: is not empty
  * 필요성: 구글 시트에 빈 줄이 수집되면 매칭 기준값(이메일 주소)이 비어 있어, 후속 노드에서 `The 'Column to Match On' parameter is required` 에러가 발생한다.

**② 통합 시트 데이터 업데이트 (Append or Update Row)**

  * 1번 폼 (최초 제출):
    * Operation: Append Row
    * 1번 폼을 제출하면 통합 시트에 새로운 행(Row)을 최초로 생성한다.
  * 2번 & 3번 폼 (추가 제출):
    * Operation: Append or Update Row
    * Column to match on: 이메일 주소
    * 1번 폼을 통해 시트에 미리 등록된 이메일을 찾아, 해당 사용자의 행에 취미/음식/영화 정보를 추가로 기록한다.

> ➕ **더 알아두기**
> 여기서 이메일 주소가 **키(key)** 역할을 한다. 흩어진 3개의 폼 응답을 한 사람의 데이터로 묶어주는 유일한 기준이기 때문이다.
> 데이터베이스에서 이 역할을 하는 열을 **기본 키(Primary Key)**라고 부른다. 나중에 DB를 배울 때 나오는 개념을, n8n에서 `Column to match on`이라는 이름으로 먼저 써본 셈이다.

**③ 1번 폼 미제출자 예외 처리 (검문소)**

  * 문제 상황: 1번 폼(이름/이메일)을 쓰지 않고 2·3번 폼을 먼저 쓴 사용자에게는 메일 발송을 막아야 한다.
  * 해결 방법:
    1. Get row(s) in sheet 노드로 통합 시트를 조회한다.
    1. If 노드에서 시트 내 이름 항목이 있는지 확인한다 ({{ $json['이름'] }} is not empty).
    1. 1번 폼을 쓰지 않은 사용자는 이름 데이터가 없으므로 If 노드에서 False로 판정되어, 메일 발송 없이 자동 종료된다.

### 4.3 💡 트러블슈팅 (주요 에러 및 원인 정리)

**❓ Issue 1: The 'Column to Match On' parameter is required 에러 발생**

  * 원인:
    1. Append or Update Row를 사용할 때, 매칭 기준(Column to match on) 열이 UI상에서 파라미터 등록이 완료되지 않은 상태였다.
    1. 트리거를 통해 빈 줄(Blank Row, 이메일이 빈 값인 행) 데이터가 들어오면서 매칭 대상 값을 찾지 못했다.
  * 해결:
    * 트리거 바로 뒤에 Skip empty rows (Filter 노드)를 추가해서, 이메일이 있는 정상 데이터만 통과되도록 조치했다.

**❓ Issue 2: 개별 응답 시트에 상단 빈 공간(행)이 생기는 현상**

  * 원인:
    * 구글 폼 연동 시트는 데이터를 추가할 때 아래쪽에 새로운 행을 물리적으로 삽입(Insert)한다.
    * 키보드의 Delete 키는 셀 내부의 텍스트만 삭제할 뿐 행 자체를 지우지 않는다. 그래서 구글 폼은 빈 행 아래쪽에 응답을 계속 쌓는다.
  * 해결:
    * 구글 시트에서 빈 행 번호를 마우스 우클릭한 뒤 '행 삭제'를 실행해야, 물리적으로 아래 행들이 위로 바짝 당겨진다.

> ➕ **더 알아두기**
> 두 이슈는 사실 같은 뿌리에서 나온 문제다. **"비어 보이는 것"과 "없는 것"은 다르다.**
> 셀의 글자를 지운 행은 사람 눈에는 비어 보이지만 시트에는 여전히 **존재하는 행**이고, 트리거는 그 행도 데이터로 읽어서 흘려보낸다. Issue 1의 에러가 바로 그 결과다.
> 그래서 자동화를 만들 때는 항상 **"들어오면 안 되는 데이터가 들어왔을 때"를 먼저 막는 노드**를 트리거 바로 뒤에 두는 것이 정석이다. 이걸 방어적 프로그래밍이라고 부른다.
