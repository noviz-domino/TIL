## 1. AI 에이전트 기획, TDD, 신입 개발자 경쟁력, 환경변수 관리

### 1.1 AI 에이전트 기획의 중요성과 TDD

- **AI 에이전트와 기획**: AI 에이전트는 자율적으로 판단하고 행동하므로, 기획(설계)이 정교하지 않으면 의도하지 않은 동작을 하거나 자원(예산 등)을 낭비하기 쉽다.
- **TDD (Test-Driven Development, 테스트 주도 개발)**: 코드를 작성하기 전에 테스트 코드를 먼저 작성하는 개발 방식이다.
  - 진행 순서: `테스트 작성 → 실패 확인 → 본 코드 작성 → 테스트 통과`
- **AI 개발에서의 TDD 역할**: AI 에이전트의 환각(Hallucination)이나 잘못된 도구 호출을 방지하기 위한 명확한 동작 검증 기준(Pass/Fail) 역할을 한다.

### 1.2 요즘 채용 시장과 신입 개발자의 경쟁력

- **시장 요구사항 (풀스택 & 문제 해결 능력)**: 단순히 모든 분야의 기술을 완전히 외우는 것보다, 프런트엔드·백엔드를 가리지 않고 주어진 문제를 기술적으로 해결할 수 있는 역량을 요구한다.
- **경쟁력 확보 전략**:
  1. **깊은 기본기 하나 확보**: 백엔드나 프런트엔드 중 하나를 깊게 이해하여 확장 가능성을 보여준다.
  2. **의사결정 과정 기록**: 문제에 접근한 논리, 기술 선택 이유, 시행착오 및 해결 과정을 TIL이나 PR 등에 문서화한다.

### 1.3 환경별 환경변수(Key) 분리 관리

- **환경 분리 이유**: 로컬(Local), 개발(Dev), 운영(Prod) 환경의 키값을 각각 다르게 발급받아 관리해야 한다.
  - **안전성 (사고 방지)**: 개발 및 테스트 중 실수로 프로덕션 DB나 결제 서비스 등 실제 고객 데이터에 영향을 주는 것을 방지한다.
  - **비용 및 권한 통제**: 환경별로 API 요청 제한, 접근 권한, 비용 설정을 다르게 적용한다.
- **실무 활용 방식**: `DB_URL`, `OPENAI_API_KEY`, `PAYMENT_SECRET_KEY` 등을 `.env.local`, `.env.development`, `.env.production` 등으로 분리하여 환경에 맞게 주입한다.

### 1.4 팀 프로젝트 시 환경변수 공유 방법

- **기본 원칙**: 키가 들어있는 파일(`.env`)은 **절대 Git에 커밋하거나 공유 레포지토리에 올려서는 안 된다.**
- **공유 방식**:
  1. **소규모 팀**: Git에는 키 이름만 정의된 `.env.example` 파일만 공유하고, 실제 값은 암호 관리 툴(1Password)이나 보안 채널을 통해 개별 전달하여 로컬 `.env`에 저장한다.
  2. **중규모 이상 팀**: Vault, AWS Secrets Manager, Doppler 등 중앙 환경변수·비밀 관리 시스템을 사용해 로그인 및 명령어로 자동 동기화한다.

**⚠️ 헷갈리기 쉬운 점**

- `.env` 파일을 `.gitignore`에 추가하지 않고 GitHub 퍼블릭 레포지토리에 올리면, 자원 탐색 봇에 의해 API 키가 유출되어 심각한 비용 폭탄이나 보안 사고가 발생할 수 있다.

> ➕ **더 알아두기**
> 7월 29일에 배운 `.gitignore`/`.env` 규칙이 여기서 "환경별로" 한 단계 더 세분화된 것이다. 그때는 "키를 코드에 안 쓴다"가 전부였다면, 오늘은 **같은 종류의 키라도 로컬·개발·운영을 다른 값으로 나눈다**는 것이 추가됐다. 이유는 같다 — 로컬에서 실험하다 실수로 운영 DB를 건드리는 사고를 막기 위해서다.

## 2. URL 보안 난독화와 AI 기반 디자인 프로세스

### 2.1 URL 경로 난독화 (Security through Obscurity)

- **URL의 특성**: URL은 브라우저 주소창이나 네트워크 로그 등에 노출되므로, 그 자체를 완벽한 보안 요소(Secret)로 신뢰해서는 안 된다.
- **어드민 경로 난독화 (Obscure Path)**: `aaa.com/a8f93e/admin`처럼 URL 경로에 해시값이나 난수를 넣어, 관리자 페이지 경로를 무차별 대입(Brute Force) 공격으로부터 숨기는 기법이다.
- **실무 보안의 본질**: 경로 난독화는 공격 시도를 늦추는 보조 수단일 뿐이며, IP 접근 제한, 2차 인증(MFA), 엄격한 권한 제어(RBAC)가 필수적이다.

> ➕ **더 알아두기**
> 이 개념의 정식 이름이 그대로 소제목에 있다. **"Security through Obscurity"**(모호함을 통한 보안)는 보안 업계에서 절반은 농담, 절반은 경고로 쓰이는 표현이다. "숨겨놨으니 안전하다"는 가정 자체가 위험하다는 뜻이다. URL은 브라우저 히스토리, 프록시 로그, `Referer` 헤더를 통해 생각보다 쉽게 새어 나간다.

### 2.2 AI 기반 디자인 프로세스

- **도입 배경**: 카카오 등 기업에서 생산성 증대, 시안 작업 시간 단축, 부서 간 의사소통 비용 절감을 위해 AI 디자인 프로세스를 전사적으로 추진한다.
- **주요 흐름**:
  1. **아이데이션/무드보드**: AI를 활용해 이미지 시안을 빠르게 추출한다.
  2. **프로토타이핑**: 텍스트 기획서를 UI 와이어프레임 및 디자인 시스템으로 전환한다.
  3. **코드 연동**: 디자인 요소를 HTML/CSS 코드로 전환하여 개발 협업 시간을 단축한다.
- **무드보드 (Moodboard)**: 프로젝트의 전체적인 분위기, 콘셉트, 감성을 한눈에 보여주는 이미지·색상·텍스트 모음판이다. 말로 설명하기 어려운 디자인 톤앤매너에 대한 오해를 줄여준다.
- **핀터레스트 (Pinterest) 활용**: 전 세계 크리에이터들의 검증된 이미지 레퍼런스가 모인 플랫폼으로, AI(미드저니 등)에 고퀄리티 프롬프트를 전달하기 위한 참고 자료로 필수적으로 활용된다.

### 2.3 AI와의 협업 프롬프트 패턴 (`.md` 활용)

- **협업 기획 방식**: AI에게 단일 명령만 내리기보다, 참고 스크린샷과 시장 조사 자료 등 명확한 맥락(Context)을 제공하여 환각을 줄이고 완성도를 높인다.
- **지시어 패턴**:
  - 참고 자료(무드보드, 디자인 사진 등)를 `.md` 파일 형태로 제공한다.
  - AI에게 디자인 시스템 설계를 요청하며 "필요한 것이 있으면 나에게 질문하라"는 권한을 부여하여 짐작에 의한 오류를 방지한다.

### 2.4 Claude Design (베타 기능)

- **개념**: 클로드 챗 내에서 요구사항을 기반으로 시각적인 UI·디자인 시안을 바로 생성하고 편집할 수 있는 기능이다.
- **주의점**: 시각적 렌더링 및 복잡한 컴포넌트 구조 데이터를 처리하므로 **토큰(Token) 소비량이 매우 크다.** 비효율적인 연쇄 질문을 줄이고 핵심 위주로 요청해야 한다.

**⚠️ 헷갈리기 쉬운 점**

- **URL 숨기기 vs 보안**: Admin URL을 난독화했다고 해서 보안이 끝난 것이 아니다. 내부망 IP 제한이나 인증 체계 없이 URL만 숨기는 것에 의존하면, 로그 유출 시 바로 침해 사고로 이어진다.
- **AI 생성 방식**: "알아서 다 만들어줘" 방식보다, 레퍼런스(`.md`, 스크린샷)를 직접 첨부하고 대화형으로 고도화하는 것이 훨씬 정교한 결과물을 만든다.

## 3. Claude Code 스킬(Skills) 및 MCP 활용

### 3.1 Claude Code의 '스킬(Skills)' 개념

- **개념**: 클로드 코드(Claude Code)에 외부 도구 연결 및 사용자 정의 기능을 붙여 **새로운 능력(Custom Tools)을 추가하는 확장 기능**이다.
- **기능 및 역할**: 단순 파일 조작이나 기본 터미널 명령을 넘어, 실시간 웹 검색, DB 조회, 외부 서비스(Jira, GitHub 등) 연동 등 프로젝트 맞춤형 자동화 작업을 수행하게 한다.
- **대표 사례 (MCP 연동)**: Model Context Protocol(MCP) 기반의 외부 스킬(예: SearchPro 등)을 장착하면, AI가 학습 데이터 한계를 넘어 **실시간 구글·네이버 검색 스킬을 스스로 호출**하여 최신 정보를 수집하고 답변할 수 있다.

> ➕ **더 알아두기**
> 어제(8월 3일) 배운 MCP 정의와 겹쳐서 정리하면, **MCP는 "AI와 도구를 연결하는 통신 규격"**이고 **Skill은 "그 규격을 이용해 클로드 코드에 실제로 장착한 기능 하나하나"**다. MCP가 USB-C 포트라면, Skill은 그 포트에 꽂는 개별 USB 장치에 해당한다.

### 3.2 스킬 오남용 주의점 (무분별한 스킬 등록의 위험성)

- **스킬 등록 과다의 문제점**:
  1. **의도치 않은 오호출**: 명시적 지침이 부족하면, 프롬프트 맥락을 오해한 AI가 불필요하거나 엉뚱한 스킬(외부 API)을 멋대로 실행한다.
  2. **컨텍스트 및 토큰 낭비**: 등록된 스킬들의 도구 정의서(명세)가 요청마다 전달되므로, 질문 하나당 소비되는 토큰 비용이 급증한다.
- **실무적 관리 방법**: 꼭 필요한 필수 스킬 위주로 단출하게 관리하고, 각 스킬이 호출될 조건과 상황을 프롬프트·설정 파일에 상세히 명시하여 사용한다.

**⚠️ 헷갈리기 쉬운 점**

- **스킬은 다다익선이 아니다**: 스킬이 많을수록 AI가 똑똑해지는 것이 아니라, 선택지가 너무 많아져 환각(Hallucination) 호출이나 속도 저하, 토큰 낭비가 발생할 수 있으므로 최소한의 스킬만 엄선해서 등록해야 한다.

## 5. 컨텍스트 관리: 하네스 문서 다이어트 (실습 중 질문에 대한 강사 답변)

### 5.1 질문자의 문제와 상황

- **상황**: 새 세션을 열고 `.md` 파일만 읽혔는데, 시작부터 AI의 기억 용량(컨텍스트 윈도우)이 **25%나 차버렸다.**
- **질문자의 생각**: "문서가 너무 커서 그런가? AI를 시켜서 `.md` 파일을 요약·압축해야 하나?"

### 5.2 강사님 답변의 핵심 의미

1. **이전 대화 때문이 아니다**: 새 세션이므로 이전 대화 기록이 쌓인 문제가 아니다.
2. **원인은 '하네스(기본 설정) 문서'다**: 개발 도구(Cursor 등)가 세션을 열 때마다 **백그라운드에서 자동으로 읽어들이는 기본 규칙 파일(`.cursorrules` 등)이 너무 커서** 발생한 문제다.
3. **압축(요약)은 비추천한다**: AI로 내용을 요약·압축하면 핵심 변수명, 규칙, 파일 경로 등 중요한 세부 정보가 **유실**될 위험이 크다.

### 5.3 압축 없는 '문서 다이어트(군살 제거)' 4가지 방법

AI 문맥을 아끼는 것은 '요약(압축)'이 아니라 불필요한 군살을 빼는 '다이어트'로 해결해야 한다.

- **줄글을 리스트로 바꾸기 (중복/사족 제거)**: 긴 설명글 대신 `Zustand 사용 (Store 분리 필수)`처럼 두괄식 키워드로 정리한다.
- **문서 쪼개기 (모듈화)**: 거대한 통합 문서 하나 대신 `핵심 규칙`, `DB 구조`, `API 명세` 등으로 나누고 **필요할 때만 호출**한다.
- **긴 코드 예시를 파일 경로 참조로 대체**: 수십 줄의 예시 코드 대신 `참고: src/utils/error.ts`처럼 실제 프로젝트 파일 경로만 명시한다.
- **기본 자동 로드 범위(Scope) 축소**: 세션 시작 시 자동으로 로드되는 메인 규칙 파일에는 **최소한의 행동 지침만** 남겨둔다.

> 💡 **한 줄 결론**
>
> AI로 내용을 뭉뚱그려 압축하지 말고, **자동으로 불러오는 기본 규칙 파일의 불필요한 사족을 쳐내고 문서를 역할별로 분리(다이어트)**해야 정보 유실 없이 용량을 아낄 수 있다.

> ➕ **더 알아두기**
> 이 조언은 사실 이 TIL 저장소의 CLAUDE.md 구조와 정확히 같은 원리다. 7월 28일에 배운 "CLAUDE.md는 프로젝트 설명만 짧게 두고, 규칙은 `docs/rules.md`로 빼서 참조시킨다"가 바로 "기본 자동 로드 범위 축소"와 "문서 쪼개기"다. 매 세션 자동으로 읽히는 CLAUDE.md가 무거우면, 이 저장소를 열 때마다 오늘 겪은 것과 같은 컨텍스트 낭비가 똑같이 발생한다.

내일은 '딥 에이전트 빌더'라고 하는 툴을 사용해볼 것이라고 한다.
