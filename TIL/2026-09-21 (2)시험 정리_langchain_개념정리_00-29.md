# LangChain/LangGraph 개념 정리 (00번~29번)

시험 직전 복습용 키워드 압축 정리. 각 항목은 "이게 왜 필요한지 → 핵심 용어 → 관계"로 정리.

---

## 00. Prompt Engineering

**핵심**: 프롬프트를 어떻게 구성해야 모델이 원하는 답을 내는지에 대한 기법 모음.

- **제로샷(Zero-shot) vs 퓨샷(Few-shot)**: 예시 없이 시키는 것 vs 예시 몇 개 보여주고 시키는 것. 퓨샷이 형식·톤을 더 정확히 따르게 함.
- **역할·관점 지정**: "너는 ~전문가야"처럼 역할을 주면 답변 스타일이 그 역할에 맞게 좁혀짐.
- **평가 기준 지정**: 원하는 결과물의 기준을 미리 알려주면 모델이 그 기준에 맞춰 자체 점검하며 생성.
- **system 프롬프트 vs user 프롬프트**: system은 대화 내내 유지되는 규칙, user는 매번 바뀌는 실제 요청.
- **XML 태그로 구조화**: `<context>`, `<instruction>` 등으로 프롬프트 영역을 나누면 모델이 각 부분의 역할을 더 명확히 구분.
- **프롬프트 체이닝**: 하나의 거대한 프롬프트 대신, 여러 단계로 나눠 순서대로 실행 (앞 단계 출력이 다음 단계 입력).
- **Temperature**: 0에 가까우면 일관적·결정적, 높으면 다양하고 창의적인 답변.
- **긴 컨텍스트 처리**: 중요한 정보는 프롬프트 앞/뒤에 배치 (중간에 있으면 모델이 놓치기 쉬움 — "lost in the middle" 현상).
- **프롬프트 반복 평가**: 같은 프롬프트를 여러 번 돌려보고 결과 일관성 확인.

## 01. LangChain 기초

**핵심**: LLM을 직접 호출하는 것과 LangChain을 쓰는 것의 차이, 그리고 LangChain의 핵심 빌딩 블록.

- **LangChain을 쓰는 이유**: 프롬프트·모델·파서를 표준화된 인터페이스로 연결해, 모델을 바꿔도 코드 구조를 거의 안 바꿔도 됨.
- **ChatModel**: `.invoke()`로 호출하면 `AIMessage` 객체를 반환 (문자열이 아니라 메타데이터 포함 객체).
- **PromptTemplate / ChatPromptTemplate**: f-string보다 재사용성이 좋고, system/user 메시지를 구조적으로 구성 가능.
- **OutputParser**: 모델 응답을 원하는 형태(문자열, 리스트, JSON 등)로 후처리.
- **LCEL (LangChain Expression Language)**: `프롬프트 | 모델 | 파서`처럼 `|`로 컴포넌트를 파이프처럼 연결하는 문법.
- **Runnable**: LCEL로 연결되는 모든 컴포넌트가 공통으로 갖는 인터페이스 (`invoke`, `batch`, `stream` 등 제공).
- **RunnableLambda**: 일반 파이썬 함수를 체인에 끼워 넣을 수 있게 감싸는 것.
- **RunnablePassthrough**: 입력을 그대로 다음 단계로 전달 (원본 값을 유지하면서 다른 값도 같이 넘길 때 유용).
- **batch() vs stream()**: batch는 여러 입력을 한 번에 처리(동시성), stream은 하나의 응답을 토큰 단위로 실시간 출력.
- **토큰 사용량 모니터링 / 에러 핸들링 / 응답 캐싱**: 실무에서 비용·안정성·속도를 관리하는 요소들.

## 02. LangSmith

**핵심**: LangChain 실행을 추적·디버깅하는 관찰(observability) 도구.

- **추적(Trace)**: 체인의 각 단계 입력/출력, 걸린 시간, 토큰 수를 자동으로 기록.
- **환경 변수 설정**: `LANGCHAIN_TRACING_V2`, `LANGCHAIN_API_KEY` 등으로 활성화.
- **태그/메타데이터**: 실행을 분류하기 위한 라벨을 붙여서 나중에 필터링.
- **선택적 추적**: 특정 실행만 추적을 켜거나 끌 수 있음 (전체를 다 남기지 않아도 됨).

## 03. Chat Memory (대화 메모리)

**핵심**: LLM은 기본적으로 대화를 기억하지 못하므로(상태 없음, stateless), 이전 대화를 어떻게 다시 넣어줄지의 문제.

- **메모리 없는 대화**: 매 호출마다 완전히 새로운 대화로 취급됨.
- **수동으로 히스토리 전달**: 이전 메시지 리스트를 직접 만들어서 매번 프롬프트에 포함.
- **InMemoryChatMessageHistory**: 메시지 기록을 자동으로 쌓아주는 객체 (앱 재시작하면 사라짐 — 이름 그대로 "in-memory").
- **Context window 관리**: 대화가 길어지면 모델의 최대 입력 길이를 넘길 수 있어서, 오래된 메시지를 자르거나 요약해야 함.
- **Short-term memory vs Long-term memory**: 짧은 대화 세션 안의 기억 vs 세션이 끝나도 남아야 하는 기억 (13번의 Store와 연결됨).

## 04. Structured Output과 Output Parser

**핵심**: 모델 응답을 자유 텍스트가 아니라 정해진 형식(리스트, JSON, 특정 스키마)으로 강제하는 방법.

- **Output Parser 종류**: StrOutputParser(그냥 문자열), CommaSeparatedListOutputParser(쉼표 리스트), JsonOutputParser(JSON), **PydanticOutputParser**(정의한 클래스 스키마로 파싱).
- **format_instructions**: 파서가 "이런 형식으로 답해달라"는 지시문을 자동 생성해서 프롬프트에 끼워 넣음.
- **타입으로 허용값 제한**: 설명 문장으로 "A, B, C 중 하나만"이라고 적는 것보다, Pydantic의 `Literal` 타입으로 강제하는 게 더 확실함.
- **Gemini Structured Output**: 모델 자체가 JSON 스키마를 강제하는 기능을 지원하는 경우, 파서 없이도 구조화된 출력 가능.
- **실패 시 대응**: 재시도(다시 물어보기) 또는 Fallback(다른 파서·모델로 전환). 모든 실패를 무조건 재시도하진 않음 (27번의 retry_on 개념과 연결).

## 05. Tool + 기본 Agent

**핵심**: LLM이 직접 못하는 일(실시간 조회, 계산 등)을 외부 함수로 위임하는 방법.

- **Tool**: LLM이 호출할 수 있는 함수. `@tool` 데코레이터로 일반 함수를 Tool로 변환.
- **Tool 설계 원칙**: 이름과 docstring이 곧 LLM에게 주는 "이 도구가 뭘 하는지" 설명이므로 명확하게 작성해야 함.
- **Tool 바인딩**: 모델에 `.bind_tools([...])`로 어떤 Tool을 쓸 수 있는지 알려줌.
- **Tool 호출 루프**: 모델이 Tool 호출을 제안 → 실제로 실행 → 결과를 다시 모델에 전달 → 모델이 최종 답변 생성(또는 다른 Tool 재호출), 이 반복이 Agent의 기본 동작.
- **Function Calling**: Google Gen AI SDK로 직접 구현하는 것과 LangChain의 `@tool`이 뒤에서 같은 메커니즘을 표준화해서 감싸준 것의 차이.

## 06. RAG 기초 — 문서 처리와 임베딩

**핵심**: 모델이 모르는 외부 문서를 검색해서 답변에 활용하는 RAG(Retrieval-Augmented Generation)의 준비 단계.

- **RAG 파이프라인 흐름**: 문서 로드 → 분할(chunking) → 임베딩 → 저장 → (질문 시) 검색 → 모델에 근거로 제공.
- **Document Loader**: 텍스트/PDF 등 다양한 형식의 파일을 표준 Document 객체로 불러오는 도구.
- **Text Splitter**: 문서가 너무 길면 모델이 한 번에 처리 못하므로 작은 청크(chunk)로 나눔.
- **RecursiveCharacterTextSplitter**: 문단→줄→단어 순으로 재귀적으로 나눠서, 의미 단위가 최대한 안 끊기게 분할.
- **핵심 파라미터**: chunk_size(청크 크기), chunk_overlap(청크 간 겹치는 부분 — 경계에서 의미가 끊기는 걸 완화).
- **임베딩(Embedding)**: 텍스트를 의미를 담은 숫자 벡터로 변환.
- **코사인 유사도**: 두 벡터의 방향이 얼마나 비슷한지로 "의미가 얼마나 비슷한지" 측정 (1에 가까울수록 유사).

## 07. 벡터 DB와 검색

**핵심**: 임베딩 벡터를 대량으로 저장하고 빠르게 유사도 검색하는 저장소.

- **왜 일반 DB로는 부족한가**: 일반 DB는 정확한 값 매칭(WHERE id = ...)엔 강하지만, "의미상 비슷한 것 찾기"엔 안 맞음.
- **ANN (Approximate Nearest Neighbor)**: 벡터가 수백만 개일 때 정확한 최근접 탐색은 너무 느려서, 약간의 정확도를 포기하고 빠르게 "거의 가장 가까운" 것을 찾는 알고리즘.
- **메타데이터**: 벡터와 함께 저장하는 부가 정보(날짜, 카테고리 등) — 검색 시 필터로 활용.
- **Chroma**: 실습에서 쓰는 로컬 벡터 DB.
- **Retriever**: 벡터 DB를 "질문 텍스트 넣으면 관련 문서 반환"하는 표준 인터페이스로 감싼 것 (LangChain의 Runnable과 호환).

## 08. RAG 파이프라인

**핵심**: 06, 07에서 만든 조각들(Loader, Splitter, 벡터DB, Retriever)을 하나의 LCEL Chain으로 합치는 단계.

- **RAG Chain 구성**: Retriever가 찾은 문서 + 사용자 질문을 프롬프트에 넣고 → 모델 호출 → 파서로 정리.
- **딕셔너리로 Chain 입력 구성**: `{"context": retriever, "question": RunnablePassthrough()}`처럼 여러 입력을 동시에 준비해서 프롬프트에 채워 넣는 패턴.
- **출처 표시**: 답변에 어떤 문서(청크)를 근거로 썼는지 같이 보여주는 방식 (신뢰성·검증 가능성 확보).

## 09. RAG 검색 고도화

**핵심**: 단순 유사도 검색만으론 부족한 상황을 보완하는 검색 전략들.

- **검색 전략보다 먼저 데이터 품질 확인**: 청크 나누는 방식·메타데이터가 잘못되면 어떤 전략을 써도 소용없음.
- **MMR (Maximal Marginal Relevance)**: 관련성은 높지만 서로 비슷비슷한 문서만 뽑히는 걸 막고, **다양성**을 함께 고려해서 검색.
- **BM25**: 임베딩 기반이 아니라 키워드 빈도 기반 검색 — 정확한 단어(모델명, 코드 등)를 찾을 때 임베딩보다 유리.
- **Metadata Filter**: "이번 달 문서만" 처럼 조건으로 검색 범위를 좁힘.
- **Hybrid Search**: 임베딩 검색 + BM25(키워드 검색)을 결합해서 서로의 약점을 보완.
- **Re-ranking**: 1차로 넉넉하게 뽑은 후보들을 별도 모델로 다시 정렬해서, 진짜 관련 있는 것을 상위로.

## 10. RAG 평가

**핵심**: RAG가 잘 작동하는지 숫자로 측정하는 방법. 검색 평가와 답변 평가로 나뉨.

- **검색 평가 지표**:
  - **Hit@k**: 상위 k개 안에 정답 문서가 있는지 (있으면 1, 없으면 0).
  - **Precision@k**: 상위 k개 중 실제 관련 문서 비율.
  - **Recall@k**: 전체 관련 문서 중 상위 k개에 포함된 비율.
  - **RR / MRR**: 정답이 처음 등장한 순위의 역수(Reciprocal Rank), 여러 질문의 평균이 MRR.
- **답변 평가**: 규칙 기반 검사(키워드 포함 여부 등) + **RAGAS** 같은 프레임워크.
- **RAGAS 핵심 지표**:
  - **Faithfulness(충실도)**: 답변이 검색된 문서 내용에 실제로 근거하는지 (환각 여부).
  - **Answer Relevancy(관련성)**: 답변이 질문에 실제로 맞는 답인지.
- **LLM-as-Judge**: 사람이 채점하기 힘든 답변 품질을 다른 LLM에게 평가시키는 방법 (직접 정의한 루브릭 기반 Judge도 가능).

## 11. LangGraph 기초

**핵심**: 단순 직선형 Chain으로는 "조건에 따라 분기", "결과가 부족하면 재검색" 같은 로직을 표현하기 어려워서 등장한 그래프 기반 실행 구조.

- **Workflow vs Agent**: Workflow는 미리 정해진 경로를 따라 실행, Agent는 LLM이 스스로 다음 행동을 결정.
- **State**: 그래프 실행 중 노드들이 주고받는 데이터. **TypedDict**로 정의 — 일반 dict는 키/타입을 몰라도 되지만 TypedDict는 명확히 선언해서 실수를 줄임.
- **Node**: 그래프의 한 실행 단계 (파이썬 함수).
- **Edge**: 노드 간 연결. 고정 연결 vs **조건부 연결**(분기 조건에 따라 다른 노드로).
- **루프**: 조건이 만족될 때까지 같은 노드들을 반복 실행하도록 Edge를 구성.
- **Reducer**: 여러 노드가 같은 State 필드를 갱신할 때 "덮어쓸지, 합칠지(예: 리스트에 추가)"를 정하는 규칙.
- **Chain vs LangGraph**: Chain은 한 방향 파이프라인, LangGraph는 분기·루프·상태 저장까지 가능한 더 일반적인 구조.

## 12. ReAct Agent

**핵심**: "Reasoning(생각) + Acting(행동)"을 반복하는 대표적인 Agent 패턴.

- **ReAct 패턴**: 모델이 "생각한다 → Tool을 부른다 → 결과를 보고 다시 생각한다"를 반복하며 최종 답에 도달.
- **ToolNode**: Tool 실행을 전담하는 LangGraph 내장 노드.
- **tools_condition**: 모델의 마지막 응답에 Tool 호출이 있으면 ToolNode로, 없으면 END로 라우팅하는 조건 함수 (미리 만들어진 라우팅 로직).
- **create_agent**: 이 ReAct 구조(노드+조건부 라우팅+루프)를 직접 그래프로 안 짜고 한 번에 만들어주는 고수준 함수.

## 13. Memory & State 관리

**핵심**: 3번(단순 히스토리)보다 발전된, LangGraph의 checkpointer/Store 기반 메모리 시스템.

- **Checkpointer**: 그래프 실행 중 State를 자동 저장 (thread_id 단위) — 27번 fault-tolerance의 재개 기능이 여기서 나옴. **단기 기억**에 해당.
- **Store**: thread를 넘어서 **장기적으로** 유지되는 기억 저장소 (예: 사용자 선호도). **namespace**로 사용자/세션별 데이터를 분리.
- **대화 요약 관리**: 대화가 길어지면 오래된 부분을 요약해서 State에 남기고, 원본은 따로 보관 — Context window 초과를 막는 실전 기법.

## 14. RAG Agent

**핵심**: 07~09에서 만든 Retriever를 "스스로 검색 여부를 판단하는 Agent"의 Tool로 바꿔서 쓰는 단계.

- **Retriever Tool 생성**: Retriever를 `@tool`로 감싸면, 모델이 "지금 검색이 필요한가"를 스스로 판단해서 호출할 수 있게 됨 (무조건 매번 검색하는 08번 방식과 차이).
- **문서 기반 답변만 허용**: 검색 결과에 없는 내용은 답하지 않도록 시스템 프롬프트로 제약.
- **대화형 RAG Agent**: 03/13번의 메모리와 결합해서 이전 대화를 참고하며 검색·답변.

---

## 15. Router

**핵심**: 사용자 요청을 여러 처리 경로 중 하나로 분류해서 보내는 구조.

- **Deterministic Routing**: 규칙(키워드, 정규식 등)으로 분기 — 빠르고 예측 가능하지만 유연성 낮음.
- **LLM Routing**: LLM이 분류를 판단 — 유연하지만 비용·지연·오분류 가능성.
- **Semantic Routing**: 임베딩 유사도로 가장 가까운 카테고리를 선택.
- **Hybrid Routing + Fallback**: 여러 방식을 조합하고, 애매하면 기본 경로로 전환.
- **Flat vs Hierarchical Routing**: 한 번에 최종 분류 vs 큰 카테고리 → 세부 카테고리 순으로 단계적 분류.

---

## 16. Guardrails

**핵심**: Agent/LLM 입출력에 대한 안전장치 — 28번(Tool Control)의 전신 개념.

- **Input Guardrails**: 사용자 입력 검사. **프롬프트 인젝션**(악의적 지시를 입력에 숨겨 시스템 프롬프트를 무력화하려는 공격) 방어가 대표적.
- **Output Guardrails**: 모델 출력 검사 (민감 정보 유출, 형식 위반 등).
- **Input/Output Schema**: 검사를 스키마(Pydantic 등)로 정형화해서 자동 검증.

---

## 17. Reflection + Evaluator-Optimizer

**핵심**: 모델이 자기 결과물을 스스로(또는 다른 평가자를 통해) 검토하고 개선하는 패턴.

- **Reflection 패턴**: 같은 모델이 "생성 → 자기 비평 → 재생성"을 반복.
- **Evaluator-Optimizer 패턴**: 생성자와 평가자를 역할로 분리 — 평가자가 **루브릭**(채점 기준)에 따라 점수/피드백을 주고, 생성자가 그에 맞춰 개선.
- **차이**: Reflection은 혼자 자기 검토, Evaluator-Optimizer는 별도 평가 기준·역할 분리로 더 체계적.

---

## 18. Parallelization

**핵심**: 서로 독립적인 작업을 동시에 실행해서 시간을 줄이는 패턴 (27번의 super-step 병렬 개념과 연결).

- **Fan-out / Fan-in**: 하나의 노드에서 여러 노드로 갈라졌다가(fan-out), 다시 하나로 모이는(fan-in) 구조.
- **결과 순서 문제**: 병렬 실행은 완료 순서가 보장 안 되므로, 순서가 중요하면 별도로 정렬해야 함.
- **Voting 패턴**: 같은 작업을 여러 번(또는 여러 모델로) 병렬 실행해서 다수결로 최종 답 결정 — 안정성 향상.

---

## 19. Orchestrator-Worker

**핵심**: 작업 개수를 **미리 알 수 없을 때**(동적으로) 여러 Worker에게 나눠 분배하는 패턴.

- **Orchestrator**: 전체 작업을 분석해서 몇 개의 하위 작업으로 나눌지 결정하는 역할.
- **Send API**: LangGraph에서 실행 시점에 동적으로 병렬 Worker를 생성하는 기능 (18번 Fan-out은 정적으로 몇 개인지 미리 알지만, 여기선 개수가 가변적).
- **전체 State vs Worker State**: Orchestrator가 보는 전체 State와, 각 Worker가 자기 작업만 보는 좁은 State를 구분.
- **Rate Limiting**: 병렬 호출이 많아지면 API 호출 제한에 걸릴 수 있어 속도 제한 관리 필요.

---

## 20. Plan-and-Execute

**핵심**: 복잡한 작업을 "계획 → 실행 → 재계획"으로 나눠 처리하는 패턴.

- **Planner**: 사용자 목표를 여러 단계 계획으로 분해.
- **Executor**: 계획의 각 단계를 실제로 실행 (Tool 호출 등).
- **Replanner**: 실행 결과를 보고 계획을 수정 (처음 계획이 틀렸거나 새 정보가 생기면 조정) — 없으면 처음 계획을 그대로 끝까지 실행.

---

## 21. Human-in-the-Loop

**핵심**: Agent가 특정 시점에 실행을 멈추고 사람의 승인/입력을 기다리는 패턴.

- **`interrupt()`**: 그래프 실행을 일시 중단시키는 함수 — 22번 Time Travel과 마찬가지로 checkpointer가 있어야 동작.
- **중단에 사용되는 세 가지 값**: 중단 시 전달하는 값, 사람이 응답으로 주는 값, 재개 후 반환되는 값 (역할이 서로 다름).
- **Tool 실행 전 중단**: 위험한 Tool 호출 전에 멈춰서 사람 승인을 받음 (28번의 실행 전 검사와 목적은 비슷하지만, 여긴 사람이 직접 판단).
- **승인 재개 / 거절과 사유 전달**: 승인 값을 주면 이어서 실행, 거절 사유를 주면 그에 따라 다른 처리.
- **Client-Server 구분**: 실제 서비스에서는 서버가 중단 상태를 클라이언트에 알리고, 클라이언트가 사용자 응답을 받아 서버에 재개 요청.

---

## 22. Time Travel

**핵심**: checkpoint 기록을 이용해 과거 시점으로 돌아가거나, 그 시점에서 다른 경로로 다시 실행하는 기능.

- **현재 State vs 과거 State 조회**: `get_state()`는 최신, `get_state_history()`류로 과거 체크포인트들을 조회.
- **Replay**: 과거 checkpoint에서 **그대로** 다시 실행 (같은 결과 재현).
- **Fork**: 과거 checkpoint의 State를 **바꿔서** 그 지점부터 다른 경로로 실행 — 새로운 분기가 생김.
- **활용 사례**: 디버깅("이 시점에 이 값이었으면 어떻게 됐을까"), 실험적 재실행.
- **외부 작업 주의사항**: 27번의 멱등성과 같은 이유 — Fork/Replay로 노드를 다시 실행하면 이미 벌어진 부작용(DB 저장 등)이 중복될 수 있음.

---

## 23. Agentic RAG

**핵심**: 14번 RAG Agent에서 한 단계 더 나가서, 검색 결과가 부실하면 Agent가 스스로 **재검색하거나 검색 방법을 바꾸는** 패턴.

- **근거 없는 질문 확인**: 검색된 문서가 질문에 답할 근거가 안 되는지 스스로 판단.
- **검색 방법 확장**: 처음 검색이 부족하면 다른 쿼리로 다시 검색하거나 검색 전략(09번의 것들)을 바꿔서 재시도.

---

## 24. Subgraph

**핵심**: 그래프 안에 또 다른 그래프를 하나의 노드처럼 끼워 넣는 구조 (복잡한 로직을 모듈화).

- **Subgraph를 쓰는 이유**: 반복되는 하위 로직을 독립적으로 만들어 재사용, 큰 그래프를 관리 가능한 단위로 분리.
- **State 스키마 공유 여부**: 부모와 Subgraph가 같은 State 구조를 쓸 수도, 다른 구조를 쓰고 값을 변환해서 주고받을 수도 있음.
- **내부 실행 스트리밍 포함/제외**: 부모 그래프를 스트리밍할 때 Subgraph 내부의 세부 단계까지 보여줄지 선택 가능.

---

## 25. Supervisor

**핵심**: 여러 Agent를 감독(supervise)하며 작업을 배분하는 **Multi-Agent** 구조.

- **Multi-Agent를 고려하는 이유**: 하나의 Agent가 모든 역할(검색, 코딩, 계산 등)을 다 잘하기 어려워서, 전문화된 Agent들로 나눔.
- **Supervisor 패턴**: 중앙의 Supervisor Agent가 사용자 요청을 보고 "이건 어느 하위 Agent가 처리할지" 결정해서 위임.
- **동작 방식**: Supervisor → 적절한 하위 Agent 실행 → 결과를 다시 Supervisor가 받아 판단(끝인지, 다른 Agent에 더 넘길지).

---

## 26. Handoff

**핵심**: Agent 간에 작업을 **넘겨주는(hand off)** 구체적인 메커니즘.

- **Command**: LangGraph에서 "State를 갱신하면서 동시에 다음 Node로 이동"을 한 번에 지정하는 반환 객체 (27번 error_handler에서도 나왔던 그 Command).
- **Edge와 Command의 차이**: 미리 정해진 Edge로 가는 것과 달리, Command는 노드 실행 결과에 따라 **그 자리에서 동적으로** 다음 목적지를 정함.
- **25번 Supervisor와의 관계**: Supervisor는 "중앙에서 배분"하는 구조, Handoff는 "Agent가 스스로 다른 Agent에게 넘기는" 더 분산된 구조.

---

## 27. Fault Tolerance (장애 허용)

**핵심**: 실행 중 오류가 나도 복구하거나 이어서 계속할 수 있는 능력.

- **재시도(RetryPolicy)**: 노드 단위로, **한 번의 그래프 호출 안에서** 자동으로 다시 시도. `initial_interval`/`backoff_factor`/`max_interval`(점점 늘어나는 대기시간), `max_attempts`(최초 포함 총 횟수), `jitter`(무작위성), `retry_on`(재시도할 예외 종류만 선별).
- **with_retry() / with_fallbacks()**: 노드보다 더 좁은 단위(Runnable 하나)로 재시도하거나, 다른 모델/체인으로 대체.
- **checkpoint 재개**: 재시도를 다 써버려 예외가 터진 뒤, 원인을 고치고 같은 thread_id로 `invoke(None, config)` 호출 → 이미 완료된 노드는 건너뛰고 실패 지점부터 이어감.
- **super-step**: 같은 차례에 실행되는 노드들의 묶음. checkpoint는 super-step이 끝날 때마다 저장 (병렬 노드는 다 끝나야 한 번 저장).
- **timeout**: 노드 실행 시간 제한 (`NodeTimeoutError`), 재시도와 조합 가능.
- **멱등성(idempotency)**: 같은 요청을 여러 번 처리해도 결과가 같도록 만드는 성질. **멱등성 키**로 이미 처리한 요청인지 확인해서 재개 시 중복 부작용(중복 저장 등) 방지.

---

## 28. Agent Tool Control

**핵심**: 에이전트가 제안한 Tool 호출을 실행 전/후로 검사하고 통제하는 방법.

- **Middleware**: 모델 호출/Tool 실행 전후에 공통 처리를 끼워 넣는 장치. `wrap_model_call`(모델 호출 감싸기), `wrap_tool_call`(Tool 실행 감싸기).
- **handler 패턴**: Middleware가 `handler(request)`를 호출하면 다음 단계로 진행, 호출 안 하고 바로 결과를 반환하면 실행을 막은 것.
- **Context vs State**: State는 실행 중 갱신되는 데이터(대화 기록), Context는 프로그램이 실행 시 넘겨주는 고정 기준(사용자 권한 등) — LLM 제안과 실제 실행 권한 판단을 분리.
- **실행 전 검사**: tool 이름·인자 형식(Pydantic)·접근 권한·금액 한도·사람 승인 여부 확인 후 통과해야 실제 실행.
- **실행 후 검사**: Tool이 반환한 값의 형식·정합성 확인 (단, 이미 실행된 부작용은 못 되돌림).
- **ToolCallLimitMiddleware**: 한 번의 실행에서 Tool을 몇 번까지 부를 수 있는지 제한 (`run_limit`, 특정 tool만 제한도 가능).

---

## 29. LangGraph Logging

**핵심**: `print()` 대신 `logging` 모듈로 실행 기록을 남기면 중요도별로 걸러보거나 파일로 저장 가능.

- **로거(Logger)/핸들러(Handler)/포매터(Formatter)**: 각각 "기록한다"/"어디로 보낼지"/"어떤 형식으로"를 담당.
- **로그 레벨**: `DEBUG < INFO < WARNING < ERROR < CRITICAL` — 로거 레벨과 핸들러 레벨을 **둘 다** 통과해야 출력됨 (화면은 INFO만, 파일은 DEBUG까지처럼 다르게 설정 가능).
- **RotatingFileHandler**: 파일이 `maxBytes`를 넘으면 새 파일로 교체, `backupCount`개까지만 이전 파일 보관.
- **logger.exception()**: ERROR 메시지 + traceback(오류 경로)까지 기록. 기록만 할 뿐 오류 처리(재시도 등)는 안 되므로, 필요하면 직접 `raise`.
- **LangGraph 노드 로깅**: 노드도 일반 함수이므로 로거를 그대로 사용, 각 노드 시작/완료를 남기면 실패 지점을 로그로 추적 가능.
