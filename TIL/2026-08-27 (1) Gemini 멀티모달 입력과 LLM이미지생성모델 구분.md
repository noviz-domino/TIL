## 오늘 배운 것

  

### 1. Gemini 멀티모달 입력 (`multimodal.ipynb`)

Gemini에게 텍스트뿐 아니라 이미지, PDF, 음성, 동영상을 함께 전달해서 이해시키는 실습.

  

**파일 전달 방법 3가지**

| 방법 | 전달 값 | 적합한 상황 |

| --- | --- | --- |

| Base64 | `data` | 작고 한 번만 쓸 파일 |

| Files API | `uri` | 크거나 여러 요청에서 재사용할 파일 |

| 공개 URL | `uri` | 인터넷에서 바로 접근 가능한 파일 |

  

**기본 흐름**

```python

from google import genai

client = genai.Client(api_key=api_key)

  

# Base64 방식 (작은 파일)

image_data = base64.b64encode(image_path.read_bytes()).decode("utf-8")

client.interactions.create(

    model=model,

    input=[

        {"type": "image", "data": image_data, "mime_type": mime_type},

        {"type": "text", "text": "이 이미지에 무엇이 보이는지 설명해 줘."},

    ],

)

  

# Files API 방식 (재사용/큰 파일)

uploaded_file = client.files.upload(file=str(image_path))

client.interactions.create(

    model=model,

    input=[

        {"type": "image", "uri": uploaded_file.uri, "mime_type": uploaded_file.mime_type},

        {"type": "text", "text": "..."},

    ],

)

```

파일 종류(이미지/오디오/비디오/문서)에 따라 `type` 값만 바뀔 뿐, 업로드 방식 자체는 동일함.

  

setup 셀(`.env` 로드 → API 키 확인 → client 생성)은 특별한 게 아니라 API 클라이언트 초기화의 일반적인 패턴.

  

### 2. "이해용 LLM"과 "생성용 이미지 모델"이 왜 나뉘어 있는가

  

- 이미지/PDF/음성/영상을 **이해**하고 답하는 것 → 일반 LLM(`gemini-3.6-flash`)으로 충분. Gemini 계열은 원래 멀티모달 입력을 이해하도록 학습되어 있음.

- 이미지를 **생성**하는 것 → 별도의 이미지 생성 전용 모델(`gemini-3.1-flash-image`, 소위 "나노바나나" 계열) 사용.

  

**왜 원리는 같은데 모델이 갈라져 있는가**

- 근본 메커니즘(다음 값을 예측하는 트랜스포머 방식)은 텍스트든 이미지든 동일함. 컴퓨터에게는 결국 텍스트도 이미지도 숫자(벡터) 시퀀스일 뿐이고, "다음 토큰을 예측한다"는 틀 자체는 같음.

- 다만 실제로 모델을 나누는 이유:

  1. **토큰화 방식이 다름** — 텍스트는 단어 사전 기반 토큰화, 이미지는 픽셀/패치를 코드북으로 압축하는 전혀 다른 전처리가 필요함.

  2. **예측해야 할 숫자의 차원이 다름** — 이미지는 픽셀 수가 훨씬 많아 압축된 표현(latent space) 등 이미지 전용 최적화가 들어감.

  3. **비용/속도 최적화** — 이해만 필요한 요청에 생성까지 가능한 무거운 모델을 쓰는 건 비효율적이라, 용도별로 특화된 모델을 나눠 서비스함.

  

**한 줄 정리**: 원리는 "다음 값 예측"으로 동일하지만, "어떤 도메인의 숫자를 예측하도록 학습시켰는가"(자연어 토큰 vs 이미지 픽셀/패치)가 달라서 실무에서는 이해용 모델과 생성용 모델을 분리해서 사용한다.
