# 📝 [TIL] 웹 기초 & 통신 프로토콜 (HTTP, 도메인, API, Stateless)

## 1. HTTP와 하이퍼텍스트의 본질

* 하이퍼텍스트 (HyperText): 모르는 단어나 연관 내용이 있을 때, 순서대로 읽지 않고 클릭을 통해 다른 문서로 바로 이동(점프)할 수 있도록 만들어진 비선형 문서 방식.
* 하이퍼링크 (Hyperlink): 하이퍼텍스트 문서 내에서 다른 문서나 위치로 이동시켜 주는 연결 고리. (<a> 태그의 href 속성 활용)
* HTTP (HyperText Transfer Protocol): 하이퍼링크로 연결된 하이퍼텍스트(웹 문서)를 인터넷상에서 주고받기 위해 클라이언트(브라우저/앱)와 서버가 지키기로 한 전송 규약(약속).
> 💡 참고: 역사적으로 '인터넷(ARPANET)'은 냉전 시절 군사적 분산 통신망으로 출발했고, '웹(WWW)'은 학술 정보 및 논문을 링크로 이어 편하게 찾기 위해 탄생했습니다.

## 2. IP 주소, 도메인, 그리고 DNS

* IP 주소: 인터넷상에서 컴퓨터(웹 서버)가 가지는 고유한 숫자 번지수 (예: 142.250.196.142).
* 도메인 (Domain Name): 숫자로 된 IP 주소를 사람이 기억하기 쉽게 문자로 만든 이름 (예: google.com).
* DNS (Domain Name System): 도메인 이름을 입력했을 때 해당 IP 주소로 변환해 주는 시스템.
  * 핵심: DNS 조회의 경우 데이터가 매우 작기 때문에, 속도와 효율성을 위해 HTTP(TCP 기반)가 아닌 DNS 전용 프로토콜(UDP 방식)을 사용합니다.
## 3. 웹 브라우저에 google.com을 입력하면 일어나는 일

1. DNS 조회: 브라우저가 DNS 서버에 google.com의 IP 주소를 물어보고 알아냅니다.
1. 서버 연결 수립: 알아낸 IP 주소 기반으로 서버와 네트워크 연결(TCP 3-Way Handshake)을 맺습니다.
1. HTTP 요청 (Request): 브라우저가 서버에 *"메인 페이지(HTML 등)를 주세요"*라고 요청을 보냅니다.
1. HTTP 응답 (Response): 서버가 요청을 처리한 후 성공 코드(200 OK)와 함께 웹 문서 코드를 반환합니다.
1. 브라우저 렌더링 (Rendering): 전달받은 코드(HTML, CSS, JS)를 브라우저가 해석하여 시각적인 화면으로 그려 사용자에게 보여줍니다.
## 4. API와 Request / Response 구조

* API Request (요청): 클라이언트가 URL을 통해 서버로 데이터나 처리 결과를 요구하는 통신.
* API 요청의 4가지 핵심 요소:
  1. HTTP Method: 수행할 행위 (GET: 조회, POST: 생성, PUT: 수정, DELETE: 삭제)
  1. URL (Endpoint): 요청할 목적지 주소
  1. Headers: 요청에 대한 부가 정보 (Content-Type, 인증 토큰 등)
  1. Body: 서버로 전달할 실제 데이터 (주로 POST, PUT 사용)
## 5. HTTP의 2대 핵심 특징: Stateless & Connectionless

### ① Stateless (무상태성)

* 개념: 서버는 클라이언트의 이전 상태(맥락)를 기억하지 않으며, 각 요청을 독립적인 개별 사건으로 처리합니다.
* 장점: 서버가 사용자 상태를 보관하지 않으므로, 요청이 몰릴 때 서버를 수평적으로 확장(Scale-out)하기 매우 용이합니다.
### ② Connectionless (비연결성)

* 개념: 요청을 보내고 응답을 받으면 즉시 연결(Connection)을 끊는 특징.
* 장점: 서버가 접속을 계속 유지할 필요가 없어 서버 자원(메모리/통신)을 대폭 절약할 수 있습니다.
## 6. Stateless 한계 극복: 쿠키, 세션, 토큰 (인증 방식)

HTTP가 상태를 기억하지 못하므로, 로그인 유지 등을 위해 클라이언트가 요청 시마다 '입장권'을 매번 첨부해서 보냅니다.

## 7. 네트워크 보안과 탈취(슈킹) 대책

네트워크 패킷 자체를 중간에서 도청/탈취(MITM, Replay Attack)하는 것을 물리적으로 100% 막기는 불가능하므로, 탈취당해도 사용할 수 없도록 보안을 강화합니다.

1. HTTPS (SSL/TLS): 데이터를 암호화하여 통신하므로 탈취당해도 내용을 해독할 수 없음.
1. 토큰 유효기간 제한: Access Token의 수명을 짧게(10~30분) 설정하여 탈취된 토큰의 악용 방지.
1. CORS 설정: 허용된 도메인에서 온 요청만 서버가 응답하도록 제한.

# 📝 [TIL] 웹 기초 추가 정리 (GET/POST, 서브도메인, HTTPS, Port)

## 1. 서버 요청(Request) 데이터 전송 방식: GET vs POST

* 주소창 엔터의 비밀: 웹 브라우저 주소창에 URL을 입력하고 Enter를 누르는 모든 동작은 서버에 해당 페이지를 달라고 요청하는 GET 요청입니다.
## 2. API 문서 (API Specification)와 규격

* API 서비스마다 특정 기능에 대해 GET을 써야 할지, POST를 써야 할지 API 문서에 미리 정해두고 제공합니다.
* 정해진 규칙과 다른 방식(메서드)으로 요청을 보내면 서버는 405 Method Not Allowed 에러를 반환합니다.
* Swagger (OpenAPI): FastAPI 등에서 API 규격 및 테스트 화면을 자동으로 시각화해 주는 웹 문서 도구입니다.
## 3. 서브도메인 (Subdomain)

* 메인 도메인(google.com) 앞에 붙여서 하나의 서비스 내에서 역할이나 서버를 분리할 때 사용합니다.
  * 예: [www.google.com](https://www.google.com) (메인 웹), mail.google.com (메일), api.google.com (백엔드 API 서버)
* 도메인을 하나 구매하면 서브도메인은 추가 비용 없이 마음대로 여러 개 만들어 서로 다른 서버에 연결할 수 있습니다.
## 4. HTTP vs HTTPS & 포트(Port)

### ① HTTP vs HTTPS

* HTTP (:80): 암호화되지 않은 평문 통신. 네트워크 중간에서 데이터를 탈취(스니핑)당하면 내용이 그대로 노출됨.
* HTTPS (:443): HTTP에 SSL/TLS 암호화 계층을 추가한 보안 통신. 데이터가 암호화 상자에 담겨 전송되므로 안전함.
### ② 포트 (Port)

* 하나의 서버(IP 주소) 내부에서 어떤 프로그램(서비스/방)으로 찾아갈지 지정하는 번호입니다.
* 기본 포트 생략: http://는 :80, https://는 :443 포트로 자동 연결되므로 주소창에서 포트 번호가 생략됩니다.
* 주요 개발 포트 예시: FastAPI (8000), Streamlit (8501), React (3000)


# 📝 [TIL] URL 구성 요소 & Query String (쿼리 스트링)

## 1. URL의 전체 구조

우리가 브라우저에 입력하는 URL 주소는 다음과 같은 순서와 규격으로 구성되어 있습니다.


# 

```plain text
 https://  www.example.com  :8080  /users/profile  ?lang=ko&page=1
[프로토콜]    [도메인]      [포트]       [Path]        [Query String]
```

1. Protocol: 통신 규약 (http://, https://)
1. Domain: 서버의 이름 (example.com)
1. Port: 서버 내부의 서비스 방 번호 (:8080, 생략 시 HTTP는 80, HTTPS는 443)
1. Path: 서버 내 파일/페이지/리소스를 찾아가는 경로
1. Query String: 데이터를 식별하고 필터링하기 위한 조건(옵션)
## 2. Path (경로)

* 범위: 포트 번호(또는 도메인)의 끝 슬래시(/)부터 물음표(?)가 나오기 전까지의 영역.
* 역할: 폴더 경로처럼 서버 내부에서 구체적으로 어떤 페이지나 리소스(위치)에 접근할지 나타냅니다.
  * 예: /users/profile (사용자 프로필 페이지 경로)
## 3. Query String (쿼리 스트링) & Identifier (식별자)

* 범위: 물음표(?) 뒤에 붙는 모든 영역.
* 역할: 서버의 수많은 데이터 중 내가 원하는 조건의 데이터를 정확히 식별(Identify) 및 필터링하기 위해 넘겨주는 데이터 영역입니다.
* 구조 (Key-Value):
  * 데이터를 Key=Value (키=값) 쌍 형태로 전달합니다.
  * 여러 개의 조건을 붙일 때는 & (엠퍼샌드) 기호로 연결합니다.
  * 
```plain text
? category = shoes & color = black
  └─ 키 ─┘   └─ 값 ─┘  └─ 키 ─┘  └─ 값 ─┘
```

* 서버에서의 처리: URL로 전달받은 ?category=shoes&color=black 문장을 서버(Python 등)가 넘겨받으면 {"category": "shoes", "color": "black"} 형태의 딕셔너리(JSON)로 해석하여 사용합니다.

# 📝 웹 네트워크 기초: HTTP Response & Status Code

## 1. HTTP 응답 (Response)의 핵심 구성 요소를 이해한다

서버가 클라이언트의 요청(Request)을 처리한 뒤 돌려주는 응답은 크게 두 가지로 나뉩니다.

* Status Code (상태 코드): 처리 결과가 성공인지, 실패인지(실패했다면 원인이 무엇인지) 3자리 숫자로 요약한 정보.
* Response Body (본문): 클라이언트가 요청한 실제 데이터 (HTML, JSON, 이미지 등).
## 2. Status Code 백의 자리별 5가지 분류 (1xx ~ 5xx)

## 3. 개발에서 가장 중요한 핵심 분류와 책임 소재

실무 개발에서는 2xx, 4xx, 5xx 이 세 가지가 전체의 대부분을 차지합니다.

* 2xx (성공): 요청과 처리가 완벽히 성공함.
* 4xx (클라이언트 잘못): 존재하지 않는 주소 호출, 권한 없음, 데이터 형식 오류 등 요청자 측 문제.
* 5xx (서버 잘못): 서버 코드 버그, DB 다운 등 백엔드 개발자 측 문제. 백엔드 개발자 입장에서는 예외 처리를 철저히 하여 500번대 에러가 절대 발생하지 않도록 코딩하는 것이 원칙입니다.
## 4. 가장 자주 쓰이는 대표 Status Code Top 4

1. 200 OK: 요청 처리 성공 (기본 성공 응답)
1. 201 Created: POST 요청 등을 통해 새로운 데이터/리소스 생성 성공
1. 404 Not Found: 요청한 Path(주소)나 리소스를 찾을 수 없음
1. 500 Internal Server Error: 서버 내부 코드 또는 시스템 오류 발생
