## 과제 개요

  

**요구사항**: 캐릭터가 직업(전사/마법사)과 무기(검/지팡이)를 가지고, 직업에 맞는 무기만 장착할 수 있어야 한다. 공격/스킬 사용은 직업·무기 종류에 따라 다르게 동작해야 한다.

  

**파일 구성**: `weapon.py`(무기) → `job.py`(직업) → `character.py`(캐릭터) → `main.py`(실행). 나중에 한 파일로도 합침.

## 1. 추상 클래스로 "무기"와 "직업" 설계하기

  

```python

from abc import ABC, abstractmethod

  

class Weapon(ABC):

    @abstractmethod

    def skill(self):

        pass

  

class Sword(Weapon):

    def skill(self):

        print('강력한 베기!')

  

class Staff(Weapon):

    def skill(self):

        print('강력한 마법!')

```

  

`Job`도 똑같은 구조로 만듦. 다만 직업은 **클래스 변수**도 하나 가짐:

  

```python

class Job(ABC):

    allow_weapon_list: set = set()   # 클래스 변수 — 인스턴스가 아닌 직업 자체가 공유

  

    @abstractmethod

    def attack(self):

        pass

  

class Warrior(Job):

    allow_weapon_list = {Sword}      # Sword() 아니라 Sword — 물건이 아니라 종류

    def attack(self):

        print('검을 휘두른다!')

  

class Magicion(Job):

    allow_weapon_list = {Staff}

    def attack(self):

        print('마법 발사!')

```

  

**`allow_weapon_list`에 `self.`가 없는 이유**: `__init__` 안이 아니라 클래스 몸통에 바로 썼기 때문에, `Warrior` 인스턴스를 몇 개를 만들든 전부 같은 목록 하나를 공유한다. 개별 캐릭터마다 다를 이유가 없는 값(그 직업 자체의 규칙)이라서 클래스 변수로 둔 것 — `population` 세던 것과 같은 이유.

## 2. `Character`에서 Composition으로 조립하기

  

```python

class Character:

    def __init__(self, name, job):

        self.name = name

        self.job = job          # Job 을 상속하지 않고 속성으로 가짐 (Composition)

        self.weapon = None

  

    def attack(self):

        self.job.attack()        # ← 다형성이 실제로 쓰이는 자리

  

    def equip_weapon(self, weapon):

        if type(weapon) in self.job.allow_weapon_list:

            self.weapon = weapon

        else:

            print('이 직업은 해당 무기를 장착할 수 없습니다.')

  

    def use_skill(self):

        if self.weapon is None:

            print('장착된 무기가 없습니다.')

            return

        self.weapon.skill()      # ← 여기도 다형성

```

  

`class Character(Job)` 이 아니라 `self.job = job`. **"캐릭터는 직업이다"는 말이 안 되고, "캐릭터가 직업을 가진다"가 맞기 때문** — 상속(Is-A)이 아니라 Composition(Has-A).

## 3. `type(weapon) in self.job.allow_weapon_list` 뜯어보기

  

여기서 막혔던 부분 — `type()`과 `in`이 왜 필요한지.

  

- **`type()`**: 이미 `problem01`에서 써본 함수. `type(v1)` → `<class 'int'>` 처럼 "이 값이 무슨 종류냐"를 알려줌.

- **왜 필요한가**: `weapon`은 "검 한 자루"(물건)인데, `allow_weapon_list`에는 `{Sword}`처럼 "검이라는 종류"(설계도)가 들어있음. 물건과 설계도는 종류가 달라서 그냥 비교가 안 됨. `type(weapon)`을 씌우면 물건 → 종류로 바뀌어서 비교가 가능해짐.

  ```python

  sword1 = Sword(); sword2 = Sword()

  sword1 == sword2                # False (서로 다른 물건)

  type(sword1) == type(sword2)    # True  (둘 다 '검'이라는 종류)

  ```

  우리가 확인하고 싶은 건 "이게 검이냐?"이지 "이게 그 특정 검 한 자루냐?"가 아니므로 종류로 비교해야 함.

- **`in`**: `problem05`에서 이미 사용. `if n in lst` 처럼 "이게 저 안에 들어있니?"를 True/False로 답함. `for ... in`(꺼내기)과는 다른 쓰임이라는 점 주의.

  

전체 문장을 우리말로 옮기면: **"이 무기의 종류가, 내 직업이 허용하는 목록 안에 있나?"**

## 4. `self.job.attack()`을 파이썬이 처리하는 순서

  

`arther`는 클래스가 아니라 `Character`로 만들어진 **객체**. `arther` 안에는 `name`, `job`, `weapon` 값 3개만 있고, `attack` 같은 메서드는 **클래스 쪽에** 있다.

  

파이썬이 `점(.)`을 만나면 순서대로 찾는다:

```

① 그 객체 안에 있나?  →  없으면

② 그 객체의 클래스에 있나?  →  없으면

③ 그 클래스의 부모에 있나?

```

  

`self.job.attack()`은 두 단계:

```

self.job        → arther 객체 안에서 job 을 꺼냄 → Warrior 객체

(Warrior 객체).attack → Warrior 객체 안엔 없음 → Warrior 클래스에서 찾음 → 실행

```

  

`self.job`에 Warrior가 들었으면 Warrior의 attack, Magicion이 들었으면 Magicion의 attack이 실행됨. **코드(`self.job.attack()`)는 그대로인데 실행되는 곳이 달라지는 것 — 이게 다형성.**

  

메서드가 객체마다 복사되지 않고 클래스에 한 벌만 있는 이유: 캐릭터 1000명을 만들어도 `attack` 코드가 1000벌 생기면 낭비이므로, 기능은 클래스에 두고 객체는 값만 가짐. 누가 불렀는지 알려주는 게 `self`.

## 5. `abc` 모듈

  

```python

from abc import ABC, abstractmethod

```

  

`abc` = Abstract Base Class 줄임말, 파이썬 내장 모듈. `from dotenv import load_dotenv`와 완전히 같은 구조 — "abc라는 창고에서 ABC와 abstractmethod 두 개를 꺼내온다."

  

- `ABC`: 상속하면 직접 인스턴스를 못 만드는 클래스가 됨

- `abstractmethod`: 자식이 반드시 구현해야 하는 메서드로 지정

## 6. 남은 버그를 setter로 고치기

  

**버그 상황**: 검을 장착한 상태에서 직업을 마법사로 바꾸면(`arther.job = Magicion()`), 마법사가 검을 든 이상한 상태가 됨. `equip_weapon()`의 검사는 장착할 때만 실행되고, `job`을 직접 대입하는 경로는 검사를 안 거치기 때문.

  

**해결**: `job`을 `@property` + `@setter`로 만들어서, 대입하는 순간 검사가 자동으로 끼어들게 함.

  

```python

class Character:

    def __init__(self, name, job):

        self.name = name

        self.weapon = None

        self.job = job          # 이 대입이 실제로는 아래 job.setter 를 실행시킴

  

    @property

    def job(self):

        return self._job

  

    @job.setter

    def job(self, new_job):

        if self.weapon is not None and type(self.weapon) not in new_job.allow_weapon_list:

            print('직업을 변경하여 기존 무기를 사용할 수 없습니다. 무기가 해제됩니다.')

            self.weapon = None

        self._job = new_job

```

  

**setter가 하는 일 한 줄 정리**: `p.age = 25` 처럼 `=`로 대입하는 순간, 그 대입을 함수 호출로 바꿔치기하는 것. `arther.job = Magicion()`은 겉보기엔 그냥 대입이지만 실제로는 `job.setter` 함수 전체가 실행됨. 그 안에서 검사하고, 필요하면 무기를 강제로 뺀 뒤에야 `self._job`에 실제로 저장.

  

**검증 결과**:

```python

arther.equip_weapon(Sword())

arther.job = Magicion()

# 출력: 직업을 변경하여 기존 무기를 사용할 수 없습니다. 무기가 해제됩니다.

arther.weapon   # None

arther.attack() # 마법 발사!  (정상적으로 마법사로 전직됨)

```

## 오늘의 핵심 정리

  

1. **추상 클래스(ABC)**: "이 기능은 자식이 반드시 구현해야 한다"를 파이썬이 강제하게 만드는 장치. `Weapon(ABC)` + `@abstractmethod`.

2. **다형성**: `self.job.attack()`처럼 코드는 하나인데, `self.job`에 어떤 객체가 들었느냐에 따라 실행되는 메서드가 달라지는 것. `if`문으로 종류를 분기하지 않아도 됨.

3. **Composition**: `class Character(Job)`이 아니라 `self.job = job`. "A는 B다"가 아니라 "A가 B를 가진다"일 때 쓰는 방식. 상속과 달리 실행 중에 부품(직업)을 갈아끼울 수 있음.

4. **`type(x) in {클래스, ...}`**: 물건이 아니라 종류로 비교할 때 쓰는 패턴. 허용 목록 검사에 자주 쓰임.

5. **setter의 실전 용도**: 이미 `p.속성 = 값`으로 여기저기 쓰고 있는 코드를 안 고치고, 대입 시점에 검사 로직을 몰래 끼워넣을 때 쓴다. 오늘 `job` setter가 정확히 이 사례.
