# 📌 Claude Code 메모리 시스템 가이드

  Claude Code의 메모리(컨텍스트 지침)는 전역(Global), 프로젝트(Project), 자동(Auto Memory) 단위로 관리됩니다.

---

## 1. 전역 메모리 (Global Memory)

  모든 프로젝트에 공통으로 적용되는 개인 설정, 코딩 컨벤션, 작업 선호도 등을 저장하는 파일입니다.

  * macOS / Linux / WSL~/.claude/CLAUDE.md
  * Windows%USERPROFILE%\.claude\CLAUDE.md(예: C:\Users\Username\.claude\CLAUDE.md)
> 💡 환경 변수 CLAUDE_CONFIG_DIR를 별도로 설정한 경우, 설정된 경로 내의 CLAUDE.md를 우선 참조합니다.

---

## 2. 조직/전사 공통 메모리 (Managed Policy Level)

  IT/DevOps 팀이나 시스템 관리자가 회사 전체 차원의 보안 규정 및 개발 표준을 강제 적용할 때 사용합니다.

  * macOS: /Library/Application Support/ClaudeCode/CLAUDE.md
  * Linux / WSL: /etc/claude-code/CLAUDE.md
  * Windows: C:\Program Files\ClaudeCode\CLAUDE.md

## html에서 작동하는 게임 만들기

  클로드에게 index.html 안에서 돌아가는 게임 만들어줘라고 할것.

### 팡팡 아케이드

  1. 아래 표의 제출자 칸에서 내 이름을 찾아 그 줄을 클릭한다.
  1. 제목을 게임명 으로 바꾼다. (예: 좀비 피하기)
  1. index.html을 포함해 zip으로 압축해서 게임 파일 (zip) 칸에 올린다.
  1. 한 문장 규칙, 조작법, 장르를 채운다.
  1. 제출 상태를 Done으로 바꾼다.
  1. 배포는 나중에 해도 된다. 배포하고 나면 배포 URL 칸에 주소를 넣는다.


## zip 만드는 법

  * macOS: index.html 파일 우클릭 → "압축하기"
  * Windows: index.html 파일 우클릭 → "보내기" → "압축(ZIP) 폴더"
  파일이 여러 개면 폴더째 압축해도 됩니다.
단, 압축을 풀었을 때 index.html이 바로 보여야 해요!

  파일 구조: index.html 하나에 <style>+<script> 인라인. 섹션 배너 주석으로 논리 모듈 분리: [0]목차 [1]CONFIG상수 [2]수학/유틸 [3]오브젝트풀 [4]엔티티정의(무기/패시브/적/보스 데이터 테이블) [5]시스템(Input/Spawner/AI/Weapon/Collision/XP/Particle/Camera/Save) [6]상태머신 [7]UI브릿지 [8]렌더러 [9]메인루프 [10]부트스트랩. 예상 규모 JS 2500~4500줄. 무기/패시브/적/보스는 로직이 아닌 순수 데이터 테이블로 선언.

  루프/상태: requestAnimationFrame + 고정 타임스텝 accumulator(1/60초, 프레임당 최대 반복 캡 5). 상태머신은 문자열enum + handler map: MENU/HANGAR/PLAYING/LEVELUP/ABYSS_CHOICE/RESULT.

  엔티티/충돌: plain object + 고정크기 배열 오브젝트 풀(적탄950/아군탄500/적260/파티클900/파편300, free-index 스택 방식). 충돌은 전부 원-원(제곱거리, sqrt 없음).

  렌더링: 레이어 고정순서(배경→파티클뒤→적→플레이어→탄→파티클앞→적탄 항상 최상위). 카메라(2400×1600 아레나 추적)는 world/screen 좌표 분리 + translate.

  입력: keysDown 상태맵을 매 fixed-tick 폴링(OS key-repeat 의존 금지). blur/visibilitychange 시 전체 초기화.

  저장: localStorage, 런 종료·구매 시점에만 저장(디바운스).

  오디오: WebAudio OscillatorNode 기반 절차적 SFX, 외부 파일/BGM 없음.

### 13. 구현 착수 단계 기술 검토 및 개선 제언

> 실제 코드 작성을 시작하는 과정에서, 12절 초안이 그대로 구현될 경우 발생할 수 있는 성능/게임성 문제를 사용자가 사전에 검토하여 아래와 같이 설계를 보강했다. 이 절의 내용은 최종 구현에 반드시 반영해야 하는 확정 사항이다.

  문제: 아군탄 vs 적 충돌에 128px 셀 그리드를 쓰되 양쪽(적+아군탄)을 모두 매 프레임 등록/해제하면 연산 오버헤드가 커지고, 셀이 크면 고속 이동하는 작은 탄이 셀을 건너뛰며 충돌을 놓치는 "터널링"이 발생할 수 있다.

  결정된 방식: 적(Enemy)만 그리드에 등록하고(GRID_CELL = 96px), 아군탄은 자신의 좌표가 속한 셀 기준 **3×3 인접 셀(자기 셀 + 인접 8개)**의 적만 조회해서 충돌 검사한다. 그리드는 매 fixed-tick마다 적 목록으로부터 새로 구성(적은 최대 260개라 재구성 비용이 낮음). 아군탄은 등록 대상이 아니므로 등록/해제 연산 자체가 없다.

  96px 셀 + 3×3 조회 범위(288px)는 보스(반경 66)처럼 큰 적이 인접 셀로 걸쳐 있어도 충돌을 놓치지 않을 만큼 충분히 넓다.

  적탄 vs 플레이어는 상대가 1개뿐이므로 그리드 없이 전체 순회로 충분(플레이어 기준 전체 적탄 최대 950개 순회는 60fps에서 무리 없음).

  문제: 하드캡(900) 도달 시 단순히 "화면 밖" 탄부터 지우면, 보스/엘리트가 화면 밖에서 미리 깔아둔 탄막이 플레이어에게 도달하기 전에 사라져 버려 난이도가 싱거워지거나 패턴이 어색해질 수 있다.

  결정된 방식:

  판정 기준을 "아레나 경계 밖"이 아니라 **"카메라 뷰포트 + 패딩 300px 밖"**으로 변경 — 화면에 곧 보일 예정인 탄은 보호된다.

  모든 적탄에 priority 필드를 부여: 일반 잡몹/원거리 적의 탄은 priority=1, **보스 및 오벨리스크(엘리트)처럼 의도된 탄막 패턴을 구성하는 탄은 priority=2*로 표시해 우선 보호한다.

  하드캡 초과 시 1차로 "뷰포트+패딩 밖 && priority<2" 탄부터 제거하고, 그래도 초과 상태면 2차로 "priority<2" 탄 중에서 추가 제거한다. priority=2(보스 패턴)는 캡 강제 상황이 아니면 건드리지 않는다.

  문제: 탄막 게임은 초당 다수의 피격/히트 이벤트가 발생한다. 매 이벤트마다 OscillatorNode를 새로 생성하면 오디오 버퍼가 과부하되어 "지직거리는" 클리핑/팝 노이즈와 프레임 드랍이 함께 발생할 수 있다.

  결정된 방식: SFX 함수마다 **최소 재생 간격(디바운스 게이트)**을 둔다. performance.now() 기준으로 마지막 재생 시각을 이벤트 종류별로 기록하고, 간격이 미달이면 재생을 건너뛴다. 기준값(안): 타격 45ms / 처치 30ms / 피격 80ms / 그레이즈 60ms / 대시 100ms / 파밍 35ms. 레벨업·보스 등장·오버드라이브·클리어처럼 드물게 발생하는 이벤트는 게이트가 필요 없다.

  문제: XP/에센스 파편의 흡수 반경이 넉넉해도, 후반 탄막 밀도가 높아지면 플레이어는 파밍을 포기하고 외곽에서 도망만 다니게 되어 "쌓는 재미"가 죽는다. 회피와 파밍 사이의 딜레마를 풀어줄 보상 장치가 필요하다.

  결정된 방식: 오버드라이브 발동 시 화면의 적탄을 전멸시키는 것과 동시에, 현재 필드에 남아있는 모든 XP/에센스 파편을 즉시 전량 회수한다. 그레이즈로 채운 게이지가 곧 "탄막을 뚫고 들어가 쓸어담기"라는 명확한 쾌감으로 이어지도록 하여, 리스크(그레이즈를 노리고 접근)와 리워드(오버드라이브의 화면 정리+파밍)를 직접 연결한다.

  문제: 원래 설계는 패널이 "이동 방향 전방"에 생성되는 구조였다. 그런데 마우스가 없는 자동조준 서바이버 게임에서 플레이어는 대부분 적을 등지고 후퇴하며 회피하게 되므로, "이동 방향 전방" 패널은 정작 안전한 방향(플레이어가 향하는 쪽)을 막을 뿐, 실제로 위협적인 탄이 오는 방향(플레이어가 물러나고 있는, 즉 적들이 있는 방향)은 전혀 막지 못하는 구조적 결함이 있었다. 고숙련자용으로 의도했더라도, 핵심 조작 구도(등지고 후퇴하며 사격)와 정면으로 충돌해 스트레스만 유발할 위험이 컸다.

  결정된 방식: 패널 위치를 **"이동 반대 방향(후방)"**으로 재정의한다. 즉 플레이어가 특정 방향으로 후퇴하고 있으면, 패널은 플레이어를 기준으로 그 반대편(=플레이어가 방금 있었던 자리, 대개 적들이 몰려있는 방향)에 생성되어 추격탄을 실제로 가로막는다. 구현상 플레이어의 facing 값(마지막으로 입력이 있었던 이동 방향)에 +π를 더한 각도를 패널 위치로 사용하면 별도의 상태 저장 없이 자연스럽게 구현된다. 무기 설명 문구도 "이동 방향 전방 반사 패널"에서 "이동 반대 방향(후방) 반사 패널 — 추격탄 차단"으로 수정한다.
