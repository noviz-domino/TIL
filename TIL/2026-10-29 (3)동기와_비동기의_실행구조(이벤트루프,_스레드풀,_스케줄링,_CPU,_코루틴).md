## 주제 1: 이번 혼란의 원인 — 용어가 나온 수준부터 구분한다

이 글의 재료는 [RAG Agent 연결과 스트리밍](https://ucanlabs.kr/classroom/aicampus-agent-python/lesson/1470/)의 사전 확인, 사용자가 붙여넣은 Gemini 문답 전체, 이후 Codex와 진행한 개념 질문·교정이다. 기존 TIL에 덧붙이지 않는 **2026-10-29의 세 번째 새 파일**이다. RAG 구현 완료 기록이 아니라 실행 구조를 이해하는 학습 기록이다.

### 용어 관계 지도

> ➕ **더 알아두기**
> 단어의 정의만 따로 외우면 다시 섞일 수 있다. 어느 계층의 용어인지 먼저 배치하고 연결한다.
>
> | 개념의 수준 | 용어 | 무엇을 말하는가 |
> |---|---|---|
> | CPU 하드웨어 | 프로세서·코어·하드웨어 스레드·SMT | 실제 명령 실행 자원 |
> | 운영체제 | 프로세스·소프트웨어 스레드·CPU 스케줄링 | 실행 흐름에 CPU 시간을 배정 |
> | 프로그램의 호출·I/O 방식 | 동기·비동기·블로킹·논블로킹 | 결과 대기와 실행 진행 방식 |
> | Python 비동기 런타임 | 코루틴·Task·이벤트 루프·협력적 스케줄링 | 같은 루프에서 비동기 작업 진행 |
> | FastAPI 요청 처리 | 경로 함수·Depends·스레드 풀·worker | 어떤 요청 코드를 어디에서 실행하는가 |
> | LangChain·LangGraph | invoke·ainvoke·stream·astream | 최종 결과 또는 중간 결과를 받는 API |
> | HTTP·네트워크 | SSE·응답 스트림·TCP·바이트 순서 | 결과를 전송·복원하는 방식 |

> ➕ **더 알아두기**
> “점유한다”, “기다린다”, “전환한다”는 말만으로는 부족하다. CPU 실행 자리를 점유하는지, 작업 스레드가 한 요청에 배정된 상태인지, Task가 네트워크 응답을 기다리는지 밝혀야 한다. 운영체제 스케줄러가 스레드를 바꾸는 것과 이벤트 루프가 Task를 바꾸는 것도 관리 대상이 다르다.

### 처음 서로 다른 구조를 가정했다

> ➕ **더 알아두기**
> 사용자의 초기 가정은 “A에게 전용 스레드 하나, B에게 전용 스레드 하나, 둘을 관리하는 공용 이벤트 루프 스레드 하나”였다. 반면 초기 설명은 “A·B가 한 이벤트 루프 스레드에서 Task로 실행되는 경우”를 전제로 했다. 이후 사용자는 “RAG 채팅은 비동기이고 다른 웹 기능은 동기인 혼합 구조”를 묻고 있었다고 분명히 했다. 서로 다른 구조를 놓고 같은 용어를 썼으므로 반문이 반복됐다.
>
> 설명 측도 “동기면 서버 전체가 멈춘다”, “점유는 CPU 이야기다”처럼 범위를 생략하거나 지나치게 단순화했다. 그 설명을 그대로 정답으로 남기지 않는다. 요청별 데이터 분리, 스레드별 실행, CPU 배정, Task 전환을 먼저 구분한 것이 이해의 전환점이었다.

> ♻️ 처음엔 “함수·기능·사용자마다 별도 스레드가 하나씩 있다”는 그림으로 이해했으나, 기본 함수 호출과 사용자 요청만으로 전용 스레드가 자동 생성되는 것은 아니며 서버의 실행 구조에 따라 배정된다는 것이 맞다.

## 주제 2: CPU·코어·하드웨어 스레드와 소프트웨어 스레드

### 같은 단어인 스레드의 두 의미

> ➕ **더 알아두기**
> | 용어 | 뜻 |
> |---|---|
> | CPU·프로세서(Processor) | 명령을 실행하는 하드웨어. 여러 코어를 포함할 수 있음 |
> | 코어(Core) | 명령어를 실제로 실행하는 물리 처리 자원 |
> | 하드웨어 스레드(Hardware Thread) | CPU가 제공하는 독립된 실행 상태·문맥. OS에는 논리 프로세서로 보임 |
> | 소프트웨어 스레드(Software Thread) | 운영체제가 관리하는 프로그램의 실행 흐름 |
>
> 이벤트 루프 스레드와 스레드 풀의 작업 스레드는 모두 소프트웨어 스레드이다. 이들이 코어 안에 영구적으로 들어 있는 것은 아니다. 운영체제가 실행할 스레드를 CPU의 논리 프로세서에 배정한다.

### 4코어·8하드웨어 스레드와 프로그램 스레드 100개

> ➕ **더 알아두기**
> 이 대화의 수치는 구조 설명용 가정이다.
>
> 1. CPU에는 물리 코어 4개가 있다.
> 2. 코어당 하드웨어 스레드 2개를 지원한다고 가정하면 논리 프로세서는 총 8개이다.
> 3. 프로그램·시스템에는 소프트웨어 스레드가 100개 이상 존재할 수 있다.
> 4. OS는 실행 가능한 스레드를 골라 최대 8개의 논리 실행 자리에 배정할 수 있다.
> 5. 나머지는 실행 차례를 기다리거나 I/O 등 조건을 기다린다.
> 6. OS가 배정을 바꾸면 이전 스레드는 멈춘 실행 상태에서 나중에 다시 이어간다.
>
> “최대 8개 배정”은 코어 8개와 같은 독립 계산 능력을 뜻하지 않는다. 같은 코어의 두 하드웨어 스레드는 코어 내부 자원을 공유한다. 모든 프로그램 스레드가 항상 실행 가능하거나 CPU를 필요로 하는 것도 아니다.

> ♻️ 처음엔 “CPU 사양의 스레드 수가 프로그램에서 만들 수 있는 스레드 수”로 이해했으나, 하드웨어 실행 문맥 수와 소프트웨어 스레드 수는 다르며 OS가 많은 실행 흐름을 번갈아 배정한다는 것이 맞다.

### 코어 수가 더 적은 이유와 SMT

> ➕ **더 알아두기**
> 코어 수보다 하드웨어 스레드 수가 항상 많은 것은 아니다. 둘이 같은 CPU도 있다. 4코어 8스레드 예시에서는 코어 하나가 두 실행 문맥을 제공하므로 논리 프로세서 수가 두 배인 것이다. 이런 동시 다중 스레딩을 SMT(Simultaneous Multithreading)라고 하며, Intel의 Hyper-Threading은 그 구현 중 하나이다.
>
> 코어 내부의 실행 자원이 특정 스레드에서 모두 사용되지 않을 때 다른 스레드의 명령어로 더 활용할 수 있다. SMT는 OS가 긴 시간 단위로 스레드를 교대하는 것과 같지 않다. 코어 내부에서 여러 스레드의 명령어가 같은 기간에 진행될 수 있지만 실행 장치·캐시 등은 공유한다.

> ♻️ 처음엔 “돌아가며 쓸 자리라면 코어당 스레드를 많이 늘릴수록 좋다”로 이해했으나, 실행 상태를 보관하는 하드웨어 비용과 공유 자원 경쟁이 있고 실제 계산 자원은 함께 늘지 않으므로 무조건 많을수록 좋은 것은 아니라는 것이 맞다.

> ➕ **더 알아두기**
> A·B가 코어의 계산 자원·메모리 대역폭을 충분히 사용 중이면 C·D 문맥을 추가해도 처리 능력이 비례해서 늘지 않는다. 효과가 작거나 자원 경쟁 때문에 느려질 수도 있다. SMT가 메우려는 코어 내부 빈 실행 기회와, 웹 비동기가 활용하려는 외부 API의 긴 I/O 대기는 수준과 시간 규모가 다르다. 둘 다 자원 활용과 관련 있지만 같은 기술은 아니다.
>
> 하드웨어 상태의 분리와 실행 자원 공유는 [Intel Hyper-Threading 설명](https://edc.intel.com/content/www/us/en/design/products/platforms/details/raptor-lake-s/13th-generation-core-processors-datasheet-volume-1-of-2/003/intel-hyper-threading-technology/)을 참고했다.

## 주제 3: 프로세스·스레드와 운영체제의 CPU 스케줄링

### 프로그램 파일과 실행 중인 프로세스를 구분한다

> ➕ **더 알아두기**
> 프로세스(Process)는 실행 중인 프로그램의 자원·주소 공간을 관리하는 단위이다. 스레드는 프로세스 안에서 명령어를 실행하는 흐름이다. 한 프로세스에 여러 스레드가 있을 수 있고, 별도 프로세스는 주소 공간을 별도로 가진다. 사용자 요청은 이 단위들과 일대일로 대응하지 않는다.
>
> 아래 그림은 학습용 구성이다.

```text
서버 컴퓨터
├─ CPU의 코어·논리 프로세서: 실제 명령 실행 자원
└─ 서버 프로세스
   ├─ 소프트웨어 스레드 1
   ├─ 소프트웨어 스레드 2
   └─ 소프트웨어 스레드 3

운영체제: 실행 가능한 소프트웨어 스레드를 CPU에 배정
```

### 스케줄링은 OS에만 쓰는 단어가 아니다

> ➕ **더 알아두기**
> 스케줄링(Scheduling)은 여러 작업 중 무엇을 언제 실행할지 정하는 넓은 개념이다. 다음 세 용례가 모두 가능하다.
>
> | 스케줄러 | 선택하는 대상 |
> |---|---|
> | 운영체제 CPU 스케줄러 | 실행 가능한 프로세스·스레드의 CPU 실행 |
> | 이벤트 루프 | 준비된 비동기 Task의 다음 실행 |
> | 예약 작업 실행기 | 정해진 시간·주기의 작업 |
>
> “무엇을 관리하는 스케줄러인지”를 붙여야 의미가 분명하다. 스케줄링이라는 말에 강제 중단이나 선점이라는 뜻이 자동 포함되는 것은 아니다.

### 스레드의 대기와 실행 가능 상태

> ➕ **더 알아두기**
> CPU에 배정되지 않았다는 사실만으로 모든 스레드가 같은 상태인 것은 아니다. 실행할 준비는 됐지만 CPU 차례를 기다리는 경우와, DB·네트워크·잠금 등의 조건이 끝나기를 기다려 당장 실행할 수 없는 경우를 구분한다. 일반적인 동기 I/O 대기에서 OS는 해당 스레드를 대기시키고 다른 실행 가능한 스레드에 CPU를 줄 수 있다. CPU가 반드시 바쁜 반복으로 응답을 감시하는 것은 아니다.
>
> Windows의 실제 스레드 우선순위·선점 개요는 [Microsoft Scheduling Priorities](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling-priorities)를 참고한다. 이번 실습에서 OS의 우선순위를 직접 바꾸거나 스케줄러를 계측하지는 않았다.

## 주제 4: CPU 점유와 작업 스레드 배정은 다른 이야기이다

> ➕ **더 알아두기**
> 이번 대화에서 가장 중요한 구분 중 하나이다.
>
> | 표현 | 실제 의미 |
> |---|---|
> | 스레드가 CPU에서 실행 중 | CPU 실행 자리를 배정받아 명령어 수행 |
> | 작업 스레드가 A에 묶임 | A 호출이 끝나지 않아 같은 작업 스레드에 새 B 작업을 맡길 수 없음 |
> | A Task가 비동기 대기 중 | A의 상태를 보관하고 같은 이벤트 루프가 다른 Task 진행 가능 |
>
> 동기 요청을 맡은 스레드가 DB 응답을 기다리면 CPU를 계속 사용하지 않을 수 있다. 그래도 호출이 끝나지 않았으므로 스레드 풀 관점에서는 그 스레드가 아직 A 작업을 처리 중이다.

### 운영체제가 선점해도 맡은 작업은 그대로이다

> ➕ **더 알아두기**
> 1. 작업 스레드 1이 A 요청 코드를 실행한다.
> 2. OS가 스레드 1의 CPU 실행을 중단하고 스레드 2를 실행할 수 있다.
> 3. 스레드 1에 CPU가 다시 배정되면 A 요청의 멈춘 부분부터 이어간다.
> 4. 스레드 1이 A 대신 새 B 요청으로 자동 교체된 것은 아니다.
>
> OS는 스레드 실행 상태를 전환한다. 일반적인 스레드 풀 내부에서 어떤 함수 호출이 끝났고 새 작업을 받을 수 있는지까지 바꿔 주는 것은 아니다.

> ♻️ 처음엔 “동기 작업이 스레드를 점유하므로 비선점 상태이고 CPU도 계속 독점한다”로 이해했으나, 동기 작업 배정은 유지돼도 OS가 그 스레드를 선점하거나 I/O 대기 상태로 둘 수 있으며 CPU의 지속 점유와는 다르다는 것이 맞다.

> ➕ **더 알아두기**
> 일반적인 동기 파일·네트워크 대기와 CPU를 계속 사용하는 긴 계산은 모두 호출이 끝나지 않는다는 점은 같지만 CPU 사용 양상은 다르다. “블로킹”을 곧 “CPU 100%”로 해석하지 않는다. 같은 이벤트 루프 스레드에서 둘 중 어느 작업을 직접 오래 실행하든 다른 Task의 진행을 지연시킬 수 있다는 점은 공통이다.

## 주제 5: 선점·비선점·협력적 전환·교착상태

### 선점은 강제 전환이 가능한가에 관한 분류이다

> ➕ **더 알아두기**
> 선점형(Preemptive) 스케줄링에서는 관리자가 실행 중인 작업의 실행 자원을 강제로 회수해 다른 작업을 진행시킬 수 있다. OS 예시에서는 스레드가 끝나지 않았더라도 시간 할당량·우선순위 등에 따라 CPU 배정을 바꾼다.
>
> 비선점형(Non-preemptive) 정책에서는 해당 작업이 끝나거나 대기 상태로 들어가 실행 자원을 내놓는 등의 계기가 있어야 다음 작업으로 바뀐다. 비선점형이라는 이유만으로 I/O를 기다리는 작업이 계속 CPU에서 실행해야 한다는 뜻은 아니다.

### Python Task 전환은 협력적이다

> ➕ **더 알아두기**
> Python asyncio 이벤트 루프는 한 Task를 실행하다가 그 Task가 실제 대기를 위해 제어권을 돌려주거나 완료하면 다른 준비된 Task를 실행한다. 이를 협력적 스케줄링(Cooperative Scheduling)이라고 한다. 같은 루프가 실행 중인 Task를 OS처럼 임의의 명령 사이에서 강제로 중단하고 다른 Task로 바꾸는 방식은 아니다.
>
> 따라서 하나의 실행 상황에서 OS 수준의 선점과 Task 수준의 협력적 전환이 동시에 존재할 수 있다. OS는 이벤트 루프 스레드를 선점할 수 있지만 그 스레드 안의 A Task를 B Task로 직접 바꿔 실행하지 않는다.

> ♻️ 처음엔 “동기 호출 자체가 비선점형이고 비동기는 선점형이다”로 이해했으나, 호출 방식과 스케줄러의 전환 정책은 서로 다른 분류이며 asyncio의 동기 호출 문제와 비동기 대기 모두 같은 협력적 루프 구조 안에서 봐야 한다는 것이 맞다.

> ♻️ 처음엔 “이벤트 루프가 동기인 것을 알아보고 기다려 주지만 원하면 강제로 빼앗을 수 있다”로 이해했으나, 루프도 같은 스레드에서 실행되는 코드이므로 동기 호출이 제어권을 돌려주기 전에는 다음 Task를 고르는 코드로 돌아오지 못한다는 것이 맞다.

### 양보가 교착상태를 자동 해결하는 것은 아니다

> ➕ **더 알아두기**
> 비동기로 대기하며 양보하는 주된 목적은 I/O 대기 시간을 다른 작업 진행에 활용하는 것이다. 교착상태(Deadlock)는 서로 필요한 자원·조건을 상대방이 쥔 채 기다려 아무도 진행하지 못하는 별도 문제이다.
>
> 예를 들어 A가 잠금 X를 가진 채 Y를 기다리고, B가 Y를 가진 채 X를 기다리면 둘 다 비동기로 대기해도 상대방이 자원을 놓지 않는 한 해결되지 않는다. 비동기에서도 자원 획득 순서·취소·시간 제한 등 별도 설계가 필요할 수 있다.

> ♻️ 처음엔 “비동기는 선점과 같고 교착상태 회피를 위해 양보하는 것”으로 이해했으나, 이 맥락의 비동기는 협력적으로 I/O를 기다리는 방식이고 교착상태를 자동으로 방지하지는 않는다는 것이 맞다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> CPU 스케줄링에서 라운드 로빈(Round Robin)은 시간 할당량을 이용하는 선점형 예시이고 FCFS(First-Come, First-Served)는 비선점형 예시이다. 선점형 정책을 OS 스레드에 적용하는 것과 asyncio Task의 협력적 전환을 구분한다. 교착상태는 자원 점유·대기의 관계 문제이며 “양보한다”는 표현만으로 회피 여부를 판단하지 않는다. 기사 용어의 학습 연결이며 LangGraph 함수의 출제 빈도를 단정하는 것은 아니다.

## 주제 6: 이벤트 루프는 어느 스레드에서 무엇을 하는가

### 별도의 감시 스레드가 옆에서 Task를 움직이는 그림이 아니다

> ➕ **더 알아두기**
> 실행 중인 이벤트 루프는 특정 스레드에서 돌아간다. 반드시 새로운 전용 스레드를 생성해야 하는 것은 아니고 메인 스레드에서 실행할 수도 있다. 이 글의 “이벤트 루프 스레드”는 루프가 실행되는 스레드를 가리킨다.

```text
한 소프트웨어 스레드에서 번갈아 실행되는 코드

이벤트 루프가 A Task를 선택
    ↓
A의 Python 코드 실행
    ↓ 실제 비동기 대기로 제어권 반환
이벤트 루프가 B Task를 선택
    ↓
B의 Python 코드 실행
```

> ➕ **더 알아두기**
> 루프가 작업을 선택하는 코드와 선택된 Task의 요청 처리 코드는 같은 스레드에서 실행된다. A가 동기 함수 안에서 오래 기다리거나 계산을 계속하면 루프도 다음 선택 단계로 돌아오지 못한다. A가 비동기 I/O를 실제로 기다리며 제어권을 돌려주면 다른 Task를 고를 수 있다.

### await가 보인다고 매번 무조건 다른 Task로 바뀌지는 않는다

> ➕ **더 알아두기**
> await는 기다릴 수 있는 작업의 완료를 연결하는 문법이다. 해당 작업이 이미 완료됐거나 내부에서 즉시 끝나면 그 await가 다른 Task의 실행 기회를 반드시 만든다고 보장하지 않는다. 반대로 실제로 대기 중인 비동기 I/O를 기다리면 현재 Task가 멈추고 루프가 다른 준비된 작업을 진행할 수 있다. “await마다 무조건 한 번씩 스위칭한다”로 외우지 않는다.
>
> 루프는 새 이벤트가 없을 때 I/O 알림 등을 기다릴 수 있다. 언제나 CPU를 사용해 각 요청을 끊임없이 확인해야 하는 바쁜 반복과 동일하지 않다. 내부 이벤트 감시 방식은 OS·루프 구현마다 달라 이번에는 자세히 계측하지 않았다.

> ♻️ 처음엔 “이벤트 루프를 돌리는 별도 스레드가 A·B 전용 스레드를 감시한다”로 이해했으나, 비동기 A·B Task는 같은 루프 스레드에서 번갈아 실행될 수 있고 Task마다 스레드가 필요한 것은 아니라는 것이 맞다.

## 주제 7: 스레드 풀과 비동기 Task가 공존하는 FastAPI 구조

### 공용 풀이라는 이름의 의미

> ➕ **더 알아두기**
> 스레드 풀(Thread Pool)은 작업용 스레드를 모아 두고 요청·작업마다 배정해 재사용하는 관리 방식이다. pool은 공동으로 사용하는 자원 묶음이다. 작업마다 스레드를 새로 만들고 없애는 비용을 줄이고 동시 실행 자원 수를 관리할 수 있다. 구현에 따라 필요할 때 스레드를 생성·증가시키기도 하므로 모든 스레드가 서버 시작 때 반드시 한꺼번에 만들어진다는 뜻은 아니다.
>
> A 작업을 맡은 스레드가 일을 끝내면 그 스레드를 C 작업에 재사용할 수 있다. A 사용자에게 영구 소유권이 생기는 것이 아니다. 사용 가능한 실행 여력이 없으면 새 작업은 대기할 수 있다. 구체적인 제한과 대기 정책은 사용하는 실행기·프레임워크에 따라 다르다.

### 사용자에게 적용된 최종 구조 그림

> ➕ **더 알아두기**
> “A·B 모두 비동기 RAG 채팅을 사용하며 다른 동기 웹 기능도 호출한다”는 혼합 구조를 한 worker로 단순화한 예시이다.

```text
FastAPI 서버 worker 프로세스 1개
│
├─ 이벤트 루프가 실행되는 스레드 1개
│  ├─ A의 비동기 RAG 요청 Task
│  └─ B의 비동기 RAG 요청 Task
│
└─ 공용 스레드 풀
   ├─ 작업 스레드 1: 배정받은 동기 요청 처리
   ├─ 작업 스레드 2: 배정받은 동기 요청 처리
   └─ 작업 스레드 3: 배정받은 동기 요청 처리
```

> ➕ **더 알아두기**
> 이 그림에 표시한 실행 스레드만 세면 1+3=4개이다. 이는 대화의 예시 숫자이며 현재 앱의 전체 스레드 수를 측정해 4개라고 확인한 것은 아니다. 런타임·라이브러리·재로더 등의 다른 스레드가 존재할 수도 있다. 실제로 프론트엔드나 DB 프로세스까지 포함한 시스템 전체 수와도 다르다.

### FastAPI가 자동으로 스레드에 맡기는 범위

강의의 비동기 Router·Service 연결과 일반 FastAPI 실행 규칙을 구분한다.

> ➕ **더 알아두기**
> | 구현 방식 | 기본 실행 위치·주의 |
> |---|---|
> | async def 경로 함수 | 이벤트 루프에서 비동기로 실행 |
> | 일반 def 경로 함수 | FastAPI가 공용 스레드 풀에 맡김 |
> | async def 경로 함수가 직접 호출한 일반 동기 Service | 호출한 루프 스레드에서 그대로 실행. 자동 오프로딩 아님 |
> | run_in_threadpool 등에 명시적으로 맡긴 동기 함수 | 작업 스레드에서 실행하고 호출 Task는 비동기로 결과 대기 |
>
> 모든 “다른 기능”이 자동으로 동기라는 뜻도 아니다. 기존 게시글·회원·댓글 API는 비동기로 연결했다. 이 표는 실제 함수를 어떤 방식으로 선언·호출하는지에 따른 규칙이다. [FastAPI의 경로 함수와 유틸리티 함수 설명](https://fastapi.tiangolo.com/async/#other-utility-functions)을 근거로 한다.

> ♻️ 처음엔 “비동기는 이벤트 루프, 나머지 모든 Service 함수는 자동으로 스레드 풀”로 이해할 수 있었으나, 일반 동기 경로 함수와 async 경로 내부에서 직접 호출한 동기 유틸리티는 다르게 처리된다는 것이 맞다.

> ♻️ 처음엔 “스레드 풀 전체는 동기 작업을 순차 처리한다”로 이해했으나, 여러 작업 스레드가 서로 다른 요청을 동시에 진행할 수 있고 각 스레드가 현재 맡은 동기 호출에 묶이는 것이라는 설명이 맞다.

## 주제 8: A·B 요청을 실제 시간 순서로 비교한다

### 같은 이벤트 루프에서 두 비동기 요청을 처리하는 경우

> ➕ **더 알아두기**
> CPU 코어 1개, 서버 프로세스 1개, 이벤트 루프 실행 스레드 1개를 가정한 설명용 시간표이다. A는 외부 AI 답을 5초 기다리고 B는 DB 답을 0.2초 기다린다고 둔다. 실제 벤치마크가 아니다.
>
> | 시점 | 이벤트 루프 스레드에서 하는 일 |
> |---|---|
> | 0초 | A의 요청을 받아 외부 AI 서버로 전송 |
> | 직후 | A가 실제 비동기 응답 대기로 제어권 반환 |
> | 0.1초 | B 요청을 처리하고 DB에 목록 조회 전송 |
> | 직후 | B도 DB 응답을 비동기로 대기 |
> | 0.3초 | B의 응답이 준비돼 B 처리를 이어서 실행하고 결과 전송 |
> | 5초 | A의 응답이 준비돼 A 처리를 이어서 실행하고 결과 전송 |
>
> 실행 순서는 A 요청 전송 → B 요청 전송 → B 응답 처리 → A 응답 처리이다. A·B의 Python 코드가 이 스레드에서 같은 순간 동시에 계산되는 것은 아니다. 외부 시스템의 응답을 기다리는 시간을 겹친 것이다. Gemini 답변 계산은 외부 서버가 수행하고 우리 루프는 요청·수신·전달을 처리한다.

### 동기 요청 두 개를 서로 다른 작업 스레드에 맡긴 경우

> ➕ **더 알아두기**
> 1. 풀의 스레드 1이 A 동기 요청을 맡고 외부 응답을 기다린다.
> 2. 풀의 스레드 2가 B 동기 요청을 맡아 처리한다.
> 3. A의 대기가 끝나면 스레드 1이 A 처리 후 풀에서 다른 작업을 받을 수 있게 된다.
>
> 이 경우 B를 처리할 수 있는 이유는 **다른 작업 스레드가 있기 때문**이다. 앞의 비동기 사례에서 B를 처리할 수 있는 이유는 **A가 제어권을 돌려주어 같은 루프 스레드를 활용하기 때문**이다. 설명 중 이 둘을 섞어 “동기가 같은 스레드의 대기 시간을 활용한다”고 말한 부분은 정정한다.

> ♻️ 처음엔 “동기를 사용하면 A의 대기 때문에 모든 사용자가 멈춘다”로 받아들였으나, 다른 스레드·worker가 처리할 수도 있으며 같은 이벤트 루프를 동기 호출로 막는 경우와 구분해야 한다는 것이 맞다.

### 공유 실행 자원과 데이터 분리는 별개이다

> ➕ **더 알아두기**
> 여러 요청이 같은 루프 스레드·연결 풀·CPU 시간을 공유할 수 있다는 사실이 A의 질문과 B의 질문이 섞여도 된다는 뜻은 아니다. 각 요청의 상태는 따로 관리해야 한다. RAG 그래프 객체를 앱에 공유해도 질문·검색 결과·답변 같은 실행 상태를 요청별로 다루는 것이 강의의 구조이다. 전역 가변 변수에 사용자별 상태를 무분별하게 저장해도 자동 분리된다는 뜻은 아니다.

## 주제 9: 코루틴·async def·코루틴 객체·Task·비동기 제너레이터

### 코드에 coroutine이라는 단어가 없는 이유

> ➕ **더 알아두기**
> async def는 문법이고 코루틴(coroutine)은 그 문법으로 만든 함수·실행 객체를 설명하는 개념 이름이다. def를 쓰고 그것을 함수라고 부르는 것과 같은 구분이다. coroutine이라는 별도 키워드를 코드에 적어야 하는 것은 아니다.

```python
async def ask_ai():
    return "답변"
```

> ➕ **더 알아두기**
> | 표현 | 의미 |
> |---|---|
> | async def | 비동기 함수를 선언하는 문법 |
> | ask_ai | 위 코드의 코루틴 함수 |
> | ask_ai() | 호출해서 생성한 코루틴 객체 |
> | await ask_ai() | 현재 작업에서 코루틴을 실행하고 완료를 기다림 |
> | Task | 이벤트 루프가 코루틴 실행 상태를 관리하는 단위 |
>
> 코루틴 함수를 호출해 객체를 만들었다는 것만으로 자동 실행·동시 실행이 시작되는 것은 아니다. await로 실행하거나 Task로 등록해 실행할 수 있다. await로 내부 코루틴을 호출할 때마다 반드시 별도 Task가 만들어지는 것도 아니다.

### 왜 코루틴이라고 부르는가

> ➕ **더 알아두기**
> 이름은 co-(함께)와 routine(실행 절차·흐름)을 연결한 것이다. 실행을 잠시 멈추고 나중에 그 지점부터 재개할 수 있는 실행 흐름들이 협력적으로 진행하는 특징을 가리킨다. 이름 자체가 CPU 병렬 실행이나 여러 스레드 생성을 뜻하지 않는다.
>
> A 코루틴이 AI 답을 기다리며 양보하면 다른 Task의 코루틴이 진행할 수 있고, A의 결과가 준비되면 멈춘 지점 다음부터 이어간다. 현재 함수의 지역 상태와 실행 위치를 보관할 수 있다는 점이 기본적인 중단·재개의 핵심이다.

### async def 안의 yield는 또 다른 종류이다

강의에서는 async def 안에서 yield로 여러 이벤트를 내보내고 호출자가 async for로 값을 받는 비동기 제너레이터를 사용한다. 일반적인 코루틴 함수와 구분한다.

> ➕ **더 알아두기**
> 비동기 제너레이터는 다음 값을 받을 때까지 비동기로 기다릴 수 있는 반복 대상을 만든다. await는 한 awaitable의 완료를 연결하고, async for는 다음 항목을 차례로 비동기로 요청한다. yield 하나가 곧 모든 상황에서 OS 스케줄링이나 다른 Task 실행을 반드시 발생시킨다고 외우지 않는다. 루프·소비자·실제 I/O 대기의 연결을 함께 봐야 한다.
>
> 코루틴 객체·Task·협력적 실행의 공식 정의는 [Python 3.13 Coroutines and Tasks](https://docs.python.org/3.13/library/asyncio-task.html)를 참고했다. 위 코드는 설명용이며 이번 요청에서 앱에 추가·실행한 구현 코드가 아니다.

## 주제 10: 동기·비동기와 블로킹, 언제 비동기가 유리한가

### 같은 뜻으로 외우지 않고 이 문맥에서 연결한다

> ➕ **더 알아두기**
> 동기·비동기는 작업의 결과를 받고 이어가는 인터페이스와 관련하고, 블로킹·논블로킹은 실행 흐름이 대기 때문에 막히는지와 관련한다. 더 엄밀한 시스템 API 분류에서는 둘을 별도 축으로 다룬다. 이번에는 흔히 쓰는 동기 블로킹 I/O와 await 가능한 비동기 I/O를 비교했다. 모든 동기 연산이 오래 막히거나 모든 async 함수가 자동으로 논블로킹이라는 뜻은 아니다.
>
> | 호출 상황 | 기다리는 동안의 결과 |
> |---|---|
> | 작업 스레드의 동기 I/O | 해당 작업 스레드는 호출에 묶임. OS는 다른 스레드 실행 가능 |
> | 이벤트 루프의 비동기 I/O 대기 | Task가 제어권을 돌려주면 같은 루프가 다른 Task 진행 가능 |
> | async 함수 안의 직접적인 동기 블로킹 호출 | 루프 스레드가 호출에 묶여 같은 루프의 다른 Task 진행 지연 가능 |
> | 동기 함수를 스레드 풀에 맡기고 비동기로 대기 | 작업 스레드는 사용하지만 이벤트 루프는 다른 Task 진행 가능 |

> ♻️ 처음엔 “비동기를 하면 블로킹이 생긴다”는 것으로 받아들일 수 있었으나, 비동기 대기 자체가 문제가 아니라 비동기 함수 안에서 동기 블로킹 코드를 직접 실행할 때 루프를 막을 수 있다는 것이 맞다.

### 100개의 대기 요청과 스레드 수

> ➕ **더 알아두기**
> 외부 AI 응답을 기다리는 요청 100개를 가정한다. 동기+스레드 풀에서는 동시에 실행 중인 각 요청이 작업 스레드에 묶이고, 풀의 실행 여력을 넘는 요청은 기다려야 한다. 비동기에서는 요청별 대기 상태를 Task로 보관해 하나의 루프 스레드에서 많은 대기를 관리할 수 있다. 네트워크 연결·메모리·API 제한 등 다른 자원은 여전히 필요하므로 무한 처리한다는 뜻은 아니다.
>
> OS 선점은 CPU를 다른 스레드에 줄 수 있게 한다. 그러나 대기 중인 동기 호출을 Task처럼 분해해 같은 작업 스레드에 B를 추가로 실행시키지는 않는다. 이것이 “OS 스케줄링이 있는데도 왜 비동기를 사용하는가”의 핵심 답이다.

### 단일 응답 시간과 처리량은 다르다

> ➕ **더 알아두기**
> 비동기를 썼다고 외부 Gemini가 답변 하나를 만드는 계산 시간이 짧아지는 것은 아니다. 대기 요청이 많이 겹칠 때 같은 실행 자원으로 다른 일을 처리할 수 있다는 이점이다. 요청이 적고 대기가 짧으면 체감 차이가 작을 수 있다. 동기+적절한 스레드·프로세스 구성으로도 동시 처리가 가능하다.
>
> 실시간 표시를 시작하는 시점, 한 요청의 전체 지연시간, 단위 시간당 처리량, 사용하는 스레드·메모리는 서로 다른 지표이다. 모두 “속도”라는 단어로 합쳐 판단하지 않는다. 비동기의 이익은 작업 특성과 구현에 따라 달라 실제 측정이 필요하다.

> ♻️ 처음엔 “동기와 비동기는 선점형 스케줄링이 있으면 결국 속도·유연성만 다른 것”으로 이해했으나, 둘 다 동시 처리가 가능하다는 점은 비슷해도 대기 상태를 어떤 실행 자원에 배치하는지가 다른 구조적 차이라는 것이 맞다.

### 왜 모든 것을 비동기로 통일하지 않는가

> ➕ **더 알아두기**
> 한 번 실행하고 끝내는 간단한 스크립트, 기존 동기 라이브러리, 작업 수가 적은 도구 등에서는 동기 API가 편리하다. 비동기는 이벤트 루프·취소·동시 작업 상태 관리 등을 함께 이해해야 한다. CPU 계산이 길다고 async 문법만 붙여 CPU 병렬 실행이 생기지도 않는다.
>
> “동기는 혼자 쓰는 스크립트에서만 가능하고 다중 사용자 서버에는 비동기가 필수”라는 제공 문답의 표현은 지나치다. 적절한 동기 서버·스레드·worker 구성도 가능하다. 이번 강의는 외부 I/O 대기가 긴 RAG를 기존 FastAPI 비동기 코드와 연결하므로 ainvoke·astream을 선택한다.

## 주제 11: 함수·기능·프로그램 개수와 스레드 수는 일치하지 않는다

### 기본 함수 호출은 호출한 스레드에서 실행된다

> ➕ **더 알아두기**
> 함수는 코드를 나누는 단위이고 스레드는 그 코드를 실행하는 흐름이다. 기본적으로 함수 A가 B를 호출하면 B도 호출한 같은 스레드에서 실행된다. 함수 세 개가 호출됐다고 스레드가 세 개 만들어지지 않는다.

```text
작업 스레드 1
└─ 로그인 경로 함수
   └─ 사용자 조회 함수
      └─ 비밀번호 검증 함수

별도 실행기에 맡기지 않았다면 같은 스레드의 호출 흐름
```

> ➕ **더 알아두기**
> 다른 스레드에서 실행하려면 직접 스레드를 만들거나 풀에 작업을 맡기거나 프레임워크가 그런 처리를 해줘야 한다. async 함수마다 스레드가 생기는 것도 아니다. FastAPI의 일반 def 경로 자동 오프로딩과 일반 def 유틸리티 직접 호출이 다른 이유가 여기에 있다.

> ♻️ 처음엔 “함수나 기능 단위가 하나의 스레드”로 이해했으나, 호출한 실행 흐름을 따라 같은 스레드에서 여러 함수가 실행될 수 있으며 별도 배정이 있어야 다른 스레드로 간다는 것이 맞다.

### 무거운 프로그램 하나도 여러 코어를 사용할 수 있다

> ➕ **더 알아두기**
> 프로그램 개수와 병렬 작업 수는 다르다. 영상 인코딩·렌더링 등은 하나의 프로그램 안에서 여러 스레드·프로세스로 나누어 실행할 수 있다. 반대로 핵심 작업이 한 스레드에서 순서대로 실행되면 코어 수만 늘려 그 구간을 크게 가속하기 어렵다.
>
> | 실행 특성 | 살펴볼 점 |
> |---|---|
> | 한 스레드가 핵심 CPU 작업 수행 | 코어 하나의 성능과 직렬 병목 |
> | 여러 실행 흐름이 병렬 CPU 작업 수행 | 물리 코어 수·메모리 자원·병렬화 효율 |
> | 외부 I/O 응답 대기가 큼 | 비동기·스레드 배치·연결 수 등 |
>
> CPU·메모리·GPU·네트워크 중 어디가 병목인지도 별개로 확인해야 한다. 이 대화에서 실제 CPU 구매 모델이나 성능 점수는 비교하지 않았다.

> ♻️ 처음엔 “무거운 프로그램 하나만 사용하면 많은 코어와 스레드가 불필요하다”로 이해했으나, 프로그램 하나도 여러 코어를 활용할 수 있으므로 프로그램 개수가 아닌 내부 작업의 병렬화 가능성을 봐야 한다는 것이 맞다.

> 📝 **기사 시험 포인트** (정보처리기사)
> 동시성(Concurrency)은 여러 작업이 겹치는 기간에 진행되는 구조이고 병렬성(Parallelism)은 여러 작업이 같은 시간에 실제로 실행되는 것을 말한다. 단일 이벤트 루프의 Task 전환으로 동시성을 만들 수 있지만 같은 스레드에서 두 Python 코드가 동시에 실행되는 것은 아니다. 프로그램·프로세스·스레드·하드웨어 실행 문맥의 개수도 일치하지 않는다.

## 주제 12: Docker·worker·서버 한 대라는 표현의 한계

> ➕ **더 알아두기**
> Docker 컨테이너는 애플리케이션 실행 환경을 격리·패키징하는 단위이다. 컨테이너 하나에 서버 프로세스를 하나만 실행하도록 구성할 수도 있고 여러 worker 프로세스를 실행할 수도 있다. 같은 컴퓨터에 컨테이너 여러 개를 배치할 수도 있다. Docker를 사용했다고 사용자별 전용 스레드나 코어가 자동으로 생기는 것은 아니다.
>
> | 표현 | 확인해야 하는 것 |
> |---|---|
> | 서버 한 대 | 물리 컴퓨터·가상 머신·서버 프로그램 중 무엇을 뜻하는가 |
> | 컨테이너 하나 | 그 안의 프로세스 수·CPU/메모리 제한은 무엇인가 |
> | worker 여러 개 | 서로 다른 서버 프로세스들이 요청을 분담하는가 |
> | 이벤트 루프 하나 | 어떤 프로세스의 어느 스레드에서 실행되는가 |
> | 공용 상태 | 프로세스 메모리·DB·외부 저장소 중 어디에 있는가 |
>
> 한 worker의 이벤트 루프가 블로킹됐다고 다른 worker까지 반드시 같은 순간에 멈춘다는 뜻은 아니다. 반대로 여러 worker가 있더라도 CPU·DB 연결·외부 API 한도 등은 공유 병목이 될 수 있다. worker 간 메모리가 자동으로 하나로 합쳐지는 것도 아니므로 그래프 같은 앱 초기화 객체의 수명도 프로세스 단위로 봐야 한다.

> ♻️ 처음엔 “물리 서버가 한 대이거나 Docker 컨테이너가 하나면 실행 흐름도 하나”로 이해할 수 있었으나, 컨테이너 수·프로세스 수·스레드 수·루프 수·CPU 제한은 서로 별도로 확인해야 한다는 것이 맞다.

> ➕ **더 알아두기**
> 현재 실습의 실제 Docker 배포·worker 개수·CPU affinity는 확인하거나 변경하지 않았다. 예시는 한 worker를 기준으로 한 개념 설명이다. 컨테이너를 새로 만들거나 여러 서버에 배포한 완료 기록으로 보지 않는다.

## 주제 13: RAG는 순서가 중요한데 왜 비동기를 쓰는가

강의의 RAG는 검색과 답변 생성이 고정된 순서로 실행되는 그래프이다.

```text
START → retrieve → generate → END

상태: question → 검색 documents → 생성 answer
```

검색 결과를 기반으로 답변해야 하므로 generate는 필요한 retrieve 결과가 준비된 뒤 실행한다. Service는 그래프를 실행하고 Router는 결과를 SSE 형식의 HTTP 응답으로 전송한다.

### 한 요청의 순서와 여러 요청의 진행은 다른 축이다

> ➕ **더 알아두기**
> A 질문 안에서는 검색 완료 → 검색 문서로 LLM 요청 → 답변 생성이라는 의존 순서를 지킨다. async라는 이유로 검색 결과 없이 답변 생성을 먼저 시작하거나 모든 단계를 동시에 실행하는 것이 아니다. A가 검색·LLM 응답을 기다리는 동안 루프는 B의 독립된 요청을 처리할 수 있다.
>
> | A 요청의 상태 | 같은 루프가 처리할 수 있는 다른 작업 예시 |
> |---|---|
> | 검색 결과를 비동기로 기다림 | B의 게시글 조회 준비 |
> | Gemini 답변을 비동기로 기다림 | C의 로그인 요청 준비 |
> | 답변 조각이 준비됨 | A의 조각 전달을 재개 |
>
> 다른 작업도 제대로 비동기로 대기하거나 적절히 오프로딩되어야 이 그림대로 진행할 수 있다. await를 붙인 함수 이름만으로 내부의 모든 검색·임베딩 작업이 자동 논블로킹이 되는 것은 아니다.

> ♻️ 처음엔 “절차를 지켜야 하는 RAG라면 비동기를 쓰면 안 되는 것 아닌가”로 의문이 생겼으나, 한 요청 안의 데이터 의존 순서는 유지하면서 외부 대기 중 다른 요청을 진행시키는 것이므로 모순이 아니라는 것이 맞다.

### Agent라는 이름과 자율적인 행동 선택을 구분한다

> ➕ **더 알아두기**
> “RAG 기반으로 답변하는 Agent”라는 이해는 기능의 큰 방향으로 맞다. 다만 이번 강의 그래프는 모든 질문에 검색과 생성을 수행하는 고정 워크플로이다. LLM이 검색 여부·도구 선택·반복 횟수를 스스로 결정하는 자율적인 Agent 구조까지 구현한 것은 아니다. Agent라는 이름만으로 내부 절차가 항상 동적이라고 가정하지 않는다.

### 기존 프로젝트에 이어서 적용할 수 있는가

강의는 기존 fastapi_agent의 로그인·chat 도메인·lifespan·React 화면에 RAG를 연결한다. .env의 GEMINI_API_KEY와 PDF 적재, Chroma 검색 컬렉션이 필요하다. 원문에서 rag-ingest 재실행은 기존 해당 컬렉션을 다시 만들므로 기존 데이터 여부를 확인해야 하는 작업이다.

> ➕ **더 알아두기**
> 별도 프로젝트를 새로 만드는 대신 현재 프로젝트 안에 src/rag, src/agents/rag, domains/chat의 요청·Service·Router, frontend의 질문 화면을 추가하는 방향을 확인했다. 하지만 이번 대화에서는 실제 API 키 설정·문서 적재·RAG 실행 구현을 아직 시작하지 않았다. 강의 본문을 확인했다는 사실과 실행 완료를 구분한다.

## 주제 14: 스트리밍과 비동기는 독립된 두 축이다

### 최종 결과와 중간 결과, 동기와 비동기

LangChain·LangGraph는 동기·비동기 호출과 최종·중간 결과 수신을 구분하는 API를 제공한다.

| 목적 | 동기 | 비동기 |
|---|---|---|
| 완료된 결과를 받음 | invoke() | await ainvoke() |
| 생성·진행 중의 결과를 받음 | for ... in stream(...) | async for ... in astream(...) |

비동기는 대기 중 실행 자원을 활용하는 방식이고, 스트리밍은 결과를 완성 전부터 나눠 전달하는 방식이다. ainvoke는 비동기로 실행하지만 호출자에게 최종 결과를 돌려준다. stream은 동기 방식으로도 중간 결과를 받는다.

### async 안에서 stream을 쓰면 자동으로 비동기가 되는가

> ➕ **더 알아두기**
> async def는 함수의 실행 인터페이스를 바꾸는 문법이지, 내부의 동기 호출을 모두 변환하는 마법이 아니다. stream의 일반 반복자는 다음 항목을 얻는 동안 호출한 스레드를 막을 수 있다. astream은 async for로 다음 값을 비동기로 기다릴 수 있는 인터페이스이다. 동기 stream을 쓰는 방식도 별도 실행 자원에 맡기는 등 적절한 배치를 하면 가능하지만, 이 강의의 비동기 요청 경로에서는 astream을 사용한다.

> ♻️ 처음엔 “async 함수를 만들고 그 안에서 stream을 사용하면 같은 것 아닌가”로 이해했으나, 함수 바깥의 선언과 내부 호출의 I/O·반복자 인터페이스는 별개여서 비동기용 astream이 필요하다는 것이 맞다.

### 모델의 최종 호출과 그래프의 토큰 스트림은 공존할 수 있다

강의에서는 노드 내부에서 await model.ainvoke를 사용하고 그래프 외부에서 astream의 messages·updates 모드로 읽는다. 스트리밍 지원 모델의 토큰 이벤트가 그래프 외부로 전달되는 구조이다.

| 모드 | 무엇을 받는가 | 용도 |
|---|---|---|
| messages | 메시지 조각과 실행 메타데이터 | generate 노드의 답변 조각 표시 |
| updates | 완료한 노드의 상태 변경 | 검색 문서·최종 답변 확인 |

> ➕ **더 알아두기**
> LangGraph 스트리밍 API의 형식은 버전·선택한 옵션에 따라 달라질 수 있다. 강의는 mode·data를 받는 흐름을 사용한다. 이번에는 문법·실행 원리만 확인했으며 설치된 LangGraph와 강의 코드의 실제 호환성은 구현 때 확인해야 한다. [LangGraph 스트리밍 문서](https://docs.langchain.com/oss/python/langgraph/streaming)를 참고한다.

## 주제 15: LLM 생성·토큰·문자·전송 조각을 구분한다

### 완성된 답을 타이핑 효과로 쪼개 보여주는가

> ➕ **더 알아두기**
> Gemini 사전 문답에서 사용자는 “AI 서버에 완성된 텍스트가 있고 for로 한 글자씩 보여주는가, 계산되는 중간 결과를 보내는가”를 물었다. 강의의 의도는 모델이 생성하는 중간 텍스트를 스트림으로 받아 전달하는 것이다. 완성본을 화면 타이머로 잘라 표시하는 가짜 타이핑 효과와는 구분한다.
>
> 일반적인 자기회귀 텍스트 생성은 앞의 문맥과 생성 내용을 바탕으로 다음 토큰을 결정하며 진행한다. 토큰은 한 글자나 단어와 일치하지 않는다. 선택도 언제나 최대 확률 토큰만 고르는 것으로 단정하지 않고 디코딩 설정에 따라 달라질 수 있다. 공급자 내부의 추론 최적화·버퍼링 구현까지 이번에 관찰한 것은 아니다.

### 토큰 생성과 chunk 전달은 일대일이 아니다

> ➕ **더 알아두기**
> | 단위 | 뜻 |
> |---|---|
> | 문자 | 사람이 읽는 글자 표현 |
> | 모델 토큰 | 모델이 처리하는 텍스트 단위 |
> | 스트림 조각(chunk) | 라이브러리·API가 이번에 전달한 일부 결과 |
> | SSE 이벤트 | event·data·빈 줄로 구분한 응용 메시지 |
> | 네트워크 수신 청크 | reader.read 등이 이번에 받은 바이트 묶음 |
> | TCP 세그먼트 | 전송 계층이 바이트를 운반하는 단위 |
>
> 한 조각에 여러 글자·토큰의 텍스트가 포함될 수 있다. 이벤트 하나가 여러 수신 청크로 나뉘거나 한 수신 청크에 여러 이벤트가 들어갈 수도 있다. “1글자 생성 → 1이벤트 → 1패킷”이라는 고정 대응은 없다.

> ♻️ 처음엔 “LLM은 한 글자씩 쓰고 for도 한 글자씩 받는다”로 이해할 수 있었으나, 글자·모델 토큰·API 조각·전송 단위는 다르며 실제 수신 경계가 일치하지 않는다는 것이 맞다.

### 외부 Gemini와 로컬 모델

> ➕ **더 알아두기**
> 외부 Gemini API도 스트리밍을 지원하므로 로컬 모델만 가능한 기능은 아니다. 외부 API에서는 모델 계산은 제공자 서버에서 수행하고 우리 서버는 결과 조각을 받아 브라우저로 전달한다. 로컬 모델을 쓰면 추론 자원의 위치가 바뀌므로 CPU·GPU·메모리 병목도 따로 확인해야 한다. 로컬 모델·서버·연동 라이브러리가 스트리밍을 지원하는지 역시 실제 설정에 따라 확인한다.
>
> [Gemini 텍스트 생성 공식 문서](https://ai.google.dev/gemini-api/docs/text-generation)의 스트리밍 지원을 참고했다. 이번 요청에서 Gemini 키를 사용해 실제 호출하거나 로컬 LLM을 설치·측정하지 않았다.

## 주제 16: 요청 수·SSE 형식·통신 오버헤드

### 1만 글자라고 1만 HTTP 요청이 되는 것은 아니다

강의의 브라우저는 질문을 POST /chat/rag/stream으로 보내고 하나의 HTTP 응답 본문에서 여러 SSE 이벤트를 읽는다. 일반 JSON 응답은 완성된 결과 하나를 받고, SSE는 text/event-stream 형식의 이벤트들을 순서대로 받는다.

| 구분 | 일반 JSON 응답 | SSE 스트리밍 응답 |
|---|---|---|
| Content-Type | application/json | text/event-stream |
| 본문 | 완성된 JSON | 여러 텍스트 이벤트 |
| 화면 표시 | 본문 수신·변환 후 | 받은 이벤트에 맞춰 점진적으로 갱신 |
| 읽는 방식 | response.json() | response.body의 바이트 스트림 처리 |

```text
브라우저 ── 질문 요청 ──→ 우리 FastAPI
브라우저 ←─ 여러 SSE 이벤트를 담은 응답 ── 우리 FastAPI

우리 FastAPI ── 모델 요청 ──→ 외부 Gemini API
우리 FastAPI ←─ 모델 결과 스트림 ── 외부 Gemini API
```

> ➕ **더 알아두기**
> 브라우저와 FastAPI의 한 질문 요청·응답 스트림을 기준으로 “요청 한 번”이라고 말한다. 시스템 전체에 통신이 딱 한 번만 있다는 뜻은 아니다. 인증·검색·임베딩·LLM 호출 등은 각기 별도 통신일 수 있고, 연결 중단·재시도도 별도 고려한다. HTTP 응답 스트림을 곧 물리 TCP 연결 전체와 일대일이라고 일반화하지 않는다. HTTP 버전에 따라 같은 연결에 여러 스트림을 사용할 수도 있다.

> ♻️ 처음엔 “1만 글자를 출력하면 최소 1만 번 요청·응답해야 한다”로 이해했으나, 답변 조각마다 새 HTTP 요청을 보내지 않고 한 응답 본문에서 여러 조각을 계속 받을 수 있다는 것이 맞다.

### 헤더는 매번 안 붙어도 부가 바이트는 있다

강의의 SSE 이벤트 예시는 다음과 같다. 마지막 빈 줄이 이벤트 경계이다.

```text
event: token
data: {"content":"AI 산업에서는 "}

event: token
data: {"content":"인프라 투자가 확대되고 있습니다."}

```

> ➕ **더 알아두기**
> 한 HTTP 응답의 헤더가 event마다 새 HTTP 응답 헤더로 반복되는 것은 아니다. 그러나 event·data 라벨, JSON 필드명과 구분자, 전송 계층·암호화 등의 부가 데이터는 존재한다. 조각이 지나치게 작으면 본문 대비 형식 오버헤드가 커질 수 있다. “한 응답이므로 일반 JSON과 통신 비용이 전혀 같다”는 제공 설명은 수정한다.
>
> 모델 API의 과금과 네트워크 바이트·연결 유지 비용도 구분한다. 스트리밍 조각마다 새 생성 요청을 하는 것은 아니지만, 실제 요금은 모델·서비스 정책·실제 토큰 사용량·옵션 등에 따라 확인해야 한다. “항상 정확히 같은 금액”이라는 단정이나 이번에 실제 과금을 비교했다는 기록은 남기지 않는다. 오늘은 가격표를 조사하거나 유료 호출을 실행하지 않았다.

### 화면에서 이벤트 이름에 따라 처리한다

강의는 status·sources·token·done·error 이벤트를 구분한다. status는 진행 안내, sources는 참고 문서, token은 누적할 텍스트, done은 최종 답변·출처·시간, error는 실패 안내이다. SSE의 done은 이 API가 정한 이벤트 이름이며 네트워크 reader의 done과 다른 수준이다.

> ➕ **더 알아두기**
> 이번 대화에서는 SSE를 직접 구현하지 않았으므로 최종 이벤트 처리·시간 제한·중단 복구가 동작한다고 확인하지 않았다. 그래프 이벤트 → Service 데이터 → Router의 SSE 직렬화 → 브라우저 파서 → React 누적이라는 경계는 다음 실습에서 코드로 확인할 대상이다.

## 주제 17: 전송 순서·TCP 시퀀스 번호·수신 경계

### 라우팅 경로 변경과 애플리케이션 전달 순서는 다르다

> ➕ **더 알아두기**
> 사용자는 패킷이 다른 경로로 오면 도착 순서가 바뀔 수 있지 않느냐고 물었다. 실제 네트워크에서는 재정렬·유실·재전송이 발생할 수 있다. 그렇다고 TCP를 사용하는 애플리케이션이 무작위 순서의 바이트를 그대로 받는 것은 아니다. TCP는 시퀀스 번호·확인 응답·재전송 등의 기제로 순서 있는 바이트 스트림을 제공한다. 해결할 수 없는 연결 실패가 생기면 스트림이 끊기거나 오류가 날 수 있으므로 “항상 전체 답변이 100% 도착한다”는 보장과는 다르다.

### TCP 번호는 글자·토큰 번호가 아니다

> ➕ **더 알아두기**
> TCP 시퀀스 번호는 바이트 스트림의 위치를 기준으로 한다. 임의로 “이 패킷은 1번, 저 패킷은 2번”만 매기는 것과 다르고, SSE의 content 글자나 LLM 토큰 번호를 나타내지도 않는다. 유실·분할·재전송이 있어도 바이트 순서를 복원하는 것은 전송 계층의 책임이다.
>
> 반면 API에 직접 넣는 event id·index는 응용 수준의 의미를 가질 수 있다. 하나의 정상적인 응답 스트림에서 단순 텍스트를 덧붙이는 데 개발자가 별도 정렬 번호를 반드시 넣어야 하는 것은 아니다. 재연결·재생·중복 제거·여러 생산자 메시지 병합 등 요구가 생기면 별도 설계가 필요할 수 있다. SSE의 선택적인 id도 TCP 시퀀스 번호와 같은 것은 아니다.

> ♻️ 처음엔 제공 답변의 “인덱스가 없다”는 표현과 TCP 순서 번호 설명이 모순으로 보였으나, 응용 JSON에 직접 넣는 번호가 불필요한 경우와 TCP 내부에 바이트 순서 정보가 존재하는 것은 서로 다른 수준의 설명이라는 것이 맞다.

### 순서는 있어도 메시지 경계까지 보존되는 것은 아니다

> ➕ **더 알아두기**
> TCP의 순서 있는 바이트 스트림은 SSE 이벤트 경계를 그대로 한 번의 read에 맞춰 주는 기능이 아니다. 한글 UTF-8 문자도 바이트 경계에서 나뉠 수 있다. 따라서 브라우저는 스트리밍 TextDecoder로 문자를 복원하고, 버퍼에서 줄·빈 줄 경계를 찾아 이벤트를 구성해야 한다. 정상 순서 전달과 이벤트 파싱은 둘 다 필요하다.
>
> 한 HTTP 스트림을 소비하는 일반적인 텍스트 누적 예시에서는 전송 순서를 활용한다. LangGraph 자체가 모든 외부 네트워크 패킷 순서를 보장하기 때문이라고 설명하지 않는다. 또한 모든 현대 HTTP가 TCP 위에서만 동작한다고 일반화하지 않고 여기서는 TCP를 사용하는 HTTP 연결을 기준으로 한다. [TCP 표준 RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)을 참고했다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> TCP는 전송 계층(Transport Layer)의 프로토콜이고 HTTP·SSE의 응용 데이터와 구분한다. 시퀀스 번호(Sequence Number), 확인 응답(Acknowledgment), 재전송(Retransmission)을 순서·신뢰성 기제와 연결한다. IP 패킷 도착 순서와 애플리케이션 바이트 전달 순서는 같지 않다. 여기서 말한 네트워크 라우터와 FastAPI Router도 서로 다른 개념이다.

## 주제 18: 이해가 막힌 이유와 앞으로 질문·설명하는 방법

### 어디에서 이해가 바뀌었는가

> ➕ **더 알아두기**
> 사용자는 처음부터 “OS가 스케줄링해 주는데 왜 비동기를 또 쓰는가”라는 유효한 질문을 하고 있었다. 이해가 막힌 이유를 단순히 기초 지식 부족으로 결론 내리지 않는다. 다음 전제들이 뒤섞인 것이 주요 원인이었다.
>
> - 함수·기능·사용자마다 스레드가 있다고 가정했다.
> - 하드웨어 스레드와 프로그램 스레드를 같은 수로 생각했다.
> - OS의 스레드 선점과 이벤트 루프의 Task 전환을 같은 관리자 동작으로 보았다.
> - “스레드에 작업이 배정된 상태”와 “CPU를 계속 사용하는 상태”를 점유라는 단어로 함께 말했다.
> - 비동기 Task끼리의 경우와 동기·비동기가 공존하는 FastAPI 구조를 구분하지 않았다.
> - 스트리밍·비동기·병렬 실행을 같은 이점으로 묶었다.
>
> 설명 측도 “서버 전체가 멈춘다”는 식의 과장, 사용자 전제 그림 확인 누락, 같은 단어의 계층 미표시로 혼란을 늘렸다. 사용자가 A·B 스레드와 루프 스레드의 그림을 직접 제시한 뒤 실제 차이를 확인할 수 있었다.

### 사용자가 요청한 설명 방식

> ➕ **더 알아두기**
> 사용자는 “비유는 사람으로 하지 말고 스레드로 하라”고 요청했다. 앞으로 실행 구조는 사람·카페 같은 비유보다 실제 프로세스·스레드·Task 도표와 단계로 설명한다. “용어 구분부터”, “어떤 개념에서 나온 용어인지 관계를 먼저”라는 사용자 결론도 다음 학습의 기준으로 남긴다.
>
> 권장 순서는 다음과 같다.
>
> 1. 용어가 속한 계층과 같은 단어의 여러 의미를 구분한다.
> 2. CPU·프로세스·스레드·루프·Task 개수의 가정을 먼저 고정한다.
> 3. 사용자가 생각한 구조 그림이 맞는지 확인한다.
> 4. A·B 요청이 시간에 따라 어느 스레드에서 실행되는지 표시한다.
> 5. 각 “기다림”의 주체, 점유하는 자원, 제어권을 넘기는 지점을 명시한다.
> 6. 실제 앱 구조·실험 결과와 설명용 가정을 구분한다.

### 효과적인 질문 문장

> ➕ **더 알아두기**
> - “내가 이해한 구조는 A 스레드·B 스레드·루프 스레드가 따로 있다는 거야. 이 그림부터 맞는지 확인해줘.”
> - “지금 말한 스레드는 CPU 사양의 스레드야, 프로그램의 스레드야?”
> - “누가 무엇을 기다리고, 어떤 자원을 점유하고 있는지 정확히 말해줘.”
> - “같은 스레드에서 B를 처리한다는 거야, 다른 스레드가 B를 맡는다는 거야?”
> - “한 worker와 스레드 풀 3개를 가정하고 요청 두 개를 시간 순서로 보여줘.”
> - “이 동작은 OS가 해주는 거야, 이벤트 루프가 해주는 거야, FastAPI가 해주는 거야?”
> - “이 함수 호출만으로 새 스레드·Task가 생기는지 구분해줘.”
>
> 전문 용어를 더 많이 쓰는 것보다 머릿속 전제와 관리 단위를 먼저 보여주는 것이 효과적이었다. 이것은 이번 대화의 관찰이며 사용자의 일반적인 학습 능력에 대한 진단이 아니다.

### 설명한 것·저장한 것·실행한 것을 구분한다

> ➕ **더 알아두기**
> 이번 구간에서 수행한 것은 강의 사전 읽기, 제공 문답 읽기, 공식 문서 대조와 개념 설명이다. 새 RAG API·Chroma 적재·Gemini 유료 호출·Docker 배포·스레드 수 계측·성능 비교를 수행하지 않았다. 예시 타임라인과 4개 스레드 그림은 실측 결과가 아니다. 오늘 앞선 두 TIL의 앱 구현·테스트 기록과 이 구간을 섞지 않는다.
>
> 제공된 Gemini 문답은 질문의 좋은 출발점이지만 “항상·무조건·정확히 같다”는 중간 설명을 그대로 학습 결론으로 삼지 않는다. 동기 서버도 동시 처리가 가능하고, 토큰과 글자는 다르며, 요금·TCP 연결·HTTP 응답 수는 서로 다른 항목이다. 이 글에는 교정한 의미를 남겼다. 원본 파일에 포함된 질문·답변은 실제로 읽었지만, 이 요청으로 그 원본이나 앱 코드를 수정하지 않았다.

## 정리

- 먼저 개념의 수준을 구분한다. 하드웨어 → 운영체제 → 호출·I/O → asyncio → FastAPI → LangGraph → HTTP·네트워크의 역할을 섞지 않는다.
- 코어는 실제 계산 자원이고 하드웨어 스레드는 논리 실행 문맥이다. 프로그램 스레드 수와 일치하지 않는다.
- 함수·기능·사용자마다 전용 스레드가 생기지 않는다. 기본 함수는 호출한 스레드에서 실행된다.
- OS는 스레드의 CPU 실행을 관리하고, 이벤트 루프는 같은 스레드 안의 Task를 협력적으로 진행한다.
- 동기 작업에 스레드가 배정되어 있다는 것과 CPU를 계속 독점하는 것은 다르다. OS 선점 후에도 해당 스레드는 원래 작업을 이어간다.
- 같은 루프에서 비동기로 대기하면 다른 Task를 실행할 수 있다. 동기 블로킹 호출을 직접 실행하면 루프 자체가 다음 선택 단계로 돌아오지 못한다.
- FastAPI의 한 worker에는 이벤트 루프와 공용 작업 스레드가 공존할 수 있다. 일반 def 경로와 async 경로 내부의 일반 def 호출을 구분한다.
- RAG는 한 요청 안의 검색·생성 순서를 유지하면서 다른 요청과 I/O 대기 시간을 겹칠 수 있다.
- 스트리밍은 결과 전달 방식이고 비동기는 대기·진행 방식이다. stream과 astream은 그 차이를 반영한다.
- 코루틴은 async def 문법으로 만드는 중단·재개 가능한 실행 개념이다. Task·스레드·비동기 제너레이터와 구분한다.
- 문자·토큰·chunk·SSE 이벤트·수신 바이트·TCP 세그먼트는 일대일로 대응하지 않는다.
- RAG 실습과 성능 검증은 아직 시작하지 않았으므로 다음에는 구현과 계측으로 확인한다.
