## 1. 환경변수

### 왜 쓰나

API 키나 비밀번호를 코드에 직접 적으면, GitHub에 올라가는 순간 전 세계에 공개된다.
한 번 올라간 키는 git 기록에 남아 완전히 지우기 어렵다.

```python
api_key = "sk-abcd1234"    # 이 파일을 push 하면 키가 노출된다
```

환경변수는 **값을 코드 밖(운영체제)에 두고, 코드에는 이름만 적는** 방식이다.

```python
import os
api_key = os.environ.get('API_KEY')    # 코드에 키가 없다
```

### os 모듈로 다루기

```python
import os

os.environ['SERVICE_KEY'] = 'abcd1234'          # 설정

port = os.environ['SERVICE_KEY']                # 없으면 KeyError
db_host = os.environ.get('DB_HOST', 'localhost') # 없으면 기본값
```

`os.environ`은 **딕셔너리처럼 동작**한다. `[]`와 `.get()`의 차이가 딕셔너리와 같다.

`os.getenv('X')` == `os.environ.get('X')` (같은 것, 짧은 버전)

### .env 파일 + python-dotenv

코드로 값을 설정하면 결국 코드에 값이 남으므로, 별도 파일에 적어둔다.

```bash
pip install python-dotenv
```

`.env` (프로젝트 최상위 폴더에 위치)
```
DEBUG=True
SECRET_KEY=c3f9a2b1e4d5
PORT=8000
```
- 등호 앞뒤 **공백 없음**
- 값에 **따옴표 없음**

```python
import os
from dotenv import load_dotenv

load_dotenv()                       # .env 를 읽어 환경변수로 등록
secret_key = os.getenv('SECRET_KEY')
```

### .gitignore 로 반드시 차단

`.env`에 비밀이 들어있으므로 git에 올라가면 의미가 없어진다.

```
.env
.env.local
.env.*.local
```

> ➕ **더 알아두기**
> 7월 29일에 배운 "이미 커밋된 키는 `.gitignore`에 추가해도 소용없다"는 원칙이 여기서도 그대로다. `.env`를 프로젝트에 만들자마자, 값을 채우기 전에 `.gitignore`부터 등록하는 순서를 지켜야 한다.

### 함정: 값은 항상 문자열

```python
port = os.getenv('PORT')        # "8000"  (문자열!)
port = int(os.getenv('PORT'))   # 8000    (숫자로 변환 필요)
```

`DEBUG=False` 도 읽으면 `"False"` 라는 **내용 있는 문자열**이라 `if debug:` 가 참이 된다. 자주 나는 버그.

## 2. 클래스와 self

### 왜 클래스를 쓰나

클래스가 없으면 한 사람의 정보가 흩어지고, 짝을 맞추는 책임이 전부 나에게 있다.

```python
name1, age1 = "김철수", 25
name2, age2 = "이영희", 30

introduce(name1, age2)    # 철수 이름 + 영희 나이. 파이썬은 막아주지 않는다
```

클래스는 데이터와 기능을 한 덩어리로 묶어서, **짝 맞추는 일을 파이썬에게 넘긴다.**

```python
p1.introduce()            # 괄호가 비어있다. 짝이 어긋날 수 없다
```

### `__init__`

객체를 만들 때 자동 실행되는 함수. `Person(...)` 이 실행시킨다.

```python
p1 = Person("김철수", 25)
```
1. 파이썬이 **빈 덩어리**를 만든다
2. 그 덩어리를 `self`에 넣고 `__init__` 실행
3. 채워진 덩어리를 돌려준다 → `p1` 에 담긴다

`p1` 이라는 이름은 `__init__` 이 **끝난 뒤에** 붙는다.

### self = 점(.) 앞에 쓴 것

```python
p1.introduce()          # 파이썬은 이렇게 실행한다 → Person.introduce(p1)
```

**점 앞에 있는 것이 첫 번째 매개변수로 들어간다.** 이 규칙 하나로 전부 설명된다.

```python
def __init__(self, name, age):     # 매개변수 3개
p1 = Person("김철수", 25)           # 넣은 값 2개
```
차이나는 1개(`self`)는 파이썬이 자동으로 채운다. **값은 자동으로 넣어주지만 받을 자리는 내가 적어야 한다.**

`self`는 예약어가 아니라 그냥 첫 번째 매개변수 이름. `me` 로 바꿔도 동작한다(관례상 `self`를 쓴다).

### self.name = name 의 좌우는 다른 것

```python
def __init__(self, name):
    self.name = name
```
- 오른쪽 `name` : 괄호로 받은 값. `__init__` 끝나면 사라짐
- 왼쪽 `self.name` : **덩어리 안에 저장**. 계속 남음

`self.` 가 붙으면 "이 덩어리 것", 안 붙으면 "클래스 전체 것"(클래스 변수).

```python
class Person:
    population = 0            # 클래스 변수 — 모두가 공유
    def __init__(self, name):
        self.name = name      # 인스턴스 변수 — 덩어리마다 따로
```

> ➕ **더 알아두기**
> 8월 13일에 배운 참조·복사 개념이 여기서도 그대로 적용된다. `self`는 결국 **그 인스턴스(덩어리)를 가리키는 하나의 메모리 주소**이고, `self.name = name`은 그 주소가 가리키는 공간 안에 값을 저장하는 것이다. 클래스 변수(`population`)를 인스턴스 여러 개가 공유하는 이유도 같다 — 모든 인스턴스가 `self.population`으로 읽을 때는 각자 자기 것을 안 갖고 있으니 클래스라는 같은 주소를 함께 바라보기 때문이다.

## 3. 매직 메서드 (던더, `__`)

### 규칙

던더는 **파이썬이 정해진 상황에서 자동으로 부르는 메서드**다. `__init__` 도 그중 하나일 뿐이다.

| 내가 쓰는 코드 | 파이썬이 자동 호출 |
|---|---|
| `Person("김철수", 25)` | `__init__` |
| `print(p)`, `str(p)` | `__str__` |
| `len(p)` | `__len__` |
| `p1 == p2` | `__eq__` |
| `p1 < p2` | `__lt__` |
| `del p` | `__del__` |

### 던더 이름은 약자다

| 던더 | 약자 | 담당 |
|---|---|---|
| `__init__` | **init**ialize | 만들 때 안 채우기 |
| `__str__` | **str**ing | 글자로 바꾸기 |
| `__len__` | **len**gth | 길이 알려주기 |
| `__eq__` | **eq**ual | 같은지 판단 |

이름이 곧 업무다. `__init__` 은 "초기화"만 담당하고 "글자로 바꾸기"는 안 한다.

### print 와 __str__ 의 관계

```python
print(p)
```
파이썬 내부 처리:
1. `p.__str__()` 실행 → 글자를 받음
2. 그 글자를 화면에 출력

`print`는 **파이썬 내장 함수(내가 부르는 쪽)**, `__str__`은 **내 클래스 안(불려지는 쪽)**. 서로 다른 편이다.

`__str__` 은 **출력하지 않고 `return` 으로 글자를 돌려준다.** (안에 `print` 를 쓰면 안 됨)

### 안 만들면 어떻게 되나

```python
print(len(p))
# TypeError: object of type 'Person' has no len()
```

`__str__` 이 없으면 `<__main__.Person object at 0x...>` 가 나온다.
→ 이건 최상위 부모 `object` 가 가진 기본 `__str__` 이다 (상속으로 설명됨).

### 무엇을 반환할지는 내가 정한다

```python
def __len__(self):
    return len(self.hobbies)    # 취미 개수를 길이로 볼지
    # return len(self.name)     # 이름 글자수를 길이로 볼지 — 내가 결정
```

파이썬은 **"언제 실행될지"만 연결**하고, 내용은 내가 정한다.

### 이름을 바꿀 수 없다

`self` 는 이름을 바꿔도 되지만(위치가 규칙), 던더는 **이름 자체가 규칙**이라 못 바꾼다.

```python
def to_text(self):     # __str__ 대신 다른 이름
    return "..."

print(p)               # <__main__.Person object at 0x...>  ← 안 먹힘
```

`__` 는 **"내가 지은 이름이 아니라 파이썬과 약속된 이름"** 이라는 표시다.
- `__` 붙은 것 → 파이썬이 부른다
- 안 붙은 것 → 내가 직접 부른다

## 4. 데코레이터 원리

### 핵심: `@X` 는 대입문의 줄임말

```python
@trace_log
def walk(self):
    ...
```
는 정확히 아래와 같다.
```python
def walk(self):
    ...
walk = trace_log(walk)      # ← @ 안에 숨어있는 코드
```

**함수 이름도 그냥 변수**라서 다른 값으로 갈아끼울 수 있다. `@` 는 이 대입을 대신 해준다.

역할 정리:
- `trace_log` (@ 뒤) : **호출되는 쪽**
- `walk` (아래 함수) : **재료로 넘겨지는 쪽** (실행되지 않음)
- `walk` (이름) : **결과를 받는 쪽**

괄호를 안 쓰는 이유: `@` 가 괄호와 인자를 대신 넣어준다.

### 실행 시점이 두 개로 나뉜다

```python
def trace_log(func):
    print("[B] trace_log 본체")
    def wrapper(self):
        print("[D] wrapper")
        return func(self)
    return wrapper

class Person:
    @trace_log
    def walk(self):
        print("[E] 원본 walk")
```

| 시점 | 실행되는 것 | 횟수 |
|---|---|---|
| **class 를 읽을 때** | `trace_log` 본체 `[B]` | **딱 한 번** |
| **`p.walk()` 부를 때** | `wrapper` 내부 `[D][E]` | **부를 때마다** |

`p.walk()` 는 실제로 `wrapper` 를 실행한다. 원본 `walk` 은 `wrapper` 안에 `func` 라는 이름으로 보관되어 있다.

`@` 가 하는 일은 **실행이 아니라 포장/등록**이다.

### wrapper 는 붙인 개수만큼 만들어진다

`def wrapper` 는 "만들어라"는 지시라서, `trace_log` 를 3번 부르면 wrapper 가 3개 생긴다. 각자 자기 `func` 를 품는다.

### 두 종류의 데코레이터

| 종류 | 예시 | 정의 위치 |
|---|---|---|
| 파이썬 내장 | `@property`, `@classmethod`, `@staticmethod` | 이미 들어있음 (안 써도 됨) |
| 직접 만든 것 | `@trace_log` | **내 파일, 클래스보다 위**에 작성 |

직접 만든 것은 클래스보다 **위**에 있어야 한다(파이썬은 위에서 아래로 읽음).

## 5. @property / @setter / @classmethod / @staticmethod

### @property — 괄호 없이 쓰게 만든다

```python
@property
def full_name(self):
    return f"{self.last_name}{self.first_name}"

print(p.full_name)        # 괄호 없음
```

**왜 괄호를 없애나:** 쓰는 쪽에서 일관성이 생긴다. `p.first_name`(속성)과 `p.full_name`(계산값)이 똑같이 보인다. 계산값인지 저장값인지는 클래스 내부 사정이므로 쓰는 사람이 알 필요가 없다.

**저장 방식과의 차이:**
```python
self.full_name = f"{first} {last}"    # __init__ 에서 저장하면
p.first_name = "철수"
print(p.full_name)                     # 옛 값이 남는다
```
`@property`는 **부를 때마다 새로 계산**하므로 항상 최신이다.

**제약:** 괄호가 없으니 인자를 넘길 수 없다 → `self` 하나만 받는다.
**기본은 읽기 전용:** setter 없이 대입하면 `AttributeError`.

### @setter — 대입(`=`)을 함수 호출로 바꾼다

```python
@property
def age(self):
    return self._age

@age.setter
def age(self, value):
    if value < 0:
        print("나이는 음수일 수 없습니다.")
    else:
        self._age = value
```

**동작 조건: `p.age` 가 `=` 의 왼쪽에 있을 때.**

| 코드 | 실행되는 것 |
|---|---|
| `p.age = 25` | **setter** |
| `print(p.age)`, `x = p.age` | property |
| `if p.age > 20:` | property |

`x = p.age` 는 `=` 가 있지만 오른쪽이라 읽기다.

### 작동 원리 — 파이썬은 대입할 때 클래스를 먼저 본다

```
p.age = 25 실행
  └─ Person 클래스에 age 라는 property 가 있나?
       ├── 없다 → p 안에 age 칸을 만들어 저장
       └── 있다 → 그 property 의 setter 실행
```

**이 확인이 대입할 때마다 매번 일어난다.** 그래서 나중에 property를 추가하면 기존의 `p.age = 25` 코드를 한 글자도 안 고쳐도 전부 setter를 거친다. 이게 setter의 존재 이유.

클래스가 인스턴스보다 **우선**이므로 우회할 수 없다. setter 없는 property면 대입 시 에러(읽기 전용).

### `_age` 를 쓰는 이유

`@property def age` 를 만든 순간 `age` 는 **값 저장소가 아니라 함수(통로)** 가 된다. 그래서 실제 값을 담을 다른 이름이 필요하다.

setter 안에서 `self.age = value` 라고 쓰면 → 또 setter 호출 → **무한 반복**.
`self._age = value` 는 평범한 변수라 그냥 저장되고 끝난다.

| 이름 | 정체 |
|---|---|
| `age` | 함수 (통로) |
| `_age` | 실제 값이 저장되는 곳 |

### 밑줄 정리

| 표기 | 예시 | 접근 |
|---|---|---|
| 앞에 1개 | `_age` | **그대로 접근 가능.** 관례상 "내부용" 표시뿐 |
| 앞에 2개 | `__age` | 이름이 `_Person__age` 로 바뀜. 우회하면 접근 가능 |
| 앞뒤 2개 | `__str__` | private과 무관. 파이썬 약속된 이름 |

**Python 에는 Java 의 private 같은 진짜 접근 제한이 없다.** 차단이 아니라 안내와 검사가 파이썬 방식.

### property/setter 의 이름이 같아야 하는 이유

`@` 규칙대로 결과가 `def` 뒤의 이름에 담기기 때문이다.

```python
age = property(age함수)       # ① 읽기만 있는 property
age = age.setter(age함수)     # ② 읽기+쓰기 있는 property 로 덮어씀
```

이름이 다르면 property 가 두 개로 갈라진다. 파이썬은 `p.age = 25` 에서 **`age` 라는 이름**을 찾으므로, 완전한 property 가 `age` 에 있어야 한다.

### @classmethod — cls(클래스)를 받는다

```python
class Person:
    population = 0

    @classmethod
    def get_population(cls):
        return cls.population

print(Person.get_population())    # 인스턴스 없이 호출
```

일반 메서드로 만들면 `self` 에 넣을 인스턴스가 필요해서, "전체 인구수"를 알려고 사람을 한 명 만들어야 한다. `cls` 는 클래스 자체(`Person`)가 들어간다.

### @staticmethod — 아무것도 안 받는다

```python
@staticmethod
def is_adult(age):
    return age >= 19

print(Person.is_adult(20))
```

`self`, `cls` 둘 다 필요 없는 기능. 밖에 함수로 만들어도 동작하지만, 관련된 것을 클래스에 모아두면 찾기 쉽다.

### 전체 비교 — 첫 매개변수로 구분된다

| | 첫 매개변수 | 쓰는 방법 |
|---|---|---|
| 일반 메서드 | `self` (인스턴스) | `p.introduce()` |
| `@property` | `self` (인스턴스) | `p.age` — 괄호 없음 |
| `@setter` | `self, value` | `p.age = 25` — 대입 |
| `@classmethod` | `cls` (클래스) | `Person.get_population()` |
| `@staticmethod` | 없음 | `Person.is_adult(20)` |

### 실무 기준

파이썬에서 `get_age()` / `set_age()` 를 만드는 건 "자바 습관"으로 본다.
1. **기본**: 아무것도 안 쓰고 `self.age = age`
2. 계산해서 만드는 값 → `@property` (자주 씀)
3. 검사가 꼭 필요한 속성 → `@setter` (드물게 씀)

Java는 "나중에 필요할까봐 미리" getter/setter를 만들고, Python은 "일단 단순하게 쓰고 필요해지면 감싼다".

## 6. 상속

### 왜 쓰나

비슷한 클래스에 같은 코드가 복붙된다. 공통 부분을 부모로 뽑으면 한 곳만 고치면 된다.

```python
class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age
    def walk(self):
        print(f"{self.name}이 걷습니다.")

class Student(Person):          # 괄호에 부모 클래스
    def study(self):
        print(f"{self.name}이 공부합니다.")
```

```python
s = Student("김철수", 20)
s.walk()          # Person 것을 물려받아 씀
s.study()         # Student 자기 것
```

- `Person` = 부모(상위/기반) 클래스
- `Student` = 자식(하위/파생) 클래스

### 핵심 원리

> **자기 클래스에서 찾고, 없으면 부모로 올라간다. 먼저 찾은 것을 쓴다.**

```
s.walk() 실행
1. Student 에 walk 있나? → 없음
2. 부모 Person 에 walk 있나? → 있음 → 실행
```

### 오버라이딩 — 자식이 같은 이름으로 다시 정의

```python
class Person:
    def greet(self):
        print("안녕하세요.")

class Employee(Person):
    def greet(self):
        print("안녕하십니까, 업무를 시작합니다.")
```

자식에서 **먼저 찾아서 멈추므로** 자식 것이 이긴다. 부모 것을 지운 게 아니라 먼저 발견된 것이다. `Person` 인스턴스는 여전히 원래 것을 쓴다.

### super() — 부모 것도 쓰면서 추가

```python
class Developer(Person):
    def __init__(self, name, language):
        super().__init__(name)       # 부모 __init__ 실행
        self.language = language

    def introduce(self):
        super().introduce()          # 부모 것 먼저
        print(f"주력 언어는 {self.language}입니다.")
```

오버라이딩 = 부모 것 버리고 새로 하기
super() 사용 = **부모 것을 하고 나서 추가하기**

**self 는 왜 안 쓰나:** `super()` 가 이미 `self` 를 들고 있다. 점 앞의 것이 첫 매개변수로 들어가는 규칙 그대로다.

```python
super().__init__(name)          # 이것과
Person.__init__(self, name)     # 이것이 같다 (클래스로 부르면 self 를 직접 씀)
```

**super() 를 쓰는 이유:** 부모 이름이 바뀌어도 안 고쳐도 되고, 다중 상속에서 MRO 순서를 따라간다.

### 다중 상속

```python
class Professional(Person, Job):    # 부모 여러 개, 콤마로
    pass
```

### MRO (Method Resolution Order)

메서드를 찾는 순서. 두 규칙을 동시에 만족하는 순서다.

1. **왼쪽 우선** — `class D(B, C)` 면 B가 C보다 먼저
2. **부모는 자기를 상속한 모든 클래스 뒤에 온다**

**다이아몬드 (A가 공통 부모)**
```
    A
   / \
  B   C     →  [D, B, C, A, object]
   \ /
    D
```
A는 B, C 둘 다의 부모 → **둘 다 지난 뒤에** A.

`D → B → A → C` 가 안 되는 이유: C는 A의 자식인데 A보다 뒤에 오면 규칙 위반. 실제로도 C가 A를 오버라이딩했다면 C의 것이 이겨야 하는데 A가 먼저 실행돼버린다.

**부모가 서로 다를 때**
```
  A     E
  |     |
  B     C   →  [D, B, A, C, E, object]
   \   /
     D
```
A를 상속한 건 B 하나뿐 → 기다릴 이유가 없으니 B 다음 바로 A. **한 계보를 끝까지 올라간 뒤** 다음 계보로.

정리: **나중에 다시 만날 클래스만 남겨둔다.**

> ➕ **더 알아두기**
> 이 규칙의 정식 이름은 **C3 선형화(C3 Linearization)** 알고리즘이다. 파이썬 2.3부터 도입됐다. 이름까지 알아둘 필요는 없지만, "MRO는 그냥 파이썬이 대충 정하는 게 아니라 정해진 알고리즘으로 계산된 것"이라는 정도는 알아두면 좋다.

### MRO 는 언제 계산되나

**클래스를 정의할 때 한 번** 계산되어 저장된다. 메서드를 부를 때마다 재계산하지 않는다.

```python
class A: pass          # A.__mro__ = (A, object)
class B(A): pass       # B.__mro__ = (B, A, object)
class C(A): pass       # C.__mro__ = (C, A, object)
class D(B, C): pass    # D.__mro__ = (D, B, C, A, object)
```

각 클래스가 **자기 차례에 자기 것을 완성**하고, 다음 클래스가 그걸 재료로 쓴다(계단처럼 쌓임).
`D` 를 계산할 때 `B`, `C` 의 MRO 는 이미 완성된 목록으로 저장돼 있으므로, "C를 아직 모르는" 상황은 없다. 탐색이 아니라 **완성된 목록들을 합치는 계산**이다.

```python
print(D.__bases__)    # (B, C)                — 내가 괄호에 쓴 직접 부모
print(D.__mro__)      # (D, B, C, A, object)  — 계산된 전체 순서
```

### 재귀처럼 메모리를 먹지 않는다

결과가 **평평한 목록 하나**다. 클래스가 100개 얽혀도 100칸 목록 하나. 호출 스택이 쌓이는 재귀와 구조가 다르다.

실제로 걱정할 것은 성능이 아니라 **사람이 읽기 어려워지는 것**. 그래서 실무에서는 단일 상속을 주로 쓴다.

순서를 만들 수 없는 구조는 클래스 정의 시점에 막힌다.
```python
class C(A, B): pass    # B(A) 일 때
# TypeError: Cannot create a consistent method resolution order (MRO)
```

### object

모든 클래스의 최종 부모. 아무것도 상속하지 않아도 자동으로 붙는다.
`__str__` 을 안 만들었을 때 나오던 `<__main__.Person object at 0x...>` 가 `object` 의 기본 `__str__` 이다.

### 언제 상속을 쓰나

**"자식은 부모다" 가 성립할 때.**
- 학생은 사람이다 → `class Student(Person)`
- 자동차는 엔진이다? → 아니다. 자동차가 엔진을 **가지고 있다** → Composition (다음 주제)

## 오늘의 핵심 규칙 5개

1. **`self` = 점(`.`) 앞에 쓴 것.** `p1.introduce()` → `Person.introduce(p1)`
2. **`@X` = `함수 = X(함수)`.** 데코레이터는 대입문의 줄임말이고, 클래스 정의 시점에 한 번 실행된다.
3. **던더는 파이썬이 정해진 상황에 자동으로 부르는 약속된 이름.** 연결만 파이썬이 하고 내용은 내가 정한다.
4. **파이썬은 대입할 때마다 클래스를 먼저 확인한다.** 그래서 property/setter 를 나중에 추가해도 기존 코드에 적용된다.
5. **상속은 자기 클래스에서 찾고 없으면 부모로 올라간다. 부모는 자기를 상속한 모든 클래스 뒤에 온다(MRO).**
