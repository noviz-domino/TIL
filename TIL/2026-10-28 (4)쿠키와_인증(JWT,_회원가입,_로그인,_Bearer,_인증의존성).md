## 주제 1: 인증·인가와 HTTP 무상태

원문은 [쿠키, 세션, 토큰](https://ucanlabs.kr/classroom/aicampus-agent-python/lesson/1454/)과 [회원가입, 로그인](https://ucanlabs.kr/classroom/aicampus-agent-python/lesson/1455/)이다. 아래는 강의 예제의 설명이며 현재 board-practice에 인증 코드나 라이브러리를 설치한 기록이 아니다.

인증(Authentication)은 사용자의 신원을 확인하는 과정이며 로그인은 대표적 절차이다. 인가(Authorization)는 확인한 사용자에게 해당 행동을 허용할 권한이 있는지 판단하는 과정이다. 관리자만 공지사항을 작성하게 하는 것은 인가이다.

| 인증 | 권한 | 강의의 비유와 의미 |
|---|---|---|
| 실패 | 확인 전 | 신분증 없이 입장 불가: 신원 확인부터 실패 |
| 성공 | 없음 | 신분은 확인했지만 입장 자격 없음 |
| 성공 | 있음 | 신원과 자격이 모두 확인되어 허용 |

HTTP는 무상태(Stateless)라 각 요청을 독립 처리한다. HTTP 자체가 이전 요청의 로그인 사실을 자동 기억하지 않으므로 다음 요청에서 확인할 세션 ID나 토큰을 전달하는 방식을 사용한다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> 인증은 신원 확인, 인가는 접근 권한 판단이다. 로그인한 사용자라도 다른 사람의 게시글 수정 권한은 없을 수 있다. 접근 통제와 연결해 이 둘을 구분한다. 이 구분을 이해하는 것과 특정 회차 출제 빈도를 주장하는 것은 다르다.

## 주제 2: 쿠키·서버 세션·토큰·JWT

| 개념 | 어디에 무엇을 두며 무슨 일을 하는가 |
|---|---|
| Cookie | 브라우저가 작은 값을 저장하고 조건에 맞는 요청에 자동 전송하는 수단 |
| 로그인 Session | 서버 저장소의 사용자 상태를 클라이언트가 제시한 세션 ID로 조회하는 방식 |
| Token | 인증·권한 확인을 위해 제시하는 값 |
| JWT | 정보를 담고 서명할 수 있는 토큰 형식 중 하나 |

쿠키와 세션·JWT는 서로 배타적인 대안이 아니다. 쿠키 안에 세션 ID를 저장할 수도 JWT를 저장할 수도 있다. 쿠키의 Expires/Max-Age는 만료 시각·남은 초, HttpOnly는 JS 직접 접근 차단, Secure는 HTTPS에서만 전송하도록 제한하는 속성이다.

서버 세션의 사용자 ID·상태는 DB·메모리·Redis 등에 저장하고 클라이언트에는 식별용 ID를 준다. 서버에서 그 세션을 만료·삭제할 수 있다. 토큰 방식은 로그인 때 발급한 값을 클라이언트가 보관하고 인증 요청 때 제시하면 서버가 검증한다.

> ➕ **더 알아두기**
> 이 글의 로그인 Session과 SQLAlchemy Session은 같은 이름을 쓰지만 다른 개념이다. 전자는 여러 HTTP 요청에 걸친 사용자 상태, 후자는 ORM 객체와 DB 작업의 관리 도구이다. 로그인 세션을 닫는 것과 ORM Session.close는 서로 다른 동작이다.

## 주제 3: JWT 구조·검증·로그아웃

JWT(JSON Web Token)는 JSON 정보를 담는 표준 형식이다. 강의는 일반적인 서명형 JWT의 헤더·페이로드·서명을 다룬다. 헤더에는 알고리즘·타입, 페이로드에는 claim(주체에 대한 정보), 서명에는 위변조 검증 정보를 둔다.

| Claim | 의미 | 강의 값 |
|---|---|---|
| sub | 토큰의 주체 | 사용자 ID를 문자열로 변환 |
| iat | 발급 시각 | UTC 현재 시각 |
| exp | 만료 시각 | 발급 시각에 유효기간을 더한 시각 |

Base64URL 인코딩은 암호화가 아니므로 페이로드를 읽을 수 있다. 비밀번호·JWT 서명 키를 토큰에 넣지 않는다. HS256은 서버 비밀 키로 서명·검증한다. 디코딩해 읽는 것과 서명·만료·필수 claim을 검증하는 것은 다르며, 검증 안 된 사용자 ID·권한을 신뢰하지 않는다.

JWT는 자체 정보를 가져 서버 간 확장에 유리할 수 있지만 세션 ID보다 큰 경우가 많고 발급한 토큰을 만료 전 개별 취소하기 어렵다. 토큰에 담긴 권한만 믿으면 서버의 권한 변경이 즉시 반영되지 않는다.

Access Token은 리소스 접근용, Refresh Token은 Access Token 재발급용이다. 역할의 이름이지 JWT 같은 형식의 이름이 아니다. Refresh Token은 선택 사항이며 보통 더 오래 유효하고 서버 저장소에서 폐기 가능하도록 관리하기도 한다.

로그아웃에서 서버 세션은 서버 기록과 클라이언트 쿠키를 정리한다. JWT는 클라이언트에서 토큰을 삭제해 이후 제시하지 않게 할 수 있지만 이미 발급된 Access Token 자체가 자동 무효화되는 것은 아니다. Refresh Token 폐기는 재발급을 막는 것이며 기존 Access Token의 효력과 구분한다.

> 📝 **기사 시험 포인트** (정보보안기사)
> 인코딩·암호화·해시는 다르다. 서명 검증은 무결성·출처 검증에 관련되며 페이로드 기밀성을 제공하는 것과 다르다. Bearer 토큰은 소지자가 사용할 수 있으므로 노출을 막아야 한다. 복호화해서 원문을 얻는 방식과 비밀번호 해시 검증을 구분한다.

## 주제 4: 회원가입 모델·입력·해싱

| API | 기능 | 정상 코드 |
|---|---|---|
| POST /auth/signup | 회원가입 | 201 |
| POST /auth/login | 로그인·Access Token 발급 | 200 |
| GET /me | 인증 사용자 정보 | 200 |

security.py는 비밀번호·JWT, dependencies.py는 토큰 추출과 사용자 제공을 담당한다. 강의 설치 명령은 다음과 같다.

```bash
uv add "pwdlib[argon2]" pyjwt
openssl rand -hex 32
```

생성한 비밀 키는 .env의 JWT_SECRET_KEY에 두고 저장소에 올리지 않는다. JWT_EXPIRE_MINUTES는 유효 시간(분)이다. 강의 실습값은 반복 로그인을 줄이려는 3000분이며 운영용 권장값으로 해석하지 않는다. 환경변수 기본값은 코드에서 30분으로 설정한다. 최초 import 시 읽으므로 .env 변경 후 서버 재시작이 필요하다.

```python
# security.py

import os
from pathlib import Path

from dotenv import load_dotenv

load_dotenv(Path(__file__).with_name(".env"))

JWT_SECRET_KEY = os.environ["JWT_SECRET_KEY"]
JWT_EXPIRE_MINUTES = int(os.getenv("JWT_EXPIRE_MINUTES", "30"))
```

User 모델은 user_auth 테이블에 id 자동 기본키, 이메일 최대 254자·고유·필수, hashed_password 최대 255자·필수, created_at을 둔다. 생성 시각은 timezone=True인 DateTime과 server_default=func.now()로 DB에서 설정한다.

```python
# mysite_auth/models/user.py

from datetime import datetime

from sqlalchemy import DateTime, String, func
from sqlalchemy.orm import Mapped, mapped_column

from database import Base


class User(Base):
    __tablename__ = "user_auth"

    id: Mapped[int] = mapped_column(primary_key=True, autoincrement=True)
    email: Mapped[str] = mapped_column(String(254), unique=True, nullable=False)
    hashed_password: Mapped[str] = mapped_column(String(255), nullable=False)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now(), nullable=False
    )
```

```python
# mysite_auth/schemas/user.py

class UserCreate(BaseModel):
    email: EmailStr = Field(max_length=254)
    password: str = Field(min_length=15, max_length=128, repr=False)


class UserResponse(BaseModel):
    id: int
    email: EmailStr
    created_at: datetime

    model_config = ConfigDict(from_attributes=True)
```

repr=False는 모델 출력 표현에서 비밀번호를 빼는 설정이다. 원문을 DB에 저장하거나 응답에 포함해도 된다는 뜻이 아니다. 응답 DTO에는 해시도 넣지 않는다. EmailStr로 형식 검증하고 이 앱은 이메일을 소문자로 통일해 저장·조회한다.

Argon2id는 비밀번호 추측의 연산·메모리 비용을 높인다. 무작위 salt로 같은 비밀번호의 해시가 달라지고 원문을 복호화하지 않는다.

```python
# security.py

from pwdlib import PasswordHash

password_hash = PasswordHash.recommended()


def hash_password(password: str) -> str:
    return password_hash.hash(password)
```

```python
# mysite_auth/services/auth_service.py

def signup(self, db: Session, data: UserCreate) -> User:
    email = str(data.email).lower()
    hashed_password = hash_password(data.password)

    with db.begin():
        if user_repository.find_by_email(db, email) is not None:
            raise HTTPException(
                status_code=status.HTTP_409_CONFLICT,
                detail="이미 등록된 이메일입니다.",
            )
        user = User(email=email, hashed_password=hashed_password)
        user_repository.save(db, user)

    return user
```

해싱 후 트랜잭션에서 이메일 중복 확인·사용자 저장을 수행한다. 이름만 미리 확인한다고 동시 요청의 중복까지 보장되는 것은 아니며 DB UNIQUE 제약도 실제 중복을 막는다. 이 강의 코드를 현재 앱에 복사·실행한 것은 아니다.

## 주제 5: 로그인 검증·JWT 생성

```python
# mysite_auth/schemas/user.py

class UserLogin(BaseModel):
    email: EmailStr = Field(max_length=254)
    password: str = Field(min_length=1, max_length=128, repr=False)


class TokenResponse(BaseModel):
    access_token: str
    token_type: Literal["bearer"] = "bearer"
```

로그인 입력 길이는 1~128자로 회원가입의 15~128자 조건과 다르다. Literal은 token_type 값을 bearer로 제한한다. 잘못된 이메일과 잘못된 비밀번호를 같은 401 응답으로 처리한다.

```python
# security.py

from pwdlib.exceptions import UnknownHashError


def verify_password(password: str, hashed_password: str) -> bool:
    try:
        return password_hash.verify(password, hashed_password)
    except UnknownHashError:
        return False
```

입력값을 새 salt로 해싱해서 저장 문자열과 직접 비교하지 않는다. verify가 저장 해시의 salt·매개변수로 검증한다. 해시 형식을 인식하지 못해도 실패로 처리한다.

```python
# security.py

from datetime import datetime, timedelta, timezone

import jwt

ALGORITHM = "HS256"


def create_access_token(user_id: int) -> str:
    now = datetime.now(timezone.utc)
    payload = {
        "sub": str(user_id),
        "iat": now,
        "exp": now + timedelta(minutes=JWT_EXPIRE_MINUTES),
    }
    return jwt.encode(payload, JWT_SECRET_KEY, algorithm=ALGORITHM)
```

PyJWT가 시각을 숫자 타임스탬프로 변환한다. 토큰에는 사용자 식별자와 시각만 담고 비밀번호·서명 키를 넣지 않는다.

```python
# mysite_auth/services/auth_service.py

def login(self, db: Session, data: UserLogin) -> str:
    email = str(data.email).lower()
    with db.begin():
        user = user_repository.find_by_email(db, email)
        if user is None or not verify_password(data.password, user.hashed_password):
            raise authentication_error("이메일 또는 비밀번호가 올바르지 않습니다.")

        user_id = user.id

    return create_access_token(user_id)
```

회원가입·로그인 Router는 get_db 의존성을 사용하고, 로그인 응답의 Cache-Control: no-store와 Pragma: no-cache로 토큰 응답의 캐시를 제한한다. Response 매개변수는 응답 헤더를 설정하는 객체이다.

```python
@router.post("/signup", response_model=UserResponse, status_code=status.HTTP_201_CREATED)
def signup(data: UserCreate, db: Annotated[Session, Depends(get_db)]):
    return auth_service.signup(db, data)


@router.post("/login", response_model=TokenResponse)
def login(data: UserLogin, db: Annotated[Session, Depends(get_db)], response: Response):
    access_token = auth_service.login(db, data)
    response.headers["Cache-Control"] = "no-store"
    response.headers["Pragma"] = "no-cache"
    return TokenResponse(access_token=access_token)
```

위 라우터의 prefix는 /auth이다. 강의가 생략한 모듈 import·router 준비와 함께 사용되는 조각이며 현재 프로젝트의 완성 파일로 제시한 것이 아니다.

## 주제 6: 토큰 추출·검증·인증 의존성

401 응답의 WWW-Authenticate: Bearer는 요구하는 인증 방식을 알린다.

```python
def authentication_error(
    detail: str = "유효하지 않거나 만료된 토큰입니다.",
) -> HTTPException:
    return HTTPException(
        status_code=status.HTTP_401_UNAUTHORIZED,
        detail=detail,
        headers={"WWW-Authenticate": "Bearer"},
    )
```

```python
def decode_access_token(token: str) -> int:
    try:
        payload = jwt.decode(
            token,
            JWT_SECRET_KEY,
            algorithms=[ALGORITHM],
            options={"require": ["sub", "iat", "exp"]},
        )
        return int(payload["sub"])
    except (jwt.InvalidTokenError, ValueError, TypeError):
        raise authentication_error() from None
```

서버에서 허용 알고리즘을 고정하고 필수 claim 존재·서명·만료 등 PyJWT의 검증을 거친다. 검증된 sub를 정수로 바꾸는 데 실패해도 인증 실패이다. 다음 Service는 실제 사용자가 아직 존재하는지까지 조회한다.

```python
def get_current_user(self, db: Session, token: str) -> User:
    user_id = decode_access_token(token)
    user = user_repository.find_by_id(db, user_id)
    if user is None:
        raise authentication_error()
    return user
```

클라이언트 헤더는 `Authorization: Bearer <access_token>` 형태이다. HTTPBearer는 헤더를 분리하고 Swagger 인증 입력 UI도 제공하지만 JWT 서명 검증 자체를 대신하는 것은 아니다.

```python
# dependencies.py

from typing import Annotated

from fastapi import Depends
from fastapi.security import HTTPAuthorizationCredentials, HTTPBearer

from database import SessionLocal
from mysite_auth.schemas.user import UserResponse
from mysite_auth.services.auth_service import auth_service
from security import authentication_error

bearer_scheme = HTTPBearer(bearerFormat="JWT", auto_error=False)


def get_current_user(
    credentials: Annotated[HTTPAuthorizationCredentials | None, Depends(bearer_scheme)],
) -> UserResponse:
    if credentials is None:
        raise authentication_error("로그인이 필요합니다.")
    with SessionLocal() as db:
        user = auth_service.get_current_user(db, credentials.credentials)
        return UserResponse.model_validate(user)
```

credentials.scheme은 Bearer, credentials.credentials는 접두사를 제외한 JWT 문자열이다. auto_error=False이면 누락·잘못된 방식에서 None을 받아 직접 401을 처리한다. 인증용 별도 Session이 열려 있을 때 ORM User를 UserResponse로 변환해 반환하고 닫는다. 인증 조회로 이미 자동 시작한 트랜잭션과 이후 쓰기 Service의 begin이 충돌하지 않도록 이 강의는 인증 조회와 쓰기 Session을 분리한다.

> ➕ **더 알아두기**
> 이는 이 강의의 트랜잭션 경계를 명확히 하기 위한 설계이다. 모든 앱에서 인증·쓰기 Session을 반드시 두 개 사용해야 한다는 보편 규칙은 아니다. Session 수명과 트랜잭션 시작 위치를 일관되게 설계하는 것이 핵심이다. 필요한 값만 DTO로 복사하면 닫힌 인증 Session의 지연 로딩에 의존하지 않을 수 있다.

## 주제 7: 내 정보·Swagger 시험 절차·실패 응답

```python
@router.get("/me", response_model=UserResponse)
def get_me(current_user: Annotated[UserResponse, Depends(get_current_user)]):
    return current_user
```

의존성이 먼저 검증하고 사용자 DTO를 전달하므로 Router는 인증된 값만 반환한다. 모든 API에 자동으로 인증이 생기는 것이 아니라 해당 의존성을 사용하는 API에 적용된다.

강의 시험 절차는 다음과 같다. 예시 이메일 learner@example.com과 비밀번호 my-long-password-123으로 POST /auth/signup 후 같은 입력으로 /auth/login한다. 응답은 access_token과 token_type: bearer이다. Swagger의 Authorize Value에는 토큰만 넣으며 Bearer 접두사는 UI가 붙인다. /me가 반환하는 id·email·created_at을 확인하고 UI Logout 후 재요청하면 401이다. 여기의 이메일·암호는 강의의 공개 예시이며 실제 사용자의 계정이 아니다.

| 요청·실패 상황 | 상태 코드 |
|---|---|
| 이메일 중복 가입 | 409 |
| 이메일 형식·암호 길이 위반 | 422 |
| 미가입 이메일·틀린 암호 로그인 | 401 |
| 토큰 없는 /me | 401 |
| 변조·만료·필수 claim 누락 토큰 | 401 |
| 토큰은 검증되지만 사용자 삭제됨 | 401 |

이 TIL 작성 중 회원가입·로그인 요청을 실제 전송하지 않았고 토큰·비밀 키도 생성하거나 저장하지 않았다. 단순히 /docs가 열린다는 것만으로 인증과 오류 케이스를 검증한 것이 아니다.

## 정리

쿠키는 전달 수단, 로그인 세션은 서버 상태 방식, 토큰은 제시할 값, JWT는 그 형식이다. 인증과 인가는 다르고 비밀번호 해싱과 JWT 서명도 다르다. 사용자 입력의 검증·해시·고유 제약·서명 검증·사용자 존재 확인·응답 DTO의 정보 제한을 각각 수행한다.
