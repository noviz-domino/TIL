## Part 1. Tool + 기본 Agent

### Tool 개념 — TMDB 때 배운 Function Calling의 응용

원리는 완전히 같음. LLM은 텍스트만 생성하고, 실제 도구 실행은 개발자 코드가 함.

```
사용자 질문 → LLM 판단 → Tool 호출 필요?
  → Yes: Tool 이름 + 인자 반환 → 개발자가 실행 → 결과를 LLM에 전달 → 최종 응답
  → No: 바로 텍스트 응답
```

| TMDB 때 | LangChain에서 |
|---|---|
| Function Calling | Tool |
| `function_call` (step.type) | `response.tool_calls` |
| 직접 실행 | 직접 실행 (동일) |
| `function_result`로 응답 | `ToolMessage`로 응답 |

### `@tool` 데코레이터 — 함수를 Tool 객체로 변환

```python
@tool(parse_docstring=True)
def search_weather(city: str) -> str:
    """주어진 도시의 현재 날씨를 검색한다.

    Args:
        city: 날씨를 검색할 도시 이름. 예: '서울', '부산'
    """
    ...
```

- 함수 이름 → Tool 이름 자동 사용
- docstring 첫 줄 → `description` 자동 추출
- `Args:` 아래 설명 → 매개변수 설명 자동 추출
- 타입 힌트(`city: str`) → JSON 스키마 타입(`"string"`)으로 자동 변환

**TMDB 때는 이 스키마를 손으로 딕셔너리로 다 썼음.** 함수 이름·매개변수 이름을 두 군데(함수 정의 + 딕셔너리)에 중복해서 적어야 했는데, `@tool`은 함수 하나만 잘 쓰면 스키마가 자동 생성됨.

실제 확인한 스키마:
```
{"description": "주어진 도시의 현재 날씨를 검색한다.",
 "properties": {"city": {"description": "날씨를 검색할 도시 이름...", "type": "string"}},
 "required": ["city"]}
```

### `bind_tools()` — 모델에게 도구 목록 알려주기

TMDB 때 `tools=TOOLS`와 같은 역할. **`bind_tools()`만으로는 도구가 실행되지 않는다** — LLM은 "불러달라"는 요청만 하고, 실제 실행은 개발자 몫.

실제 확인한 응답 구조:
```
tool_calls: [{'name': 'search_weather', 'args': {'city': '서울'}, 'id': 'call_...', 'type': 'tool_call'}]
```

- 도구 호출 필요 없으면 → `content`에 답변, `tool_calls`는 빈 리스트
- 여러 도구를 한 턴에 동시 요청 가능 (실제 확인: "서울이랑 부산 비교해줘" → `tool_calls`에 2개 동시에 담김)

### Tool 호출 루프 (`run_agent`)

```python
def run_agent(user_input: str) -> str:
    messages = [HumanMessage(content=user_input)]
    for _ in range(MAX_ITERATIONS):
        response = llm_with_tools.invoke(messages)
        messages.append(response)
        if not response.tool_calls:
            return response.content
        for tool_call in response.tool_calls:
            tool_result = tool_map[tool_call["name"]].invoke(tool_call["args"])
            messages.append(ToolMessage(content=str(tool_result), tool_call_id=tool_call["id"]))
    return "최대 반복 횟수를 초과했습니다."
```

- `tool_map = {t.name: t for t in tools}` — 이름(문자열) → 실제 Tool 객체로 바꿔주는 사전. TMDB의 `TOOL_FUNCTIONS`와 동일 역할
- `tool_call["id"]` (`tool_call_id`) — 택배 주문번호와 같은 개념. 여러 도구를 동시 호출했을 때 "이 결과가 어느 요청에 대한 응답인지" 짝을 맞추는 용도. 함수 자체에 붙는 게 아니라 **호출할 때마다 새로 생성**되는 번호
- `messages` 리스트에 계속 쌓아가는 방식 = 03번(메모리)에서 배운 수동 히스토리 관리와 동일

**딕셔너리 컴프리헨션(`{t.name: t for t in tools}`)은 왼쪽부터 실행되는 게 아니라, 파이썬이 전체를 먼저 "이건 컴프리헨션이다"라고 문법으로 인식한 뒤, `for`가 값을 채우고 그다음 왼쪽 표현식을 계산하는 순서로 실행됨.**

### 실습: TMDB + Tool + 세션 메모리

`get_movie_list`(목록: id/제목/개봉일만), `get_movie_detail`(상세: 줄거리/장르/러닝타임)을 Tool로 만들고, 03번의 `InMemoryChatMessageHistory`와 결합. 같은 세션에서는 "그중 첫 번째" 같은 후속 질문이 이어지고, 다른 세션에서는 이전 목록을 모른다고 답하는지 확인하는 구조.

## Part 2. RAG 기초

### RAG가 뭔지

질문과 관련된 문서를 먼저 검색(Retrieval)하고, 그 문서를 프롬프트에 넣어서 답변을 생성(Generation)하는 방식. 모델을 재학습시키지 않고도 학습 이후 정보나 비공개 문서를 답변 근거로 쓸 수 있음.

### 두 단계로 나뉨

```
[인덱싱 단계 - 질문 전에 미리] 문서 → 로드 → 분할 → 임베딩 → 벡터 DB 저장
[질의응답 단계 - 질문마다]     질문 → 임베딩 → 검색 → 관련 문서 추출 → LLM 전달 → 응답
```

문서 처리는 미리 끝내둬야 질문마다 매번 다시 하지 않아 빠름.

### Document Loader

파일 종류마다 로더가 다름 (`TextLoader`→.txt, `PyPDFLoader`→.pdf, `CSVLoader`→.csv, `WebBaseLoader`→웹페이지). `load()` 실행하면 `Document` 객체 리스트 반환.

```python
Document(page_content="텍스트 내용...", metadata={"source": "경로", "page": 0})
```

`TextLoader`는 파일 전체가 `Document` 1개, `PyPDFLoader`는 **페이지 단위**로 나눠서 페이지 수만큼 생성. **페이지 번호는 0부터 시작** (10페이지 문서의 마지막 페이지 = `page: 9`).

### Text Splitter — 문서를 청크로 쪼개기

이유 두 가지: ① 문서에 여러 주제가 섞이면 임베딩 벡터가 어느 주제에도 확실히 안 가깝게 애매해짐(검색 정확도 저하) ② 모델의 토큰 입력 제한.

- `chunk_size`: 청크 최대 크기 (문자 수 기준. 단, 임베딩 모델의 실제 제한은 **토큰 수** 기준이라 서로 안 맞을 수 있음— 주의)
- `chunk_overlap`: 인접 청크끼리 겹치는 부분. 문장이 청크 경계에서 반토막 나는 문맥 단절을 줄여줌

`RecursiveCharacterTextSplitter`: 빈 줄(문단) → 줄바꿈 → 공백(단어) 순으로 큰 단위부터 잘라봄. 의미 단위가 최대한 안 깨지게.

**한계**: 마크다운 표처럼 `-----`, `|` 기호로 이루어진 구조는 이 분할기가 인식 못 함. 표의 헤더 행과 데이터 행이 서로 다른 청크로 갈라질 수 있음. `MarkdownHeaderTextSplitter`(헤더 기준 분할)가 섹션 단위 분리는 도와주지만 표 자체의 무결성을 완벽히 지켜주진 않음.

다른 청킹 방법: `TokenTextSplitter`(토큰 수 기준), `MarkdownHeaderTextSplitter`/`HTMLHeaderTextSplitter`(헤더 기준), `SemanticChunker`(인접 문장 임베딩 유사도로 주제 전환 지점 탐지, 계산 비용 증가), Parent-Child Chunking(검색용 작은 청크 + 전달용 큰 청크 연결).

### 임베딩(Embedding)

텍스트를 숫자 벡터로 변환. 의미가 비슷하면 벡터도 비슷해짐. 벡터 안의 숫자는 자연수가 아니라 **음수·소수점이 있는 실수**이고, 임베딩 모델(신경망)이 대량의 텍스트로 학습하며 만든 계산 결과라 개별 숫자 하나하나는 사람이 해석할 수 없음. 상대적 거리만 의미 있음.

**왜 채팅 모델과 임베딩 모델을 따로 쓰는지**: 학습 목표가 다름. 채팅 모델은 "그럴듯한 다음 텍스트 생성", 임베딩 모델은 "의미가 비슷하면 벡터도 비슷하게"만 학습됨. Day 1에 배운 "이해 모델과 이미지 생성 모델을 나누는 이유"와 같은 원리.

- `embed_query(문자열)` → 벡터 1개 (사용자 질문용)
- `embed_documents(문자열 리스트)` → 벡터 리스트 (저장할 문서 여러 개, 각각 독립적으로 계산됨 — 여러 개를 하나로 합치는 게 아니라 한 번의 호출로 각각 따로 처리하는 것. `batch()`와 같은 효율화 개념)

**벡터 안쪽에 숫자를 추가로 끼워 넣는 것(`vec.append(0.5)`)은 안 됨** — 그 자리는 모델이 학습한 특정 의미 방향을 나타내므로 임의의 숫자를 넣으면 계산이 왜곡됨. **반면 벡터들의 리스트에 새로 임베딩한 벡터 하나를 통째로 추가하는 것은 정상** — RAG에서 문서를 나중에 추가할 때 실제로 쓰는 방식.

차원(dimension) = 벡터 안의 숫자 개수. 같은 임베딩 모델로 만든 벡터는 항상 같은 차원이라 서로 비교 가능. 차원이 다르면 비교 자체가 안 됨.

정규화된 벡터는 길이(크기)가 1 — 벡터의 각 숫자를 제곱해서 더한 값이 1이라는 뜻 (제곱합의 제곱근 = 길이).

### 코사인 유사도

```
cosine_similarity(A, B) = (A · B) / (|A| × |B|)
```

- 내적(A·B): 같은 자리 숫자끼리 곱해서 다 더한 값. 방향이 비슷할수록 커짐
- `|A|`: 벡터 길이 (제곱합의 제곱근)
- 값의 범위: -1~1, 1에 가까울수록 유사
- **보편적인 기준선이 없음** — "0.7 이상이면 유사하다" 같은 절대 기준이 없고, 모델·데이터마다 분포가 다름

**실제 확인한 결과**: "고양이가 소파에서 낮잠" vs "고양이가 침대에서 잠"(0.7754, 높음) vs "강아지가 공원에서 뛰어놈"(0.4716) vs "주식 시장 급락"(0.4775, 강아지보다 오히려 살짝 높음). 무관한 것들끼리는 서로 다른 이유로 멀어진 것이라, 그 사이의 미세한 순위 차이는 신뢰할 만한 정보가 아님. 코사인 유사도는 "확실히 비슷/확실히 무관"은 잘 가르지만 "무관한 것들끼리의 세밀한 순위"는 신뢰도가 낮음.

### 실전 검색 데모 (실제 실행 결과)

회사 규정 문서 6개 vs 다른 표현으로 된 질문 3개:

| 질문 | 1등 문서 | 점수 |
|---|---|---|
| "휴가를 쓰려면 어디서 신청?" | 연차 신청 문서 | 0.7226 |
| "집에서 일하려면 절차는?" | 재택근무 문서 | 0.6815 |
| "회사 카드로 결제 후엔?" | 법인카드 문서 | 0.8041 |

단어가 하나도 안 겹쳐도(휴가↔연차, 신청↔제출) 의미로 검색됨 — 키워드 매칭으로는 불가능한 것.

1등과 2등 점수 차이가 좁을 때(예: 0.72 vs 0.65) 주의할 점: 1등이 실제로 정답이 아닐 수도 있고, 질문이 저장된 문서 어디와도 무관해도 "1등은 무조건 나온다"는 함정이 있음. 실무에서는 최소 점수 기준을 두거나, 애매하면 상위 몇 개를 다 참고자료로 넘기는 보완이 들어감.

### 코사인 유사도 vs LLM 추론 — 왜 2단계로 나뉘는가

임베딩+코사인 유사도는 "고정된 수학 공식"으로 매번 똑같이 계산 — 학습된 벡터 하나를 뽑아낸 뒤엔 그 이후 비교는 신경망이 아니라 순수 계산. LLM의 "추론"은 토큰을 하나씩 생성하며 매번 문맥 전체를 다시 훑어보는(어텐션) 방식이라, 같은 신경망 계산이라도 훨씬 문맥 의존적이고 유연함.

세밀한 관련도 판단은 LLM 쪽이 더 정확할 수 있지만, 수백만 개 문서를 전부 LLM 컨텍스트에 넣고 판단시키는 건 비용 문제 이전에 **컨텍스트 윈도우 한계로 물리적으로 불가능**함. 그래서 임베딩으로 먼저 후보를 수십 개로 좁히고(1차, 빠름), 그다음 LLM으로 재판단(리랭킹, 2차, 정확함)하는 2단계 구조를 씀.

어텐션 메커니즘은 2017년 구글의 "Attention Is All You Need" 논문에서 소개된 트랜스포머 구조의 핵심. GPT, Claude, Gemini 등 대부분의 LLM이 이 구조를 기반으로 하되, 모델 크기·학습 데이터·추가 학습 방식(Anthropic의 Constitutional AI 등)·토크나이저는 회사마다 다름.

## 핵심 한 줄 정리

- Tool = Function Calling의 LangChain 버전. `@tool`이 스키마 자동 생성, `tool_call_id`는 택배 주문번호처럼 매 호출마다 새로 생성됨
- 청킹 ≠ 임베딩. 청킹은 텍스트를 텍스트로 쪼개는 것, 임베딩은 텍스트를 숫자로 변환하는 것
- 벡터 내부 수정은 불가(모델이 계산한 고정값), 벡터 리스트에 새 벡터 추가는 정상
- 코사인 유사도는 빠르지만 세밀한 순위는 부정확할 수 있음 → 임베딩(1차 검색) + LLM 리랭킹(2차 정제)의 2단계 구조가 이를 보완
