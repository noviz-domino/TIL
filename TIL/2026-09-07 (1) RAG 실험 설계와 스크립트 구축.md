오늘은 크게 두 가지를 했다. 오전에는 10번 노트북의 실습 문제(공공문서 검색 평가)를 채웠고,

## Part 1. 공공문서 검색 평가 실습

### File Hit과 Page Hit — 정답을 어디까지 맞혀야 하는가

기존 실습은 정답을 "파일" 단위로만 봤는데, 공공문서 PDF는 한 파일이 수십 페이지라 파일만 맞혀도
실제로는 엉뚱한 페이지를 가져올 수 있다. 그래서 정답 판정을 두 단계로 나눈다.

```python
def file_hit_at_k(docs, case, k):
    # 상위 k개 중 정답 파일과 같은 source가 하나라도 있으면 1
    return int(any(doc.metadata["source"] == case["target_file_name"] for doc in docs[:k]))


def page_hit_at_k(docs, case, k):
    # 파일명과 페이지 번호가 둘 다 정답과 같아야 1
    return int(any(
        doc.metadata["source"] == case["target_file_name"]
        and doc.metadata["page_no"] == case["target_page_no"]
        for doc in docs[:k]
    ))
```

Page Hit은 조건이 두 개(`and`)라 항상 File Hit보다 같거나 낮다.
실측에서도 File Hit@1 0.971 > Page Hit@1 0.886으로 나왔다. 즉 파일은 맞혔지만 페이지가 틀린 경우가 있었다.

### PDF는 페이지 단위로 로드된다

`TextLoader`는 파일 하나가 `Document` 하나였지만, `PyPDFLoader`는 **페이지 하나가 `Document` 하나**다.
PDF 형식 자체에 페이지 구조가 있어서 로더가 그걸 그대로 따르기 때문이다.

```python
for pdf_path in sorted(pdf_dir.glob("*.pdf")):
    pages = PyPDFLoader(pdf_path).load()
    for page in pages:
        page.metadata["source"] = Path(page.metadata["source"]).name   # 전체 경로 → 파일명만
        page.metadata["page_no"] = page.metadata["page"] + 1           # 0부터 → 1부터
    page_documents.extend(pages)
```

- `Path(...).name`은 경로에서 파일명만 뽑는다(확장자 포함). 확장자를 빼려면 `.stem`.
- `page + 1`을 하는 이유는 `PyPDFLoader`는 첫 페이지를 0으로 세지만 golden set은 1로 세기 때문이다.

> ➕ **더 알아두기**
> 로더가 나누는 단위와 청킹은 별개의 두 단계다. 로더가 1차로 나누고(파일 전체 또는 페이지),
> 그 결과를 `RecursiveCharacterTextSplitter`가 2차로 더 잘게 나눈다.
>
> 그래서 PDF는 문제가 하나 있다. `chunk_overlap`은 **같은 Document 안의 청크 사이에만** 적용되므로,
> 페이지 경계에 걸친 문장은 겹침 없이 잘린다. 4페이지 마지막 청크와 5페이지 첫 청크는 서로 다른
> Document에서 나왔기 때문이다. 해결하려면 전체 텍스트를 이어붙여 자르고 페이지 번호를 글자 위치로
> 역산해야 하는데, 코드가 복잡해져서 이번 실습에서는 페이지 단위 방식을 그대로 썼다.

## Part 2. 실험 설계 방법론

여기부터가 오늘의 핵심이다. 코드보다 **설계를 먼저** 확정했다.

### 실험은 결정을 내리기 위해 하는 것

초보가 흔히 하는 실수는 "일단 여러 설정을 다 돌려보자"로 시작하는 것이다. 그러면 표는 잔뜩 나오는데
"그래서 뭘 쓸 건데?"에 답할 수 없다. 숫자가 많은 것과 결론을 낼 수 있는 것은 다르다.

그래서 코드를 짜기 전에 두 가지를 먼저 정한다.
1. 이 실험이 끝나면 내가 내려야 하는 결정이 무엇인가
2. 그 결정을 내리려면 어떤 숫자를 보면 되는가

### 기준선(baseline)을 못박고, 한 번에 하나만 바꾼다

실험이 많아지면 서로를 비교하기 시작하는데 그러면 조합이 폭발한다. 대신 기준이 되는 설정 하나를 정하고
모든 실험을 "기준선 + 한 가지만 바꿈"으로 만들면, 실험 하나하나가 한 문장짜리 결론을 갖는다.

조합 폭발을 숫자로 보면 명확하다. 변수 4개에 값 3가지씩을 **모든 조합**으로 돌리면
`3 × 3 × 3 × 3 = 81번`이다. 조합은 더하는 게 아니라 **곱해진다**(변수 하나가 늘면 그 변수의 값 개수만큼 배가 된다).
질문 35개를 곱하면 2,835번 호출이라 하루 한도 1,000번을 세 배 넘긴다.

"하나만 바꿈" 방식이면 기준선 1개 + 변수마다 나머지 값 2개씩 = 9개로 끝난다.

> ♻️ 처음엔 "변수 4개 × 값 3개 = 12번"으로 알았으나, 조합은 곱셈이므로 3⁴ = 81번이 맞다.

### 품질만 재면 안 된다 — 비용은 코드가 직접 세야 한다

목표가 "절대 품질 1위"가 아니라 "품질 대비 비용"이면 비용 축이 숫자로 나와야 한다.
그런데 API는 "이번에 얼마 썼습니다"를 알려주지 않으므로, 호출할 때마다 코드가 직접 세는 계수기를 붙인다.

측정한 4가지 비용 지표가 각각 다른 것에 걸린다.
- **호출 수** → 하루 한도(RPD)에 걸리는 축
- **소요 시간** → 분당 한도(RPM)와 사용자 체감에 걸리는 축
- **토큰 수** → 실제 과금 단위
- **금액** → 그 토큰을 사람이 이해하는 단위

넷 다 재두면 상대에 맞춰 설명할 수 있다. 개발자에겐 호출 수로, 결정권자에겐 금액으로.

### 비교 가능성 — 아무 두 줄이나 비교하면 안 된다

같은 표에 있어도 조건이 다르면 비교할 수 없다. 오늘 실제로 문항 수가 다른 실험(35문항 vs 10문항)이
한 표에 섞여서, 그냥 보면 "rerank가 11%p 올렸다"는 틀린 결론이 나오게 돼 있었다.
숫자를 많이 모으는 것보다 **어떤 숫자끼리 비교해도 되는지 아는 것**이 중요하다.

## Part 3. config와 CLI — 설정을 코드에서 분리한다

### YAML

설정값을 코드에 박아두면 조건을 바꿀 때마다 코드를 고쳐야 한다. 그래서 별도 파일로 분리한다.

```yaml
chunk:
  size: 700          # 청크 하나의 최대 글자 수
  overlap: 100
search:
  strategy: similarity   # similarity | mmr | bm25 | hybrid
  k: 5
rerank:
  enabled: false
```

- `키: 값` — 콜론 뒤에 **공백 한 칸**이 필수
- 들여쓰기로 계층을 표현(공백 2칸 관례, **탭 금지**)
- `#`부터 줄 끝까지 주석 → JSON에는 없는 기능이고, 이게 YAML을 고른 이유
- `[0.5, 0.5]`는 리스트, `true`/`false`는 **소문자**(파이썬의 `True`와 다름)

핵심은 **YAML을 읽으면 파이썬 딕셔너리가 된다**는 것이다. `yaml.safe_load()`로 읽으면
`{"chunk": {"size": 700, ...}}`가 되고 코드에서는 `cfg["chunk"]["size"]`로 꺼낸다.
즉 이미 아는 딕셔너리의 겉모습만 바뀐 것이다.

> ➕ **더 알아두기**
> JSON도 가능하다. JSON은 파이썬 내장이라 설치가 필요 없고 dict와 모양이 같지만, 주석을 달 수 없다.
> YAML은 `pip install pyyaml`이 필요하지만 주석이 가능하고, GitHub Actions·Docker·Kubernetes 설정이
> 대부분 YAML이라 나중에 반드시 만난다.

### argparse — 터미널에서 값을 넘긴다

```python
import argparse

parser = argparse.ArgumentParser()
parser.add_argument("--config", required=True)         # 없으면 오류를 내고 종료
parser.add_argument("--limit", type=int, default=None) # "3" 문자열을 숫자 3으로 바꿔줌
parser.add_argument("--dry-run", action="store_true")  # 값 없이 붙이면 True
args = parser.parse_args()

print(args.dry_run)   # 하이픈(--dry-run)은 코드에서 언더스코어로 접근
```

### config와 CLI의 역할 분담

- **config** = 그 실험이 무엇인지 정의하는 것(신원). `chunk_size`, `strategy`, `k`, rerank 여부.
  결과가 어떤 설정에서 나왔는지 증거로 남아야 한다.
- **CLI** = 이번 실행에 대한 것. 어떤 config를 쓸지, 문항을 임시로 줄일지 등.

`--limit 3`을 config에 넣지 않은 이유가 여기 있다. 문항을 3개로 줄인 것은 실험 설계가 아니라
시험 삼아 돌려본 것이라, config에 기록으로 남으면 "이 실험은 3문항이었다"는 오해를 만든다.

`--dry-run`(API 없이 예상 호출 수만 계산)은 만들고 보니 이득이 두 개였다. 예산 확인이 원래 목적이고,
부수적으로 **설계 검증**도 된다 — BM25가 임베딩 0회로 나오는 것 자체가 "코드가 BM25에서 임베딩을
건너뛴다"는 증거다.

## Part 4. 프로젝트 구조와 안정성

### 파일을 나누는 기준은 줄 수가 아니라 "바뀌는 이유"

```
10-rag-evalution-script/
  configs/      # 실험별 YAML
  main.py       # CLI 입구
  config.py     # YAML 읽기 + 검증
  pipeline.py   # PDF 로드·청킹·벡터저장소·검색기 생성
  metrics.py    # 지표 계산
  runner.py     # 문항 반복·체크포인트·비용 집계
  report.py     # 결과 비교 표
  outputs/      # 실험별 결과 폴더
```

각 파일이 바뀌는 이유가 다르다. `metrics.py`는 정답 형식이 바뀔 때, `pipeline.py`는 새 검색 전략을
추가할 때, `main.py`는 CLI 옵션을 늘릴 때만 바뀐다.

반대 함정도 있다. 너무 잘게 쪼개면 초보 단계에서 **내 코드의 흐름을 스스로 설명하지 못하게** 된다.
발표가 있는 과제에서는 실제 리스크라서 6개로 제한했다.

부수 효과: 파일이 독립적이면 **작업도 독립적으로 끊을 수 있다.** 하루에 다 안 해도 된다.

### 중단돼도 이어서 실행 — 체크포인트

오늘 두 번 중단됐는데 결과가 달랐다. 그 차이가 설계 근거가 됐다.
- 문서 임베딩 중 중단 → **보존됨.** Chroma에 넣는 즉시 디스크에 기록되는 구조
- 35문항 평가 중 중단 → **전부 소실.** 점수를 리스트(메모리)에만 쌓고 마지막에 저장

원칙은 **"일이 끝날 때마다 즉시 디스크에 기록하고, 재실행 시 남아있는 것은 건너뛴다."**

```python
def append_row(rows_path, row):
    # "a" 모드 = append, 기존 내용을 지우지 않고 뒤에 이어 쓴다 ("w"는 덮어써서 쓰면 안 된다)
    with rows_path.open("a", encoding="utf-8") as f:
        f.write(json.dumps(row, ensure_ascii=False) + "\n")
```

JSONL(한 줄에 JSON 하나) 형식을 쓰는 이유는, 줄 단위로 읽으면 프로그램이 줄을 쓰던 중 강제 종료돼도
**깨진 마지막 줄만 버리고 앞부분은 살릴 수 있기** 때문이다.

### 지연 임포트(lazy import)

파이썬의 `import`는 파일을 읽는 순간 실행된다. 그래서 특정 기능에서만 쓰는 라이브러리를 맨 위에서
import하면, 그 기능을 한 번도 안 써도 라이브러리가 반드시 있어야 한다.

```python
def kiwi_tokenize(text):
    global _kiwi
    if _kiwi is None:
        from kiwipiepy import Kiwi   # 이 함수가 처음 불릴 때만 불러온다
        _kiwi = Kiwi()
```

실제로 이걸 안 했을 때 `kiwipiepy`가 없어서 BM25를 쓰지 않는 실험까지 전부 실행이 안 됐다.

> ➕ **더 알아두기**
> BM25는 라이브러리가 두 개 필요하다. `kiwipiepy`(한국어를 단어로 쪼개는 토크나이저)와
> `rank_bm25`(BM25 알고리즘 구현). LangChain의 `BM25Retriever`가 내부에서 `rank_bm25`를 불러 쓴다.

| chunk-500 | 0.857 | 0.943 | 0.943 | 0.895 | 52 | - |

| k-3 | 0.886 | 0.914 | 0.914 | 0.900 | 35 | - |

| search-bm25 | 0.886 | 0.914 | 0.943 | 0.907 | **0** | **15ms** |

- **청크 700이 최적.** 1000으로 키우면 page_hit_1이 0.829로 떨어진다 — 한 청크에 여러 주제가 섞여
  정답 지점의 신호가 희석된다. 500은 1등 정확도는 떨어지나 3등 안에는 더 잘 들어온다(정답 조각이 분산됨).
- **k는 5가 적절.** k=10은 baseline과 모든 수치가 동일(이득 0). k=3은 page_hit_5에서 손실.
- **MMR은 효과 없음.**
- **BM25가 가성비 1위.** 품질이 baseline과 전부 동일한데 임베딩 0회, 지연은 1/35.
- **Hybrid가 품질 1위.** MRR 0.910. 단 개선폭 1문항이고 가장 느리다.

### 결론과 유보 조건 (⚠️ Part 8에서 뒤집힘)

> 이 절의 결론은 Part 8의 교차 실험에서 바뀌었다. OFAT로는 상호작용을 볼 수 없었기 때문이다.
> "OFAT만으로 도달했던 결론"의 기록으로 남긴다.

추천 조합은 **chunk 700 / BM25 / k=5**. 근거는 벡터 검색과 품질이 동일하면서 임베딩 비용이 0이고
35배 빠르다는 것 — 즉 **이 데이터셋에서는 벡터 검색이 자신의 비용을 정당화하지 못했다.**

단 유보 조건이 있다. 이 golden set의 질문들이 문서 표현을 상당히 그대로 써서 키워드 검색에 유리했을
수 있다. 질문이 동의어·의역으로 들어오면 결론이 달라질 수 있다.

**문항이 35개라 1문항이 2.86%p**라는 것도 같이 말해야 한다. Hybrid의 개선(1문항)이 진짜 실력인지
우연인지 이 데이터만으로는 단정할 수 없다. 반면 BM25의 "비용 0, 35배 빠름"은 우연의 여지가 없는
구조적 차이라 결론이 훨씬 튼튼하다.

## Part 6. 계획과 어긋난 것들 (오늘 가장 많이 배운 부분)

### 배치는 하루 한도를 아껴주지 않는다

"청크 402개를 10개씩 묶으면 41번"으로 계산했는데 틀렸다. API는 배치로 묶어도 **텍스트 하나하나를
1회 요청으로 계산**한다. 402개는 41회가 아니라 402회가 차감된다.

즉 배치는 **분당 요청 수(RPM)는 줄여주지만 하루 한도(RPD)는 전혀 아껴주지 않는다.**

### 같은 429가 세 가지 다른 문제였다

| 상황 | 실제 원인 | 해결 |
|---|---|---|
| 배치를 연속 전송 | 분당 토큰 한도(30,000) 초과 | 배치 간 대기 추가 |
| 누적 사용 후 | 하루 요청 한도(1,000) 소진 | 대기로 해결 불가 |
| 새 키로 교체 후 | 한도는 **프로젝트 단위** 공유 | 다른 프로젝트 키 필요 |

에러 메시지 본문을 읽어야 구분된다. 우리 `retry_on_429`는 세 경우를 구분하지 않고 다 재시도하는데,
하루 한도 소진은 재시도가 무의미하므로 즉시 중단해야 맞다.

### 오류 없이 조용히 틀리는 버그가 가장 위험하다

컬렉션 재사용 판단이 `count() > 0`이었다. 하루 한도로 중단돼 390/552개만 저장된 상태를
완성본으로 착각해 재사용했고, 문서 29%가 빠진 채로 실험이 돌아 page_hit_1 0.686이라는 오염된 값이 나왔다.
**프로그램은 정상 종료했고 표에도 숫자가 잘 찍혔다.**

dry-run 예상치(552)와 실제 저장량(390)을 대조해서 발견했다. 수정 후 재실행하니 0.857로 정상화됐다.

```python
if stored == len(documents):        # "비어있지 않다"가 아니라 "다 들어있다"를 확인
    재사용
elif stored < len(documents):
    pending = documents[stored:]    # 순서대로 넣으므로 앞 stored개는 이미 들어간 것
```

부수 발견: 체크포인트는 "어느 문항을 처리했는가"만 기억하고 **"어떤 코퍼스로 처리했는가"는 모른다.**
그래서 코퍼스를 고친 뒤에는 그 실험의 `rows.jsonl`을 지워야 재채점된다.

### 천장 효과 — 측정이 안 되는 경우가 있다

rerank 실험이 모든 지표 1.000으로 나왔는데, 비교군인 baseline-10도 1.000이었다.
`llm_limit: 10`이 golden set의 **앞** 10문항을 가져오고 그게 하필 쉬운 문항들이라, 이미 만점이어서
올라갈 여지가 없었다(천장 효과, ceiling effect).

정확한 결론은 "rerank가 무용하다"가 아니라 **"이 10문항 구성으로는 rerank 효과를 측정할 수 없었다"**다.
rerank는 개선 0에 LLM 40회, 시간 6.7배(45.7초 → 308.2초)를 썼다.

### 천장 효과 해소 — 난이도를 섞어 다시 측정

문항을 다시 고르기 전에, baseline의 실패를 두 유형으로 나눴다. **rerank는 이미 검색된 문서의 순서만
바꾸므로, 검색되지 않은 문서는 데려올 수 없다**는 점이 기준이 된다.

| 유형 | 개수 | 문항 | rerank로 개선 가능? |
|---|---|---|---|
| Page Hit@5 = 0 (정답이 상위 5개에 없음) | 2 | #33, #34 | **불가** |
| Page Hit@1 = 0, Page Hit@5 = 1 (5개 안에 있으나 1등 아님) | 2 | #18(4등), #20(2등) | **가능** |
| 이미 1등이 정답 | 31 | - | 개선 여지 없음 |

즉 **rerank가 개선할 수 있는 문항은 35개 중 2개**이고 이것이 효과의 상한선이다.
실험을 돌리기 전에 이 상한을 계산했다면 rerank 실험을 다르게 설계했을 것이다.
→ **실험 전에 "최대 얼마나 좋아질 수 있는가"를 먼저 계산하는 습관이 필요하다.**

문항을 앞에서부터 자르지 않고 번호로 직접 고르는 기능을 config에 추가했다.

```yaml
evaluation:
  # 18, 20 : 5개 안에 있으나 1등이 아님 -> rerank가 고칠 수 있는 문항
  # 33, 34 : 상위 5개에 아예 없음 -> rerank가 고칠 수 없는 문항(한계 확인용)
  # 0~5    : baseline이 이미 1등을 맞히는 쉬운 문항(맥락 유지용)
  case_indices: [0, 1, 2, 3, 4, 5, 18, 20, 33, 34]
```

```python
indices = cfg["evaluation"].get("case_indices")   # .get()은 키가 없으면 None (기존 config도 그대로 동작)
if indices:
    cases = [cases[i] for i in indices]           # 지정한 번호의 문항만 뽑는다
```

두 config의 `diff`를 떠보니 차이가 **실험 이름과 `rerank.enabled` 딱 두 줄**이었다.
"한 번에 하나만 바꾼다"가 파일 수준에서 증명된 것이다.

### 결과 — rerank는 이론상 최대치를 달성했지만 비용이 정당화되지 않는다

| 실험 | page_hit_1 | page_hit_3 | page_hit_5 | mrr | LLM 호출 | 소요 시간 |
|---|---|---|---|---|---|---|
| hard-baseline | 0.600 | 0.700 | 0.800 | 0.675 | 0 | 43.9초 |
| hard-rerank | **0.800** | 0.800 | 0.800 | **0.800** | 50 | 370.4초 |

먼저 **사전 예측이 검증 도구가 됐다.** 실행 전에 계산한 hard-baseline 예상치
(page_hit_1 0.6 / page_hit_5 0.8 / MRR 0.675)가 세 값 모두 정확히 맞았다.
문항 선택과 코드가 의도대로 작동한다는 증거다.

- **Page Hit@1: 0.600 → 0.800 (+0.2)** — 개선 가능했던 2문항을 둘 다 1등으로 끌어올렸다(최대치)
- **Page Hit@5: 변화 없음** — 예측대로. 검색되지 않은 #33·#34는 손댈 수 없다
- **비용**: 문항당 4.4초 → **37초**(+32.6초), LLM 5회 추가

전체 35문항 환산: page_hit_1이 0.886 → 0.943(+5.7%p)이 최대이고 대가는 LLM 175회다.
서비스 관점에서는 **질문마다 30초 이상 더 기다려 5.7%를 개선**하는 셈이다.

> ➕ **더 알아두기**
> 이 결과의 구조가 핵심이다. rerank는 완벽하게 작동했는데, **그 가치의 상한은 baseline이 이미
> 1등을 맞히는 비율(88.6%)에 의해 정해진다.** 즉 도구의 성능이 아니라 기존 시스템의 수준이
> 도입 가치를 결정한다. "좋은 기술인가"가 아니라 "여기서 고칠 게 남아있는가"를 먼저 봐야 한다.

### 새 코드는 성공을 확인한 뒤에 최적화한다

`--dry-run`은 비용 예측을 검증하지만 "코드가 끝까지 도는가"는 검증하지 못한다(검색기를 만들지 않으므로).
그건 `--limit 3` smoke test의 역할이다. BM25에서 `rank_bm25` 누락으로 5분 낭비한 뒤 배운 것.
**싸고 빠른 검증으로 걸러낼 수 있는 오류를 먼저 걸러낸다.**

## Part 7. 강사 구현과 비교하며 배운 것

수업 중 강사 화면에서 같은 과제의 구현을 봤다. 우리 쪽이 열등한 부분을 그대로 기록한다.

| 항목 | 내 구현 | 강사 구현 |
|---|---|---|
| config 형식 | YAML | JSON |
| **실험 단위** | 전략마다 config (9개) | **청킹마다 config (3개), 내부에서 4전략을 배열로** |
| 청킹 결과 | 매 실행마다 재파싱 | `outputs/*/chunks.jsonl`로 저장 |
| 프롬프트 | 코드에 하드코딩 | `prompts/basic.txt`, `grounded.txt`로 분리 |
| 실패 문항 | report에서 매번 필터링 | `retrieval_misses.jsonl`로 별도 저장 |
| 출력 | `summary.json` 하나 | `retrieval_metrics.json` / `generation_metrics.json` 분리 |
| 추가 실험 변수 | 없음 | `separators`, `include_source` |

### 가장 중요한 차이 — 실험 단위를 무엇으로 잡는가

강사 config에는 전략이 배열로 들어있다.

```json
"retrieval": {
  "strategies": ["similarity", "mmr", "bm25", "hybrid"],
  "k": 5,
  "fetch_k": 20
}
```

즉 실험 단위가 "검색 전략"이 아니라 **"청킹 설정"**이고, config는 chunk-500 / chunk-700 / chunk-1000 3개뿐이다.

나는 전략마다 config를 나눠 9개를 만들었고, 그래서 **같은 코퍼스를 4번 다시 로드**했다.
실측한 "PDF 로드+청킹 38초"가 전략마다 반복돼 실험 9개에서 약 6분을 낭비했다.

논리적으로도 강사 방식이 맞다. **청킹이 바뀌면 코퍼스가 바뀌지만, 전략이 바뀌어도 코퍼스는 그대로다.**
즉 "무엇이 코퍼스를 바꾸는가"를 기준으로 실험 단위를 잡아야 한다.
컬렉션 이름을 `public_c700_o100`처럼 청킹 값만으로 만든 것과 같은 원리인데, 그 원리를
config 구조에까지 적용하지 못했다.

### 프롬프트도 실험 변수다

강사는 프롬프트를 `prompts/*.txt`로 분리했다. 그러면 "프롬프트를 바꾸면 답변 품질이 어떻게 변하나"를
config만 바꿔 실험할 수 있다. 나는 rerank 프롬프트를 `runner.py` 안에 문자열로 박아뒀으니
프롬프트 실험을 하려면 코드를 고쳐야 한다 — **이 과제가 지적한 문제("설정을 코드에서 분리하라")를
프롬프트에 대해서는 그대로 답습한 셈이다.**

## Part 8. 교차 실험 — 결론이 뒤집힌 지점

### 빠진 칸을 발견한 경위

강사 구현과 비교하다가, 우리 실험에 빠진 칸이 드러났다.

```
chunk 700 : similarity ✓  mmr ✓  bm25 ✓  hybrid ✓   ← 4개 다 함
chunk 500 : similarity ✓  mmr ✗  bm25 ✗  hybrid ✗   ← similarity만
chunk 1000: similarity ✓  mmr ✗  bm25 ✗  hybrid ✗   ← similarity만
```

OFAT를 택했으니 "청크만 바꾼" 실험은 전략이 similarity로 고정돼 있었다.
그래서 "청크를 줄이면 BM25가 유리해지는가"에 답할 수 없었다.

빠진 6칸을 채우는 비용은 낮았다. 컬렉션이 이미 완성돼 있어 **문서 임베딩 0회**,
질문 임베딩만 140회(BM25는 0회)였다.

### 결과 격자 (35문항)

**Page Hit@1**

| | similarity | mmr | bm25 | hybrid |
|---|---|---|---|---|
| chunk 500 | 0.857 | 0.857 | 0.886 | **0.943** |
| chunk 700 | 0.886 | 0.886 | 0.886 | 0.886 |
| chunk 1000 | 0.829 | 0.829 | 0.857 | 0.886 |

**MRR**

| | similarity | mmr | bm25 | hybrid |
|---|---|---|---|---|
| chunk 500 | 0.895 | 0.886 | 0.914 | **0.943** |
| chunk 700 | 0.907 | 0.907 | 0.907 | 0.910 |
| chunk 1000 | 0.872 | 0.871 | 0.895 | 0.910 |

`chunk 500 + hybrid`가 Page Hit@1 0.943, MRR 0.943, **File Hit@1 1.000**으로 전체 최고다.

### 상호작용 — OFAT가 원리적으로 볼 수 없는 것

OFAT로 각각 찾은 최적값은 "청크 700"(similarity 기준)과 "hybrid"(청크 700 기준)였고,
그 조합 `700 + hybrid`는 MRR 0.910이었다. 그런데 실제 최고는 `500 + hybrid`의 **0.943**이었다.

격자를 보면 원인이 읽힌다.
- 청크 700에서 hybrid의 이득은 거의 없다 (0.907 → 0.910)
- 청크 500에서 hybrid의 이득은 크다 (0.895 → 0.943)

즉 **"hybrid가 얼마나 도움이 되는가"가 청크 크기에 따라 달라진다.** 이게 상호작용이고,
한 번에 하나만 바꾸는 방식으로는 절대 보이지 않는다.

원인 가설도 데이터 안에 있다.
- **BM25는 청크가 작아질수록 좋아진다** (MRR 1000: 0.895 → 700: 0.907 → 500: 0.914).
  청크가 짧으면 안에 든 단어가 적어서 키워드 매칭이 더 정밀해진다.
- **벡터 검색은 청크 500에서 나빠진다** (Page Hit@1 0.886 → 0.857). 짧은 청크는 의미 정보가 부족하다.
- hybrid는 둘을 합치니, **BM25가 강해지고 벡터가 약해지는 지점에서 이득이 가장 크다.**
  "서로의 약점을 보완한다"는 09번 노트북의 설명이 여기서 숫자로 확인됐다.

### 수정된 결론

| 노선 | 조합 | 근거 |
|---|---|---|
| 품질 우선 | `chunk 500 + hybrid + k=5` | MRR 0.943, File Hit@1 1.000. baseline보다 2문항 더 맞힘 |
| 가성비 우선 | `chunk 500 + BM25 + k=5` | MRR 0.914로 baseline(0.907)보다 높은데 **임베딩 0회**, 43.5초 |

청크를 500으로 줄이는 것이 두 노선 모두에서 이득이었다.

> ➕ **더 알아두기**
> 여기서 얻은 방법론적 교훈이 셋이다.
>
> 1. **완전 요인(81회)과 OFAT(9회) 사이에 중간이 있다.** 상호작용이 있을 만한 변수 2개만 교차시키는
>    부분 요인 설계(12회)가 이번엔 정답이었다. 설계 단계에서 이 선택지를 아예 계산하지 않은 것이 실수.
> 2. **캐시 구조가 실험 설계의 폭을 결정한다.** 청킹이 같으면 임베딩을 재사용하는 구조 덕에
>    교차 실험 추가 비용이 140회뿐이었다. 비용 구조를 알면 더 넓은 설계를 택할 수 있다.
> 3. **"각 요인의 최적값을 합친 것이 전체 최적"이라는 보장이 없다.** 이번에 실제로 어긋났다.

## 핵심 한 줄 정리

- 실험은 결정을 내리기 위해 하는 것이므로, 기준선을 못박고 한 번에 하나만 바꿔야 결론이 나온다.
- 단, **OFAT는 상호작용을 볼 수 없다.** 각 요인의 최적값을 합친 것이 전체 최적이라는 보장이 없고,
  이번 실험에서 실제로 어긋났다(`700+hybrid` 0.910 vs `500+hybrid` 0.943).
- 완전 요인(81회)과 OFAT(9회) 사이의 **부분 요인 설계(12회)** 를 설계 단계에서 계산해봐야 한다.
- 설정을 config로 분리하고 CLI로 실행 옵션을 받으면, 코드를 고치지 않고 실험을 반복할 수 있다.
- 오류를 내며 죽는 버그보다 **조용히 틀린 결과를 만드는 버그**가 위험하다. 예상치와 실측을 대조해야 잡힌다.
- 실험 전에 **"최대 얼마나 좋아질 수 있는가"(상한선)를 계산**하면, 돌려보지 않고도 도입 가치를 판단할 수 있다.
- **캐시 구조가 실험 설계의 폭을 결정한다.** 무엇을 재사용할 수 있는지 알면 더 넓은 설계를 택할 수 있다.
