## 1. HTTP와 웹의 기본 구조

> 09:00–10:00 어제 한 디스코드 자동화 날씨·운세 시스템 작동 확인. HTTP 설명

어제 만든 디스코드 자동화가 정상적으로 작동 중인 것을 확인했다.

### 1.1 HTTP와 하이퍼텍스트의 본질

* **하이퍼텍스트 (HyperText)**: 모르는 단어나 연관 내용이 있을 때, 순서대로 읽지 않고 클릭을 통해 다른 문서로 바로 이동(점프)할 수 있도록 만들어진 비선형 문서 방식.
* **하이퍼링크 (Hyperlink)**: 하이퍼텍스트 문서 내에서 다른 문서나 위치로 이동시켜 주는 연결 고리. (`<a>` 태그의 `href` 속성 활용)
* **HTTP (HyperText Transfer Protocol)**: 하이퍼링크로 연결된 하이퍼텍스트(웹 문서)를 인터넷상에서 주고받기 위해, 클라이언트(브라우저/앱)와 서버가 지키기로 한 전송 규약(약속).

> 💡 참고: 역사적으로 '인터넷(ARPANET)'은 냉전 시절 군사적 분산 통신망으로 출발했고, '웹(WWW)'은 학술 정보 및 논문을 링크로 이어 편하게 찾기 위해 탄생했습니다.

### 1.2 IP 주소, 도메인, 그리고 DNS

* **IP 주소**: 인터넷상에서 컴퓨터(웹 서버)가 가지는 고유한 숫자 번지수. (예: 142.250.196.142)
* **도메인 (Domain Name)**: 숫자로 된 IP 주소를 사람이 기억하기 쉽게 문자로 만든 이름. (예: google.com)
* **DNS (Domain Name System)**: 도메인 이름을 입력했을 때 해당 IP 주소로 변환해 주는 시스템.
  * 핵심: DNS 조회는 데이터가 매우 작기 때문에, 속도와 효율성을 위해 HTTP(TCP 기반)가 아닌 DNS 전용 프로토콜(UDP 방식)을 사용합니다.

> ➕ **더 알아두기**
> TCP와 UDP의 차이가 여기서 왜 갈리는지 알아두면 좋다.
> - **TCP** — 보내기 전에 연결을 맺고("잘 들려?" "응"), 빠진 조각이 있으면 다시 보내준다. **정확하지만 느리다.** 웹 페이지처럼 한 글자도 틀리면 안 되는 데이터에 쓴다.
> - **UDP** — 연결 없이 그냥 던진다. **빠르지만 유실될 수 있다.** DNS 조회처럼 "짧은 질문 하나, 짧은 답 하나"인 경우, 실패하면 그냥 한 번 더 물어보는 게 연결을 맺는 것보다 빠르다.
>
> 실시간 게임이나 화상통화도 UDP를 쓴다. 프레임 하나 빠지는 것보다 지연이 더 치명적이기 때문이다.

### 1.3 웹 브라우저에 google.com을 입력하면 일어나는 일

1. **DNS 조회**: 브라우저가 DNS 서버에 google.com의 IP 주소를 물어보고 알아냅니다.
1. **서버 연결 수립**: 알아낸 IP 주소를 기반으로 서버와 네트워크 연결(TCP 3-Way Handshake)을 맺습니다.
1. **HTTP 요청 (Request)**: 브라우저가 서버에 "메인 페이지(HTML 등)를 주세요"라고 요청을 보냅니다.
1. **HTTP 응답 (Response)**: 서버가 요청을 처리한 후 성공 코드(200 OK)와 함께 웹 문서 코드를 반환합니다.
1. **브라우저 렌더링 (Rendering)**: 전달받은 코드(HTML, CSS, JS)를 브라우저가 해석하여 시각적인 화면으로 그려 사용자에게 보여줍니다.

> ➕ **더 알아두기**
> **3-Way Handshake**는 연결을 맺기 전에 세 번 인사를 주고받는 절차다.
> ① 클라이언트 "연결할까?(SYN)" → ② 서버 "좋아, 나도 연결할까?(SYN+ACK)" → ③ 클라이언트 "좋아(ACK)"
> 세 번인 이유는, **양쪽 모두가 "보내기"와 "받기"가 되는지 확인**해야 하기 때문이다. 두 번이면 서버는 자기 응답이 도착했는지 알 수 없다.
> 이 절차 때문에 첫 요청에는 항상 약간의 지연이 생긴다. UDP가 DNS에서 빠른 이유가 바로 이 과정을 건너뛰기 때문이다.

### 1.4 API와 Request / Response 구조

* **API Request (요청)**: 클라이언트가 URL을 통해 서버로 데이터나 처리 결과를 요구하는 통신.
* **API 요청의 4가지 핵심 요소**:
  1. **HTTP Method**: 수행할 행위 (GET: 조회, POST: 생성, PUT: 수정, DELETE: 삭제)
  1. **URL (Endpoint)**: 요청할 목적지 주소
  1. **Headers**: 요청에 대한 부가 정보 (Content-Type, 인증 토큰 등)
  1. **Body**: 서버로 전달할 실제 데이터 (주로 POST, PUT에서 사용)

> ➕ **더 알아두기**
> 이 4가지가 그대로 n8n의 **HTTP Request 노드 설정 화면**이다. Method 드롭다운, URL 칸, Headers 탭, Body 탭이 각각 하나씩 대응된다.
> 어제 Open-Meteo를 호출할 때 Body를 안 쓴 이유도 여기서 설명된다. **GET은 "달라"는 요청이라 보낼 데이터가 없어서** 조건을 URL 뒤 쿼리 스트링에 붙인다. 반대로 POST는 보낼 데이터가 있으니 Body를 쓴다.

### 1.5 HTTP의 2대 핵심 특징: Stateless & Connectionless

**① Stateless (무상태성)**

* **개념**: 서버는 클라이언트의 이전 상태(맥락)를 기억하지 않으며, 각 요청을 독립적인 개별 사건으로 처리합니다.
* **장점**: 서버가 사용자 상태를 보관하지 않으므로, 요청이 몰릴 때 서버를 수평적으로 확장(Scale-out)하기 매우 용이합니다.

**② Connectionless (비연결성)**

* **개념**: 요청을 보내고 응답을 받으면 즉시 연결(Connection)을 끊는 특징.
* **장점**: 서버가 접속을 계속 유지할 필요가 없어 서버 자원(메모리/통신)을 대폭 절약할 수 있습니다.

> ➕ **더 알아두기**
> "수평적 확장(Scale-out)"이 왜 Stateless 덕분에 쉬워지는지가 핵심이다.
> 서버가 사용자 상태를 기억한다면, 그 사용자는 **반드시 같은 서버로만** 연결되어야 한다. 서버를 10대로 늘려도 "이 손님은 3번 서버 담당"이라고 묶여 있으면 부하 분산이 안 된다.
> Stateless라면 매 요청이 독립적이므로 **아무 서버나 받아도 결과가 같다.** 그래서 트래픽이 몰릴 때 서버를 그냥 복사해서 늘리면 된다.
> 참고로 Scale-**out**은 서버 대수를 늘리는 것, Scale-**up**은 서버 한 대의 성능(CPU·RAM)을 올리는 것이다.

### 1.6 Stateless 한계 극복: 쿠키, 세션, 토큰 (인증 방식)

HTTP가 상태를 기억하지 못하므로, 로그인 유지 등을 위해 클라이언트가 요청 시마다 '입장권'을 매번 첨부해서 보냅니다.

> ➕ **더 알아두기**
> 수업에서는 개념만 짚고 넘어갔으니, 셋의 차이를 한 번 정리해두면 좋다.
> - **쿠키(Cookie)** — 브라우저가 저장하는 작은 메모지. 서버가 "이거 갖고 있다가 다음에 올 때 보여줘"라고 주는 것. 요청할 때마다 자동으로 함께 전송된다.
> - **세션(Session)** — 진짜 정보는 **서버가** 보관하고, 클라이언트에게는 사물함 번호표(세션 ID)만 쿠키로 준다. 안전하지만 **서버가 기억해야 하므로** 위에서 말한 Scale-out의 장점이 줄어든다.
> - **토큰(Token, 주로 JWT)** — 정보를 **서명된 문자열 자체**에 담아 클라이언트가 들고 다닌다. 서버는 서명만 검증하면 되므로 아무것도 기억하지 않아도 된다. **Stateless를 유지한 채 로그인을 구현하는 방식**이라 요즘 API에서 주로 쓴다.
>
> 아래 1.7에서 "토큰 유효기간을 짧게"라고 하는 이유도 여기 있다. 서버가 기억하지 않으니 **한 번 발급한 토큰을 중간에 취소하기 어렵기 때문**이다.

### 1.7 네트워크 보안과 탈취(슈킹) 대책

네트워크 패킷 자체를 중간에서 도청·탈취(MITM, Replay Attack)하는 것을 물리적으로 100% 막기는 불가능하므로, 탈취당해도 사용할 수 없도록 보안을 강화합니다.

1. **HTTPS (SSL/TLS)**: 데이터를 암호화하여 통신하므로 탈취당해도 내용을 해독할 수 없음.
1. **토큰 유효기간 제한**: Access Token의 수명을 짧게(10~30분) 설정하여 탈취된 토큰의 악용 방지.
1. **CORS 설정**: 허용된 도메인에서 온 요청만 서버가 응답하도록 제한.

> ➕ **더 알아두기**
> 용어 두 개만 풀어두면 이해가 쉽다.
> - **MITM(Man-In-The-Middle, 중간자 공격)** — 통신 경로 중간에 끼어들어 훔쳐보거나 내용을 바꿔치기하는 것. 카페 공용 와이파이가 대표적인 위험 지점이다.
> - **Replay Attack(재전송 공격)** — 내용을 해독하지 못해도, **탈취한 요청을 그대로 다시 보내는** 것. "1만 원 송금" 요청을 100번 재전송하는 식이다. 그래서 암호화만으로는 부족하고 유효기간·1회용 값이 필요하다.

## 2. URL 구조와 요청 방식

> 10:00–11:00 URL에 대한 설명, request 요청의 종류와 포트, 프로토콜의 기초 개념

### 2.1 서버 요청(Request) 데이터 전송 방식: GET vs POST

* **주소창 엔터의 비밀**: 웹 브라우저 주소창에 URL을 입력하고 Enter를 누르는 모든 동작은, 서버에 해당 페이지를 달라고 요청하는 **GET 요청**입니다.

> ➕ **더 알아두기**
> 그래서 GET과 POST를 구분하는 실용적인 기준이 생긴다. **"주소만 복사해서 남한테 보냈을 때 똑같이 재현되어야 하는가?"**
> 검색 결과, 상품 목록, 게시글 보기는 GET이다. 주소를 공유하면 상대도 같은 화면을 본다.
> 반대로 **로그인, 결제, 글쓰기는 절대 GET을 쓰면 안 된다.** GET은 정보가 URL에 그대로 노출되어 브라우저 방문 기록과 서버 로그에 남기 때문이다. 비밀번호가 주소창에 찍히는 셈이다.

### 2.2 API 문서 (API Specification)와 규격

* API 서비스마다 특정 기능에 대해 GET을 써야 할지 POST를 써야 할지를 **API 문서에 미리 정해두고** 제공합니다.
* 정해진 규칙과 다른 방식(메서드)으로 요청을 보내면 서버는 **405 Method Not Allowed** 에러를 반환합니다.
* **Swagger (OpenAPI)**: FastAPI 등에서 API 규격 및 테스트 화면을 자동으로 시각화해 주는 웹 문서 도구입니다.

### 2.3 서브도메인 (Subdomain)

* 메인 도메인(google.com) 앞에 붙여서, 하나의 서비스 내에서 역할이나 서버를 분리할 때 사용합니다.
  * 예: [www.google.com](https://www.google.com) (메인 웹), mail.google.com (메일), api.google.com (백엔드 API 서버)
* 도메인을 하나 구매하면 서브도메인은 **추가 비용 없이** 마음대로 여러 개 만들어 서로 다른 서버에 연결할 수 있습니다.

> ➕ **더 알아두기**
> 서브도메인이 공짜인 이유는, 유료로 산 것이 **도메인 이름 자체(google.com)에 대한 권리**이고 그 아래를 어떻게 쪼갤지는 **내 DNS 설정**이기 때문이다. 등록 기관을 다시 거칠 일이 없다.
> 7월 30일에 배운 도메인 비용 구조와 연결해서 기억하면 좋다. 매년 내는 돈은 "google.com이라는 이름을 나만 쓴다"는 등록 비용이지, 그 아래 주소 개수에 대한 비용이 아니다.

### 2.4 HTTP vs HTTPS & 포트(Port)

**① HTTP vs HTTPS**

* **HTTP (:80)**: 암호화되지 않은 평문 통신. 네트워크 중간에서 데이터를 탈취(스니핑)당하면 내용이 그대로 노출됨.
* **HTTPS (:443)**: HTTP에 SSL/TLS 암호화 계층을 추가한 보안 통신. 데이터가 암호화 상자에 담겨 전송되므로 안전함.

**② 포트 (Port)**

* 하나의 서버(IP 주소) 내부에서 **어떤 프로그램(서비스/방)으로 찾아갈지** 지정하는 번호입니다.
* **기본 포트 생략**: `http://`는 :80, `https://`는 :443 포트로 자동 연결되므로 주소창에서 포트 번호가 생략됩니다.
* 주요 개발 포트 예시: FastAPI (8000), Streamlit (8501), React (3000)

> ➕ **더 알아두기**
> IP와 포트의 관계는 **건물 주소와 호수**로 기억하면 된다. IP는 "이 건물"까지 안내하고, 포트는 "그 건물의 몇 호"를 가리킨다. 서버 한 대에서 여러 프로그램을 동시에 돌릴 수 있는 이유가 이것이다.
> 개발할 때 자주 만나는 `EADDRINUSE: address already in use` 에러도 여기서 나온다. **한 포트는 한 프로그램만** 쓸 수 있어서, 이미 3000번을 쓰는 프로그램이 떠 있으면 다른 프로그램이 못 들어간다.

### 2.5 URL의 전체 구조

우리가 브라우저에 입력하는 URL 주소는 다음과 같은 순서와 규격으로 구성되어 있습니다.

```plain text
 https://  www.example.com  :8080  /users/profile  ?lang=ko&page=1
[프로토콜]    [도메인]      [포트]       [Path]        [Query String]
```

1. **Protocol**: 통신 규약 (`http://`, `https://`)
1. **Domain**: 서버의 이름 (example.com)
1. **Port**: 서버 내부의 서비스 방 번호 (:8080, 생략 시 HTTP는 80, HTTPS는 443)
1. **Path**: 서버 내 파일·페이지·리소스를 찾아가는 경로
1. **Query String**: 데이터를 식별하고 필터링하기 위한 조건(옵션)

### 2.6 Path (경로)

* **범위**: 포트 번호(또는 도메인)의 끝 슬래시(`/`)부터 물음표(`?`)가 나오기 전까지의 영역.
* **역할**: 폴더 경로처럼 서버 내부에서 구체적으로 어떤 페이지나 리소스(위치)에 접근할지 나타냅니다.
  * 예: `/users/profile` (사용자 프로필 페이지 경로)

### 2.7 Query String (쿼리 스트링) & Identifier (식별자)

* **범위**: 물음표(`?`) 뒤에 붙는 모든 영역.
* **역할**: 서버의 수많은 데이터 중 내가 원하는 조건의 데이터를 정확히 식별(Identify)하고 필터링하기 위해 넘겨주는 데이터 영역입니다.
* **구조 (Key-Value)**:
  * 데이터를 `Key=Value` (키=값) 쌍 형태로 전달합니다.
  * 여러 개의 조건을 붙일 때는 `&` (앰퍼샌드) 기호로 연결합니다.

```plain text
? category = shoes & color = black
  └─ 키 ─┘   └─ 값 ─┘  └─ 키 ─┘  └─ 값 ─┘
```

* **서버에서의 처리**: URL로 전달받은 `?category=shoes&color=black` 문장을 서버(Python 등)가 넘겨받으면, `{"category": "shoes", "color": "black"}` 형태의 딕셔너리(JSON)로 해석하여 사용합니다.

> ➕ **더 알아두기**
> 어제 Open-Meteo를 호출할 때 n8n의 **Query Parameters 칸에 Key와 Value를 하나씩 채워 넣은 것**이 바로 이 쿼리 스트링이다. n8n이 `?`와 `&`, `=`를 알아서 붙여서 완성된 URL을 만들어준다.
> 그때 "쉼표 뒤에 공백을 넣지 말라"는 주의사항이 있었던 것도 같은 맥락이다. 쿼리 스트링은 **URL의 일부**라서, 공백이나 한글처럼 URL에 그대로 쓸 수 없는 문자는 `%20` 같은 형태로 인코딩되어야 한다. 이걸 **URL 인코딩**이라고 하고, 이 저장소에서 이미지 파일명의 공백을 `%20`으로 바꾸는 것과 완전히 같은 규칙이다.

## 3. HTTP Response와 Status Code

> 11:00–12:00 Response, Status Code 분류, 3대 핵심 상태 코드, 유명한 상태 코드 Top 4

### 3.1 HTTP 응답(Response)의 핵심 구성 요소

서버가 클라이언트의 요청(Request)을 처리한 뒤 돌려주는 응답은 크게 두 가지로 나뉩니다.

* **Status Code (상태 코드)**: 처리 결과가 성공인지 실패인지(실패했다면 원인이 무엇인지) 3자리 숫자로 요약한 정보.
* **Response Body (본문)**: 클라이언트가 요청한 실제 데이터 (HTML, JSON, 이미지 등).

### 3.2 Status Code 백의 자리별 5가지 분류 (1xx ~ 5xx)

  *(수업에서 다뤘으나 내용 미기록)*

> ➕ **더 알아두기**
> 미기록 부분이라 5가지 분류를 채워둔다. **백의 자리 숫자만 봐도 누구 책임인지 알 수 있다**는 것이 핵심이다.
> - **1xx (정보)** — 처리 중. 실무에서 볼 일이 거의 없다.
> - **2xx (성공)** — 요청이 정상 처리됨.
> - **3xx (리다이렉션)** — "그 주소 아니고 저기로 가세요". http로 접속했을 때 https로 자동 이동시키는 것이 대표적이다.
> - **4xx (클라이언트 잘못)** — 요청한 쪽의 문제.
> - **5xx (서버 잘못)** — 받은 쪽의 문제.

### 3.3 개발에서 가장 중요한 핵심 분류와 책임 소재

실무 개발에서는 2xx, 4xx, 5xx 이 세 가지가 전체의 대부분을 차지합니다.

* **2xx (성공)**: 요청과 처리가 완벽히 성공함.
* **4xx (클라이언트 잘못)**: 존재하지 않는 주소 호출, 권한 없음, 데이터 형식 오류 등 요청자 측 문제.
* **5xx (서버 잘못)**: 서버 코드 버그, DB 다운 등 백엔드 개발자 측 문제. 백엔드 개발자 입장에서는 예외 처리를 철저히 하여 **500번대 에러가 절대 발생하지 않도록** 코딩하는 것이 원칙입니다.

### 3.4 가장 자주 쓰이는 대표 Status Code Top 4

1. **200 OK**: 요청 처리 성공 (기본 성공 응답)
1. **201 Created**: POST 요청 등을 통해 새로운 데이터·리소스 생성 성공
1. **404 Not Found**: 요청한 Path(주소)나 리소스를 찾을 수 없음
1. **500 Internal Server Error**: 서버 내부 코드 또는 시스템 오류 발생

> ➕ **더 알아두기**
> n8n에서 워크플로우가 빨갛게 실패했을 때, **상태 코드만 보면 어디를 고쳐야 하는지 바로 판단**할 수 있다.
> - **401 Unauthorized / 403 Forbidden** → 내 API 키·토큰 문제. 자격 증명(Credentials)을 다시 확인한다.
> - **404** → URL 오타. 내가 고칠 수 있다.
> - **405** → 메서드를 잘못 골랐다. GET/POST를 바꿔본다. (2.2 참고)
> - **429 Too Many Requests** → 너무 자주 호출했다. 트리거 주기를 늘려야 한다.
> - **5xx** → **내 잘못이 아니다.** 상대 서버 문제이므로 코드를 아무리 고쳐도 소용없고, 재시도(Retry) 설정을 켜두는 것이 답이다.
>
> 4xx와 5xx를 구분하는 습관만 들여도 "내 코드를 고칠 것인가, 기다릴 것인가"가 바로 갈린다.

### 4.4 AI Agent 단기 메모리(Simple Memory) 설정

**AI Agent의 메모리 기능 필요성**

기본 AI Agent 노드는 **상태를 저장하지 않는(Stateless)** 특성이 있어, 이전 질문이나 대화 맥락을 기억하지 못합니다. 이전 대화를 기억하게 만들려면 AI Agent 노드에 **Memory** 하위 노드(예: Simple Memory)를 연결해야 합니다.

> ♻️ 원문에는 "상태를 저장하지 않는(Stateful 하지 않은) 특성"이라고 적혀 있었으나, 정확한 용어는 **Stateless(무상태)**다. Stateful은 그 반대말이다.

**Context Window Length의 개념**

- **개념**: AI가 기억할 **최근 대화 메시지의 개수**를 지정하는 설정값입니다.
- **동작 방식**: 수치를 `10`으로 설정하면, 최근 주고받은 10개의 메시지(질문 5개 + 답변 5개)의 대화 맥락만 유지합니다.

**⚠️ 헷갈리기 쉬운 점**

- **Context Window Length는 식별자(ID)가 아닙니다**: 특정 기준이 되는 ID를 지정하는 것이 아니라, 유지할 '대화 개수(분량)'를 숫자로 지정하는 값입니다.
- **메모리 크기와 비용·속도**: Context Window Length를 지나치게 높게 잡으면 AI가 기억하는 대화량이 늘어나지만, LLM에 전송되는 **토큰(Token) 수가 급증하여 비용이 크게 증가하고 응답 속도가 느려질 수 있습니다.**

> ➕ **더 알아두기**
> 이름이 같아서 헷갈리기 쉬운데, n8n의 `Context Window Length`(대화 **개수**)와 LLM의 컨텍스트 윈도우(토큰 **개수**)는 **단위가 다르다.** 전자는 "최근 몇 통을 챙겨갈까", 후자는 "한 번에 몇 토큰까지 볼 수 있나"이다.
> 그리고 여기서 1.5장의 **Stateless**가 다시 등장한다. LLM API 역시 무상태라서, 사실 AI는 아무것도 기억하지 않는다. **매 요청마다 지난 대화를 통째로 다시 보내는 것**뿐이다. "기억한다"는 건 착각이고, 실제로는 n8n이 대화 기록을 들고 있다가 매번 첨부하는 것이다.
> 그래서 대화가 길어질수록 비용이 늘어난다. 10번째 질문을 할 때 앞의 9번을 전부 다시 보내기 때문이다.

## ✅ 확인 질문

1. 하이퍼텍스트, 하이퍼링크, HTTP의 관계를 한 문장씩으로 설명해보라.
2. DNS 조회는 왜 TCP가 아니라 UDP를 쓰는가? TCP와 UDP의 차이는?
3. 브라우저에 google.com을 입력하고 화면이 뜨기까지의 5단계를 순서대로 말해보라.
4. TCP 3-Way Handshake가 왜 두 번이 아니라 세 번인가?
5. API 요청의 4가지 핵심 요소는? GET 요청에 보통 Body가 없는 이유는?
6. Stateless가 왜 서버 확장(Scale-out)을 쉽게 만드는가?
7. Stateless인데 로그인이 유지되는 이유는? 쿠키·세션·토큰의 차이는?
8. 세션 방식이 Stateless의 장점을 깎아먹는 이유는?
9. 주소창에 URL을 입력하고 Enter를 누르면 어떤 메서드의 요청이 나가는가?
10. 로그인·결제에 GET을 쓰면 안 되는 이유는?
11. 405 에러는 무엇을 잘못했다는 뜻인가?
12. 서브도메인이 추가 비용 없이 만들어지는 이유는?
13. IP 주소와 포트의 관계를 비유로 설명해보라. 포트가 필요한 이유는?
14. URL의 5개 구성 요소를 순서대로 말하고, Path와 Query String의 경계는 어디인가?
15. 쿼리 스트링에서 `?`와 `&`는 각각 무슨 역할인가?
16. 상태 코드의 백의 자리 5가지 분류는? 4xx와 5xx의 책임 소재 차이는?
17. n8n에서 401, 404, 429, 500이 떴을 때 각각 무엇을 해야 하는가?
18. Schedule Trigger와 Telegram Trigger의 작동 방식 차이는? 후자를 뭐라고 부르는가?
19. 봇 토큰이 유출되면 무슨 일이 생기고, 어떻게 대응해야 하는가?
20. 날씨는 API로 가져오고 잡담은 AI에게 맡긴 이유는?
21. n8n에서 `{{ }}` 표현식이 문자열 그대로 나온다면 무엇을 안 켠 것인가?
22. AI Agent에 Memory 노드를 붙여야 이전 대화를 기억하는 이유는? AI가 진짜로 기억하는 것인가?
23. Context Window Length를 크게 잡으면 무엇이 좋아지고 무엇이 나빠지는가?
