## AI 모델 기초 및 LLM의 한계와 대응 전략

> 📍 정리 #1
> 
> 🏷️ 키워드: input, llm, token, context, rag

### AI 모델의 제어 요소와 LLM의 본질

- **AI 모델 제어 제약**: 사용자가 직접 제어 가능한 핵심 요소는 Input(프롬프트)이다. 개발자 관점에서는 파라미터(Temperature, Top-p 등)나 파인튜닝 데이터를 통해 출력을 추가 제어한다.
    
- **LLM의 본질**: LLM은 문장을 '이해'하는 시스템이 아니라, 입력된 토큰을 바탕으로 **"다음에 올 가장 확률 높은 토큰"을 계속 예측해서 이어 붙이는 확률 모델**이다.
    

### LLM의 주요 한계점

1. **환각 (Hallucination)**
    
    - 확률상 '그럴듯한 토큰'을 생성하기 때문에 완전한 거짓말을 당당하게 만들어내는 현상이다.
        
2. **지식 컷오프 (Knowledge Cutoff)**
    
    - 특정 시점까지의 데이터로만 사전 학습(Pre-training)되었기 때문에, 학습 이후 발생한 최신 정보나 실시간 사건은 알지 못한다.
        
3. **컨텍스트 윈도우의 한계**
    
    - 대화 맥락(Context)을 수용하는 용량에 한계가 있어 완벽한 무한 기억력을 갖지 못한다.
        

### 컨텍스트 초과 시 대응 전략

대화 용량이 다 찼을 때 선택할 수 있는 두 가지 핵심 방식:

1. **컴팩트 (Compact / 압축)**
    
    - 이전 대화 내용을 요약해 용량을 줄인다. 다만 디테일이나 소스코드 조건 등의 정보가 유실될 위험이 있다.
        
2. **새로운 세션 시작 (Session Reset)**
    
    - 대화를 리셋하고 새로운 세션을 시작하되, 작업 기록을 보존해 전달한다.
        
    - **실무 활용법**:
        
        - 기획서/설계서를 미리 `.md` 파일로 작성해 보관한다.
            
        - 진행 상황을 `TODO.md` 등의 파일로 지속해서 기록한다.
            
        - Git Commit을 통해 작업 단위를 자주 저장하여, 컨텍스트가 꼬이거나 AI 출력이 오작동할 때 즉시 복구(Rollback)할 수 있도록 한다.
            

### ⚠️ 헷갈리기 쉬운 점

- **LLM의 단기 기억(Memory)**: LLM 내부에는 인간이나 컴퓨터의 RAM과 같은 물리적 '단기 기억 장치'가 독립적으로 존재하는 것이 아니다. 대화가 이어질 때마다 이전 대화 내역 전체(Context)를 매번 Input으로 다시 전달하여 다음 토큰을 예측하는 방식으로 작동한다.

> 🔗 이어짐: 정리 #1 AI 모델 기초 및 LLM의 한계와 대응 전략

### 토큰 청구 방식과 비용 구조

- **합산 청구**: API 비용 계산 시 Input 토큰과 Output 토큰 요금이 합산되어 청구된다.
    
- **단가 차이**: Input 토큰보다 **Output 토큰의 단가가 훨씬 비싸다.** (Output 생성 시 토큰을 하나씩 순차 계산하는 자원 소모가 크기 때문)
    

### 대화 누적(Input 토큰)으로 인한 두 가지 주요 문제점

1. **비용 문제 (토큰 누적)**
    
    - 대화가 길어질수록 이전 대화 기록 전체가 매 요청마다 Input 토큰으로 재전송된다.
        
    - 이에 따라 한 번 질문할 때마다 소모되는 Input 토큰 양이 기하급수적으로 증가하여 비용이 폭증한다.
        
2. **품질 문제 (노이즈 발생 및 답변 저하)**
    
    - 불필요하거나 쓸데없는 대화 내용이 Input에 누적되면 노이즈로 작용한다.
        
    - AI의 집중력을 떨어뜨려 원하지 않는 답변이나 잘못된 결과를 유발한다.
        

### 대응 전략: 새 세션 활용

- 대화 내용이 길어지거나, 쓸데없는 내용이 쌓였거나, 작업 주제가 바뀔 때는 **새 세션(New Session)을 만드는 것**이 비용 절감과 답변 품질 유지 면에서 모두 유리하다.




## 세션 관리와 LLM 제약사항 및 AI 에이전트

> 📍 정리 #3 🏷️ 키워드: session, claude.md, memory, nondeterminism, ai_agent 🔗 이어짐: 정리 #2 LLM 토큰 비용 구조와 세션 관리

### 세션 리셋과 프로젝트 설정 파일

- **프로젝트 단위 관리**: AI를 활용한 작업은 기본적으로 **폴더 단위**로 진행된다.
    
- **프로젝트 시작 단계**: 폴더 생성 후 프로젝트 구조 및 AI와의 작업 방식/기획을 수립한다.
    
- **설정 파일 활용**: 새 세션을 열면 이전 맥락을 모르므로, 프로젝트 루트의 마크다운 파일(예: `claude.md`)에 기술 스택, 커밋 방식, 작업 지침 등을 적어두어 AI가 이를 참조하게 만든다.
    

### LLM의 주요 한계점 (추가)

- **비결정성 (Nondeterminism)**
    
    - 동일한 질문(Input)을 입력하더라도 실행할 때마다 매번 조금씩 다른 답변(Output)이 생성되는 성질이다.
        
    - 다음 토큰을 선택할 때 확률적 무작위성을 사용하기 때문에 나타나는 현상이다.
        

### AI 모델 vs AI 에이전트 (6개월 과정의 핵심)

- **AI 모델 (LLM)**: 텍스트 입력에 대해 확률적으로 다음 토큰을 예측해 답변하는 '두뇌(지능)' 역할에 집중된 엔진이다.
    
- **AI 에이전트 (AI Agent)**: AI 모델(두뇌)에 목표 달성을 위한 **자율적 계획(Planning), 도구 활용(Tool Use), 기억(Memory)** 등을 결합하여 스스로 작업을 수행하도록 만든 종합 시스템이다.
    

### ♻️ 정정 및 보완 (시험/학습용 핵심 개념)

1. **'로컬 컨텍스트' 용어 정정**
    
    - 프로젝트 내 파일(`claude.md` 등)을 통한 맥락 전달은 '로컬 컨텍스트'가 아니라 '프로젝트 콘텍스트(Project Context)', '시스템 프롬프트', 또는 '규칙 파일(Rule File)'이라고 부른다.
        
2. **`claude.md` 및 전역 메모리 동작 원리**
    
    - `claude.md`는 글로벌 전역 파일이 아닌 해당 **프로젝트 전용 설정 파일**이다.
        
    - 전역적인 사용자 정보 저장은 파일 탐색 방식이 아닌, 플랫폼 자체의 **Custom Instructions(개인화 지침)** 또는 **Memory 기능**으로 처리된다.
        
3. **AI 에이전트의 차이점**
    
    - 에이전트의 차이는 단순히 '구조 설계의 자유도'라기보다, 모델이 **"스스로 판단하여 도구를 사용하고 목표를 자율적으로 완수하는가"** 여부에 있다.




## 프롬프트 구성 4대 요소와 컨텍스트 중심의 트렌드

> 🔗 이어짐: 정리 #3 세션 관리와 LLM 제약사항 및 AI 에이전트

### 좋은 프롬프트의 4대 요소

- **역할 (Role)**: AI에게 페르소나나 전문가 역할을 부여하여 답변의 범위와 톤앤매너를 설정함.
    
- **맥락 (Context)**: 현재 상황, 배경 지식, 제약 조건 등을 제공함.
    
- **작업 (Task)**: AI가 정확히 수행해야 하는 행동을 명확하고 디테일하게 지시함.
    
- **형식 (Format)**: 결과물의 출력 형태(예: JSON, 마크다운 표, 요약문 등)를 지정함.
    

### 최신 프롬프트 모범 사례 및 트렌드

- **핵심 요소의 비중**: 4가지 요소를 모두 갖출수록 AI 답변의 통제력(Control)이 극대화된다.
    
- **맥락(Context)과 작업(Task)의 중요성**: 특히 디테일한 **작업 지정**과 풍부한 **맥락 전달**이 원하는 답변을 얻어내는 데 가장 결정적인 역할을 한다.
    

### ♻️ 정정 및 보완 (시험/학습용 핵심 개념)

- **프롬프트 엔지니어링 vs 컨텍스트 엔지니어링 개념 구분**
    
    - 맥락(Context)을 풍부하게 제공하여 답변 정확도를 높이는 행위는 기존 프롬프트 엔지니어링과 대립되는 개념이 아니라, **프롬프트 엔지니어링의 핵심 기법이자 발전된 형태**로 분류된다.
        
    - 따라서 맥락을 강조하는 것 역시 넓은 의미의 프롬프트 엔지니어링 범주 안에서 이해해야 시험 및 이론 작성 시 정확하다.
