# (2) RAG 실험 설계 계획서

작성일: 2026-09-07
대상 폴더: `aim-ai-agent-practice/langchain_/10-rag-evalution-script/`

> 이 문서는 코드를 작성하기 전에 "무엇을 왜 이렇게 실험할 것인가"를 먼저 확정한 설계서다.
> 실험 종료 후 발표에서 각 선택의 근거로 사용한다.

---

## 1. 배경

10번 노트북(RAG 평가)에서 검색 전략 두 개(Similarity, MMR)를 **고정된 설정 하나로만** 평가했다.
그 결과 두 전략의 점수가 완전히 동일하게 나와(File Hit@1 0.971 / Page Hit@5 0.943 / MRR 0.907),
"어떤 설정이 우리 서비스에 더 맞는가"를 판단할 근거가 되지 못했다.

또한 설정값(`chunk_size=700`, `k=5` 등)이 코드에 직접 박혀 있어 조건을 바꿀 때마다 코드를
수정해야 했고, 조건별 결과가 남지 않아 비교가 불가능했다.

→ 조건을 config로 분리해 여러 실험을 반복 실행하고, 그 결과를 근거로 최적 조합을 선택할 수 있는
스크립트가 필요하다.

## 2. 실험 목표

두 단계로 나눈다.

1. **요소별 영향 파악** — 청크 크기, 검색 전략, k, rerank가 품질에 각각 어떤 영향을 주는지 확인
2. **가성비 조합 선택** — 1단계 자료를 근거로, 품질이 조금 낮아도 비용·시간이 훨씬 적은 조합까지
   포함해 비교하여 실제 서비스에 쓸 조합을 선택

목표가 "절대 품질 1위"가 아니라 "품질 대비 비용"이므로 **비용·시간도 반드시 함께 측정**한다.

발표 결론 형식: "요소 A는 품질에 X만큼 영향을 줬고 B는 거의 영향이 없었다. 따라서 (조합)을
선택했으며, 최고 품질 조합보다 품질은 Y% 낮지만 비용이 Z% 적다."

## 3. 기준선(baseline)

모든 실험을 **"기준선 + 한 가지만 변경"** 형태로 설계한다. 실험끼리 서로 비교하면 조합이 폭발해
결론을 못 내리지만, 기준선이 있으면 실험 하나가 "이걸 바꾸니 기준선보다 이만큼 달라졌다"는
한 문장 결론을 갖는다.

| 항목 | 기준선 값 |
|---|---|
| chunk_size | 700 |
| chunk_overlap | 100 |
| 검색 전략 | Similarity |
| k | 5 |
| rerank | 사용 안 함 |

선정 이유:
1. 가장 단순한 파이프라인이라 "여기에 무엇을 더하면 좋아지는가"를 보기에 적합하다.
2. **이미 측정을 마쳤다** (2026-09-07, 35문항). 기준선 확보에 추가 API 호출이 필요 없다.
3. 수업에서 사용한 설정과 동일해 발표 시 설명이 자연스럽다.

## 4. 실험 변수와 통제

### 통제 원칙

변수 4개 × 값 3가지를 **모든 조합**으로 돌리면 3⁴ = 81회다. 질문 임베딩만 81 × 35 = 2,835번으로
하루 한도(1,000번)를 세 배 가까이 넘긴다. 또한 두 값을 동시에 바꾸면 점수 변화의 원인을 특정할 수
없어 **결정을 내릴 수 없는 데이터**가 된다. → 한 번에 하나만 바꾼다.

### 실험 목록 (9개, 기준선 제외 신규 실행 8개)

| # | 실험명 | 기준선에서 바꾼 것 | 문서 재임베딩 |
|---|---|---|---|
| 1 | baseline | (없음) | 불필요 |
| 2 | chunk-500 | chunk_size → 500 | 필요 (약 560청크) |
| 3 | chunk-1000 | chunk_size → 1000 | 필요 (약 280청크) |
| 4 | search-mmr | 전략 → MMR | 불필요 |
| 5 | search-bm25 | 전략 → BM25 | 불필요 (임베딩 자체가 불필요) |
| 6 | search-hybrid | 전략 → Hybrid | 불필요 |
| 7 | k-3 | k → 3 | 불필요 |
| 8 | k-10 | k → 10 | 불필요 |
| 9 | rerank-on | rerank 사용 | 불필요 |

### 문항 수 (비용·시간 트레이드오프)

- **검색 지표 실험(1~8)**: 35문항 전체. 임베딩만 쓰므로 예산에 여유가 있고, 문항이 많을수록
  점수가 우연에 덜 흔들린다.
- **LLM이 개입하는 실험(9번 rerank, 답변 생성, Judge)**: 10문항. 근거는 6장 예산 계산.

## 5. 측정 지표

비용은 API가 알려주지 않으므로 **호출할 때마다 코드가 직접 세는 계수기**를 붙인다.

### 품질 축

| 지표 | 의미 | 비용 |
|---|---|---|
| File Hit@1 | 정답 파일을 찾았는가 | 무료 |
| Page Hit@1 / @3 / @5 | 정답 파일+페이지를 찾았는가 | 무료 |
| MRR | 정답이 몇 번째에 처음 나왔는가 | 무료 |
| Judge 4항목 평균 | 생성 답변의 정확성·완전성·근거성·출처정확성 | LLM 호출 |

### 비용·시간 축

| 지표 | 세는 방법 | 왜 필요한가 |
|---|---|---|
| 임베딩 호출 수 | 요청마다 +1 (문서/질문 구분) | 하루 한도(RPD)에 걸리는 축 |
| LLM 호출 수 | 요청마다 +1 (rerank/생성/Judge 구분) | 하루 한도에 걸리는 축 |
| 소요 시간 | 실험 전체 경과 + 문항당 평균 지연 | 분당 한도와 사용자 체감 |
| 토큰 수 | 요청·응답 토큰 누적 | 실제 과금 단위 |
| 예상 금액(원) | 토큰 수 × 유료 단가 | 결정권자에게 설명하는 단위 |

무료 티어라 실제 청구는 0원이지만, "유료였다면 얼마"를 환산해두면 트레이드오프 설명 근거가 된다.
**단가는 구현 시 공식 가격표에서 확인한다(추측하지 않는다).**

## 6. API 한도와 예산 계산

무료 티어. 두 모델의 한도는 서로 **별개로** 관리된다.

| 모델 | 분당 요청 | 분당 토큰 | 하루 요청 |
|---|---|---|---|
| `gemini-embedding-2` | 100 | 30,000 | 1,000 |
| `gemini-3.5-flash-lite` | 15 | 250,000 | 500 |

### 임베딩 예산

| 항목 | 요청 수 |
|---|---|
| 문서 임베딩 (chunk-500 약 56 + chunk-1000 약 28) | 약 84 |
| 질문 임베딩 (35문항 × 7실험, BM25 제외) | 245 |
| **합계** | **약 330 / 1,000** |

병목은 분당 요청(100)이 아니라 **분당 토큰(30,000)**이다. 청크 402개면 한국어 700자 ≈ 400토큰
기준 총 16만 토큰이라, 문서 임베딩 한 번에 최소 6분은 나눠 보내야 한다.
2026-09-07에 배치를 쉬지 않고 연속 전송해 429가 발생한 원인이 이것이다.

### LLM 예산 (10문항 기준)

rerank는 후보를 하나씩 채점하므로 호출 수 = 문항 수 × top_n 이다.

| 구성 | 호출 수 | 소요 시간(분당 15) | 하루 한도 소모 |
|---|---|---|---|
| rerank 끔 (생성+Judge) | 20 | 약 1.5분 | 4% |
| rerank 켬 (rerank 50 + 생성 10 + Judge 10) | 70 | 약 5분 | 14% |
| 합계 | 90 | 약 6분 | 18% |

LLM 병목은 **분당 15회**(4초에 1회)로, 하루 한도보다 시간이 먼저 제약이 된다.

### 페이싱 방침 (한도에 딱 맞추지 않고 여유를 둔다)

- 임베딩: 배치 10개 기준 **분당 5배치 이하** (약 2만 토큰/분 = 한도의 67%)
- LLM: 요청 간 **5초 대기** (분당 12회 = 한도의 80%)

## 7. 안정성 — 중단돼도 이어서 실행

2026-09-07에 두 번 중단됐고 결과가 달랐다. 그 차이가 설계 근거다.

- 문서 임베딩 중 중단 → **보존됨.** Chroma에 넣는 즉시 디스크에 기록되는 구조였다.
- 35문항 평가 중 중단 → **전부 소실.** 점수를 리스트(메모리)에만 쌓고 마지막에 저장했다.

원칙: **일이 끝날 때마다 즉시 디스크에 기록하고, 재실행 시 남아있는 것은 건너뛴다.**

- **체크포인트 단위 = 문항 단위.** 문항 하나 평가가 끝나면 결과 한 줄을 `rows.jsonl`에 즉시 추가.
  재실행 시 그 파일을 먼저 읽어 이미 기록된 문항은 건너뛴다.
- **문서 임베딩 재사용.** 청킹 설정별로 Chroma 컬렉션을 분리 저장하고, 같은 청킹으로 다시 돌릴 때는
  임베딩을 생략한다(청킹이 다르면 다른 코퍼스이므로 컬렉션도 별개).
- **429 재시도.** 429 발생 시 즉시 죽지 않고 지수 백오프로 재시도(최대 5회).

## 8. config 설계

### 형식: YAML (`pip install pyyaml`)

주석(`#`)으로 각 항목의 선택 가능한 값을 파일 안에 적어둘 수 있고, 실무 설정 파일(GitHub Actions,
Docker 등)이 대부분 YAML이라 학습 가치가 있다.

### 구조: 실험마다 파일 하나 (`configs/<실험명>.yaml`)

공통값이 9개 파일에 중복되지만, 병합 로직이 없어 코드가 단순하고 실험 하나만 다시 돌리기 쉽다.
실험이 9개 규모라 중복 비용이 감당 가능하다.

### 항목 (예: `configs/chunk-500.yaml`)

```yaml
experiment_name: chunk-500

data:
  pdf_dir: data/public
  golden_set: data/public/public_paragraph_golden_set.json

models:
  embedding: gemini-embedding-2
  llm: gemini-3.5-flash-lite

chunk:
  size: 500          # 기준선 700에서 바꾼 항목
  overlap: 100

search:
  strategy: similarity   # similarity | mmr | bm25 | hybrid
  k: 5
  mmr:
    fetch_k: 20
    lambda_mult: 0.5
  hybrid:
    weights: [0.5, 0.5]

rerank:
  enabled: false
  top_n: 5           # LLM 호출 수 = 문항 수 × top_n

evaluation:
  retrieval_limit: 35    # 검색 지표에 쓸 문항 수
  llm_limit: 10          # rerank·생성·Judge에 쓸 문항 수
  run_generation: false
  run_judge: false

pacing:
  embed_batch_size: 10
  embed_sleep_sec: 12    # 분당 5배치 (한도의 67%)
  llm_sleep_sec: 5       # 분당 12회 (한도의 80%)
  max_retries: 5
```

config는 아이디어를 새로 짜내는 것이 아니라 **3~7장의 결정을 기계가 읽을 형태로 옮겨쓴 것**이다.

## 9. CLI 설계

역할 분담: **config = 그 실험이 무엇인지(신원)**, **CLI = 이번 실행에 대한 것.**

| 옵션 | 용도 | 채택 이유 |
|---|---|---|
| `--config` | 사용할 실험 config 경로 | 필수. 어떤 실험인지 지정하는 유일한 수단 |
| `--limit N` | 문항 수를 임시로 줄여 실행 | smoke test. 전체를 돌리기 전 코드가 끝까지 도는지 30초에 확인 |
| `--dry-run` | API 호출 없이 예상 호출 수·토큰·금액만 계산 | 한도 초과 사전 방지 + 비용 집계 로직이 그대로 재사용됨 |

`--result-dir`는 제외한다. 기본값 `outputs`로 충분하고 필요해지면 한 줄로 추가할 수 있다.
(지금 필요 없는 옵션을 미리 만드는 것은 과설계)

`--limit`을 config가 아니라 CLI에 두는 이유: 문항을 3개로 줄인 것은 실험 설계가 아니라
시험 삼아 돌려본 것이므로, config 파일에 기록으로 남으면 "이 실험은 3문항이었다"는 오해를 만든다.

실행 예:
```powershell
python main.py --config configs/chunk-500.yaml --dry-run
python main.py --config configs/chunk-500.yaml --limit 3
python main.py --config configs/chunk-500.yaml
```

## 10. 프로젝트 구조

파일을 나누는 기준은 줄 수가 아니라 **"바뀌는 이유가 다른가"**다. 다만 너무 잘게 쪼개면
전체 흐름을 스스로 설명하지 못하게 되므로 6개로 제한한다.

```
10-rag-evalution-script/
  configs/                  # 실험 9개의 YAML
  main.py                   # CLI 입구: 옵션 받고 실행 순서만 지시
  config.py                 # YAML 읽기 + 값 검증
  pipeline.py               # PDF 로드·메타데이터 정규화·청킹·벡터저장소·검색기 생성
  metrics.py                # File Hit / Page Hit / MRR 계산
  runner.py                 # 문항 반복 · 체크포인트 저장 · 비용 집계 · 재시도
  report.py                 # 실험들 결과를 표로 비교
  outputs/                  # 실험별 결과
    chunk-500/
      config.yaml           # 사용한 config 사본 (결과의 증거)
      rows.jsonl            # 문항별 기록 (체크포인트 겸용)
      summary.json          # 품질·비용·시간 집계
  chroma_db/                # 청킹별 임베딩 저장소 (재사용)
```

각 파일이 바뀌는 이유:
- `metrics.py` — golden set의 정답 형식이 바뀔 때
- `pipeline.py` — 새 검색 전략을 추가할 때
- `runner.py` — 체크포인트·비용 집계 방식이 바뀔 때
- `main.py` — CLI 옵션을 늘릴 때

**기존 코드 재사용**: `pipeline.py`와 `metrics.py`의 내용은 이미 작성·검증된
`10-rag-evaluation-practice.ipynb`(PDF 로드·청킹·지표 3함수)와
`09-rag-search-advanced.ipynb`(BM25+Kiwi 토크나이저, EnsembleRetriever, rerank 함수)에서 가져온다.
새로 발명하지 않는다.

## 11. 실행 순서

비용이 낮고 위험이 적은 것부터 진행한다.

1. `--dry-run`으로 각 config의 예상 호출 수 확인
2. `--limit 3`으로 baseline smoke test (코드가 끝까지 도는지)
3. **baseline 전체 실행** — 기존에 측정한 값(Page Hit@5 0.943, MRR 0.907)이 재현되는지 확인.
   재현되면 새 스크립트가 올바르다는 증거가 된다.
4. **청킹을 바꾸지 않는 실험**(search-mmr / search-bm25 / search-hybrid / k-3 / k-10) —
   문서 임베딩 재사용으로 저렴
5. **청킹을 바꾸는 실험**(chunk-500 / chunk-1000) — 문서 재임베딩 필요, 각 6분 이상 소요
6. **rerank-on** (10문항) — LLM 사용
7. 필요 시 생성+Judge 비교 (rerank off/on, 각 10문항)
8. `report.py`로 전체 비교 표 생성 → 발표 자료

## 12. 검증 방법

- **재현 검증**: 3단계에서 기존 baseline 수치가 재현되는지 확인 (가장 중요한 검증)
- **smoke test**: 각 실험을 `--limit 3`으로 먼저 돌려 오류 없이 끝나는지 확인
- **체크포인트 검증**: 실험 중간에 의도적으로 중단(Ctrl+C)한 뒤 다시 실행해,
  이미 처리한 문항을 건너뛰고 이어서 진행하는지 확인
- **예산 검증**: `--dry-run`의 예측 호출 수와 실제 실행 후 집계된 호출 수가 일치하는지 확인

## 15. 계획 대비 어긋난 점 (발견 사항)

### 15-1. 예산 계산이 틀렸다 — 배치는 하루 한도를 아껴주지 않는다

계획서 6장에서 "청크 402개를 10개씩 묶으면 요청 41번"으로 계산했고, `CostCounter`도 배치당 1회로 셌다.
그러나 실제로 하루 한도(1,000회)가 소진된 속도를 역산하면, **API는 배치로 묶어 보내도 텍스트 하나하나를
1회 요청으로 계산**한다. 402개 청크는 41회가 아니라 402회가 차감된다.

결론: **배치는 분당 요청 수(RPM)를 줄여주지만 하루 한도(RPD)는 전혀 아껴주지 않는다.**
계획의 "전체 330회" 예산은 실제로 3배 이상이었다.

### 15-2. 부분 저장된 컬렉션을 완성본으로 착각하는 버그

`build_vectorstore`의 재사용 판단이 `count() > 0`이었다. 하루 한도로 중단돼 390/552개만 저장된
chunk-500 컬렉션을 완성본으로 판단해 재사용했고, 그 결과 문서 29%가 빠진 상태로 실험이 돌아가
page_hit_1 0.686이라는 오염된 값이 나왔다. **오류 없이 조용히 틀린 결과를 만든 것이 가장 위험한 지점.**

수정: `count() == len(documents)`일 때만 재사용하고, 적으면 `documents[stored:]`만 이어서 임베딩한다.
수정 후 chunk-500 재실행 결과는 page_hit_1 0.857로 정상화됐다.

부수 발견: 체크포인트(`rows.jsonl`)는 "어느 문항을 처리했는가"만 기억하고 "어떤 코퍼스로 처리했는가"는
모른다. 그래서 코퍼스를 고친 뒤에는 해당 실험의 `rows.jsonl`을 삭제해야 재채점된다.

### 15-3. 천장 효과 — rerank의 효과를 측정할 수 없었다

`llm_limit: 10`이 golden set의 **앞** 10문항을 가져오는데, 그 문항들은 baseline만으로도 이미 만점(1.000)이었다.
올라갈 여지가 없으니 rerank가 개선을 만들어도 감지할 수 없다(천장 효과, ceiling effect).

정확한 결론은 "rerank가 무용하다"가 아니라 **"이 10문항 구성으로는 rerank 효과를 측정할 수 없었다"**이다.
표본을 난이도 기준으로 골라야 한다(→ 17장).

### 15-4. API 한도 429는 세 가지 다른 문제였다

같은 429 에러 코드가 서로 다른 원인을 나타냈다.

| 발생 시점 | 실제 원인 | 해결 방법 |
|---|---|---|
| 배치를 연속 전송 | 분당 토큰 한도(30,000) 초과 | 배치 간 대기 시간 추가 |
| 누적 사용 후 | 하루 요청 한도(1,000) 소진 | 대기로 해결 불가, 초기화 대기 |
| 새 키로 교체 후 | 한도는 **프로젝트 단위** 공유 | 다른 프로젝트의 키 필요 |

우리 `retry_on_429`는 세 경우를 구분하지 않고 전부 재시도한다. 하루 한도 소진은 재시도가 무의미하므로
메시지를 구분해 즉시 중단하는 것이 옳다(→ 16장).

1. **Gemini Batch API 도입** — 실시간 호출이 아닌 비동기 배치 작업으로 제출하면 별도의 훨씬 큰 한도

2. **429 원인 구분** — 에러 메시지에 하루 한도 표현(`limit: 1000`)이 있으면 재시도하지 않고 즉시 중단·안내.
3. **청킹 결과 캐시** — 실험마다 PDF 11개를 다시 파싱해 청킹하는 데 약 38초가 고정으로 든다.

4. **체크포인트에 입력 지문 저장** — `rows.jsonl`에 코퍼스 해시를 함께 기록해, 코퍼스가 바뀌면
   자동으로 무효화되게 한다(15-2의 수동 삭제를 없앤다).
5. **`CostCounter`를 텍스트 단위로 수정** — 15-1의 발견을 반영해 배치가 아니라 문서 개수로 센다.

### 17-1 결과 — rerank 재측정 완료 (난이도 균형 10문항)

baseline의 실패를 두 유형으로 분류한 결과:

| 유형 | 개수 | 문항 | rerank로 개선 가능? |

즉 **rerank가 개선할 수 있는 문항은 35개 중 2개**이며, 이것이 효과의 상한선이다.
실험을 돌리기 전에 이 상한을 계산했다면 rerank 실험 자체를 다르게 설계했을 것이다.

| 실험 | page_hit_1 | page_hit_3 | page_hit_5 | mrr | LLM 호출 | 소요 시간 |
|---|---|---|---|---|---|---|
| hard-baseline | 0.600 | 0.700 | 0.800 | 0.675 | 0 | 43.9초 |
| hard-rerank | **0.800** | 0.800 | 0.800 | **0.800** | 50 | 370.4초 |

**사전 예측과 실측이 일치했다.** 실행 전 계산한 hard-baseline 예상치(page_hit_1 0.6 / page_hit_5 0.8 /
MRR 0.675)가 세 값 모두 정확히 맞았다. 문항 선택과 코드가 의도대로 작동함을 확인.

**rerank는 이론상 최대치를 달성했다.** 개선 가능한 2문항(#18 4등, #20 2등)을 둘 다 1등으로 끌어올려
page_hit_1이 0.600 → 0.800(+0.2)이 됐다. page_hit_5는 0.800에서 변하지 않았다 —
검색되지 않은 문서를 데려올 수는 없기 때문이다(예측대로).

**그러나 비용이 정당화되지 않는다.**

- 전체 35문항 환산: page_hit_1이 0.886 → 0.943(+5.7%p)이 최대. 대가는 LLM 175회.
- 문항당 소요 시간: 4.4초 → **37초**(+32.6초). 사용자가 질문마다 30초 이상 더 기다려야 한다.

결론: **rerank는 기술적으로 완벽히 작동하지만, 이 데이터셋·서비스 조건에서는 도입을 정당화하기 어렵다.**
rerank의 가치 상한은 baseline이 이미 1등을 맞히는 비율(88.6%)에 의해 결정된다.

### 17-2. 의역·동의어 질문을 직접 작성해 BM25 vs 벡터 검증

14장 결론의 유보 조건을 직접 검증한다. 문서의 표현을 그대로 쓰지 않고 의미만 같은 질문을 만든다.

**"질문 스타일에 따라 최적 전략이 달라진다"**는 결론을 근거를 갖고 말할 수 있다.

### 18-1. 가장 중요한 차이 — 실험 단위를 무엇으로 잡을 것인가

강사 config에는 `"strategies": ["similarity", "mmr", "bm25", "hybrid"]`처럼 전략이 **배열**로 들어있다.
즉 실험 단위가 "검색 전략"이 아니라 **"청킹 설정"**이고, config는 chunk-500 / chunk-700 / chunk-1000 3개다.

우리는 전략마다 config를 나눠 9개를 만들었다. 그 결과 **같은 코퍼스를 4번 다시 로드**했고,
실측한 "PDF 로드+청킹 38초"가 전략마다 반복됐다(실험 9개에서 약 6분 낭비).

논리적으로도 강사 방식이 맞다. **청킹이 바뀌면 코퍼스가 바뀌지만, 전략이 바뀌어도 코퍼스는 그대로다.**
즉 "무엇이 코퍼스를 바꾸는가"를 기준으로 실험 단위를 잡아야 한다.
우리가 컬렉션 이름을 `public_c700_o100`처럼 청킹 값만으로 만든 것과 같은 원리인데,
그 원리를 config 구조에까지 적용하지 못했다.

config만 바꿔 실험할 수 있다. 우리는 rerank 프롬프트를 `runner.py` 안에 문자열로 박아뒀으므로
프롬프트 실험을 하려면 코드를 고쳐야 한다 — 이 과제가 지적한 바로 그 문제를 프롬프트에 대해서는 답습한 셈이다.

### 18-3. 반영 우선순위

1. config를 청킹 단위로 재구성하고 전략을 배열로 받기 (효율 + 논리 정합성)
2. 프롬프트를 `prompts/`로 분리

## 19. 교차 실험 (부분 요인 설계) — 결론이 뒤집힌 지점

### 왜 추가로 돌렸는가

18장에서 강사 구현을 비교하다가, 우리 실험에 빠진 칸이 드러났다.

```
chunk 700 : similarity ✓  mmr ✓  bm25 ✓  hybrid ✓   ← 4개 다 함
chunk 500 : similarity ✓  mmr ✗  bm25 ✗  hybrid ✗   ← similarity만
chunk 1000: similarity ✓  mmr ✗  bm25 ✗  hybrid ✗   ← similarity만
```

OFAT("기준선에서 하나만 바꿈")를 택했기 때문에, 청킹을 바꾼 실험은 전략이 similarity로 고정돼 있었다.
그래서 "청크를 줄이면 BM25가 유리해지는가" 같은 질문에 답할 수 없었다.

빠진 6칸을 채우는 비용은 낮았다. 컬렉션(`public_c500_o100` 552개, `public_c1000_o100` 308개)이
이미 완성돼 있어 **문서 임베딩 0회**, 질문 임베딩만 140회(BM25는 0회)였다.

### 결과 격자 (35문항)

**Page Hit@1**

| | similarity | mmr | bm25 | hybrid |
|---|---|---|---|---|
| chunk 500 | 0.857 | 0.857 | 0.886 | **0.943** |
| chunk 700 | 0.886 | 0.886 | 0.886 | 0.886 |
| chunk 1000 | 0.829 | 0.829 | 0.857 | 0.886 |

**MRR**

| | similarity | mmr | bm25 | hybrid |
|---|---|---|---|---|
| chunk 500 | 0.895 | 0.886 | 0.914 | **0.943** |
| chunk 700 | 0.907 | 0.907 | 0.907 | 0.910 |
| chunk 1000 | 0.872 | 0.871 | 0.895 | 0.910 |

`chunk 500 + hybrid`가 Page Hit@1 0.943, MRR 0.943, **File Hit@1 1.000**으로 18개 실험 중 최고다.

### 상호작용 — OFAT가 놓친 것

OFAT로 각각 찾은 최적값은 "청크 700"(similarity 기준)과 "hybrid"(청크 700 기준)였고,
그 조합인 `700 + hybrid`는 MRR 0.910이었다. 그러나 실제 최고는 `500 + hybrid`의 **0.943**이다.

격자를 보면 원인이 읽힌다.
- 청크 700에서 hybrid의 이득은 거의 없다 (0.907 → 0.910)
- 청크 500에서 hybrid의 이득은 크다 (0.895 → 0.943)

즉 **"hybrid가 얼마나 도움이 되는가"가 청크 크기에 따라 달라진다.** 이것이 상호작용이며,
한 번에 하나만 바꾸는 방식으로는 원리적으로 관찰할 수 없다.

원인 가설도 데이터에 있다.
- **BM25는 청크가 작아질수록 좋아진다** (MRR 1000: 0.895 → 700: 0.907 → 500: 0.914).
  청크가 짧으면 그 안의 단어 수가 적어 키워드 매칭이 더 정밀해진다.
- **벡터 검색은 청크 500에서 나빠진다** (Page Hit@1 0.886 → 0.857). 짧은 청크는 의미 정보가 부족하다.
- hybrid는 둘을 결합하므로, **BM25가 강해지고 벡터가 약해지는 지점에서 이득이 가장 크다.**
  "서로의 약점을 보완한다"는 설명이 숫자로 확인된 것이다.

### 수정된 최종 추천

| 노선 | 조합 | 근거 |
|---|---|---|
| **품질 우선** | `chunk 500 + hybrid + k=5` | MRR 0.943, File Hit@1 1.000. baseline보다 2문항 더 맞힘 |
| **가성비 우선** | `chunk 500 + BM25 + k=5` | MRR 0.914로 baseline(0.907)보다 높은데 **임베딩 호출 0회**, 43.5초 |

청크를 500으로 줄이는 것이 두 노선 모두에서 이득이었다.
14장의 추천(`700 + BM25`)은 OFAT의 한계로 인한 결론이었고, 여기서 대체된다.

### 방법론적 교훈

1. **완전 요인(81회)과 OFAT(9회) 사이에 중간 지점이 있다.** 상호작용이 있을 만한 변수 2개만
   교차시키는 부분 요인 설계(12회)가 이번 경우 정답이었다. 설계 단계에서 이 선택지를 계산하지 않은 것이 누락.
2. **캐시 구조가 실험 설계의 폭을 결정한다.** 청킹이 같으면 임베딩을 재사용하는 구조를 만들어둔 덕에
   교차 실험의 추가 비용이 질문 임베딩 140회에 불과했다. 비용 구조를 알고 있으면 더 넓은 설계를 택할 수 있다.
3. **OFAT의 결론은 "각 요인의 최적값을 합친 것이 전체 최적"이라는 보장이 없다.** 이번에 실제로 어긋났다.
