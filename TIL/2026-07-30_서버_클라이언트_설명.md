# 🌐 인터넷 도메인 시스템 & 메타(Meta) 사례 정리

> 💡 한 줄 요약

  도메인 비용은 이름을 짓는 값이 아니라, 전 세계 인터넷망에서 주소를 24시간 안전하게 찾아갈 수 있도록 유지·관리하는 행정 서비스 수수료입니다.

## 1. 웹 접속의 기본 흐름 (유저 ➔ 서버)

  우리가 웹사이트에 접속할 때 일어나는 실제 동작 원리입니다.

  Plaintext

```plain text
[ 유저 (브라우저) ]
        │  ① naver.com 입력
        ▼
[ 도메인 (DNS 시스템) ]
        │  ② 13개 루트 서버 및 대장(Registry)을 거쳐 IP 탐색
        ▼
[ IP 주소 (실제 좌표) ]
        │  ③ 예: 223.130.195.95 변환 완료
        ▼
[ 서버 (실제 웹사이트) ]
        │  ④ 해당 IP의 서버로 접속 및 화면 출력
        ▼
[ 접속 완료 ]
```

  1. 유저: 브라우저에 사람이 외우기 쉬운 문자인 도메인 주소를 입력합니다.
  1. 도메인 (DNS): DNS 시스템이 루트 서버(13개)와 Registry를 거쳐 도메인에 매핑된 IP 주소를 찾아냅니다.
  1. IP 주소: 인터넷상의 진짜 위치를 나타내는 숫자 좌표입니다.
  1. 서버: 변환된 IP 주소를 찾아가 실제 데이터가 저장되어 있는 컴퓨터(서버)에 접속합니다.
## 2. 도메인 비용을 매년 내야 하는 이유

  * 24시간 시스템 유지비: 전 세계 DNS 서버 및 네트워크가 장애 없이 가동되도록 하는 서버/보안 관리비
  * 독점권 임대료: 특정 주소를 독점 사용하는 권리 (사재기 및 주소 방치 방지)
  * 국제 보증 수수료: 전 세계 통신사와 라우터가 해당 주소를 "진짜"라고 신뢰하도록 보증하는 행정 비용
## 3. 도메인 생태계 3단계 계급 구조

## 4. .com 도메인 결제금액 배분 구조 (약 2만 원 기준)

  * Verisign (Registry): 약 13,000원~14,000원 (.com 원가 / 미국 민간 기업으로 송금)
  * ICANN (최상위 기구): 약 250원 (국제 주소 정책 수수료)
  * 가비아 (Registrar): 약 5,500원~6,500원 (한국 대행사 순수 마진 및 CS/관리 비용)
> 💡 Tip: .kr을 사면 원가가 공공기관인 KISA로 들어가 국부 유출이 없고, Cloudflare Registrar 같은 해외 직구 플랫폼을 쓰면 대행사 마진 없는 원가(약 14,000원~15,000원)로 구매 가능합니다.

## 5. 13개 루트 서버 (A~M)의 실체

  * 개념: 초기 인터넷 규격(UDP 512바이트) 한계로 A부터 M까지 13개의 식별 기호(이름표)로 등록된 최상위 길잡이 서버
  * 운영 방식: Anycast 기술을 통해 전 세계 수천 대의 물리 서버로 복제 운영 중
  * 주요 운영 주체:
    * Verisign (미국 기업): 메인인 A, J 루트 서버 운영 (.com 독점 수익으로 비용 충당)
    * 미국 정부/군대 (NASA, 미 국방부 등): B, D, E, G, H 루트 서버 운영 (국가 안보 예산)
    * KISA (한국인터넷진흥원): K, F 루트 서버의 한국 내 복제본(Mirror) 운영 (수익 목적 ❌, 국내 접속 속도 향상 및 안보 목적 ⭕)

# 🐙 Git & GitHub 오픈소스 기여 및 PR 완벽 정리

## 1. 🌳 브랜치(Branch) vs 🍴 포크(Fork)

| 구분 | **브랜치 (Branch)** | **포크 (Fork)** |
| :--- | :--- | :--- |
| **개념** | 하나의 저장소 안에서 메인 코드(`main`)를 건드리지 않고 독립적으로 만드는 작업 영역 (평행세계) | 다른 사람의 저장소 전체를 내 GitHub 계정으로 통째로 복사해 오는 기능 |
| **사용 상황** | 내 프로젝트이거나, 해당 저장소의 **권한(Collaborator)**이 있을 때 | 원본 저장소에 대한 **수정/쓰기 권한이 없는** 일반 외부인일 때 |
| **특징** | Fork 없이 저장소 내부에서 바로 브랜치를 생성하여 작업 후 PR 생성 가능 | 복사해 온 내 저장소에서 브랜치를 만들어 작업한 뒤 원본 저장소로 PR 생성 |

---

## 2. 📤 PR(Pull Request) 보내는 원리

### (1) 브랜치 지정 주체
* **기여자(작성자)**가 직접 PR을 올릴 때 **출발 브랜치(Source)**와 **목적지 브랜치(Target)**를 지정하여 요청합니다.

```text
[base: 원본 저장소의 Target 브랜치]  ◀━━━━  [compare: 내 저장소의 Source 브랜치]
       (예: develop 또는 main)                     (예: feature/login)
```

### (2) PR이 제출되었을 때의 특징

  1. 자동 반영 불가: PR을 올린다고 해서 원본 저장소의 코드에 즉시 합쳐지지 않습니다.
  1. 관리자 검토: 원본 프로젝트 관리자(Maintainer)가 코드를 검토(Code Review)하고 승인(Merge)해야 최종 반영됩니다.
  1. 목적지 브랜치 변경 가능: 기여자가 main으로 PR을 보냈더라도, 관리자의 권한으로 develop 등 다른 브랜치로 변경해서 승인(Merge)할 수 있습니다.
---

## 3. 🔄 오픈소스 기여(Contribution) 전체 흐름

  Plaintext

```plain text
[1. 원본 저장소] ── (Fork) ──> [2. 내 Fork 저장소]
                                        │
                                  (Branch 생성)
                                        │
                                  (기능 개발/수정)
                                        │
[1. 원본 저장소] <── (PR & Merge) ──────┘
```

  1. 프로젝트 탐색: 이슈 목록에서 good first issue 라벨이 붙은 작업 찾기
  1. Fork: 내 계정으로 원본 저장소 복사
  1. Branch 생성 & 수정: 내 저장소에서 작업용 브랜치를 생성하여 기능 구현 또는 버그/문서 수정
  1. Pull Request 작성: 원본 저장소의 목적지 브랜치(예: develop 또는 main)로 PR 요청
  1. Merge: 관리자 승인 후 공식 프로젝트 코드로 최종 통합

# 🌐 인터넷과 WWW 핵심 개념 정리

> 💡 한 줄 요약: 우리가 쓰는 웹(WWW)은 바닷속 해저 광케이블(유선 인터넷) 위를 달리는 서비스이며, 마지막 기지국 구간에서만 무선으로 변환되어 전달된다.

## 1. WWW (World Wide Web, 웹)

  * 개념: 인터넷이라는 도로망 위를 달리는 서비스 중 하나 (인터넷 \neq 웹)
  * 웹의 3대 핵심 요소 (by 팀 버너스리)
    * HTTP : 웹 서버와 브라우저가 대화하는 통신 규약
    * HTML : 웹페이지를 작성하는 문서 언어
    * URL : 인터넷상에서 웹페이지의 위치를 나타내는 주소
  * 하이퍼텍스트(Hypertext): 문서 내 **링크(Link)**를 통해 전 세계 정보가 거미줄처럼 연결되는 구조
## 2. 인터넷의 정체: 유선망과 해저 케이블

  * 실체: 전 세계 인터넷 데이터의 **99% 이상은 바닷속 '해저 광케이블(Submarine Cable)'**을 통해 전송됨
  * 무선 통신의 역할:
    * 내 기기 ↔ 가까운 지상 기지국(LTE/5G) 또는 공유기(Wi-Fi) 구간만 무선
    * 기지국 이후부터 전 세계 서버까지는 전부 유선 광케이블로 연결
  * 위성 인터넷 (스타링크 등): 오지, 바다, 비행기 등 지상 기지국을 설치할 수 없는 환경에서 쓰는 특수 무선인터넷
## 3. 아시아 해저 케이블망

  * 3대 디지털 허브:
    1. 싱가포르 : 동남아, 인도, 유럽으로 이어지는 관문
    1. 일본 : 태평양을 건너 미국으로 이어지는 관문
    1. 홍콩 / 대만 : 동아시아 중간 거점
  * 한국의 육양국(Landing Station): 부산, 거제, 태안 (해저 케이블이 육지와 만나는 접점)
  * 주요 해저 케이블망:
    * APCN / APCN-2 : 1990~2000년대 아시아 인터넷을 구축한 1~2세대 대표 케이블 (Ring 구조로 이중화)
    * APG, SJC, ADC : 급증하는 AI 및 클라우드 트래픽을 처리하는 차세대 케이블

# 🚀 n8n 워크플로우 & AI 연동 학습 노트

## 1. ⌨️ n8n 작업 속도를 높이는 필수 단축키

  * F2 / Space: 선택한 노드 이름 변경 (노드 구분 및 가독성 확보)
  * Tab: 캔버스 위에서 새 노드 검색/추가 창 열기
  * Ctrl + D (Mac: Cmd + D): 선택한 노드 복사/붙여넣기 (Duplicate)
  * Shift + 드래그: 여러 노드 일괄 선택
  * D: 선택한 노드 비활성화/활성화 (Deactivate/Activate)
  * Delete / Backspace: 선택한 노드 삭제
## 2. 📧 Email & Communication (Gmail/Email Send)

  * Append n8n Attribution 끄기: 메일 하단의 "This email was sent automatically with n8n" 자동 문구 제거
  * Attachments: 이전 노드에서 가져온 파일 변수명(data 등)을 지정하여 첨부파일 발송
  * 참조 설정 (Add Option):
    * CC (Carbon Copy): 메일 수신자가 모두 볼 수 있는 일반 참조인
    * BCC (Blind Carbon Copy): 수신자들에게 정보가 숨겨지는 숨은 참조인
## 3. 🎣 Webhook & Discord 연동

  * 웹훅(Webhook)이란?: 외부 시스템(디스코드, 구글 폼 등)에서 이벤트가 일어났을 때 지정된 URL로 실시간 알림/데이터를 쏘아주는 메커니즘
  * 디스코드 웹훅 메세지 전송:
    * 복잡한 Bot 토큰 설정 없이 웹훅 URL 하나만으로 메시지 전송 가능
    * JSON 키 이름 주의: 디스코드 API 수신 규격상 메시지 본문 데이터의 키 이름은 반드시 message 또는 content로 지정해 주어야 인식됨
## 4. 🧠 AI Agent 노드 활용 및 프롬프트 설정

### 4.1. Prompt 입력 모드 (Source for Prompt)

  * Take from previous node: 이전 노드의 chatInput 키 값을 자동으로 가져옴
  * Define below (추천): 프롬프트 창이 활성화되어, {{ $json.news_content }} 처럼 원하는 JSON 키를 직접 매핑하거나 고정 텍스트를 조합 가능
### 4.2. JSON 포맷 출력 문제 해결 (Output Parser vs Code Node)

## 🔧 전체 구조 — 왜 이 순서인가

```plain text
① Schedule Trigger  →  ② HTTP Request  →  ③ Set (Profile)
   매일 9시 시작신호      날씨 데이터 가져오기    내 정보 정의

   →  ④ AI Agent  →  ⑤ Set (message)  →  ⑥ Discord
      본문 생성        메시지 포장         전송
```

  흐름을 읽는 법: n8n에서 노드는 왼쪽 노드의 출력이 오른쪽 노드의 입력이 되는 컨베이어 벨트다. 각 노드는 "받아서 → 처리해서 → 넘긴다"만 한다.

  왜 이 순서여야 하나?

  * ①이 맨 앞: 트리거 노드는 워크플로우를 "시작시키는 방아쇠"라서 항상 첫 번째다. 시간(Schedule), 웹훅 수신, 수동 실행 등이 트리거가 될 수 있다.
  * ②③이 ④보다 앞: AI에게 재료(날씨 + 내 정보)를 먼저 모아줘야 한다. AI는 자기 앞에 놓인 데이터만 볼 수 있다.
  * ⑤가 ④와 ⑥ 사이: AI 출력의 **키 이름이 output*인데 디스코드 노드는 message를 원했다. 그래서 이름을 바꿔주는 "변환 어댑터" 역할.
> 💡 개념: ③⑤처럼 데이터를 만들거나 이름을 바꾸는 노드를 n8n에서는 Set / Edit Fields 노드라고 한다. 계산은 안 하고 "값 정리"만 하는 도구다.

## 1️⃣ Schedule Trigger — 시간 기반 자동 실행

### 설정값

  * Trigger Interval: Days
  * Days Between Triggers: 1
  * Trigger at Hour: 9am
  * Trigger at Minute: 0
### 개념: 크론(Cron)

  "매일 9시"처럼 반복 시각을 정해두고 프로그램을 자동 실행하는 것을 크론 스케줄링이라고 한다. n8n은 이걸 GUI로 예쁘게 감싸놨을 뿐, 내부적으로는 0 9 * * *(분 시 일 월 요일) 같은 크론 표현식으로 동작한다.

### ⚠️ 오늘 배운 함정 — Timezone

  워크플로우 Settings에서 Timezone을 **Asia/Seoul**로 지정해야 한다.

  왜? 서버는 기본적으로 UTC(협정 세계시)를 쓴다. 한국은 UTC+9다. 시간대를 안 맞추면 "9시"를 UTC 9시로 해석해서 한국 시간 오후 6시에 메시지가 온다.

> 💡 이건 n8n만의 문제가 아니라 모든 서버 자동화의 고전적 실수다. 시간이 나오는 자동화를 만들면 항상 "이 시간은 어느 시간대 기준이지?"를 먼저 확인하는 습관을 들이자.

## 2️⃣ HTTP Request — Open-Meteo 날씨 API

### 개념 정리: API란 무엇인가

  API는 **"내가 URL로 질문을 보내면, 서버가 데이터로 대답해주는 창구"**다. 사람이 보는 웹사이트가 아니라, 프로그램이 읽기 좋은 형태로 답이 온다.

  식당에 비유하면:

  * 웹사이트 = 손님이 앉아서 밥 먹는 홀 (사람용, 예쁘게 꾸며져 있음)
  * API = 주방 옆 배달 창구 (프로그램용, 꾸밈 없이 재료만 정확하게)
### URL 해부하기

```plain text
<https://api.open-meteo.com/v1/forecast?latitude=37.3805&longitude=128.6608>
└──────── 주소: 어디에 물어볼지 ────────┘ └──── 파라미터: 무엇을 물어볼지 ────┘
```

### 개념: GET 요청

  * GET = "데이터 좀 주세요" (읽기 전용, 서버 상태를 바꾸지 않음)
  * POST = "이 데이터를 받아주세요" (등록·저장·전송)
  날씨는 그냥 읽어오는 거니까 GET이다. 나중에 6번 디스코드 노드는 메시지를 "보내는" 거라 내부적으로 POST를 쓴다.

> 💡 API 키가 필요 없는 이유: Open-Meteo는 비상업적 사용에 대해 인증 없이 무료 개방하고 있다. 대부분의 API(OpenAI, 카카오, 기상청 등)는 API 키라는 신분증을 요구한다 — "누가 얼마나 썼는지" 세고 요금을 매기기 위해서다. Open-Meteo는 그 절차가 없어서 입문용으로 최고다.

### 노드 설정값

  * Method: GET
  * URL: https://api.open-meteo.com/v1/forecast
  * Authentication: None
  * Send Query Parameters: 켜기
### Query Parameters 6개

  ① latitude → 37.3805
위도. 정선군청(정선읍) 기준.

  ② longitude → 128.6608
경도. (고한·사북 쪽이면 37.2115 / 128.8253)

  ③ current → temperature_2m,relative_humidity_2m,apparent_temperature,weather_code,wind_speed_10m
지금 이 순간의 값. 순서대로 기온 / 습도 / 체감온도 / 날씨코드 / 풍속.

  ④ daily → temperature_2m_max,temperature_2m_min,precipitation_probability_max,weather_code
오늘 하루 요약. 최고기온 / 최저기온 / 강수확률 / 날씨코드.

  ⑤ timezone → Asia/Seoul
"오늘"의 기준을 한국 시간으로. 이걸 안 넣으면 UTC 기준 "오늘"이 와서 날짜가 어긋난다.

  ⑥ forecast_days → 1
오늘 하루만. 기본값은 7일치인데, 안 쓸 데이터를 받으면 응답이 무거워지고 AI에 넘길 때 토큰도 낭비된다.

> ⚠️ ③④ 값에 쉼표 뒤 공백을 절대 넣지 말 것. 공백이 들어가면 API가 항목 이름을 못 알아본다.
💡 Value 칸에는 값만 텍스트로 넣으면 된다. =나 &는 n8n이 알아서 붙여준다.

### 개념: JSON — 돌아오는 답의 형태

```json
{
  "current": {
    "temperature_2m": 21.3,
    "apparent_temperature": 22.1,
    "weather_code": 3,
    "wind_speed_10m": 5.4
  },
  "daily": {
    "time": ["2026-07-30"],
    "temperature_2m_max": [28.5],
    "temperature_2m_min": [18.2],
    "precipitation_probability_max": [40]
  }
}
```

  JSON은 데이터를 담는 표준 상자다. 두 가지 모양만 알면 된다:

  * { } 객체 = 이름표가 붙은 서랍장. current라는 서랍을 열면 그 안에 temperature_2m 칸이 있다.
  - [ ] [ ] 배열 = 번호로 세는 줄. 첫 번째가 [0], 두 번째가 [1]. 0부터 시작한다.
### ⚠️ 오늘 배운 함정 — daily는 배열이다

```plain text
current.temperature_2m        ← 숫자 하나 (그냥 접근)
daily.temperature_2m_max[0]   ← 배열이라 [0] 필수!
```

  왜 배열인가? daily는 원래 "날짜별 목록"이라서다. 7일치를 받으면 [28.5, 27.1, 30.2, ...]처럼 7개가 들어온다. 우리는 forecast_days=1로 하루만 받았지만 형태는 여전히 배열이라서 첫 번째 값을 [0]으로 꺼내야 한다.

  [0]을 빼먹으면 값이 undefined로 나오거나 [28.5] 같은 대괄호가 그대로 메시지에 찍힌다. 오늘 가장 실수하기 쉬운 지점.

### 개념: WMO 날씨 코드

  weather_code: 3처럼 숫자로 오는 이유는, 날씨 상태를 전 세계 공통 숫자 규격으로 표준화해뒀기 때문이다 (세계기상기구 WMO 표준). "흐림"을 영어로 쓸지 한국어로 쓸지 고민할 필요 없이 3 하나로 통일된다.

```plain text
0=맑음, 1=대체로 맑음, 2=구름 조금, 3=흐림, 45/48=안개,
51/53/55=이슬비, 61=약한 비, 63=비, 65=강한 비,
71/73/75=눈, 80/81/82=소나기, 95/96/99=천둥번개
```

### 왜 프로필을 별도 노드로 빼는가?

  프로필을 AI 프롬프트 안에 직접 써버려도 동작은 한다. 그런데 별도 노드로 빼면:

  1. 수정할 곳이 한 군데다. 성격 설명을 바꾸고 싶을 때 긴 프롬프트를 뒤질 필요 없이 Set 노드만 열면 된다.
  1. 재사용된다. 5번 Set 노드에서도 $('Profile').item.json.name으로 이름을 다시 꺼내 썼다.
  1. 나중에 확장이 쉽다. 여러 사람에게 각각 보내려면 이 노드만 여러 개로 늘리면 된다.
> 💡 이런 걸 **"설정값의 외부화"**라고 한다. 바뀔 수 있는 값을 로직과 분리해두는 습관은 규모가 커질 때 큰 차이를 만든다.

## 4️⃣ AI Agent — 본문 생성

### ⭐ 오늘 가장 중요하게 배운 것: $json vs $('노드이름')

  처음에 이 프롬프트를 $json.current.temperature_2m으로 쓰려다 막혔다. 이유:

```plain text
② HTTP Request  →  ③ Set (Profile)  →  ④ AI Agent
                                          ↑
                              $json은 여기서 ③번만 가리킨다!
```

  $json은 "바로 직전 노드"의 데이터만 가리킨다. ④ AI Agent 입장에서 직전 노드는 ③ Profile이니까, $json에는 프로필만 있고 날씨는 없다.

  해결책: 더 앞의 노드는 이름으로 직접 호출한다.

```plain text
$json.name                                      ← 직전 노드(Profile)
$('Weather').item.json.current.temperature_2m   ← 이름으로 ②번 지목
```

  이걸 위해 노드 이름을 알아보기 쉽게 바꿨다 (노드 제목 더블클릭):

  * HTTP Request → Weather
  * Edit Fields → Profile
> 💡 표현식({{ }})이란: 중괄호 2개 안의 내용은 "지금 이 자리에 계산된 값을 끼워넣어라"는 뜻이다. 워크플로우가 실행되는 순간 {{ $json.name }}이 김민석으로 치환된다. 편집할 때는 코드로 보이고, 실행할 때는 값이 되는 빈칸 채우기라고 생각하면 된다.

  💡 .item.이 끼어 있는 이유: n8n의 데이터는 항상 **여러 개(item 배열)**를 다룰 수 있게 설계돼 있다. .item은 "지금 처리 중인 그 하나"를 뜻한다.

### 🎓 프롬프트를 이렇게 쓴 이유 (프롬프트 엔지니어링 복습)

  이 프롬프트는 아무렇게나 쓴 게 아니라 5개 블록 구조를 따른다. 다른 AI 자동화를 만들 때도 그대로 재사용할 수 있는 틀이다.

  ① 역할 부여 (첫 문장)

> "당신은 다정한 AI 비서입니다"

  AI에게 캐릭터를 먼저 정해주면 말투와 태도가 일관되게 나온다. 이게 없으면 매번 톤이 흔들린다.

  ② 데이터 주입 ([사용자 프로필], [날씨 데이터])
AI는 내 정선 날씨를 알 방법이 없다. 필요한 사실은 전부 프롬프트에 넣어줘야 한다. 대괄호 제목으로 블록을 나눈 건 AI가 "여기까지가 재료구나"를 구분하기 쉽게 하려는 것.

  ③ 해석표 제공 ([WMO 날씨 코드 해석표])weather_code: 61만 주면 AI가 "61이 뭐지?" 하고 엉뚱하게 추측할 수 있다. 해석표를 같이 주면 정확히 "약한 비"로 읽는다.

> 💡 이게 환각(hallucination) 방지의 기본 원리다. AI가 모를 수 있는 코드·약어·내부 용어는 항상 뜻을 같이 넣어준다.

  ④ 규칙 명시 ([작성 규칙])
각 규칙에 목적이 있다:

  * 규칙 3 (900자) — 디스코드 2000자 제한 대비 + 읽기 부담 줄이기
  * 규칙 4 ("임의로 만들어내지 마세요") — 환각 방지. AI는 숫자를 그럴듯하게 지어내는 습성이 있다
  * 규칙 6 ("사족 붙이지 말고") — "알겠습니다! 작성해드릴게요~" 같은 군더더기가 디스코드에 그대로 찍히는 걸 방지
  * 규칙 7 (제목·날짜 쓰지 마) — 5번 Set 노드가 제목을 고정으로 붙이므로 중복 방지
  ⑤ 출력 형식 지정 ([포함할 3가지 항목])
"운세 써줘"라고만 하면 매번 길이와 구성이 달라진다. 항목 수, 순서, 문장 수, 형식을 못 박아두면 결과가 예측 가능해진다.

> 🎯 한 줄 요약: 좋은 프롬프트 = 역할 + 재료 + 해석 도움말 + 지켜야 할 규칙 + 원하는 출력 형태

### ⚠️ 오늘 헷갈렸던 부분 — 이건 AI 프롬프트가 아니다

  처음에 이 템플릿을 "AI Agent 프롬프트를 지우고 붙여넣으라는 건가?" 하고 오해했다. 아니다. 이건 AI Agent 다음에 오는 Set 노드의 Value 칸에 넣는 것이다.

  두 노드의 역할이 완전히 다르다:

### 개념: 왜 굳이 두 단계로 나누는가 (관심사의 분리)

  AI에게 "제목도 쓰고 날짜도 쓰고 맺음말도 써"라고 맡길 수도 있다. 그런데 나누는 게 좋은 이유:

  1. 일관성 — AI는 매번 조금씩 다르게 쓴다. 제목·날짜·구분선처럼 절대 변하지 않아야 하는 건 코드가 고정하는 게 확실하다.
  1. 정확성 — 날짜는 AI가 추측하면 틀릴 수 있다. $now로 뽑으면 100% 정확하다.
  1. 토큰 절약 — AI가 만들 분량이 줄어든다.
  1. 디버깅 — 형식이 깨졌을 때 "AI 문제냐 템플릿 문제냐"를 바로 구분할 수 있다.
> 🎯 일반 원칙: 변하는 것(AI 창작)과 변하지 않는 것(형식)을 분리하라. AI 자동화 전반에 통하는 설계 습관이다.

### 표현식 뜯어보기

```plain text
{{ $now.setZone('Asia/Seoul').toFormat('yyyy년 M월 d일') }}
   └─①─┘└────────②────────┘└──────────③──────────┘
```

  * ① $now — n8n 내장 변수. 실행 시점의 현재 시각
  * ② .setZone('Asia/Seoul') — 한국 시간대로 변환 (또 시간대!)
  * ③ .toFormat(...) — 원하는 글자 모양으로 바꾸기. yyyy=연도 4자리, M=월, d=일
> 💡 점(.)으로 계속 이어붙이는 걸 메서드 체이닝이라고 한다. "현재시각 → 한국시간으로 → 이 형식으로" 처럼 왼쪽에서 오른쪽으로 순서대로 처리된다.

  왜 여기선 $('Profile')을 썼나? ⑤번 Set의 직전 노드는 ④ AI Agent다. 그래서 $json은 AI 결과(output)만 가리킨다. 이름은 ③번에 있으니 또 이름으로 지목해야 한다. → ④에서 배운 원리가 여기서 반복된다.

### 개념: 웹훅(Webhook)이란

  * *"미리 등록해둔 주소로 데이터를 밀어넣으면, 그게 채널에 글로 올라가는 전용 배달구"**다.

  * 웹훅 = 내가 상대 서버에 "이거 받아라" 하고 밀어넣는 것 (6번에서 하는 것)
  디스코드 봇을 따로 만들지 않아도, 웹훅 URL 하나만 있으면 메시지를 보낼 수 있어서 훨씬 간단하다.

> 🔒 보안: 웹훅 URL은 비밀번호처럼 취급해야 한다. 그 URL을 아는 사람은 누구나 내 채널에 글을 쓸 수 있다. 이 노트를 노션에 올릴 때 실제 URL은 절대 붙여넣지 말자.

## 🐛 트러블슈팅 — 막히면 여기부터

  1. $('Weather')에서 오류가 난다
노드 이름 오타다. n8n 표현식 입력칸 왼쪽의 Schema 탭에서 원하는 값을 드래그하면 표현식이 자동으로 들어간다. 손으로 타이핑하지 말고 드래그하는 게 안전하다.

  2. 날씨 값이 undefined로 나온다daily에 [0]을 빼먹었을 확률이 가장 높다. current는 [0]이 필요 없고 daily는 필요하다.

  3. 디스코드에 아무것도 안 온다
AI Agent 출력 키가 정말 output인지 확인. AI Agent를 실행한 뒤 OUTPUT 패널의 JSON 탭에서 실제 키 이름을 눈으로 보고 맞추면 된다.

  4. 메시지가 오는데 새벽/저녁에 온다
Timezone. 워크플로우 Settings에서 Asia/Seoul 확인.

### 🎓 오늘 배운 개발 습관: 한 노드씩 붙이고 테스트하기

  6개를 다 만들고 실행 버튼을 누르면, 오류가 나도 어디서 터졌는지 알 수 없다.

  올바른 순서:

  1. ②번까지 만들고 Test step → JSON이 오는지 눈으로 확인
  1. ③번 붙이고 Test step → 프로필이 잘 들어갔는지 확인
  1. ④번 붙이고 Test step → 날씨 숫자가 프롬프트에 제대로 치환됐는지 확인
  1. ...이렇게 하나씩
> 이걸 점진적 개발 / 증분 테스트라고 한다. 문제가 생기면 방금 추가한 노드가 원인이라 범위가 좁아진다. 코딩할 때도 똑같이 통하는 원칙이다.
