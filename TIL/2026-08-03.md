## Claude Code와 n8n 기반 자동화 연동

> 📍 정리 #1
> 
> 🏷️ 키워드: n8n, claude-code, mcp, skill, docker

### Claude Code와 n8n 연동 개념

Claude Code와 같은 AI CLI 도구에 MCP(Model Context Protocol) 및 Skill을 연동하면 n8n 워크플로우와 노드를 자동으로 구성하고 관리할 수 있다.

- **MCP / Integration:** Claude Code가 n8n API와 통신하여 노드를 직접 생성, 수정, 실행할 수 있는 통로를 제공한다.
    
- **Skill:** Claude Code에 n8n 고유의 JSON 구조 및 노드 작성 규격을 학습시켜 올바른 워크플로우를 생성하도록 지시하는 역할을 한다.
    

### 대표 참고 깃허브 레포지토리 및 문서

- **n8n-skills:** [github.com/czlonkowski/n8n-skills](https://github.com/czlonkowski/n8n-skills)
    
    - Claude Code에 주입하여 n8n 노드 작성법과 JSON 구조를 학습시키는 스킬 모음.
        
- **n8n-mcp-server:** [github.com/kingler/n8n-mcp-server](https://github.com/kingler/n8n-mcp-server)
    
    - Claude Code와 n8n API를 연결해 실제 n8n 서버를 조작하게 해주는 MCP 서버.
        
- **n8n API 인증 문서:** [docs.n8n.io/connect/n8n-api/authentication](https://docs.n8n.io/connect/n8n-api/authentication)
    
    - n8n API Key(Bearer Token) 발급 및 연동 방법 안내.
        

### n8n 라이선스 및 Self-hosted(Docker) 활용

n8n 클라우드 서비스의 API 활용은 유료 요금제에서 제한될 수 있으나, Docker를 이용한 Self-hosted(자체 호스팅) 환경을 구축하면 API를 포함한 대부분의 기능을 무료로 활용할 수 있다.

- **Fair-code 라이선스:** n8n은 Fair-code 라이선스를 적용받는다. 이를 재판매하는 상업적 서비스가 아닌 이상 개인 프로젝트나 기업 내부용 자체 호스팅은 무료로 사용 가능하다.
    
- **실무 연동 방식:** 로컬이나 자체 서버의 Docker로 n8n을 띄운 후, `Settings ➔ n8n API` 메뉴에서 API Key를 발급받아 Claude Code MCP 설정에 입력하여 연동한다.
    

### ⚠️ 헷갈리기 쉬운 점

- n8n 클라우드의 무료 버전은 API 접근에 제한이 있으므로, Claude Code와 MCP로 API를 연동하려면 Docker를 활용한 Self-hosted 방식으로 설치해야 비용 부담 없이 개발/테스트가 가능하다.




## 미니프로젝트 우수 기획 사례 및 실무 활용 분석

> 📍 정리 #2
> 
> 🏷️ 키워드: public-data, llm, agent, api, geocoding

### 공공데이터 활용 맛집 지도 프로젝트

- **세금 내고 먹는 맛집(세먹맛):** [restaurant.coroke.net](https://restaurant.coroke.net/)
    
- **개념 및 구조:** 국회의원/공직자의 정치자금 및 업무추진비(법인카드 사용 내역) 공공데이터를 수집·가공하여 지도에 시각화한 서비스.
    
- **기술 구현 포인트:**
    
    - **수집 및 전처리:** PDF/CSV 형태의 공직자 지출 내역에서 상호명, 주소, 결제 금액, 사용 횟수 추출.
        
    - **지오코딩(Geocoding):** 장소 이름과 주소를 Kakao Maps나 Naver Maps API를 통해 위도·경도 좌표로 변환.
        
    - **시각화:** 좌표 기반 지도 위에 마커를 표시하고, 결제 건수/금액에 따라 마커 크기나 색상을 다르게 표현.
        

### 기획이 탄탄한 미니프로젝트 주제 5종

#### 1. AI 취업전략 에이전트 (Skill Gap 계산)

- **개념:** 목표 직무의 채용공고 약 30개를 집단 분석하여 요구 역량을 추출한 뒤, 사용자의 스펙과 비교해 부족한 기술(Skill Gap)을 도출하고 학습/프로젝트 방향을 제안.
    
- **구현 방식:** LLM을 이용해 채용공고 텍스트에서 기술 키워드(Python, AWS, CI/CD 등)를 추출하여 DB화하고, 사용자 이력서 데이터와 차집합 연산을 수행.
    

#### 2. CS 문의 AI 답변 초안 생성 시스템 (HITL 패턴)

- **개념:** 고객 문의가 들어오면 AI가 답변 초안을 작성하고, 담당자(사람)가 검토 및 승인 후 전송하는 인간 개입형(Human-In-The-Loop) 자동화 시스템.
    
- **구현 방식:** 기업 CS 채널(Slack, Zendesk 등)과 연동하여 `[문의 접수 ➔ LLM/RAG 기반 답변 초안 생성 ➔ 담당자 승인 ➔ 최종 발송]` 워크플로우 구성.
    

#### 3. 에빙하우스 망각곡선 기반 TIL 다시보기 봇

- **개념:** 사용자가 작성한 TIL(Today I Learned)을 바탕으로 망각곡선 주기(1일, 3일, 7일 등)에 맞춰 능동적 회상(Active Recall) 퀴즈를 전송하는 학습 도우미.
    
- **구현 방식:** 스케줄러(Cron)가 주기별로 작성된 TIL 데이터를 LLM에 전달하여 빈칸/퀴즈를 생성한 뒤 Slack, Discord, 앱 알림 등으로 복습 질문 발송.
    

#### 4. 시니어 건강관리 복약 알림 봇 (상태 머신 패턴)

- **개념:** 아침 건강수치 기록, 복약 시간 알림, 미응답 시 재알림 및 예외 처리를 수행하는 상호작용형 헬스케어 비서.
    
- **구현 방식:** 스케줄러와 비동기 메시지 큐, 상태 관리 DB를 조합하여 `[알림 ➔ 미응답 ➔ 재알림 ➔ 최종 미응답 시 보호자 연락]` 흐름 제어.
    

#### 5. 국회 통과 법안 전용 AI 정책 알림 서비스

- **개념:** 선언적 법안이 아닌 국회 본회의를 실제 통과(원안가결/수정가결)한 법안만 필터링하여 실무자 및 대중에게 전달하는 알림 서비스.
    
- **구현 방식:** 대한민국 국회 의안정보시스템 Open API를 연동하여 가결된 법안만 파싱하고, LLM을 통해 핵심 내용을 쉬운 체크리스트로 요약하여 알림 발송.
    

### 흥미 요소 및 실용성이 높은 이색 아이디어

#### 1. 업비트 API + PokéAPI 게이미피케이션 서비스

- **개념:** 가상자산 시세 변동률에 따라 포켓몬 캐릭터의 대사나 진화 상태(예: 피카츄 ➔ 라이츄)가 다이나믹하게 바뀌는 유저 친화적 시세 알림.
    
- **구현 방식:** Upbit API로 시세를 주기적으로 조회하고, PokéAPI 및 LLM 템플릿을 조합해 변동폭에 맞춘 포켓몬 컨셉 문장 및 이미지 반환.
    

#### 2. 출근길 종합 브리핑 AI 봇

- **개념:** 바쁜 출근길 특정 시점에 일정, 날씨, 실시간 버스 도착 정보 등을 하나로 엮어 개인화된 출근 브리핑을 제공.
    
- **구현 방식:** Google Calendar API(일정), 기상청 API(날씨), 공공데이터포털 API(실시간 교통)를 서버/n8n에서 오케스트레이션한 후 LLM으로 브리핑 문장을 구성하여 전송.
    

#### 3. 사용자 패턴 분석 기반 선제적 라이프 비서 (Proactive Advisor)

- **개념:** 사용자의 결제 내역이나 이용 주기를 분석하여 필요한 시점(예: 미용실 방문 4주 차, 영양제 재구매 등)에 먼저 알림과 제안을 건네는 어드바이저.
    
- **구현 방식:** 결제/행동 데이터 카테고리별 평균 주기를 산출하고, `현재 날짜 - 마지막 이용 날짜 ≥ 평균 주기` 조건을 만족할 때 AI가 맥락에 맞는 알림 생성.
    

### ⚠️ 헷갈리기 쉬운 점

- CS 답변 서비스 등 AI를 실무 서비스에 적용할 때는 AI에게 100% 자율권을 주기보다, **HITL(Human-In-The-Loop)** 방식을 적용해 AI는 초안 생성 및 추천에 집중하고 사람(담당자)이 검토 후 최종 승인하도록 설계해야 할루시네이션이나 전달 오류로 인한 사고를 방지할 수 있다.




## 좋은 기획서의 4가지 공통점 및 아이디어 구상 팁

> 📍 정리 #3
> 
> 🏷️ 키워드: loop-engineering, hitl, project-planning, scope-management

### 좋은 기획서의 4가지 핵심 원칙

1. **성공을 숫자로 정의한다**
    
    - **개념:** 성공 여부를 측정 가능한 정량적 지표(Metric)로 명확히 설정합니다.
        
    - **AI 에이전트 관점 (Loop Engineering):** AI에게 목표 숫자를 부여하여, 해당 목표(예: 테스트 통과율 100%, 응답 속도 200ms 이하)를 달성할 때까지 자동으로 수정-실행-검증 과정을 반복하도록 루프를 구성합니다.
        
2. **안 만들 것을 정한다 (Scope 축소)**
    
    - 불필요한 기능 범위를 사전에 잘라내어 프로젝트가 방향성을 잃거나 무거워지는 것을 방지합니다.
        
3. **먼저 조사하고 판단한다**
    
    - 추측에 의존하지 않고 객관적인 데이터와 사전 조사를 바탕으로 기획 방향을 결정합니다.
        
4. **리스크 대응력이 있다**
    
    - 예외 상황이나 실패 시나리오를 미리 예측하고 이에 대한 대비책(Exception Handling)을 마련합니다.
        

### 프로젝트 주제 선정을 위한 3가지 접근 전략

1. **이번 주에 막혔던 문제에서 출발하기**
    
    - 자신이 직접 경험한 페인 포인트(Pain Point)를 해결하는 주제일수록 유저 니즈를 가장 잘 이해한 채로 개발할 수 있습니다.
        
2. **한 문장 정의 (Value Proposition)**
    
    - _"이 봇은 [누구]의 [문제]를 해결하기 위해 [무엇]을 해준다"_ 형식으로 명확히 정리하여 기획의 흔들림을 방지합니다.
        
3. **기존 검증된 아이디어 변형하기 (Pivot)**
    
    - 타인의 아이디어나 기존 서비스 구조를 바탕으로 타깃 사용자, 데이터 원천(Data Source), 연동 채널 등을 바꾸어 나만의 프로젝트로 발전시킵니다.



## AI 개발과 CS(컴퓨터공학) 지식의 중요성

> 📍 정리 #4
> 
> 🏷️ 키워드: cs-fundamentals, debugging, software-engineering, non-majors

### AI 시대, 비전공자가 개발 중 막히는 진짜 이유

1. **개발 문턱의 변화**
    
    - **과거:** 코드 작성(타이핑) 자체가 거대한 진입장벽.
        
    - **현재:** AI 및 노코드/저코드 툴 덕분에 코드 작성 난이도는 대폭 감소.
        
    - **문제점:** 서비스가 동작하지 않거나 에러가 터졌을 때 해결하는 **디버깅·아키텍처의 문턱**은 여전히 CS 지식에 의존함. (90% 이상이 여기서 막힘)
        
2. **CS 지식 부족으로 자주 막히는 4대 지점**
    
    - **네트워크 / API:** CORS 에러, HTTP Status 401/403, SSL/TLS, IP 허용 목록 설정 문제.
        
    - **비동기 / 프로세스:** Async-Await 흐름 이해 부족, Race Condition, 타임아웃 에러.
        
    - **데이터베이스 / 메모리:** 트랜잭션 미이해로 인한 데이터 유실, 인덱스 미적용으로 인한 병목, 메모리 누수.
        
    - **인증 / 보안:** 세션(Session) vs 토큰(JWT) 구조 차이, OAuth 2.0 동작 메커니즘, 환경변수(`.env`) 전달 오류.
        

### 전공생과 비전공자의 차이 및 CS의 본질

1. **컴퓨터공학과 4년의 실제 구조**
    
    - **학교 수업 (CS 기초):** 자료구조, 알고리즘, 운영체제(OS), 컴퓨터 구조, 네트워크, DB 원리 등 **컴퓨터가 동작하는 근본적인 원리**만 4년 내내 학습.
        
    - **실무 기술 (프레임워크/언어):** Spring Boot, React, Python, Java 등은 방학이나 개인 시간에 독학으로 습득.
        
2. **왜 CS 지식이 지속가능한 무기가 되는가?**
    
    - **변하지 않는 근본:** 프레임워크나 유행하는 기술은 몇 년 주기로 바뀌지만, 메모리 관리·TCP/IP·DB 인덱싱 등의 기본 원리는 30~40년 전이나 지금이나 동일함.
        
    - **디버깅의 심도:** 단순히 "기능을 구현하는 것"을 넘어 "왜 서버가 터지는가?", "왜 조회가 느린가?"를 추적하고 해결하는 힘은 CS 지식에서 나옴.
        

### 비전공자/입문자를 위한 공략 방향

- **학술적 접근 피하기:** 4년치 CS를 밑바닥부터 다 공부할 필요는 없음.
    
- **프로젝트 중심 매꾸기:** AI로 프로젝트를 만들다가 막히는 지점(네트워크, 비동기, DB 등)이 생길 때마다 **해당 테마를 역으로 파고들어 채워 넣는 방식**이 가장 효율적.
    
- **개발자의 역할 변화:** Code Writer에서 Diagnostic Engineer(시스템 진단 전문가)로 변모하는 과정. AI에게 올바른 맥락을 전달하려면 최상위 CS 개념 이해가 필수적임.

### 1. 소프트웨어 분야별 기술 스택 & 특징

||**Cross-Platform**|**Flutter, React Native**|단일 코드베이스로 iOS/Android 동시 개발|
|**데스크톱 (Desktop)**|**Native / App**|**C++, C# (.NET), Swift**|PC 하드웨어(CPU/GPU/RAM) 자원 최대 활용|
||**Web-based**|**Electron, Tauri**|웹 기술로 PC 앱 제작 (VS Code, Discord 등)|

> **💡 하이브리드/멀티플랫폼의 현주소:**
> 
> 하나의 코드로 Web, Mobile, PC를 모두 개발하려는 기술(Flutter 등)이 지속 발전 중이나, 플랫폼별 UX 차이·하드웨어 제어 한계·성능 패널티로 인해 완성도가 중요한 현업 서비스는 여전히 영역별로 나누어 개발하는 추세입니다.

### 2. 하드웨어 구조와 '프로그램 실행'의 원리

- **핵심 부품 역할:**
    
    - **CPU (중앙처리장치):** 실제 연산과 실행을 담당하는 **일꾼**.
        
    - **RAM (주기억장치):** 현재 실행 중인 데이터가 올라가는 **작업대** (전원이 꺼지면 지워지는 휘발성).
        
    - **SSD / HDD (보조기억장치):** 프로그램과 데이터를 영구 보관하는 **창고** (비휘발성).
        
    - **메인보드:** 모든 부품을 물리적·전기적으로 연결하는 **기판**.
        

```
[SSD/HDD 창고]              [RAM 작업대]               [CPU 일꾼]
 (프로그램 파일 저장)  ──로딩(Loading)──>  (메모리에 데이터 적재)  ──명령어 전달──>  (연산 및 실행)
```

- **실행(Execution)의 본질:**
    
    보조기억장치(SSD)에 정적으로 저장되어 있던 프로그램 데이터를 속도가 훨씬 빠른 주기억장치(RAM)로 복사해 올린 뒤(로딩), CPU가 명령을 연산 처리하는 과정입니다.
    

### 3. 프로세스, 스레드, 그리고 동시성 vs 병렬성

1. **기본 개념:**
    
    - **프로세스 (Process):** RAM에 올라가 실행 상태가 된 프로그램.
        
    - **스레드 (Thread):** 프로세스 내에서 실제 일을 수행하는 작업의 단위.
        
2. **동시성 (Concurrency) vs 병렬성 (Parallelism):**
    

|**구분**|**동시성 (멀티스레딩)**|**병렬성 (병렬처리)**|
|---|---|---|
|**코어(일꾼) 수**|**1개** (또는 제한적 코어)|**여러 개** (Multi-Core / GPU)|
|**작업 방식**|여러 작업을 매우 빠르게 번갈아 실행 (Context Switching)|여러 작업을 물리적으로 완전히 동시에 실행|
|**주 목적**|대기 시간(I/O Idle) 최소화 및 응답성 향상|연산 처리 속도 극대화|
|**적용 타깃**|**I/O 바운드:** 네트워크, DB 조회, 파일 입출력|**CPU 바운드:** AI 모델 연산, 영상/이미지 처리|

> 📍 정리 #6
> 
> 🏷️ 키워드: data-structures, algorithms, big-o, performance-optimization

### 1. 자료구조와 알고리즘의 역할 및 관계

- **개념 비유:**
    
    - **자료구조 (Data Structure):** 데이터를 담는 **공구함** (RAM 메모리에 어떤 규칙과 모양으로 저장할 것인가?)
        
    - **알고리즘 (Algorithm):** 공구를 쓰는 **작업 절차** (저장된 데이터를 어떤 순서와 로직으로 빠르고 정확하게 처리할 것인가?)
        
- **공부 순서 (자료구조 ➔ 알고리즘):**
    
    데이터가 어떻게 배치되어 있는지(자료구조)를 알아야 최적의 해결 방법(알고리즘)을 설계할 수 있습니다.
    
- **성능 평가 (Big-O Notation):**
    
    데이터량이 증가할 때 내 코드가 얼마만큼의 시간(CPU)과 메모리(RAM)를 소모하는지 측정하는 지표입니다.
    

### 2. 실무 대표 자료구조 4종 핵심 비교

|**자료구조**|**구조 및 동작 원리**|**주요 장단점**|**실무 활용 예시**|
|---|---|---|---|
|**배열 (Array)**|연속된 메모리 공간에 데이터 배치|• **장점:** 인덱스를 통한 조회 속도가 매우 빠름 ($O(1)$)<br><br>  <br><br>• **단점:** 크기가 고정되며 중간 삽입/삭제가 느림|고정 목록, 대규모 순차 연산|
|**연결 리스트 (LinkedList)**|데이터(Node)끼리 주소(Pointer)로 연결|• **장점:** 데이터 삽입/삭제가 매우 빠름 ($O(1)$)<br><br>  <br><br>• **단점:** 특정 요소를 찾으려면 순회해야 해서 조회가 느림|가변 목록, 대기열 관리, 실행 취소 체인|
|**스택 (Stack)**|**LIFO** (후입선출 / 나중에 들어간 데이터가 먼저 나옴)|• **장점:** 가장 최근 작업 및 역순 제어가 명확함|브라우저 뒤로 가기, `Ctrl+Z` (Undo), 함수 Call Stack|
|**큐 (Queue)**|**FIFO** (선입선출 / 먼저 들어간 데이터가 먼저 나옴)|• **장점:** 순서대로 처리하는 대기열 구현에 최적화|작업 대기열(프린터/서버 요청), 메시지 큐 (Kafka 등)|



## 소프트웨어 공학, 프레임워크 & 자바·AI 생태계 정리

> 📍 정리 #7
> 
> 🏷️ 키워드: software-engineering, waterfall-vs-agile, framework, java-spring, langchain-langgraph

### 1. 소프트웨어 공학 & 개발 프로세스 (Waterfall vs Agile)

다수의 인원(FE, BE 등)이 협업할 때 시스템의 안정성과 생산성을 확보하기 위한 체계입니다.

- **워터폴 (Waterfall / 폭포수 모델):**
    
    - **방식:** 기획 $\rightarrow$ 디자인 $\rightarrow$ 개발 $\rightarrow$ QA(테스트) $\rightarrow$ 배포 순으로 **단순 순차 진행**.
        
    - **한계:** QA(검증) 단계가 극후반에 배치되어 있어, 대규모 프로젝트에서 버그나 기획 변경이 생기면 수정 비용이 폭발적으로 증가하는 리스크(Big Bang Risk)가 발생함.
        
- **애자일 (Agile):**
    
    - **방식:** 1~2주 단위(스프린트)로 **기획 $\rightarrow$ 개발 $\rightarrow$ QA 과정을 빠르게 순환**하는 방식.
        
    - **장점:** 최소 단위의 기능(MVP)을 계속 검증하며 진행하므로 요구사항 변경과 에러에 신속하게 대응 가능.
        

### 2. 프레임워크 (Framework)의 본질

- **개념:** 소켓 연결, HTTP 통신, API 라우팅, DB 접속 등 **개발자가 공통으로 다루는 밑바닥 로직(Low-level)을 미리 완성해둔 뼈대 및 도구 모음**.
    
- **존재 이유:**
    
    - 밑바닥 코드를 매번 다시 짜는 비효율을 줄이고, **핵심 비즈니스 로직에만 집중**할 수 있게 함.
        
    - 프레임워크가 정한 규칙에 따라 코딩하므로 **여러 명(FE/BE)이 협업할 때 구조가 표준화**됨.
        
- **라이브러리 vs 프레임워크:**
    
    - **라이브러리:** 필요할 때 가져다 쓰는 **공구(망치, 드라이버)**.
        
    - **프레임워크:** 규칙에 맞게 부품을 끼워 넣어야 하는 **밀키트 / 공장 라인**.
        

### 3. 한국 IT 시장의 '자바(Java) 공화국' 현상

국내 대기업, 금융권, 공공기관의 80% 이상이 **Java + Spring Framework**를 주축으로 채택하는 이유입니다.

- **전자정부 표준프레임워크 (eGovFrame):** 국가 차원의 표준으로 Java Spring이 채택되며 시장에 대규모 확산됨.
    
- **시스템 안정성 (Static Typing):** 엄격한 데이터 타입 검사로 컴파일 시점에 에러를 잡아내어 **대규모 트랜잭션/금융 시스템의 안정성을 보장**함.
    
- **풍부한 인력 시장:** 개발자 구인 및 유지보수(퇴사/입사 시 코드 이해)가 용이함.
    
- **생태계 구분:**
    
    - **Java (Spring):** 대기업, 금융, 공공, 대규모 커머스 (안정성·대용량 중심)
        
    - **Python (Django/FastAPI), Node.js:** 스타트업, AI/데이터 서비스, 빠른 검증이 필요한 팀 (생산성·개발속도 중심)
        

### 4. AI 시대의 신규 프레임워크: LangChain & LangGraph

웹/서버 프레임워크가 DB와 네트워크 연결을 쉽게 해주듯, **LLM(대형 언어 모델) 애플리케이션 개발을 쉽게 조립하도록 도와주는 AI 프레임워크**입니다.

- **랭체인 (LangChain):**
    
    - LLM API 연동, 대화 기억, 문서 검색(RAG) 등을 순차적인 일직선 흐름(Chain)으로 빠르게 연결하는 프레임워크.
        
- **랭그래프 (LangGraph):**
    
    - 상황에 따라 판단하고, 실패 시 이전 단계로 돌아가는 순환형 구조(Graph/Loop)를 지원하는 프레임워크.
        
    - 자율적으로 행동을 수정하며 과업을 수행하는 **고도화된 AI 에이전트(AI Agent)** 개발에 필수적.

## 네트워크 기초 및 FE/BE 분리형 웹 아키텍처 정리

> 📍 정리 #9
> 
> 🏷️ 키워드: client-server, http-methods, status-codes, fe-be-separation, api-architecture

### 1. 네트워크의 기본: 클라이언트-서버(Client-Server) 모델

모든 웹/앱 서비스는 요청(Request)과 응답(Response)의 주고받음으로 이루어집니다.

- **클라이언트 (Client):** 스마트폰 앱, 컴퓨터 웹 브라우저 등 **서비스를 요청하는 사용자 단말** (FE 영역).
    
- **서버 (Server):** 24시간 켜져 있으면서 요청을 받고 데이터베이스(DB) 처리 후 **결과를 응답해 주는 고성능 컴퓨터/프로그램** (BE 영역).
    

### 2. HTTP 요청 방식 (Method)과 응답 코드 (Status Code)

#### ① HTTP 요청 대표 메서드 4가지 (CRUD)

- **GET:** 데이터 **조회** (예: 프로필 조회, 게시글 읽기)
    
- **POST:** 데이터 **생성/등록** (예: 회원가입, 게시글 작성)
    
- **PUT / PATCH:** 데이터 **수정** (예: 비밀번호 변경)
    
- **DELETE:** 데이터 **삭제** (예: 회원 탈퇴)
    

#### ② HTTP 응답 상태 코드 3대장

- **`200번대` (성공):** 요청이 정상적으로 완료됨 (`200 OK`, `201 Created`).
    
- **`400번대` (클라이언트 잘못):** 사용자 입력이나 요청 주소가 잘못됨 (`400 Bad Request`, `401 Unauthorized`, `404 Not Found`).
    
- **`500번대` (서버 잘못):** 백엔드 코드 버그나 DB 오류 등으로 서버 내부 장애가 터짐 (`500 Internal Server Error`).
    

### 3. 현대적 웹 구조: FE 서버와 BE 서버의 분리

현대 웹 서비스는 하나의 거대한 서버가 아닌, **프론트엔드 서버와 백엔드 서버를 완전히 독립시켜 연결하는 방식**을 채택합니다.

```
[사용자 브라우저 (클라이언트)]
    │
    ├── (1) 화면/UI 주세요! ➔ [ 프론트엔드(FE) 서버 ] ➔ 동적 웹 페이지(HTML/JS) 전달
    │
    └── (2) 데이터 주세요! ➔ [ 백엔드(BE) 서버 ] ➔ API 결과 데이터(JSON) 전달
```

- **프론트엔드(FE) 서버:** 클라이언트 요청을 받아 브라우저에 동적 화면(UI)을 구성해 내려주는 서버.
    
- **백엔드(BE) 서버:** 화면 요소는 제외하고, DB 연동 및 비즈니스 로직을 처리해 **API 형태의 순수 데이터만 제공**하는 서버.
    
- **분리 구조의 장점:**
    
    1. **독립적 개발/배포:** FE와 BE 개발자가 서로의 코드에 영향을 주지 않고 독자적으로 작업 및 업데이트 가능.
        
    2. **API 재사용성:** 하나의 백엔드(BE) 서버로 웹, iOS, 안드로이드 앱 등에 동일한 데이터를 공통 제공.
        
    3. **효율적 자원 관리:** 화면 접속자 폭주 시 FE 서버만, 데이터 처리 폭주 시 BE 서버만 각각 확장(Scaling) 가능.
