## 주제 1: GitHub 업로드와 EC2 배포는 다르다

교안은 백엔드 저장소 준비 → Compose 작성 → EC2에서 코드 가져오기 → 환경변수 설정 → 빌드·실행 → 상태 확인 순서로 진행한다. 앞선 기록에서는 private 저장소에 백엔드 파일 12개를 push했다. 이번에는 EC2에 코드를 가져와 실행했다.

> ➕ **더 알아두기 — 코드 전달 경로**
> 로컬 작업 폴더에서 코드를 수정한 다음 GitHub에 push한다. EC2는 GitHub에서 처음 받을 때 clone하고, 이후 바뀐 코드를 받을 때 pull한다. push가 성공했다고 EC2의 파일이나 실행 중인 프로그램이 자동으로 바뀌는 것은 아니다.
>
> | 동작 | 의미 |
> |---|---|
> | git push | 로컬 커밋을 원격 저장소로 전달 |
> | git clone | 원격 저장소의 코드와 Git 기록을 새 폴더로 가져옴 |
> | git pull | 기존 저장소에서 원격 변경을 받아 현재 브랜치에 반영 |
> | ssh -T git@github.com | GitHub에 SSH 인증이 되는지 확인; 코드 다운로드는 아님 |
>
> GitHub는 코드와 이력을 보관하는 곳이고, EC2는 프로그램을 실제로 실행하는 컴퓨터다. 이 실습에서는 파일을 받은 뒤 Docker 이미지를 만들고 컨테이너를 실행해야 앱에 반영된다.

## 주제 2: 로컬 SSH 실패와 HTTPS 인증의 차이

강사 안내에 따라 사용자 PC의 Git Bash에서 GitHub SSH 인증을 확인했다.

```bash
ssh -T git@github.com
```

처음에는 GitHub 서버 지문을 보여주며 서버를 신뢰할지 물었다. 화면의 Ed25519 지문은 GitHub 공식 문서와 일치하는 것을 확인했다. 사용자는 yes를 입력했지만 이후 인증은 실패했다.

```text
Permission denied (publickey).
```

> ➕ **더 알아두기 — 두 방향의 신원 확인**
> 서버 지문을 확인하는 것은 접속 상대가 GitHub인지 확인하는 과정이다. 공개 키 인증은 GitHub가 접속한 사용자를 인증하는 과정이다. GitHub 서버를 신뢰 목록에 추가했다고 사용자 인증까지 끝난 것은 아니다.
>
> publickey 오류만으로 “키가 아예 없다”고 단정하지 않는다. 사용할 키가 없거나, SSH가 다른 키를 선택했거나, 공개 키가 GitHub에 등록되지 않았거나, 접근 대상 권한이 맞지 않는 등 원인을 구분해야 한다.

로컬에서 다음 명령으로 ~/.ssh 안의 파일 이름을 확인했다. 개인 키 내용은 열거나 공유하지 않았다.

```bash
ls -al ~/.ssh
```

기존 Oracle 접속에 쓰는 것으로 보이는 키 한 쌍과 config·known_hosts 등이 있었다. 파일 이름만으로 GitHub 등록 여부를 확정하지 않았다. 별도의 로컬 GitHub 키를 만드는 방법도 안내했지만 사용자가 나중에 하기로 했고 로컬 SSH 설정은 중단했다. 해당 키 생성 완료를 기록하지 않는다.

> ➕ **더 알아두기 — push 성공과 SSH 실패가 함께 가능한 이유**
> 앞서 백엔드 저장소에 push할 때는 GitHub CLI의 HTTPS 인증을 사용했다. 로컬 SSH는 별도의 인증 경로이므로 아직 설정되지 않아도 HTTPS push는 성공할 수 있다. 로컬 PC에서 SSH 인증에 성공하더라도 EC2의 키 파일이나 인증 설정이 자동으로 생기는 것은 아니다.

## 주제 3: EC2 전용 Deploy key로 private 저장소 가져오기

### 키 생성과 암호 입력

로컬 SSH 설정 대신 EC2에서 private 저장소를 읽을 전용 키를 준비했다. 실행 위치는 AWS 브라우저로 접속한 EC2 Ubuntu 터미널이다.

```bash
cd /home/ubuntu
ssh-keygen -t ed25519 -C "ec2-backend-deploy" -f ~/.ssh/github_backend
```

> ➕ **더 알아두기 — 키 암호는 DB 암호가 아니다**
> Enter passphrase는 새 개인 키 파일을 보호할 암호를 정하라는 질문이다. AWS 로그인·GitHub 로그인·RDS 마스터 암호와 별개다. 입력해도 화면에 표시되지 않는다. 같은 암호를 다시 입력하면 키 생성이 끝난다. Overwrite가 나오면 기존 키를 덮어쓰기 전에 중단하고 확인한다.
>
> github_backend는 개인 키이며 github_backend.pub는 공개 키다. 개인 키는 서버 밖으로 공유하지 않는다. GitHub에는 공개 키만 등록한다.

공개 키를 표시하는 명령을 실행하고, 나온 한 줄 전체를 GitHub 저장소 Settings → Deploy keys → Add deploy key에 등록했다.

```bash
cat ~/.ssh/github_backend.pub
```

Title은 EC2 backend read-only로 설정하고 Allow write access는 체크하지 않도록 안내했다. 사용자는 다음 단계로 진행했다. 이후 clone과 SSH 인증 성공은 이 읽기 접근이 동작함을 확인한 결과다.

> ➕ **더 알아두기 — Deploy key**
> Deploy key는 특정 저장소 접근에 사용하는 SSH 키다. 이번 목적은 EC2가 코드를 읽어오는 것이므로 쓰기 권한을 주지 않았다. EC2 로그인용 키와 GitHub 저장소 접속용 키 역시 서로 다른 용도다.

### clone과 코드 목록 확인

```bash
cd /home/ubuntu
GIT_SSH_COMMAND="ssh -i /home/ubuntu/.ssh/github_backend -o IdentitiesOnly=yes" git clone git@github.com:noviz-domino/aws-agent-backend.git
cd /home/ubuntu/aws-agent-backend
ls -a
```

실제 화면에서 다운로드 완료와 compose.yaml·Dockerfile·main.py·.env.example 등 파일 목록을 확인했다. 여기서 사용한 저장소는 private 실습 저장소다. 공개 기록에는 서버 주소·키 내용·계정 비밀을 넣지 않는다.

> ➕ **더 알아두기 — 긴 명령의 앞부분**
> GIT_SSH_COMMAND는 이 Git 명령에서 사용할 SSH 명령을 지정한다. -i는 개인 키 파일 위치, IdentitiesOnly=yes는 지정한 인증 키를 사용하도록 제한하는 옵션이다. Git이 기본 이름이 아닌 github_backend 키를 찾아 쓰도록 명시했다. 이 값은 해당 명령에 적용되며 다음 셸 명령까지 영구 설정되는 것은 아니다.

### pull 실패를 분리해서 확인

뒤에서 수정 코드를 pull하는 과정에 키 암호를 두 번 묻고 연결이 종료된 적이 있다.

```text
Received disconnect ... Bye Bye
fatal: Could not read from remote repository.
```

암호 불일치 가능성을 설명했지만 화면만으로 원인을 확정하지 않았다. 다음 명령으로 인증만 별도 확인했다.

```bash
ssh -T -i /home/ubuntu/.ssh/github_backend -o IdentitiesOnly=yes git@github.com
```

화면에 successfully authenticated가 나와 키와 GitHub 인증 경로가 정상 동작하는 것을 확인했다. GitHub does not provide shell access는 GitHub가 원격 터미널 셸을 제공하지 않는다는 뜻이며 인증 실패 문구가 아니다. 이후 같은 키로 pull을 다시 실행해 성공했다.

```bash
GIT_SSH_COMMAND="ssh -i /home/ubuntu/.ssh/github_backend -o IdentitiesOnly=yes" git pull --ff-only origin main
git log -1 --oneline
```

실제 EC2의 최신 커밋이 46b9ee4로 표시됐다. --ff-only는 현재 이력을 그대로 앞으로 이동할 수 있을 때만 반영하며, 서로 갈라진 이력을 임의의 병합 커밋으로 합치지 않도록 한다.

> 📝 **기사 시험 포인트** (정보보안기사)
> 공개 키 인증에서 공개 키와 개인 키의 역할, 서버 신원 확인과 사용자 인증을 구분한다. 최소 권한 원칙에 따라 읽기만 필요한 배포 주체에는 쓰기 권한을 주지 않는다. SSH는 암호화된 원격 통신을 제공하며, 접속 대상·사용자·키가 무엇인지 함께 확인한다.

## 주제 4: EC2 .env와 nano 저장·종료

교안의 EC2 환경변수 설정 단계에서 backend 폴더에 .env를 만들었다.

```bash
cp .env.example .env
nano .env
```

실제 값은 아래 자리표시자를 바꿔 입력했다. 아래 블록은 공개용 예시다.

```dotenv
DATABASE_URL=postgresql://postgres@<RDS_ENDPOINT>:5432/aim_agent
PGPASSWORD='<DB_PASSWORD>'
GEMINI_API_KEY=<GEMINI_API_KEY>
```

사용자는 직접 값을 입력하고 저장했다고 알렸다. 이후 앱 시작·DB 확인·임베딩 적재·검색이 성공해, 해당 실행에서 필요한 설정이 사용된 것을 확인했다. 실제 암호와 API 키는 읽거나 TIL에 복사하지 않는다.

| nano 조작 | 의미 |
|---|---|
| Ctrl+O → Enter | 현재 파일 저장과 파일명 확인 |
| Ctrl+X | 편집기 종료 |
| 화살표 키 | 편집 위치 이동 |

> ➕ **더 알아두기 — YAML에서 .env를 연결한다는 뜻**
> Compose의 env_file: ./.env는 .env에 있는 설정을 컨테이너 환경변수로 전달한다는 뜻이다. 실제 .env를 GitHub에 올린다는 말이 아니다. .env.example은 채울 항목의 예시만 보관하고 실제 암호·키는 EC2에서 작성한다. 코드를 pull해도 Git에서 제외된 .env를 덮어쓰는 것은 아니다. 이미 값을 입력한 뒤 cp .env.example .env를 다시 실행하면 덮어쓸 수 있으므로 불필요하게 반복하지 않는다.
>
> 코드 clone만 할 때는 실행용 비밀 값이 없어도 된다. 백엔드는 시작 시 DB에 접속하므로 실행 전에 DB 정보가 필요하다. 문서 임베딩·검색에는 Gemini API 키도 필요하다.

## 주제 5: 원본 폴더 차이와 배포 코드 교정

처음 사용자가 알려준 docker/docker_prac/backend는 로컬 실습 코드였다. 이를 별도 업로드용 복사본으로 만들고 RDS용 Compose를 준비해 GitHub에 올렸다. 나중에 사용자가 교안의 실제 원본이 docker/deploy/backend였다고 알려 비교했다.

| 파일·기능 | deploy/backend에서 확인한 차이 |
|---|---|
| main.py | CORS 미들웨어, 허용 Origin 환경변수 읽기 |
| /health | DB에 SELECT 1을 실행한 뒤 status=ok만 반환 |
| vector_store.py | 벡터 저장소 연결에 asyncpg 드라이버 사용 |
| pyproject.toml·uv.lock | asyncpg 관련 의존성 반영 |
| compose.yaml | 이미 준비한 RDS용 Compose와 실질적으로 같음 |

> ♻️ 처음에는 처음 전달받은 backend를 배포 원본으로 삼았으나, 강의의 deploy/backend와 기능 차이가 있음을 확인했다. CORS·health 응답·벡터 DB 연결 드라이버를 배포용 원본에 맞췄다. 두 폴더가 대체로 비슷하다는 이유로 동일하다고 판단하지 않는다.

배포용 복사본에서 main.py, vector_store.py, pyproject.toml, uv.lock, .env.example, README.md 여섯 파일을 수정했다. 사용자에게 파일 목록과 커밋 메시지를 보여주고 승인을 받은 뒤 46b9ee4로 커밋·push했다. EC2에서도 pull 후 같은 커밋을 확인했다.

구문·의존성 잠금 파일·Compose 구성 검사가 통과했고, DB와 Gemini를 호출하지 않는 검사로 /health의 응답과 DB 확인 쿼리, CORS 허용·차단을 확인했다. 이 로컬 검사와 이후 EC2의 실제 동작 확인은 서로 다른 근거다.

> ➕ **더 알아두기 — 폴더의 역할을 고정하기**
> 강의 원본 폴더는 보존한다. 편집은 실습용 복사본에서 하고, 업로드용 Git 저장소에 변경 파일을 반영한 뒤 push한다. EC2는 그 저장소에서 pull한다. 원본·실습 복사본·GitHub·EC2가 모두 같은 장소라고 생각하면 어느 변경이 실제 실행되는지 혼란스러워진다. 현재 업로드용 저장소 폴더 이름은 aws-deploy-backend, 사용자 로컬 실습 폴더는 aws_practice/backend다.

## 주제 6: Docker로 백엔드 실행하고 /health 검증

실행 위치는 EC2의 /home/ubuntu/aws-agent-backend다.

```bash
sudo docker compose up -d --build backend
sudo docker compose ps
sudo docker compose logs --tail 50 backend
```

- --build는 Dockerfile과 프로젝트 파일로 이미지를 만들도록 한다.
- -d는 백그라운드 실행이다.
- ps는 컨테이너 상태를, logs는 앱 출력을 확인한다.

이미지 Built, 네트워크 Created, 컨테이너 Started가 표시됐다. Started만으로 DB 연결을 포함한 앱 기능이 정상이라고 확정하지 않고 상태 확인 API를 호출했다.

```bash
curl -i http://127.0.0.1:8000/health
```

실제 응답에서 다음을 확인했다.

```text
HTTP/1.1 200 OK
server: uvicorn
```

```json
{"status":"ok"}
```

/health 코드가 DB에 SELECT 1을 실행하므로 이 성공은 FastAPI 응답과 해당 시점 RDS 연결까지 확인한다. 아직 외부 인터넷에서 접속한 결과는 아니다. 127.0.0.1은 명령을 실행한 EC2 자신을 가리키며, Compose는 호스트의 루프백 주소 8000번 포트에 연결하도록 설정돼 있었다.

> ➕ **더 알아두기 — 실패하면 확인할 순서**
> 접속 거절·500·컨테이너 재시작 등의 상태는 서로 다른 원인이 있을 수 있다. 컨테이너 상태와 앱 로그로 실행·환경변수·DB 인증·인증서 경로를 구분한다. 로그에는 비밀 값이 포함될 수 있으므로 공유하기 전에 확인한다. 이번 기록의 실제 결과는 200과 status=ok다.

## 주제 7: EC2에서 데이터 적재와 검색 성공

교안은 로컬 PC에서 적재하는 흐름이지만, 대화에서는 먼저 EC2의 실행 중인 backend 컨테이너에서 ingest.py를 실행했다.

```bash
sudo docker compose exec backend uv run --no-sync ingest.py
```

실제 출력은 다음과 같다.

```text
텍스트 6개를 임베딩해 저장했습니다.
```

Docker·Compose·볼륨·FastAPI·LangGraph·React에 관한 예제 문서 6개를 Gemini 임베딩으로 변환하고 RDS에 저장했다. 외부 Gemini API 호출이 실제 발생하는 작업이다. 확장 활성화만 한 상태에서 데이터가 들어간 상태로 진행한 것이다.

```bash
curl -i http://127.0.0.1:8000/search \
  -H 'Content-Type: application/json' \
  -d '{"query":"Docker Compose는 무엇인가요?"}'
```

실제 200 OK와 다음 응답을 확인했다.

```json
{"documents":[{"id":"compose","text":"Docker Compose는 여러 컨테이너의 실행 설정을 하나의 파일로 관리한다."},{"id":"image","text":"Docker 이미지는 컨테이너를 실행하는 데 필요한 파일과 설정을 담는다."}]}
```

> ➕ **더 알아두기 — 검색과 답변 생성의 구분**
> 검색어를 임베딩하고 RDS의 벡터 저장소에서 유사한 문서를 찾아 반환한 결과다. 저장된 문서를 바탕으로 모델이 새로운 설명 문장을 생성한 결과는 아니다. API 이름이나 프로젝트에 RAG라는 말이 있어도 이 응답 자체가 어느 단계인지 구분한다.
>
> 백엔드 실행은 계속 사용자 요청을 받는 작업이고, 적재는 처음 문서를 준비하거나 내용을 갱신할 때 실행하는 작업이다. 적재를 실행할 장소와 백엔드를 상시 실행할 장소는 달라도 된다. 로컬이든 EC2든 같은 엔드포인트의 같은 DB·테이블로 연결하면 같은 저장소를 사용한다.

## 주제 8: 강의대로 로컬 실행 준비와 원본 보존 복구

### 왜 로컬 준비를 다시 했는가

사용자는 EC2에서 실행한 것과 별개로 강의대로 로컬 적재도 따라 하겠다고 요청했다. EC2에서 성공했으니 배포만 계속할 때는 불필요했지만, 로컬 실습을 직접 확인하려는 목적에는 로컬 환경 준비가 필요하다.

> ➕ **더 알아두기 — 자동으로 공유되지 않는 설정**
> EC2의 .env와 로컬 .env는 다른 파일이다. VS Code DB 확장에 입력한 Host·암호·CA 설정도 Python 코드에 자동 적용되지 않는다. EC2에서 받은 PEM은 EC2 안에 있고, 로컬에서 Python을 실행하려면 로컬이 읽을 인증서 위치를 지정해야 한다.

로컬 .env의 형식은 다음과 같다. 실제 값은 제외한다.

```dotenv
DATABASE_URL=postgresql://postgres@<RDS_ENDPOINT>:5432/aim_agent
PGPASSWORD='<DB_PASSWORD>'
PGSSLMODE=verify-full
PGSSLROOTCERT=./global-bundle.pem
GEMINI_API_KEY=<GEMINI_API_KEY>
CORS_ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

| 환경 | TLS 설정 위치·경로 |
|---|---|
| EC2의 backend 컨테이너 | Compose environment의 PGSSLMODE·PGSSLROOTCERT, /certs/global-bundle.pem |
| EC2 호스트 | /home/ubuntu/global-bundle.pem을 컨테이너에 읽기 전용 연결 |
| 로컬 Python 실습 | 로컬 .env의 PGSSLMODE·PGSSLROOTCERT, ./global-bundle.pem |

verify-full은 암호화뿐 아니라 서버 인증서와 접속 주소 검증을 요청한다. PGSSLROOTCERT는 그 검증에 사용할 CA 파일 위치다. 상대 경로는 작업 위치에 영향을 받으므로 이번에는 backend 폴더에서 실행한다.

### 원본을 수정한 실수와 복구

로컬 환경을 준비하면서 AI가 강의 원본 deploy/backend에 .env·CA 파일을 만들고 .gitignore를 수정했다. 사용자가 원본을 건드리지 말고 복사해서 실습해야 한다고 지적했다.

> ♻️ 처음에는 실행 파일이 있는 원본 폴더에 로컬 설정을 준비했으나, 강의 원본을 보존하고 aws_practice/backend 복사본에서 실습하는 것이 사용자의 의도에 맞다. 파일을 복사해 내용 일치를 확인한 뒤 AI가 추가한 원본의 .env·CA 파일만 제거하고, .gitignore에 추가한 인증서 제외 규칙만 되돌렸다. 사용자 설정값은 복사본에 보존했고 원본 코드를 수정하지 않았다.

실습 복사본에는 코드, .env, global-bundle.pem이 있고 .env와 인증서는 Git 제외 대상이다. 기존 공용 환경 파일에서 Gemini 키를 값 출력 없이 가져왔으며 다른 DB의 암호를 RDS 암호로 대신 사용하지 않았다. RDS 암호 자리표시자는 사용자가 실제 값으로 채우도록 안내했다.

### uv sync와 uv run

```bash
cd ~/Desktop/aws_practice/backend
code .
uv sync --frozen
uv run --no-sync ingest.py
```

> ➕ **더 알아두기 — 설치와 실행**
> uv sync는 프로젝트의 필요한 패키지를 환경에 설치·동기화한다. --frozen은 기존 잠금 파일을 갱신하지 않고 사용한다. uv run은 프로젝트의 Python 환경으로 프로그램을 실행하고 --no-sync는 실행 전에 패키지 동기화를 다시 하지 않도록 한다. sync 성공 자체가 RDS 접속이나 ingest 성공은 아니다.
>
> 사용자는 저장하고 uv sync를 실행했다고 알렸다. 로컬 ingest 실행 결과는 따로 공유되지 않았으므로 로컬 적재 성공으로 기록하지 않는다. EC2에서는 이미 적재와 검색을 검증했다. 로컬에서 같은 스크립트를 다시 실행하면 외부 API 호출과 DB 쓰기가 다시 발생한다. 문서 ID가 같을 때 처리 방식은 저장소 구현에 따라 확인해야 하므로 무조건 새 문서 6개가 추가된다고 단정하지 않는다.

## 정리

- push는 코드 업로드, clone·pull은 코드 가져오기, Docker 실행은 실제 앱 기동이다.
- 로컬 HTTPS 인증과 EC2 SSH 인증은 별개다. EC2는 저장소 읽기 전용 Deploy key를 사용했다.
- 배포용 원본 차이를 확인해 코드를 교정했고 EC2에서 최신 커밋을 확인했다.
- 실제 .env는 실행 위치별로 별도 준비한다. 원본이 아닌 복사본에서 실습한다.
- EC2에서 /health 200·status=ok, 문서 6개 적재, /search 관련 문서 두 개 반환까지 성공했다.
- 로컬 실습은 별도 학습 목적이다. uv sync 실행 보고와 실제 로컬 DB 적재 성공은 구분한다.
