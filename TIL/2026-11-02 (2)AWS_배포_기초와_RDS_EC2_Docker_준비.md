## 주제 1: AWS·서버·EC2·RDS를 구분하기

### 강의에서 다루는 배포

배포는 개발한 프로그램을 서버에 올리고, 사용자가 네트워크를 통해 사용할 수 있도록 실행 환경과 접속 경로를 구성하는 작업이다. 코드를 복사하는 데서 끝나지 않는다. 프로그램을 실행하고, 데이터베이스에 연결하고, 필요한 외부 요청을 허용하고, HTTPS를 설정하는 과정이 이어진다.

EC2는 AWS에서 가상 컴퓨터를 빌려 사용하는 서비스다. 생성한 가상 컴퓨터 한 대를 인스턴스라고 한다. 운영체제·CPU·메모리·저장 공간을 갖추며, 터미널로 접속해서 프로그램을 설치하고 실행할 수 있다.

RDS는 AWS가 데이터베이스 운영 기능을 제공하는 관리형 서비스다. DB 소프트웨어 설치·패치·백업 등의 운영 작업을 지원한다. 사용자는 엔진 종류, 크기, 접속 계정, 네트워크 접근 범위 등을 설정한다. 이번 교안은 PostgreSQL을 사용한다.

> ➕ **더 알아두기 — AWS와 클라우드**
> AWS는 Amazon Web Services의 줄임말로, 아마존이 컴퓨팅·저장 공간·데이터베이스 등 여러 IT 서비스를 제공하는 곳이다. 인터넷을 통해 필요한 자원을 빌려 쓰는 방식을 클라우드라고 한다. EC2와 RDS는 AWS 전체를 이루는 여러 서비스 중 두 가지다. 필요한 자원에 따라 비용이 발생한다.
>
> EC2는 프로그램을 실행할 컴퓨터이고, 그 안의 FastAPI는 요청을 처리하는 프로그램이다. RDS의 PostgreSQL은 데이터를 보관하고 조회한다. 프로그램과 DB는 역할이 다르며, 사용자의 검색 요청을 받은 FastAPI가 DB를 조회한 뒤 결과를 돌려주는 구조로 연결된다.

### 서버는 일반 컴퓨터와 무엇이 다른가

> ➕ **더 알아두기 — 역할로 이해하는 서버**
> 서버는 다른 컴퓨터의 요청을 받아 서비스를 제공하는 역할을 뜻한다. 반드시 특별한 종류의 컴퓨터여야 하는 것은 아니다. 내 PC에서 FastAPI를 실행해서 요청을 받으면 내 PC도 서버 역할을 한다.
>
> 개인 PC는 사람이 직접 작업할 때 켜는 경우가 많다. 서비스를 운영하는 서버는 사용자가 접속할 수 있도록 계속 실행하고, 네트워크 요청을 받을 수 있게 구성한다. EC2에 FastAPI를 실행하면 AWS에서 빌린 가상 컴퓨터가 서비스의 서버 역할을 하게 된다. 가상 컴퓨터는 실제 장비의 자원을 나누어 독립된 컴퓨터처럼 사용할 수 있게 만든 환경이다.
>
> localhost는 접속하는 컴퓨터 자신을 가리킨다. 내 PC에서 FastAPI를 실행한 뒤 친구에게 localhost 주소를 알려줘도 친구는 자신의 컴퓨터를 바라보게 된다. 외부 접속에는 실제로 도달 가능한 주소와 네트워크 설정이 필요하다.

### 컴퓨터를 직접 사서 계속 켜면 되지 않는가

> ➕ **더 알아두기 — 직접 운영과 EC2 비교**
> 직접 컴퓨터를 사서 하루 종일 켜 두고 서버로 운영하는 것도 가능하다. EC2는 유일한 배포 방법이 아니다. 차이는 구입비만이 아니라 전기·인터넷·고장 대응·확장·관리 시간까지 포함해서 비교해야 한다.
>
> | 상황 | 직접 마련한 컴퓨터 | EC2 |
> |---|---|---|
> | 물리 장비 고장 | 직접 수리·교체 | 물리 장비 운영은 AWS가 담당 |
> | 집의 정전·인터넷 장애 | 집에서 운영하는 서비스에 영향 | 집의 전기·인터넷과 별도로 운영 |
> | 성능 확대 | 부품 교체나 장비 구매 | 더 큰 인스턴스로 변경하는 방식 등을 사용 |
> | 짧은 실험 | 장비 확보 필요 | 필요한 기간 동안 빌려 사용 가능 |
> | 장기간 일정한 사용 | 구매가 더 저렴할 수도 있음 | 계속 발생하는 사용 비용을 비교해야 함 |
>
> EC2 온디맨드는 장기 약정 없이 컴퓨팅 자원을 사용하는 방식이다. 다만 컴퓨터를 중지해도 저장 공간 등 다른 자원의 비용은 별도로 남을 수 있다. EC2를 쓴다고 운영체제 업데이트·애플리케이션 실행·접근 권한 설정이 모두 자동으로 해결되지는 않으며, EC2 한 대에도 장애는 생길 수 있다.

## 주제 2: Nginx와 전체 배포 구조

Nginx(엔진엑스)는 HTTP 요청을 처리하는 웹 서버이며, 요청을 다른 서버로 전달하는 리버스 프록시 역할도 한다. 리버스 프록시는 클라이언트의 요청을 먼저 받아 내부 애플리케이션에 전달하고, 애플리케이션의 응답을 클라이언트에게 돌려준다.

교안의 전체 구조는 Vercel의 React 프론트엔드, EC2의 Nginx·FastAPI 컨테이너, RDS의 PostgreSQL·pgvector, 로컬 PC의 ingest.py로 구성된다. Vercel은 GitHub 소스를 가져와 빌드하고 접속 가능한 웹 주소로 제공하는 배포 플랫폼이다.

| 구간 | 교안에서의 역할·연결 |
|---|---|
| Vercel → 브라우저 | React의 HTML·JavaScript 전달 |
| 브라우저 → EC2의 Nginx | HTTPS 443번 포트로 API 요청 |
| Nginx → FastAPI | 같은 EC2의 Docker 네트워크에서 HTTP 8000번 포트로 전달 |
| FastAPI → RDS | PostgreSQL 5432번 포트, TLS로 통신 보호 |
| 로컬 PC → RDS | ingest.py로 검색할 문서 데이터 적재 |

> ➕ **더 알아두기 — 식당 비유**
> Nginx는 주문을 받고 결과를 전달하는 직원, FastAPI는 실제 요리를 하는 주방에 비유할 수 있다. EC2는 둘이 일하는 공간에 해당한다. FastAPI가 직접 요청을 받을 수도 있지만, 교안은 Nginx가 HTTPS 연결과 요청 전달을 담당하고 FastAPI가 검색 등 앱 기능을 담당하도록 역할을 나눈다. Nginx는 EC2와 별개인 또 한 대의 컴퓨터가 아니라 EC2 안에서 실행할 프로그램이다.

이 구조는 전체 교안의 목표다. 이번 기록 시점에는 Nginx·HTTPS·Vercel 배포를 실행하지 않았다.

## 주제 3: RDS PostgreSQL 생성과 설정 의미

AWS 콘솔의 리전을 아시아 태평양 서울로 바꾸고, RDS에서 데이터베이스 생성을 시작했다. 전체 구성으로 PostgreSQL을 선택하고, 강사 안내에 따라 아래 설정을 적용했다. 각자 학생 번호를 붙여 공유 실습 계정에서 자원을 구분했다. 공개 기록에는 실제 번호 대신 NN을 사용한다.

| 항목 | 실습 설정 |
|---|---|
| 리전 | 아시아 태평양 서울, ap-northeast-2 |
| 생성 방식 | 전체 구성 |
| 엔진 | PostgreSQL |
| 엔진 버전 | 사용자 선택: 17.11 R1, 교안 기준: 17.x |
| 템플릿 | 샌드박스 |

| DB 인스턴스 식별자 | database-NN — 학생별 구분 |

후속 캡처에서 RDS 상태가 사용 가능으로 표시되는 것을 확인했다. DB 생성은 완료됐지만, 이것만으로 EC2의 접속 성공까지 검증한 것은 아니다.

### 전체 구성과 샌드박스

> ➕ **더 알아두기 — 설정을 고르는 방식**
> 전체 구성은 버전·크기·접속 관련 옵션 등을 직접 선택하는 방식이다. PostgreSQL은 데이터를 저장하고 조회하는 DB 프로그램, 즉 데이터베이스 엔진의 이름이다.
>
> 템플릿은 용도에 맞는 설정을 미리 골라둔 묶음이다. 프로덕션은 실제 운영, 개발/테스트는 개발 검증, 샌드박스는 학습과 작은 실험을 위한 기본 구성으로 이해한다. 같은 PostgreSQL을 사용해도 뒤에서 제안되는 사양과 운영 설정의 기본값이 달라진다. 실제 선택값을 확인해야 하며, 샌드박스라고 자동으로 무료가 되는 것은 아니다.

### 가용성·내구성과 단일 AZ

> ➕ **더 알아두기 — 가용성과 내구성**
> 가용성(Availability)은 필요할 때 서비스를 사용할 수 있는 정도다. DB가 멈춰 검색하지 못하면 가용성 문제다. 내구성(Durability)은 저장한 데이터가 손실되지 않고 유지되는 정도다. 저장했던 데이터가 사라지면 내구성 문제다. DB가 잠시 멈춰도 데이터가 남아 있을 수 있으므로 서비스 중단과 데이터 손실을 같은 것으로 보면 안 된다.
>
> 리전은 AWS 자원을 만드는 지역이다. AZ(Availability Zone, 가용 영역)는 한 리전 안에서 물리적으로 분리된 하나 이상의 데이터센터로 구성되는 구역이다. 서울 리전 안에도 여러 AZ가 있다.
>
> 단일 AZ는 한 AZ에서 DB 인스턴스를 운영한다. 다른 AZ에 자동 전환용 대기 DB를 따로 두지 않는다. 다중 AZ DB 인스턴스 배포는 다른 AZ의 대기 인스턴스에 데이터를 동기 복제하고, 장애 시 대기 인스턴스로 전환하는 구성을 제공한다. 전환에는 시간이 걸릴 수 있다. 이번에는 실습 규모와 비용을 고려해 단일 AZ를 선택했다.
>
> 단일 AZ도 백업을 설정할 수 있다. 백업 파일에서 복구하는 것과, 준비된 대기 DB로 전환하는 것은 다르다. 다중 AZ 역시 실수로 삭제한 데이터의 복구를 위한 백업을 대체하지 않는다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> 가용성은 정보보호의 기밀성(Confidentiality)·무결성(Integrity)·가용성(Availability), 즉 CIA 요소 중 하나다. 무결성은 데이터가 허가 없이 변경·훼손되지 않도록 하는 성질이며, RDS 화면에서 말하는 내구성과 같은 단어가 아니다. 서비스 이용 가능 여부, 데이터 변조 여부, 데이터 보존 여부를 구분해서 설명한다. 여기서는 개념을 연결한 것이며 특정 연도의 출제 빈도를 뜻하지 않는다.

### 버스터블 클래스와 CPU 크레딧

> ➕ **더 알아두기 — db.t4g.micro 읽기**
> db는 DB용 인스턴스, t4g는 버스터블 성능을 제공하는 제품군, micro는 해당 제품군 안에서의 크기를 가리킨다. 버스터블은 평소에 CPU 사용이 적다가 잠깐 기본 수준보다 높은 CPU 성능이 필요한 작업에 맞는 방식이다. CPU는 계산과 처리를 담당하는 자원이다.
>
> 설명을 듣는 동안 DB가 쉬고, 실습 중 검색할 때 잠깐 바빠지는 상황을 떠올리면 된다. 기준보다 CPU를 적게 사용할 때 크레딧을 축적하고, 더 많이 사용할 때 소비한다. RDS T4g는 Unlimited 모드이므로 CPU 사용이 지속적으로 높아 크레딧이 부족해지면 추가 요금이 발생할 수 있다. 버스터블을 단순히 RAM을 늘리는 옵션으로 이해하면 안 된다.

### 식별자·초기 DB 이름·KMS

> ➕ **더 알아두기 — 두 이름의 구분**
> DB 인스턴스 식별자는 AWS 콘솔에서 RDS 자원을 구분하는 이름이다. 초기 데이터베이스 이름 aim_agent는 그 인스턴스 안에 만들 DB의 이름이다. 접속 설정에서는 엔드포인트와 함께 dbname=aim_agent 같은 값으로 사용한다. 인스턴스 이름과 실제 DB 이름은 서로 바꿔 쓸 수 없다.
>
> KMS(Key Management Service)는 암호화 키를 관리하는 AWS 서비스다. 사용자는 수업 중 KMS 오류를 무시하라는 안내를 들었다고 전달했다. 하지만 오류 원문은 공유하지 않았으므로 원인·영향·무시 가능 여부를 확정하지 않는다. 나중에 사용 가능 상태가 확인된 사실과 그 오류가 무해하다는 판단은 구분한다.

### 퍼블릭 액세스와 ingest

교안은 로컬 PC에서 ingest.py를 실행해 검색할 데이터를 RDS에 적재하는 흐름이다. 그래서 RDS의 퍼블릭 액세스를 예로 설정하고, 로컬 PC와 EC2에서 오는 DB 접속을 보안 그룹으로 허용하도록 구성한다.

> ➕ **더 알아두기 — ingest의 뜻**
> ingest(인제스트)는 데이터를 가져와 저장하는 작업이다. DB를 만들었다고 검색할 문서까지 자동으로 들어가는 것은 아니다. 교안의 ingest.py는 검색할 문서 데이터를 DB에 넣는 역할을 한다. 이 파일은 교안 기준 이름이며, 현재 작업 폴더에 같은 파일이 실제로 있는지는 이번 대화에서 조사하지 않았다.
>
> 퍼블릭 액세스 예는 인터넷을 통한 접속이 가능하도록 구성하는 선택이다. 누구나 인증 없이 DB에 들어온다는 뜻은 아니다. 네트워크 경로, 보안 그룹의 허용 규칙, DB 계정과 암호 등도 맞아야 한다. 이번 실습에서 퍼블릭 접속을 쓰는 이유는 로컬 적재이며, 모든 운영 환경에서 반드시 이렇게 구성해야 하는 것은 아니다.

## 주제 4: EC2 생성·Ubuntu·SSH 접속

### EC2 생성에서 진행한 설정

EC2를 검색해 인스턴스 시작을 누르고 Ubuntu를 선택했다. 키 페어 없이 진행하고, 네트워크 설정의 편집에서 새 보안 그룹 aim-agent-ec2-NN을 만들었다. 인스턴스를 시작한 뒤 실행 상태와 상태 검사 통과를 기다리고, 웹 브라우저의 EC2 인스턴스 연결로 접속했다. 사용자 이름은 ubuntu였다.

> ➕ **더 알아두기 — 운영체제·메모리·권한**
> Ubuntu는 Linux 계열 운영체제다. 내 PC에 Windows가 있는 것처럼 EC2에는 Ubuntu를 선택해 설치한다. RAM은 실행 중인 프로그램과 데이터의 작업 공간이다. FastAPI·LangGraph 등이 사용하는 메모리가 부족하면 실행이 느려지거나 프로그램이 종료될 수 있다.
>
> 사용자는 강사 안내에 따라 EC2 유형으로 t3.micro를 선택한다고 말했다. RDS의 db.t4g.micro와는 다른 자원의 사양이다. “RAM이 더 필요해서 선택했다”는 말만으로 이전 유형보다 RAM이 늘었다고 판단할 수 없으며, 이전 비교 대상과 실제 선택 결과는 별도 확인이 필요하다. LangGraph를 쓴다고 항상 더 큰 RAM이 필요한 것은 아니다.
>
> 계정 권한은 어떤 AWS 자원을 만들고 변경할 수 있는가를 뜻하고, 사양은 빌린 컴퓨터의 CPU·메모리 크기를 뜻한다. 파이널 프로젝트에 더 좋은 권한을 제공한다는 강사 안내가 더 높은 사양 제공까지 의미하는지는 확인하지 않았다.

### SSH와 브라우저 연결

EC2 Instance Connect는 AWS 콘솔에서 임시 SSH 키를 이용해 EC2에 접속할 수 있게 하는 기능이다. 이번 실습은 로컬에 개인 키 파일을 내려받는 방식 대신 브라우저 연결을 사용한다.

> ➕ **더 알아두기 — SSH와 키 페어**
> SSH(Secure Shell)는 원격 컴퓨터의 터미널에 암호화된 통신으로 접속하는 방식이다. 키 페어는 인증에 쓰는 공개 키와 개인 키의 한 쌍이다. 개인 키는 비밀로 관리한다. EC2 Instance Connect가 임시 키를 이용한 접속을 지원하므로 이번 생성 단계에서는 키 페어 없이 진행했다. 단, 브라우저 접속에는 필요한 권한과 네트워크 조건도 충족해야 한다.

실제 접속 후 Ubuntu 환영 문구와 명령 프롬프트가 표시되었다. 이후 Docker 설치 명령은 로컬 Windows PC가 아니라 EC2의 Ubuntu에서 실행했다.

```text
ubuntu@<EC2_HOST>:~$
```

> ➕ **더 알아두기 — 프롬프트 읽기**
> ubuntu는 로그인 사용자, @ 뒤는 컴퓨터 이름이다. ~는 사용자 홈 디렉터리, $는 일반 사용자 셸의 명령 입력 표시다. 실제 컴퓨터 이름과 IP는 공개 기록에서 생략했다.

> ♻️ 처음엔 환영 화면의 약 -273°C를 실제 서버 온도로 받아들였으나, 가상 환경에서 센서 정보를 얻지 못해 생긴 비정상 표기일 수 있다. 실제 물리 서버가 절대영도에 가깝다는 뜻은 아니다. 정확한 표기 원인까지 조사한 것은 아니다.

## 주제 5: VPC·보안 그룹·포트·원본

VPC(Virtual Private Cloud)는 AWS 안에서 구성하는 가상 네트워크다. EC2와 RDS를 같은 VPC에 만들면 사설 네트워크로 연결하도록 구성할 수 있다. 같은 VPC라는 사실만으로 통신이 자동 허용되지는 않으며 라우팅과 보안 그룹 등도 맞아야 한다.

보안 그룹은 자원으로 들어오는 통신과 나가는 통신을 제어하는 가상 방화벽이다. 인바운드는 들어오는 연결, 아웃바운드는 나가는 연결을 말한다. IP 주소가 컴퓨터의 위치를 나타낸다면 포트는 그 컴퓨터에서 어떤 서비스에 접속할지 구분하는 번호다.

| 포트 | 교안에서의 용도 |
|---|---|
| 22 | SSH로 EC2 터미널 접속 |
| 80 | HTTP 요청, HTTPS 인증서 발급·갱신의 검증 |
| 443 | HTTPS 요청 |
| 5432 | PostgreSQL 접속 |
| 8000 | FastAPI가 요청을 받는 포트 |

> ➕ **더 알아두기 — 보안 그룹을 나누는 이유**
> EC2에는 터미널·웹 요청이, RDS에는 DB 연결이 필요하다. 허용할 통신이 달라 EC2용과 RDS용 보안 그룹을 따로 만든다. 컴퓨터마다 반드시 새 보안 그룹 하나씩을 만들어야 한다는 규칙은 아니다. 같은 정책이 필요한 여러 자원에 같은 그룹을 적용할 수 있다. 이름을 정하는 것만으로 접속이 허용되는 것도 아니며, 실제 규칙의 유형·포트·소스가 중요하다.

### 인바운드 규칙에서 원본이란

> ➕ **더 알아두기 — 접속 출발지**
> 소스 또는 원본(Source)은 어디에서 오는 접속을 허용할지 뜻한다. 건물 비유에서 포트는 출입문이고, 소스는 그 문으로 들어올 수 있는 대상이다. 소스 유형의 사용자 지정은 허용할 출발지를 직접 정한다는 뜻이며, 옆 소스 입력칸에서 실제 IP 범위·보안 그룹·접두사 목록 등을 선택한다.
>
> 내 IP를 선택하면 현재 PC의 공인 IP가 소스로 들어간다. 반면 이번 EC2 브라우저 연결은 AWS의 EC2 Instance Connect 서비스가 EC2에 접속하므로, 해당 서비스의 IP 범위를 허용한다.

실습에서 EC2의 SSH 규칙 소스로 선택한 접두사 목록 이름은 다음과 같다. 아래 서비스 이름은 공통 이름이며 개인 자원 ID가 아니다.

```text
com.amazonaws.ap-northeast-2.ec2-instance-connect
```

> ➕ **더 알아두기 — 접두사 목록**
> 접두사 목록(Prefix list)은 IP 주소 범위를 묶어 놓은 목록이다. 위 목록은 AWS가 관리하는 서울 리전의 EC2 Instance Connect 주소 범위를 나타낸다. ap-northeast-2는 서울 리전 코드다. 실제 목록 ID(pl-로 시작)는 공개 기록에 넣지 않는다.
>
> 이 목록을 소스로 둔 SSH 22번 규칙의 의미는 “서울 리전의 EC2 Instance Connect 서비스에서 들어오는 SSH 연결을 허용한다”이다. 접속 흐름은 브라우저 → AWS 접속 서비스 → EC2이므로 EC2에서 보는 직접적인 접속 출발지는 AWS 접속 서비스다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> 방화벽 정책은 출발지·목적지 주소, 프로토콜, 포트 등으로 통신을 구분한다. SSH는 원격 접속에 사용하며 일반적인 기본 포트는 TCP 22다. HTTP 80, HTTPS 443, PostgreSQL 5432는 서비스와 포트를 연결하는 예다. 포트 번호를 외우는 것에 더해 어떤 출발지에서 어느 자원의 서비스로 접속하는지 설명한다.

## 주제 6: RDS 인바운드 규칙 오류와 해결

### 올바른 편집 대상 찾기

교안은 RDS의 DB 상세 화면에서 보안 그룹 링크를 따라가 인바운드 규칙을 편집한다. 실습에서는 RDS → 데이터베이스 → 본인 DB → 연결 및 보안 → VPC 보안 그룹으로 이동했다. 보안 그룹 화면은 EC2 콘솔 안에 나타나지만, 이름이 aim-agent-rds-NN이면 RDS용 그룹이 맞다.

| 구분 | 선택하는 대상 |
|---|---|
| 편집할 보안 그룹 | aim-agent-rds-NN |
| 추가할 규칙 유형 | PostgreSQL |
| 프로토콜·포트 | TCP 5432 |
| 소스 유형 | 사용자 지정 |
| 소스로 참조할 그룹 | aim-agent-ec2-NN |

이 규칙은 해당 EC2 보안 그룹이 적용된 인스턴스에서 RDS로 접속하는 통신을 허용한다.

### 실제로 막힌 오류

기존 PostgreSQL 규칙은 소스가 특정 공인 IPv4 주소의 /32 범위였다. 그 기존 행의 소스를 EC2 보안 그룹 ID로 바꾸려고 하자 다음 오류가 표시됐다.

```text
기존 IPv4 CIDR 규칙에 참조된 그룹 ID을(를) 지정할 수 없습니다.
```

> ➕ **더 알아두기 — 오류의 원인**
> CIDR은 IP 주소 범위를 나타내는 표기법이다. IPv4 주소 뒤 /32는 해당 IP 주소 하나를 뜻한다. 화면의 기존 규칙 ID가 붙은 행은 IP 범위 기반 규칙이었다. 이 행을 보안 그룹 참조 방식으로 직접 바꾸려고 해서 오류가 났다. EC2 보안 그룹 자체를 잘못 골라서 발생한 오류는 아니었다.

해결은 기존 규칙을 유지하고 새 규칙을 추가하는 것이었다.

1. 수정 중인 내용을 취소해 기존 IP 규칙을 원래 상태로 되돌린다.
2. 인바운드 규칙 편집에 다시 들어간다.
3. 기존 첫째 행은 건드리지 않고 규칙 추가를 누른다.
4. 새 둘째 행에 PostgreSQL / TCP 5432 / 사용자 지정 / EC2 보안 그룹을 선택한다.
5. 두 줄이 있는지 확인하고 오류가 사라진 뒤 규칙 저장을 누른다.

사용자는 이 방식으로 규칙을 저장했다고 알렸다. 최종 저장 후 별도 목록 캡처까지 확인한 것은 아니므로, 저장 완료는 사용자 보고에 근거한다.

### 왜 규칙이 두 개 필요한가

| 규칙 | 출발지 | 목적 |
|---|---|---|
| 기존 규칙 | 특정 공인 IP /32 | 로컬 PC에서 RDS에 데이터 적재 |
| 추가 규칙 | EC2 보안 그룹 | EC2의 FastAPI 등에서 RDS 접속 |

> ➕ **더 알아두기 — 두 줄의 의미**
> 보안 그룹을 두 개 더 생성하는 것이 아니라, RDS 보안 그룹 하나 안에 서로 다른 출발지를 허용하는 규칙 두 줄을 두는 것이다. 같은 5432번 포트라도 출발지가 다르면 별도 규칙이 될 수 있다. 기존 IP가 현재 실습 PC의 공인 IP와 일치하는지는 실제 로컬 접속 전에 확인해야 한다. 이번 대화에서는 일치 여부를 따로 검증하지 않았다.

> ♻️ 처음엔 기존 PostgreSQL 행의 소스만 EC2 보안 그룹으로 바꾸면 된다고 접근했으나, 기존 IP 규칙은 유지하고 EC2 보안 그룹을 참조하는 새 행을 추가하는 것이 이번 실습의 해결 방법이었다.

## 주제 7: 공개 기록에서 제외할 정보

사용자는 EC2 접속 화면과 RDS 화면을 공유하면서 비밀 키가 노출되는지 질문했다. 공유된 캡처에는 DB 암호, AWS 비밀 액세스 키, API 키, SSH 개인 키 내용은 보이지 않았다. 하지만 AWS 계정 ID, 공인·사설 IP, 엔드포인트, 인스턴스·VPC·서브넷·보안 그룹의 실제 ID가 포함된 화면은 있었다.

> ➕ **더 알아두기 — 비밀과 식별자의 차이**
> 자원 ID나 서버 주소는 인증 비밀 그 자체는 아니다. 그것만으로 바로 로그인할 수 있는 것은 아니다. 그렇다고 공개 학습 기록에 실제 환경 정보를 모두 남길 필요는 없다. 이번 TIL에는 실제 계정 ID·IP·RDS 주소·자원 ID를 넣지 않고 공통 이름이나 자리표시자로 대체했다. 학생 번호도 NN으로 일반화했다. 사용자 요청에 따라 이미지는 포함하지 않는다.
>
> 반드시 공개하지 않아야 하는 정보에는 로그인 암호, DB 마스터 암호, AWS Secret Access Key·세션 토큰, SSH 개인 키 내용, Gemini 등 서비스의 API 키가 있다. .env 파일에는 이런 값이 들어갈 수 있으므로 그대로 공개하지 않는다. AWS Access Key ID도 비밀 키와 구분되는 식별자지만 인증 정보의 일부이므로 공개 기록에서는 함께 가린다.
>
> 화면의 관리형 SSH 키라는 설명 문구는 비밀 키 값이 아니다. .pem 확장자도 무조건 비밀을 의미하지 않는다. global-bundle.pem은 공개 CA 인증서 묶음이고, SSH 개인 키나 서버의 privkey.pem은 비밀이다. 파일의 역할과 내용으로 구분한다.

## 주제 8: EC2 Ubuntu에 Docker와 Compose 설치

### 실행 위치와 현재 확인 결과

아래 설치 명령은 모두 AWS 브라우저로 연결한 EC2 Ubuntu 터미널에서 실행했다. 내 Windows의 Git Bash에서 실행한 것이 아니다. 교안 명령과 공식 Docker 설치 절차를 참고해 안내했고, 최종 캡처에서 hello-world 실행 성공과 Compose 버전을 확인했다.

### 1. 설치에 필요한 도구 준비

```bash
sudo apt update
sudo apt install -y ca-certificates curl git
```

| 명령·도구 | 뜻 |
|---|---|
| sudo | 관리자 권한으로 명령 실행 |
| apt | Ubuntu의 패키지 관리 도구 |
| apt update | 설치 가능한 패키지 목록·버전 정보를 갱신 |
| apt install | 지정한 패키지를 설치 |
| -y | 설치 확인 질문에 자동 동의 |
| ca-certificates | HTTPS 서버 인증서 검증에 사용할 CA 인증서 모음 |
| curl | URL로 요청을 보내거나 파일을 다운로드하는 도구 |
| git | 소스 코드를 가져오고 버전을 관리하는 도구 |

실행 캡처에서 설치 처리가 끝나고 프롬프트가 돌아온 것을 확인했다. 이 단계는 Docker 본체가 아니라 설치에 필요한 도구를 준비하는 작업이다.

### 2. Docker 저장소 검증용 공개 키 준비

```bash
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
```

Docker 패키지 저장소의 서명을 검증할 공개 키를 내려받아 APT가 읽을 수 있도록 준비한다. install -m 0755 -d는 지정한 권한으로 폴더를 만들고, curl의 -o는 저장 경로를 정한다. chmod a+r은 모든 사용자에게 읽기 권한을 추가한다.

APT는 신뢰하는 공개 키로 저장소 정보의 서명을 검증하고, 저장소 정보에 있는 해시와 내려받은 패키지의 해시를 비교해 변조 여부를 확인한다. 이 공개 키는 사용자 인증 비밀 키가 아니다.

### 3. 공식 패키지 저장소 등록

```bash
sudo tee /etc/apt/sources.list.d/docker.sources > /dev/null <<EOF
Types: deb
URIs: https://download.docker.com/linux/ubuntu
Suites: $(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")
Components: stable
Architectures: $(dpkg --print-architecture)
Signed-By: /etc/apt/keyrings/docker.asc
EOF
```

APT에 Docker 패키지를 다운로드할 주소와 서명 검증에 사용할 공개 키를 등록한다. 블록은 마지막 EOF까지 통째로 실행하도록 안내했고 사용자는 완료했다고 답했다.

> ➕ **더 알아두기 — 이 블록이 하는 일**
> tee는 입력받은 내용을 파일에 쓰고, > /dev/null은 화면 출력을 버린다. <<EOF부터 마지막 EOF 전까지의 여러 줄을 입력으로 전달한다. 이 블록의 EOF는 따옴표가 없으므로 $(...) 안의 명령 결과가 반영된다. 운영체제 코드명과 CPU 아키텍처를 읽어 현재 EC2에 맞는 저장소 설정을 만든다. 출력이 없고 프롬프트만 돌아와도 정상일 수 있다.

### 4. Docker와 Compose 설치·실행

```bash
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
sudo systemctl enable --now docker
```

추가한 Docker 저장소까지 포함해 패키지 목록을 다시 읽은 뒤 Docker Engine·명령 도구·컨테이너 실행 구성 요소·빌드 도구·Compose 플러그인을 설치한다. systemctl enable --now docker는 Docker를 지금 시작하고, EC2 부팅 시에도 자동 시작되도록 설정한다.

> ➕ **더 알아두기 — Compose와 systemctl**
> Compose는 여러 컨테이너의 설정을 파일로 정리해 함께 실행·관리하는 도구다. 이번에는 설치만 확인했으며, 실제 프로젝트 compose.yaml로 백엔드를 올리지는 않았다. systemctl은 Ubuntu의 서비스 관리자 systemd를 제어하는 명령이다.

### 5. 실제 작동 확인

```bash
sudo docker run --rm hello-world
sudo docker compose version
```

교안은 테스트 컨테이너를 실행하고 Compose 버전이 출력되는지 확인하도록 한다. --rm은 실행을 마친 컨테이너를 자동 삭제하는 옵션이며, 내려받은 이미지까지 삭제한다는 뜻은 아니다.

실제 캡처에서 다음 문구를 확인했다. 전체 터미널 출력 중 성공 확인에 필요한 줄만 발췌했다.

```text
Hello from Docker!
This message shows that your installation appears to be working correctly.
Docker Compose version v5.6.1
```

중간에는 다음 문구도 나왔다.

```text
Unable to find image 'hello-world:latest' locally
```

> ➕ **더 알아두기 — 처음 실행할 때의 다운로드**
> 이 문구는 EC2에 해당 이미지가 없다는 뜻이다. 뒤에서 Docker Hub로부터 이미지를 내려받고 컨테이너를 정상 실행했다. 이 문구 하나만 보고 설치 실패로 판단하지 않는다. pull 완료와 Hello from Docker!라는 후속 결과를 함께 확인한다. Docker와 Compose 검증 성공은 FastAPI나 RDS 접속 성공과는 별개다.

## 주제 9: RDS CA 인증서와 엔드포인트 확인

### TLS와 CA의 역할

교안은 PostgreSQL 클라이언트로 접속하기 전에 RDS의 CA 인증서 묶음을 준비한다. TLS(Transport Layer Security)는 네트워크로 주고받는 내용을 암호화하고 변조를 검출하는 통신 보안 기술이다. RDS에 보내는 SQL 요청과 조회 결과도 보호한다.

RDS는 연결 과정에서 서버 인증서를 제시한다. 클라이언트는 CA(Certificate Authority, 인증 기관)의 인증서를 신뢰 기준으로 삼아 서버 인증서를 검증한다. global-bundle.pem에는 RDS 서버 인증서를 검증할 CA 인증서들이 들어 있다.

sslmode=verify-full은 암호화된 연결을 사용하면서 인증서의 신뢰성과 접속한 호스트 이름까지 확인하는 설정이다.

### 안내한 다운로드 명령과 확인 범위

Docker 검증 후 같은 EC2 터미널에서 다음 명령을 실행하도록 안내했다.

```bash
curl -fsSL https://truststore.pki.rds.amazonaws.com/global/global-bundle.pem -o /home/ubuntu/global-bundle.pem
```

이 명령은 공개 CA 인증서 묶음을 /home/ubuntu/global-bundle.pem에 저장한다. 사용자가 이후 RDS 화면으로 이동했지만, 다운로드 명령의 실행 결과나 파일 존재를 별도로 보여주지는 않았다. 따라서 이 기록에서는 다운로드 완료로 단정하지 않는다.

### 엔드포인트 찾기

RDS → 데이터베이스 → 본인 DB → 연결 및 보안 탭으로 이동했다. 실제 화면은 코드 스니펫 / CloudShell / 엔드포인트 선택 상자가 있는 구성이었다. 처음에는 코드 스니펫이 선택돼 있어 접속 명령이 표시됐고, 그 안의 RDSHOST 값으로도 주소를 찾을 수 있었다.

엔드포인트 선택 상자를 누른 뒤 실제 캡처에서 아래 정보를 확인했다.

| 항목 | 확인한 내용 |
|---|---|
| 데이터베이스 이름 | aim_agent |
| 마스터 사용자 이름 | postgres |
| 포트 | 5432 |
| 엔드포인트 유형 | 인스턴스 엔드포인트 |
| 엔드포인트 | 실제 주소 확인, 공개 기록에서는 생략 |
| 퍼블릭 액세스 가능 | 예 |

엔드포인트는 RDS에 접속할 때 사용하는 주소다. 아래는 형식만 보여주는 예시이며 실제 접속 주소가 아니다.

```text
<DB_IDENTIFIER>.<AWS_ASSIGNED_PART>.ap-northeast-2.rds.amazonaws.com
```

> ♻️ 처음에는 연결 및 보안 탭 위쪽에 엔드포인트 및 포트가 바로 표시된다고 안내했으나, 실제 화면은 먼저 엔드포인트 선택 상자를 눌러야 해당 정보가 보이는 구성이었다. 화면 캡처를 기준으로 안내를 수정했다.

> ➕ **더 알아두기 — 이름과 주소 구분**
> DB 식별자는 AWS 자원을 부르는 이름이고, 엔드포인트는 네트워크 접속 주소이며, aim_agent는 접속할 DB 이름이다. 주소를 안다고 인증 없이 접속할 수 있는 것은 아니고, 보안 그룹·DB 사용자·암호·TLS 설정까지 맞아야 한다.

> 📝 **기사 시험 포인트** (정보처리기사·정보보안기사)
> TLS 통신에서 암호화와 서버 인증은 구분해서 이해한다. CA 인증서를 이용해 서버 인증서의 신뢰성을 검증하며, 호스트 이름 확인은 접속 주소가 인증서와 맞는지 검사하는 것이다. 공개 인증서와 개인 키의 비밀성 요구는 다르다. verify-full은 이 실습의 PostgreSQL 연결 옵션으로 연결해 기억한다.

## 주제 10: 완료 범위와 다음 실습

### 여기까지 확인한 것

| 작업 | 기록 근거·상태 |
|---|---|
| 서울 리전 선택 | 사용자 진행 보고와 화면 |
| RDS PostgreSQL 생성 | 후속 화면에서 사용 가능 확인 |
| RDS 초기 DB 이름 | aim_agent 표시 확인 |
| EC2 생성과 Ubuntu 접속 | Ubuntu 터미널 캡처 확인 |
| RDS에 EC2 소스 규칙 추가 | 오류 해결 후 저장했다는 사용자 보고 |
| Docker 설치와 테스트 | Hello from Docker! 캡처 확인 |
| Compose 설치 | v5.6.1 출력 확인 |
| CA 인증서 다운로드 | 명령 안내만 확인, 실행 결과 미확인 |
| RDS 엔드포인트 | 사용자 화면에서 위치·주소 확인 |

아직 완료로 기록하지 않는 작업은 EC2에서 RDS 로그인, pgvector 확장 활성화, ingest.py 데이터 적재, FastAPI 컨테이너 배포, Nginx·HTTPS 설정, Vercel 프론트엔드 배포다.

### 이어서 할 일 — 교안 기준이며 아직 미실행

교안의 다음 단계는 PostgreSQL 17 이미지의 임시 컨테이너에서 psql을 실행해 RDS에 접속하는 것이다. psql은 터미널에서 PostgreSQL에 접속해 SQL을 실행하는 클라이언트 도구다. 이 방법은 EC2에 PostgreSQL DB 서버를 새로 설치하는 것이 아니라, 접속용 도구만 임시 컨테이너에서 실행하는 방식이다.

접속 시 엔드포인트, 포트 5432, DB 이름 aim_agent, 사용자 postgres, TLS 검증용 CA 파일이 필요하다. 실제 암호는 터미널의 암호 입력 안내에 따라 입력하고 TIL에 저장하지 않는다. CA 파일 준비 여부부터 확인한 뒤 진행한다.

교안은 로그인 후 현재 DB에서 vector 확장을 활성화하고, 확장 이름·버전 조회 결과를 확인하도록 한다. pgvector는 벡터 데이터를 저장하고 유사도 검색을 지원하는 PostgreSQL 확장이다. 이후 로컬 데이터 적재와 검색 검증으로 넘어간다. 아직 명령을 실행하거나 결과를 확인하지 않았으므로 완료 기록과 섞지 않는다.

## 정리

- AWS는 여러 클라우드 서비스를 제공하며, 이번에는 EC2에서 프로그램을 실행하고 RDS에 데이터를 저장한다.
- 서버는 요청을 처리하는 역할이다. 직접 장비를 운영할 수도 있고 EC2를 빌릴 수도 있다.
- RDS의 식별자, DB 이름, 엔드포인트는 서로 다른 값이다.
- 단일 AZ는 다른 AZ에 자동 전환용 대기 DB를 두지 않는다. 가용성과 데이터 내구성은 구분한다.
- 인바운드 소스는 접속 출발지다. EC2의 브라우저 SSH 접속에는 서울 리전의 EC2 Instance Connect 접두사 목록을 사용했다.
- RDS에는 기존 IP 규칙과 새 EC2 보안 그룹 규칙을 두었다. 기존 CIDR 행을 보안 그룹 방식으로 직접 수정해서 난 오류는 새 규칙 추가로 해결했다.
- Docker hello-world와 Compose 버전을 확인했다. RDS 주소는 찾았지만 실제 DB 접속은 다음 단계다.
- 공개 TIL에는 이미지와 실제 계정·IP·엔드포인트·자원 ID·암호·비밀 키를 넣지 않았다.
