## LLM API에서 비동기를 쓰는 이유

- LLM API는 응답 생성까지 기다리는 시간이 김. 여러 독립적인 질문을 순차로 보내면 대기 시간이 그대로 누적됨.
- 비동기로 여러 요청을 동시에 걸면 한 요청이 기다리는 동안 다른 요청도 진행되어 전체 시간이 줄어듦.
- 단, 비동기는 **한 요청 자체의 응답 속도를 높이는 게 아니라**, 여러 독립 요청의 대기 시간을 겹쳐서 전체 처리 시간을 줄이는 방법.
- FastAPI 같은 서버에서도 `async def` 엔드포인트 안에서 LLM 응답을 `await`하면, 그 대기 시간 동안 이벤트 루프가 다른 사용자 요청을 처리할 수 있음. 동기 클라이언트를 비동기 엔드포인트 안에서 쓰면 이벤트 루프를 막아버리므로 비동기 클라이언트를 써야 함.

## `genai.Client` — 왜 만드는가

```python
client = genai.Client(api_key=api_key)
async_client = client.aio
```

- **라이브러리(`genai`)** = 설치된 코드 묶음 전체 (설계도 창고)
- **`client`** = 그 설계도(`Client` 클래스)로 **내 API 키를 넣어 실제로 만든 객체(인스턴스)**
- **왜 만드나**: API 키(인증 정보)를 요청마다 따로 넣지 않기 위해서. `client`를 한 번 만들어두면, 이후 모든 요청이 이 통로를 재사용하며 매번 새로 인증을 증명할 필요가 없음. 비유: 회사 출입증을 한 번 발급받아서 계속 태그만 하는 것.
- **`client.aio`** = 같은 기능을 비동기 버전으로 쓸 수 있게 모아둔 하위 객체. `async_client`라는 이름으로 다시 담아 짧게 사용.

### `client`의 수명 (세션 아님)

- 서버가 관리하는 "로그인 세션"이 아니라, **그냥 로컬 파이썬 프로세스 안의 변수**임.
- 노트북 커널이 꺼지거나 스크립트가 종료되면 함께 사라짐. 다시 쓰려면 `genai.Client(...)`를 새로 호출하면 됨.
- 진짜로 만료될 수 있는 건 `client` 객체가 아니라 **API 키 자체** (Console에서 폐기하거나 정책 위반 시 무효화).

## `interactions.create()` 구조 뜯어보기

```python
interaction = await async_client.interactions.create(
    model=model,
    input=prompt,
    store=False,
)
```

계층 구조:
```
async_client (인증된 통로)
  └── .interactions (모델과 대화 주고받는 기능 묶음 = "폴더")
        └── .create(...) (새 요청-응답 기록 하나를 생성하는 메서드 = "버튼")
```

- `interactions` = 대화 관련 기능들을 모아둔 하위 객체 (다른 예: `client.files`는 파일 업로드 기능 묶음)
- `create()` = 실제로 서버에 요청을 보내고 응답을 받아 `interaction` 객체로 포장해 반환하는 메서드
- `model=model` — **모델을 새로 만드는 게 아니라**, 이미 학습되어 서버에 존재하는 모델(`gemini-3.6-flash` 등) 중 무엇을 쓸지 선택하는 것. 식당에서 메뉴판에서 메뉴 고르는 것과 같음.
- `interaction` 객체 = **재사용하는 도구가 아니라 한 번 쓰고 끝나는 결과물** (통화 기록 한 건). `.output_text`로 실제 답변 텍스트만 꺼낼 수 있음.

### `client` vs `interaction` 비교

| | `client`/`async_client` | `interaction` |
|---|---|---|
| 생성 방법 | `genai.Client(...)` — 클래스 호출 | `interactions.create(...)` — 메서드 호출 |
| 성격 | 재사용 가능한 도구/통로 | 한 번 쓰고 끝나는 결과 데이터 |
| 생성 횟수 | 보통 한 번만 | 요청할 때마다 매번 새로 |

## 실습: 세 가지 파이썬 주제를 동시에 질문하기

```python
async def explain_python(topic: str) -> str:
    prompt = f"파이썬의 {topic}에 대해 두 문장으로 설명해 줘."
    interaction = await async_client.interactions.create(
        model=model,
        input=prompt,
        store=False,
    )
    return interaction.output_text


topics = ["list comprehension", "generator", "decorator"]
start = time.perf_counter()

answers = await asyncio.gather(
    explain_python(topics[0]),
    explain_python(topics[1]),
    explain_python(topics[2]),
)

elapsed = time.perf_counter() - start
print(f"함께 실행한 시간: {elapsed:.2f}초")

for topic, answer in zip(topics, answers):
    print("주제:", topic)
    print("답변:", answer)
```

### `zip()` — 두 리스트를 같은 인덱스끼리 짝짓기

`topics`와 `answers`는 순서가 대응되는 두 리스트(`answers[0]`은 `topics[0]`의 답). `zip()`으로 짝지어 `for topic, answer in zip(topics, answers):`처럼 인덱스 관리 없이 동시에 순회 가능.

```python
# zip 없이 쓰면 번거로움
for i in range(len(topics)):
    print(topics[i], answers[i])
```

## 핵심 한 줄 정리

- `client` = API 키를 매번 안 넣기 위해 한 번만 만들어 재사용하는 인증된 통로 (세션 아님, 그냥 로컬 변수)
- `interactions.create()` = 이미 존재하는 모델을 골라 새 요청-응답 기록(`interaction`)을 하나 만드는 것
- `gather()`로 여러 `explain_python()` 코루틴을 동시에 등록하면, 순차 대비 전체 대기 시간이 크게 줄어듦
- `zip()`은 순서가 대응하는 두 리스트를 인덱스 없이 함께 순회하게 해줌
